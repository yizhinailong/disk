# 网盘系统 - 数据库设计

## 1. 设计概述

### 1.1 数据库选型

- **主数据库**：PostgreSQL 14+
- **缓存数据库**：Redis 6.0+
- **字符集**：ENCODING UTF8
- **排序规则**：LC_COLLATE = 'en_US.utf8', LC_CTYPE = 'en_US.utf8'

### 1.2 设计原则

1. **规范化设计**：遵循第三范式，减少数据冗余
2. **合理冗余**：对于频繁查询的数据适当冗余，提高查询效率
3. **索引优化**：根据查询场景设计合适的索引
4. **软删除**：重要数据采用软删除机制
5. **审计追踪**：记录数据创建和更新时间

### 1.3 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写，下划线分隔，复数形式 | `users`, `file_contents` |
| 字段名 | 小写，下划线分隔 | `user_id`, `created_at` |
| 主键 | `id` | - |
| 外键 | `关联表名单数_id` | `user_id`, `folder_id` |
| 索引 | `idx_表名_字段名` | `idx_files_user_id` |
| 唯一索引 | `uk_表名_字段名` | `uk_users_username` |

## 3. 表结构设计

### 3.0 Schema 迁移账本 (schema_migrations)

V003 起，线上增量迁移由 `scripts/migrate-db.sh` 独占执行，并在同一事务内记录脚本 SHA-256。应用启动只校验所需 schema，不自动执行 DDL。V001/V002 是引入账本前的历史手工迁移，不回写或修改既有脚本。

```sql
CREATE TABLE schema_migrations (
    version VARCHAR(128) PRIMARY KEY,
    checksum CHAR(64) NOT NULL,
    applied_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

同一版本 checksum 不一致时执行器必须失败，禁止静默接受已修改的历史迁移。全新安装由 `sql/init.sql` 创建最新 schema 并写入当前版本；随后执行迁移器应全部跳过。

完整升级验收从当前支持的 V002 兼容基线开始，严格按 `sql/migrations/manifest.tsv` 顺序执行 V003、V004。升级前必须写入代表性用户、内容、目录、文件、状态 0–3 的上传任务及分片，并覆盖非零 `storage_used` / `storage_reserved` 配额。升级后，迁移前已存在的用户、文件、内容、目录、上传与分片业务字段必须逐值一致，行数、配额汇总与 `ref_count` 必须不变；V003 新字段只能出现规定的 local 默认值、`staging/<upload_id>` 回填和空分片元数据。`staging_prefix` 回填会触发既有 `updated_at` 触发器，因此上传任务的该审计时间只要求不倒退，不将其视为业务状态变更。再次执行迁移器必须全部跳过，数据快照和账本行数不得再变化。

### 3.2 文件内容表 (file_contents)

存储文件的物理存储信息，用于文件去重。

```sql
CREATE TABLE file_contents (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    hash_md5 CHAR(32) NOT NULL,
    hash_sha256 CHAR(64) NOT NULL,
    size BIGINT NOT NULL,
    storage_path VARCHAR(512) NOT NULL,
    mime_type VARCHAR(128) DEFAULT NULL,
    ref_count INTEGER NOT NULL DEFAULT 1,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX uk_file_contents_hash ON file_contents (hash_md5, hash_sha256);
CREATE INDEX idx_file_contents_md5 ON file_contents (hash_md5);
CREATE INDEX idx_file_contents_ref_count ON file_contents (ref_count);

COMMENT ON TABLE file_contents IS '文件内容表';
COMMENT ON COLUMN file_contents.id IS '内容ID';
COMMENT ON COLUMN file_contents.hash_md5 IS 'MD5哈希';
COMMENT ON COLUMN file_contents.hash_sha256 IS 'SHA256哈希';
COMMENT ON COLUMN file_contents.size IS '文件大小(字节)';
COMMENT ON COLUMN file_contents.storage_path IS '存储路径';
COMMENT ON COLUMN file_contents.mime_type IS 'MIME类型';
COMMENT ON COLUMN file_contents.ref_count IS '引用计数';
COMMENT ON COLUMN file_contents.created_at IS '创建时间';
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 内容唯一标识 |
| hash_md5 | CHAR(32) | 文件 MD5 哈希值 |
| hash_sha256 | CHAR(64) | 文件 SHA256 哈希值 |
| size | BIGINT | 文件大小 |
| storage_path | VARCHAR(512) | 最终 Blob 的权威定位符；local 为文件路径，S3 为完整对象 key |
| mime_type | VARCHAR(128) | 文件 MIME 类型 |
| ref_count | INTEGER | 引用计数，用于去重管理 |

`storage_path` 是下载、HEAD、Range、删除和对账的唯一定位权威。服务不得根据 `hash_md5`、
`hash_sha256` 或当前存储配置重建既有路径。新内容使用 SHA-256 布局；历史 MD5 布局保持原值，
由独立迁移工具在对象校验成功后原子更新该字段。

存量 local final Blob 迁移清单必须覆盖 `file_contents` 的完整有序快照，而不是只选择当前有文件引用的行；
`ref_count=0` 但 GC 尚未完成的内容同样属于迁移或维护窗口排空范围。清单保留数据库中的原始
`storage_path`，另存相对受信 local 根目录的规范化源路径，且目标 key 必须是
`{object_prefix}/sha256/{sha256[0:2]}/{sha256}.bin` 并可写入 `VARCHAR(512)`。

manifest 子命令只执行清点：必须在 PostgreSQL `REPEATABLE READ READ ONLY` 事务中读取快照，
对 local 源 Blob 只做受信根目录内的只读检查，不创建 S3 客户端或 checkpoint，不修改数据库、
源 Blob 或目标对象。清单先以 `0600` 权限写入同目录临时文件并 `fsync`，再以“目标必须不存在”
的原子发布创建最终文件。目标已存在或生成中任一验证失败时，不得覆盖旧清单或留下可被误用的
半成品最终文件。

切换事务把清单加载到临时表，获取 `file_contents ACCESS EXCLUSIVE NOWAIT` 锁后比较 content ID、
MD5、SHA-256、大小和路径。数据库集合必须精确等于清单，且所有路径只能全部为源值或全部为目标值；
前者通过单条 `UPDATE ... FROM` 原子切换，后者视为幂等重放，任何新增、缺失、字段漂移或源/目标混合
都失败并保持数据库不变。该锁只保护数据库提交边界，不能替代维护窗口中停止 API、Worker 和 GC。

完成上传获取内容引用时，先按 `(hash_md5, hash_sha256)` 锁定已有内容行并执行 Blob GC
门禁，再使用 `INSERT ... ON CONFLICT (hash_md5, hash_sha256) DO UPDATE SET ref_count =
file_contents.ref_count + 1 ... RETURNING`。冲突分支必须保留已有行的 `storage_path`、MIME 和
创建时间，仅在已有 `size` 与候选值一致时增加引用；条件不匹配且没有 `RETURNING` 行时按
完整性错误回滚整个完成事务。“先查再插”只能用于避免不必要的对象提升，不能作为并发去重的
正确性边界。若事务外预查决定复用已有 Blob，最终事务还必须携带预查得到的 content_id；锁定
结果不存在或 ID 已变化时返回可重试的 `ResourceConflict`，不得新建一行指向已经被 GC 删除的
对象。

`files` 的 `(user_id, folder_id, name)` 唯一约束是文件名冲突的最终裁决。插入使用
`ON CONFLICT (user_id, folder_id, name) DO NOTHING RETURNING`；无返回行稳定映射为
`FileAlreadyExists`，并由同一事务回滚已经发生的内容引用、配额和目录计数变化。

### 3.3 文件夹表 (folders)

存储文件夹结构信息。

```sql
CREATE TABLE folders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    parent_id BIGINT NOT NULL DEFAULT 0,
    name VARCHAR(255) NOT NULL,
    path VARCHAR(4096) NOT NULL DEFAULT '/',
    depth INTEGER NOT NULL DEFAULT 0,
    item_count INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_folders_user_id ON folders (user_id);
CREATE INDEX idx_folders_parent_id ON folders (parent_id);
CREATE INDEX idx_folders_user_parent ON folders (user_id, parent_id);
CREATE UNIQUE INDEX uk_folders_user_parent_name ON folders (user_id, parent_id, name);

ALTER TABLE folders
    ADD CONSTRAINT fk_folders_user_id FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE;

COMMENT ON TABLE folders IS '文件夹表';
COMMENT ON COLUMN folders.id IS '文件夹ID';
COMMENT ON COLUMN folders.user_id IS '所属用户ID';
COMMENT ON COLUMN folders.parent_id IS '父文件夹ID，0表示根目录';
COMMENT ON COLUMN folders.name IS '文件夹名称';
COMMENT ON COLUMN folders.path IS '完整路径';
COMMENT ON COLUMN folders.depth IS '目录深度';
COMMENT ON COLUMN folders.item_count IS '子项数量(文件+文件夹)';
COMMENT ON COLUMN folders.created_at IS '创建时间';
COMMENT ON COLUMN folders.updated_at IS '更新时间';
```

`uk_folders_user_parent_name` 是并发同名创建的最终裁决，不得只依赖事务外“先查再插”。创建嵌套
文件夹必须在一个 PostgreSQL 事务内先对当前用户的父目录执行受影响行数可检查的 `item_count + 1`
更新以取得行锁并确认父目录仍存在，再读取稳定的父路径/深度，最后使用
`INSERT ... ON CONFLICT (user_id, parent_id, name) DO NOTHING RETURNING` 插入子目录。父目录更新、
路径计算与子目录插入任一失败均整体回滚；唯一冲突稳定映射为 `FolderAlreadyExists`，且失败事务
不得保留父目录计数增量。

文件夹重命名与创建共享 `folder-name:<user_id>:<parent_id>:<name>` 的 PostgreSQL
`pg_advisory_xact_lock(hashtextextended(...))` 名称锁。重命名必须在一个事务内先以 `FOR UPDATE`
重新读取当前用户的目标文件夹，再获取目标名称锁并执行排除自身的同名检查；父路径、重命名子树和
子树文件均使用同一 transaction client 读取和更新，所有受影响行结果必须检查。领域冲突整体回滚并
返回 `FolderAlreadyExists`，数据库异常或任一目标行消失时不得提交部分文件夹/文件路径。

批量文件夹移动也复用 `folder-name` 名称锁。事务必须先对归一化后的全部请求根按升序 `folder_id` 使用
`FOR UPDATE` 锁定当前用户文件夹，再在锁后重新读取并确定顶层移动根；随后收集实际跨目录项的目标名称、
去重排序并依次获取名称锁，最后在锁内重新查询目标目录占用并更新根位置及完整子树路径。统一的根行锁
次序使同一根并发移动到不同目标时，后执行者基于前一提交后的最新父目录计算源/目标计数，而不是重复
扣减过期父目录。已占用名称按批量部分成功语义跳过，输家不得更新根、后代路径或父目录 `item_count`；
根位置、每个后代文件夹路径、每个后代文件路径和源/目标计数的受影响行必须逐一检查；任一更新返回
0 行时，同一事务必须整体回滚并稳定映射为移动失败，不能继续提交其余子树或计数。唯一约束仅保留最终
不变量，不作为正常跳过或 HTTP 500 分支。

文件夹复制事务同样必须先获取目标根的 `folder-name` 名称锁，再用同一 transaction client 复查目标
占用。非根目标须在名称锁之后、冲突复查之前用 `FOR UPDATE` 锁定目标行，并从锁定行重读最新 `path/depth`；
这样目标目录并发移动要么先提交并由复制使用新位置，要么后执行并把新副本纳入移动子树。锁内命中并发
冲突时必须在该事务中释放整棵子树对应的预留配额，并在增加内容引用、插入根/后代文件夹与文件、更新
目标 `item_count` 之前返回批量跳过；只有锁内赢家可以执行完整子树写入和预留转已用。
目标目录计数必须通过返回布尔结果的仓储原语更新；返回 0 行时，根/后代文件夹、后代文件、内容引用和
配额提交必须随当前子树事务回滚，外层按批量跳过语义释放对应预留，不得提交孤立子树或失真计数。事务外
冲突查询只能作为快照优化，唯一约束回滚不得承担正常并发裁决。

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 文件夹唯一标识 |
| user_id | BIGINT | 所属用户 |
| parent_id | BIGINT | 父文件夹 ID，0 为根目录 |
| name | VARCHAR(255) | 文件夹名称 |
| path | VARCHAR(4096) | 从根目录的完整路径 |
| depth | INTEGER | 目录层级深度 |
| item_count | INTEGER | 直接子项数量 |

批量文件移动复用同一文件名称锁命名空间。事务必须先按升序 `file_id` 以 `FOR UPDATE` 锁定本请求全部当前用户文件，再收集实际跨目录项的目标名称、去重排序并依次获取名称锁，最后查询目标目录占用并更新位置；统一的文件行锁优先、名称锁次序避免与文件重命名及其他批量移动形成反向等待。已占用名称按批量部分成功语义跳过，不依赖唯一约束异常；文件位置和源/目标文件夹 `item_count` 的受影响行必须检查，任一持久化失败使整个请求事务回滚。

批量文件复制也复用 `file-name` 名称锁。事务外冲突查询只能作为减少工作量的快照，不能作为并发裁决；每个显式文件批次必须在同一事务中对候选目标名称去重排序、依次获取名称锁。非根目标须在全部名称锁之后用 `FOR UPDATE` 锁定，并从锁定行读取最新路径，之后才重新查询占用；这样目标目录移动和文件复制具有确定的提交顺序。批次只能基于锁内剩余项增加 `file_contents.ref_count`、插入文件元数据、按实际插入数增加目标 `item_count` 并把预留配额转为已用配额。目标不存在或计数更新返回 0 行时，批次写入必须整体回滚并由外层释放完整批次预留；锁内发现的冲突项必须在该事务中释放对应预留配额且不修改引用计数。唯一约束仅保留最终不变量，不作为正常跳过分支。

`staging_backend` 与 `staging_prefix` 是上传会话的不可变定位信息。新建任务必须在同一条 `INSERT` 中显式写入两个字段，不得依赖数据库默认值，也不得在配置切换后改写已存在任务。S3 任务的定位符为经规范化的 `<staging_prefix>/<upload_id>`；local 任务保留不含凭据的逻辑定位符，实际旧目录仍以 `temp_path` 为兼容读取权威。实例处理分片、完成、取消或清理前，必须根据该持久化定位信息选择暂存后端，不能只读当前进程配置。

V003 expand 混跑期间是上述“新建任务必须显式写入”规则的唯一过渡例外：V002 旧二进制的 `INSERT` 不包含新增列，数据库默认值必须将其归类为 local 任务；旧分片行的 `size_bytes/md5_hash/object_key/etag` 保持可空，当前版本在 `object_key IS NULL` 时按 `<upload_id>/<chunk_index>.chunk` 读取。默认值和可空性只能在所有旧二进制退出且旧任务排空后的 contract migration 中收紧。V002 任务创建使用 `RETURNING *`，因此增列后必须回收其已缓存旧 RowDescription 的 PostgreSQL 连接；字段默认值不能修复旧连接中的 prepared plan。当前版本产生了非空 `object_key` 后也不保证 V002 能反向完成，因此混跑窗口必须同时执行连接回收和上传会话路由亲和。

`staging_backend='local'` 与 `staging_prefix` 不编码物理主机、卷 ID 或绝对路径。它们只能让挂载同一 `temp_upload_path` 的兼容进程解释旧分片布局，不能把节点本地暂存变成集群共享状态。data 阶段的节点归属清单属于有截止日期的发布编排状态；在 local 非终态任务和关联清理任务全部排空前，不能仅凭数据库行把完成或清理工作交给任意实例。

V003/V004 到后续 contract migration 之间必须经过一个可审计的 data-to-contract 观察窗口。窗口只能在旧二进制退出、生产 API 仅创建 S3 staging、local 非终态任务和未完成 local cleanup 归零、逐原卷扫描无遗留后开始，并以 PostgreSQL 时间记录 `T_s3_only`。观察探针必须在该时点后按真实写入的 `expires_at` 自然到期，由晚于到期时点的小时级 `expire_uploads` 扫描及持久 `staging_cleanup` 收敛；禁止直接改写到期时间制造通过结果。

紧急应用回滚必须保留 V003/V004 expand schema 和 `schema_migrations` 账本，不执行任何
`*_rollback.sql`。仓库中的破坏性 rollback 文件仅表示“新能力启用前的迁移撤销”，不是生产
contract：直接调用或传入 `emergency_application_rollback` 上下文会在首条 DDL 前失败。唯一受支持
入口 `scripts/reverse-expand-migration.sh` 要求 `pre_activation_reversal`、显式批准、变更单和
readiness 证据 SHA-256，并继续执行脚本内的空表/未使用状态门禁。生产激活后的字段收紧或兼容对象
删除必须作为新的 contract 版本设计、备份、恢复演练和审批，不能通过历史 rollback 文件实现。

contract-readiness 快照至少报告：切点前仍活跃的上传、`Finalizing` 或有效租约、local 非终态任务、未完成 local cleanup、空 `staging_prefix`、计划收紧但仍为空的分片描述字段、Pending/Running/Retry/DeadLetter 上传任务、未解决对账 finding，以及用户 reserved/used 配额差异。历史已终态的 local 行可以作为审计记录保留，不能仅因 backend 值为 local 就删除；但任何将来要施加 `NOT NULL` 或删除兼容读取的字段，都必须先单独回填到零。通过快照仅允许评审 V005，不在本阶段修改列默认值、可空性、旧字段或兼容读取代码。

#### 上传完成 CAS 原语

完成租约的权威判断只允许由 `UploadTaskRepository` 的条件 SQL 执行：

1. 首次认领使用单条 `UPDATE ... WHERE` 同时校验 `id + user_id + status=InProgress + expires_at >= NOW()` 和 `upload_task_chunks` 完整覆盖；成功后写入 `Finalizing`、`lease_owner`、`NOW() + lease duration`，并递增 `state_version` 与 `finalize_attempts`。
2. 接管只允许命中 `status=Finalizing AND lease_expires_at <= NOW()` 的同一条件更新；不得使用 API 实例本地时钟判断过期。
3. 续租必须同时匹配 `status=Finalizing + lease_owner + state_version + lease_expires_at > NOW()`，并返回递增后的版本。调用方必须显式把当前 standalone client 或短事务连接传给仓储续租原语；`UploadTaskRepository` 不提供隐式回退到构造时默认 client 的续租重载。调用方后续只能使用最新返回版本；已过期 owner 不能复活租约，只能重新竞争接管。
4. 最终短事务的首条业务语句必须在事务连接上执行同一续租 CAS。命中后该更新持有任务行锁，后续文件、内容引用与配额写入只能使用它返回的新版本；未命中则在任何业务写入前返回冲突。事务末尾仍须匹配同一组 `lease_owner + state_version + lease_expires_at > NOW()`，写入 `Completed + completed_file_id`、清空租约并递增版本。旧 owner、旧 generation 或过期租约的更新影响行数必须为 0，事务内先前写入必须整体回滚。
5. CAS 未命中后可用新的数据库语句读取当前状态，以区分分片不完整、有效租约冲突、完成重放和稳定终态；该读取结果不能替代成功 CAS 或授予完成权限。
6. 管理员解除已确认死亡 owner 的租约只允许匹配 `id + Finalizing + expected lease_owner + expected state_version + lease_expires_at > NOW()`，将 `lease_expires_at` 写为数据库 `NOW()` 并递增版本。不得回退为 `InProgress` 或清空 owner；这既满足状态字段约束，也阻止旧 owner 续租/提交，下一次 complete 仍按第 2 条接管。已自然到期或已解除的租约不再重复更新。

租约时长必须是正整数秒并有配置上限。任何对象读取、组装、哈希或复制都在认领事务提交后执行，不能持有任务行锁等待外部 I/O。

取消上传的权威原语同样位于 `UploadTaskRepository`：单条条件更新只匹配 `id + user_id + status=InProgress + expires_at >= NOW()`，写入 `Cancelled`、结束时间和原因，同时执行 `state_version = state_version + 1` 并 `RETURNING` 清理描述符与新版本。只有该更新的赢家可以在同一短事务中释放 reserved quota、写入唯一 staging cleanup 任务并删除分片元数据。CAS 未命中后只读当前 `status + state_version + task_expired` 决定取消重放、完成冲突、已超时的进行中任务或稳定终态；`Cancelled` 重放返回持久版本但不得再次递增。取消从不取得 finalize lease，因此其日志关联不得伪造 `lease_owner`。

过期上传也只允许使用 `UploadTaskRepository` 的单行权威原语：条件更新匹配 `id + status=InProgress + expires_at < NOW()`，写入 `Expired`、结束时间和原因，同时执行 `state_version = state_version + 1`，并 `RETURNING` 清理描述符与新版本。赢家在同一短事务释放 reserved quota、写入唯一 staging cleanup 任务并删除分片元数据；事务提交后逐上传生命周期事件使用返回版本。候选分页只负责稳定枚举，不能批量越过逐任务事务，也不能把扫描页码、job attempts 或 Worker generation 当作上传状态版本。CAS 未命中不推进版本、不释放配额且不创建重复清理任务。

| uploaded_at | TIMESTAMP | 分片上传完成时间 |

**并发安全说明：**

- 使用 `PRIMARY KEY(task_id, chunk_index)` 确保同一任务的同一分片只有一个权威记录。
- S3 分片 key 同时包含索引和已验证 MD5；重复内容写入幂等，冲突记录必须验证大小/hash/object key 一致。
- 分片记录通过 `INSERT ... SELECT` 或同一事务内的条件原语写入，只在父任务仍为 `status=0` 时成功。
- 对象已写但记录条件未命中属于 staging 孤儿；不得修改终态，由持久清理/对账任务回收。
- 进度查询：`SELECT COUNT(*) FROM upload_task_chunks WHERE task_id = $1`。
- 组装查询：按 `chunk_index` 返回大小、MD5、object key 和 ETag；完成前逐对象复核。

### 3.5.2 持久存储任务表 (storage_jobs)

保存可重试的对象存储副作用与周期扫描任务。API/Worker 崩溃不能丢失任务；Worker 使用 `FOR UPDATE SKIP LOCKED` 和有期限租约认领。

```sql
CREATE TABLE storage_jobs (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    job_type VARCHAR(64) NOT NULL,
    aggregate_id VARCHAR(128) NOT NULL,
    dedupe_key VARCHAR(255) NOT NULL,
    payload JSONB NOT NULL DEFAULT '{}'::jsonb,
    status SMALLINT NOT NULL DEFAULT 0,
    attempts INTEGER NOT NULL DEFAULT 0,
    max_attempts INTEGER NOT NULL DEFAULT 8,
    available_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    locked_by VARCHAR(128) DEFAULT NULL,
    locked_until TIMESTAMP DEFAULT NULL,
    last_error VARCHAR(2048) DEFAULT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMP DEFAULT NULL,
    CONSTRAINT uk_storage_jobs_dedupe_key UNIQUE (dedupe_key),
    CONSTRAINT ck_storage_jobs_status CHECK (status BETWEEN 0 AND 4),
    CONSTRAINT ck_storage_jobs_attempts CHECK (attempts >= 0 AND max_attempts > 0),
    CONSTRAINT ck_storage_jobs_running_lease CHECK (
        (status = 1 AND locked_by IS NOT NULL AND locked_until IS NOT NULL)
        OR (status <> 1 AND locked_by IS NULL AND locked_until IS NULL)
    )
);

CREATE INDEX idx_storage_jobs_ready
    ON storage_jobs (available_at, id)
    WHERE status IN (0, 2);
CREATE INDEX idx_storage_jobs_expired_lease
    ON storage_jobs (locked_until, id)
    WHERE status = 1;
CREATE INDEX idx_storage_jobs_type_status
    ON storage_jobs (job_type, status);
```

状态值：`0 Pending`、`1 Running`、`2 Retry`、`3 Succeeded`、`4 DeadLetter`。`payload` 只保存任务参数，不保存密钥、令牌或文件正文。相同逻辑副作用使用稳定 `dedupe_key`，例如 `staging-cleanup:{upload_id}` 或 `blob-gc:{content_id}`。

入队使用 `INSERT ... ON CONFLICT (dedupe_key) DO NOTHING RETURNING id`，并与产生副作用的业务状态放在同一个事务。Worker 每次先将已耗尽尝试次数且租约已过期的任务收敛为 `DeadLetter`，再以 `FOR UPDATE SKIP LOCKED` 选取已到 `available_at` 的 `Pending/Retry` 或租约已过期的 `Running` 任务。认领在一条 CTE `UPDATE ... RETURNING` 中写入 `Running`、`attempts + 1`、`locked_by` 和 `locked_until`。

续租、成功和失败回写都必须同时匹配 `id + Running + locked_by`；续租还要求旧租约未过期。临时失败在 `attempts < max_attempts` 时转为 `Retry`并写入下次执行时间，否则转为 `DeadLetter`。所有离开 `Running` 的转移必须清空租约字段，以满足 `ck_storage_jobs_running_lease`。人工重放只允许 `DeadLetter -> Pending`，并重置尝试次数和错误信息。

`staging_cleanup` 固定使用 `aggregate_id = upload_id`和 `dedupe_key = staging-cleanup:{upload_id}`，`payload` 仅含 `upload_id`、`backend` 与持久化的 `prefix`。完成、取消或过期赢家在同一事务内依次写终态/配额、入队和删除分片元数据。请求线程不再直接删除 staging 对象；因此事务提交即证明清理事实可恢复，对象删除失败不影响已提交的业务终态。

管理员重建清理任务时必须先锁定上传行并校验终态与精确 `state_version`，payload 只能从该行的持久化 staging 描述符构造。去重键不存在时插入；旧任务为 `Succeeded` 时使用既有 rearm 原语重置为 `Pending`；其他非终态任务不变，`DeadLetter` 走独立重放。任务变化与 `operation_logs` 审计在同一事务提交。

人工对账使用调用方确认的安全 `scan_id` 与固定 scope 构造首个 `storage_reconcile` 分页任务。相同 `scan_id + scope + 初始游标摘要` 已存在时不重置；管理员必须选择新的 scan ID。首任务入队与审计同事务提交，后续游标任务继续由 Worker 使用相同合同和唯一去重键生成。

`blob_gc` 固定使用 `aggregate_id = content_id`、`dedupe_key = blob-gc:{content_id}`，`payload`
仅含 `content_id` 与权威 `storage_path`。引用计数在同一事务中降到零时入队；若同一去重键的旧任务
已经 `Succeeded`，入队原语将其重置为 `Pending`、清空结果并更新 payload。`Pending/Retry/Running`
任务保持原状，`DeadLetter` 必须经运维确认后重放，不能由业务流静默清除。

引用增长与 GC 共享以下数据库门禁：增长事务先锁定内容行；`Pending/Running/Retry/DeadLetter`
任一状态都返回可重试的 `ResourceConflict`，只有不存在 GC 任务或任务已 `Succeeded` 才能递增。
不能取消 Retry/DeadLetter 后直接恢复引用，因为一次返回失败的对象删除仍可能已经在存储端生效。
Worker 只有将任务认领为 `Running` 后才能删除，并在持有内容行 `FOR UPDATE` 锁期间再次检查 `ref_count`、执行幂等
对象删除，并在同一 PostgreSQL 事务中删除零引用内容行和写入任务成功状态。对象存储调用通常不得跨数据库事务；Blob GC 是为了保证“检查零引用
与删除对象”互斥而允许的例外，且单 Worker 当前串行执行。若复核发现引用已恢复，Worker 不删除
对象并将任务成功收敛；未来再次归零会重置同一任务。

若 Worker 在对象删除成功后、上述事务提交前退出，数据库连接关闭必须回滚内容行与任务状态的未提交修改，而对象保持缺失。任务保留原 owner 直至租约按 PostgreSQL 时间到期；接管 Worker 对缺失对象重复执行 `DeleteBlob` 必须视为成功，再原子删除内容行、解析 `zero_reference_content` finding 并写回 `Succeeded`。不得通过人工提前清空 owner 或改写租约绕过接管协议。

优雅退出也不增加专用数据库状态。SIGTERM 只停止后续认领/播种并给当前 handler 一个有界 drain 窗口；若窗口耗尽，进程退出后该行仍必须保持 `Running + 原 locked_by + locked_until`，尝试次数不变。其他 Worker 在 `locked_until > NOW()` 时不得更新该行，到期后才由同一认领 CTE 写入新 owner、`attempts + 1` 和新租约。回滚操作和验收脚本不得执行清空 owner、把状态改回 Pending/Retry、缩短租约或直接增加 attempts 的 SQL；接管前后的唯一持久变化必须来自正常 Worker 原语。

`multipart_abort` 在 S3 `CreateMultipartUpload` 返回后、上传任何 part 前同步登记。聚合标识是
`SHA-256(object_key + "\n" + upload_id)` 的 64 位小写十六进制摘要，去重键固定为
`multipart-abort:{aggregate_id}`；`payload` 仅含 `backend="s3"`、`key` 和 `upload_id`。原始
upload ID 只进入 JSONB，不进入受长度限制的去重键，也不得出现在普通日志中。

登记时任务直接写为 `Running`，`locked_by` 使用当前请求派生的唯一 multipart owner，
`locked_until` 使用上传完成租约。请求在每次 part/copy-part 和 complete 前续租；续租失败即停止
写入并尝试 Abort。Complete 成功或即时 Abort 成功后，只有当前 owner 可以把任务收敛为
`Succeeded`。即时 Abort 失败时，请求 owner 将任务改为可立即认领的 `Retry`，清空租约并保存
脱敏错误；进程直接退出时不执行回写，租约过期的 `Running` 由普通 Worker 接管。Worker 严格
复核摘要、去重键、backend/key/upload_id 后调用幂等 Abort，成功按 owner 条件收敛，临时错误
退避重试，非法 payload 进入 DeadLetter。对象存储端未找到 upload ID 按成功处理。

S3 返回 upload ID 到 PostgreSQL 登记之间仍存在不可消除的极短崩溃窗口，因此生产 bucket 必须
配置未完成 multipart 生命周期过期规则。该规则是持久任务之外的最后保护，不能替代应用任务，
也不能覆盖 final 前缀。

`expire_uploads` 使用 `aggregate_id = scan_id`、去重键
`periodic:expire-uploads:{scan_id}:{page}`，payload 仅含 UTC 窗口标识、从 0 开始的页号和
`1..500` 的批量上限。每页按 `expires_at/id` 稳定顺序只查询一个有界候选批次；候选数达到批量
上限时当前 handler 入队下一页。续页不得依赖实际过期成功数，因为并发状态迁移可能使 CAS
失败但不代表候选集合已经耗尽。

`expire_trash` 使用 `aggregate_id = scan_id`、去重键
`periodic:expire-trash:{scan_id}:{after_id}`，payload 仅含 `scan_id`、单调 `after_id` 和
`1..500` 的批量上限。每页按 `trash.id ASC` 查询一个批次；分块中任一删除失败时
任务以原游标重试，只有整页成功且候选数达到上限时才以最大 ID 入队下一页。

`storage_reconcile` 使用 `aggregate_id = scan_id`，去重键
`periodic:storage-reconcile:{scan_id}:{scope}:{cursor_digest}`。payload 的 scope 只能是
`contents/users/staging/final`；数据库 scope 使用 `after_id`，对象清单 scope 使用不透明
`continuation_token`。`cursor_digest` 固定为
`SHA-256(scope + "\n" + decimal(after_id) + "\n" + continuation_token)` 的 64 位小写十六进制。
每页最多检查 500 个数据库聚合或 1000 个对象，并在完成当前页后入队下一页；返回 `has_more`
时下一游标必须前进，否则任务作为永久合同错误进入 dead-letter，不继续生成同游标任务。

### 3.5.3 存储一致性发现表 (storage_reconciliation_findings)

保存可查询、可告警和可审计的当前/历史不一致发现。巡检不得只打印日志，也不得把一次对象清单
观察当作删除授权。

```sql
CREATE TABLE storage_reconciliation_findings (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    finding_type VARCHAR(64) NOT NULL,
    resource_id VARCHAR(128) NOT NULL,
    resource_locator VARCHAR(1024) DEFAULT NULL,
    severity SMALLINT NOT NULL,
    resolution_strategy VARCHAR(32) NOT NULL,
    details JSONB NOT NULL DEFAULT '{}'::jsonb,
    occurrences INTEGER NOT NULL DEFAULT 1,
    first_seen_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_seen_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    resolved_at TIMESTAMP DEFAULT NULL,
    CONSTRAINT uk_storage_reconciliation_finding
        UNIQUE (finding_type, resource_id),
    CONSTRAINT ck_storage_reconciliation_severity
        CHECK (severity BETWEEN 0 AND 2),
    CONSTRAINT ck_storage_reconciliation_strategy
        CHECK (resolution_strategy IN ('auto_gc', 'alert', 'manual')),
    CONSTRAINT ck_storage_reconciliation_occurrences
        CHECK (occurrences > 0)
);

CREATE INDEX idx_storage_reconciliation_unresolved
    ON storage_reconciliation_findings (severity DESC, last_seen_at, id)
    WHERE resolved_at IS NULL;
```

`resource_id` 是稳定且有界的标识：数据库聚合使用十进制 ID，对象使用 object key 的 SHA-256；
完整 key/path 只放在 `resource_locator`，不得包含凭据或签名 URL。重复发现执行 upsert，增加
`occurrences`、刷新详情并清空 `resolved_at`；复核健康后只设置 `resolved_at`，不删除历史行。

对象 scope 在完整扫描的最后一页还必须消解“本轮未再观察到”的旧孤儿 finding，否则对象被受控删除后
历史异常会永久阻断恢复门禁。消解只允许匹配本 scope 首个 `storage_reconcile` 任务的 `created_at`：仅当
finding 的 `last_seen_at` 严格早于该扫描起点时更新 `resolved_at`。本轮重新发现或并发扫描刷新过的 finding
不得被消解；找不到持久首任务时也不得执行该批量更新。该规则只改变诊断终态，不授权巡检删除对象。

| finding_type | 检查 | 策略 |
|--------------|------|------|
| `zero_reference_content` | 内容实际引用为 0 | `auto_gc`：只入队 `blob_gc`，由 GC 再次加锁复核 |
| `content_ref_count_mismatch` | `ref_count` 与 files + trash 不同 | `alert`：不自动改计数 |
| `missing_final_blob` / `final_blob_size_mismatch` | DB 内容对应对象缺失或大小不同 | `manual`：停止相关读/复用并人工恢复 |
| `final_blob_read_interrupted` | 下载打开失败或在声明长度完成前发生上游短读 | `manual`：保留预期/已传输字节信息；内容巡检确认对象存在且大小正确后标记恢复 |
| `quota_used_mismatch` / `quota_reserved_mismatch` | 用户计数与业务记录汇总不同 | `alert`：连续观察后人工核对，不在巡检中改配额 |
| `upload_staging_mismatch` | DB 分片描述符对应对象缺失或大小、ETag、内容不一致 | `manual`：停止完成提交，保留任务/分片元数据并立即排入 staging 对账 |
| `orphan_staging_object` | staging 对象无活动任务/权威分片或组装记录 | `alert`：由 cleanup/lifecycle 回收，不直接删除 |
| `orphan_final_blob` | final 对象没有 `file_contents.storage_path` | `manual`：确认无并发提交和恢复窗口后处理 |

| 字段 | 类型 | 说明 |
|------|------|------|

| deleted_at | TIMESTAMP | 删除时间 |
| expires_at | TIMESTAMP | 自动清理时间 |

文件夹软删除的 `folder_tree` 快照和活跃行移除必须由同一 PostgreSQL 事务基于锁后计划完成。事务先递归读取请求根的当前子树，再按升序对尚未锁定的目录行执行 `FOR UPDATE`，重复读取与加锁直到计划中所有目录均已锁定；随后按升序锁定最终计划中的全部文件以及未被目录覆盖的显式文件，并以锁后文件行回填快照。只有此时才允许构造 `trash.item_data`、清理分享和删除活跃文件/目录。并发写入若先提交，最终计划必须包含其新增或移动的后代；若在目录锁后等待，目标目录计数更新未命中必须使该写入事务回滚。生产表不依赖 `folder_id`/`parent_id` 外键级联，因此不得以最终孤立行清理替代该锁协议。

单文件恢复必须以 `trash.id + user_id` 对目标回收站行执行 `FOR UPDATE`，并在同一事务内完成冲突名称仲裁、目标父目录锁定、`files` 插入和回收站行精确删除。名称 transaction advisory lock 必须先于非根目标目录行锁，与文件移动/复制保持同一锁顺序；候选名已占用时回滚当前只读尝试，再以 `name (n).ext` 开启下一次短事务，成功事务仍同时持有回收站行、候选名称和目标父目录锁。回收站删除的受影响行数不是 1 时事务必须回滚；同一回收站项的后续并发恢复在行锁释放后只能观察到不存在，不得重复生成活跃文件。软删除期间保留的 `content_id`、`ref_count` 和 `storage_used` 在恢复时不增不减。

### 4.3 语义说明

#### 4.3.1 存储空间语义

- **storage_used**（已用存储）：
  ```sql
  storage_used = SUM(files.size) + SUM(trash.item_size)
  ```
  包括当前文件和回收站项目的大小。

- **storage_reserved**（预占用存储）：
  ```sql
  storage_reserved = 进行中的上传任务预留 + 正在执行的复制候选字节预留
  ```
  上传预留可由 `upload_tasks.status IN (0, 4)` 的 `reserved_bytes` 对账；复制预留是应用事务外层的短生命周期预留，没有独立持久任务行，因此正常请求结束后必须全部提交到 `storage_used` 或释放。对账结果中超出进行中/完成中上传任务总额的部分，应视为正在执行的复制预留或需要告警的孤儿预留。

- **有效可用配额**（Effective Available Quota）：
  ```
  有效可用配额 = storage_quota - storage_used - storage_reserved
  ```
  创建上传任务时，必须确保 `storage_reserved + file_size <= storage_quota - storage_used`。

- **严格转换不变量**：
  - 释放预留和“预留转已用”都必须满足 `storage_reserved >= bytes`。
  - `CommitReservedToUsed` 不得用 `GREATEST(storage_reserved - bytes, 0)` 掩盖欠预留；条件更新未命中时必须返回内部错误并回滚同一事务内的文件行和引用计数变更。
  - 成功复制/上传提交后，`storage_reserved` 减少量必须等于 `storage_used` 增加量；失败或跳过只释放预留，不增加 `storage_used`。
  - 非秒传上传初始化必须在同一 PostgreSQL 事务内完成 `storage_reserved` 预留与 `upload_tasks` 插入；任务插入、事务提交或进程中止导致事务失败时不得留下无任务归属的预留配额，移除故障后相同初始化请求必须可正常重试。
  - 永久删除回收站项时，`storage_used` 递减必须使用可检查结果的事务连接原语；用户行未命中或数据库更新失败必须回滚同一事务内的回收站删除、`ref_count` 递减与 Blob GC 入队，不得记录错误后继续提交。

#### 4.3.2 引用计数语义

- **file_contents.ref_count**（内容引用计数）：
  ```sql
  ref_count = COUNT(files WHERE content_id=X) +
              COUNT(trash WHERE content_id=X AND item_type='file')
  ```
  包含活跃文件和回收站文件对内容的引用。

- **引用计数递增**：创建新文件（包括秒传）时，对对应 content_id 的 ref_count +1
- **引用计数递减**：
  - 删除文件并移入回收站时，ref_count 不变（trash.content_id 保持引用）
  - 彻底删除回收站文件时，ref_count -1
  - 恢复回收站文件时，无需调整 ref_count（从 trash 转回 files）

- **并行处理语义**：批量彻底删除在事务内原子递减 `ref_count` 并为每个零引用内容写入或重置
  `blob-gc:{content_id}`。请求线程不得直接删除 Blob。引用增长先锁定内容行；任一未成功 GC 状态
  都使引用增长返回 `ResourceConflict`。Worker 持有同一内容行锁
  完成零引用复核、幂等对象删除和元数据删除；本地开发存储和 S3/MinIO 使用相同约束。

#### 4.3.3 上传任务生命周期

```mermaid
flowchart TD
    A[创建任务<br/>status=0 InProgress] --> B{所有分片完整?}
    B -->|是| C[CAS认领完成租约<br/>status=4 Finalizing]
    C --> D{组装/校验/短事务成功?}
    D -->|是| E[status=1 Completed<br/>completed_file_id<br/>finalized_at=NOW]
    D -->|租约到期| C
    D -->|不可恢复| H[status=5 Failed]
    B -->|否，继续等待| A
    A --> K{收到取消请求?}
    A --> F{到期扫描命中?<br/>expires_at < NOW}
    K -->|是| G[status=2 Cancelled<br/>事务内释放配额并入队清理]
    F -->|是| I[status=3 Expired<br/>事务内释放配额并入队清理]
    E --> J[reserved转used<br/>内容引用+1<br/>入队staging清理]
```

**状态转换说明：**

- **0 → 4（进行中 → 完成中）**：分片覆盖完整后通过条件更新写入 owner、租约截止和递增后的 `state_version`；只有更新成功的实例执行外部完成步骤。
- **4 → 4（完成中接管）**：仅当 `lease_expires_at < NOW()` 时，新 owner 可递增版本和尝试次数接管；旧 owner 的续租和提交必须失败。
- **4 → 1（完成中 → 已完成）**：短事务原子提交文件、内容引用、配额转换、`completed_file_id` 与清理任务。重复 complete 根据该文件 ID 返回原结果。
- **0 → 2（进行中 → 已取消）**：状态条件更新递增并返回 `state_version`；释放 `storage_reserved`、删除分片元数据和写入清理任务位于同一事务，只有状态迁移赢家释放配额。重复取消只读取持久版本，不再推进版本。
- **0 → 3（进行中 → 已过期）**：超过 `expires_at` 后，条件更新递增并返回 `state_version`；同一事务释放配额、删除分片元数据并入队清理，提交后由 Worker 幂等删除 staging 对象。CAS 未命中不推进版本或重复副作用。
- **4 → 5（完成中 → 失败）**：仅用于明确不可恢复的数据损坏或超过已配置恢复上限；短暂错误保持完成中并由租约接管。
- `Finalizing` 不接受新分片或取消。任务创建使用 `NOW() + (ttl * INTERVAL '1 second')` 写入 `expires_at`，进行中任务查找、断点续传、分片记录、完成认领和过期转换都以 PostgreSQL `NOW()` 为准；API 进程不得把 `TIMESTAMP WITHOUT TIME ZONE` 解析为本地时间后参与权限判断。外部 S3 I/O 不持有数据库长事务。

### 5.4 Redis 实现

#### 5.4.1 RedisService 活跃边界

**目的**: 封装 Drogon RedisClient API，只向业务层暴露已有生产调用者的原子命令能力。

`disk::services::RedisService` 是进程内单例。启动时由 `Initialize()` 注入 Redis client，业务代码通过 `GetInstance()` 获取同一实例。活跃命令 API 如下：

| API | 权威语义 |
|-----|----------|
| `Ping` | readiness 与系统状态探测 |
| `Set` | 通过 SET/SETEX 原子写入值及可选 TTL |
| `Get` | 读取单键字符串值 |
| `Delete` | 删除单键 |
| `Exists` | 检查单键是否存在 |
| `Incr` | 递增文件列表缓存世代 |
| `CompareAndSwap` | 以 Lua 原子旋转 refresh token hash 并同步设置 TTL |
| `IncrWithExpire` | 以 Lua 原子递增固定窗口计数，仅第一次递增设置 TTL |

全部命令都可接收可选 `LogContext`，并保持统一 `Result<T>` 错误边界。服务不提供通用 Hash 门面，也不保留无生产调用者的独立 `Expire`、任意步长 `IncrBy`、`TtlType` 类型或 `MSet`/`MGet`/`MDelete` 批量预留面。TTL 必须由 `Set`、`CompareAndSwap` 或 `IncrWithExpire` 在同一原子操作中管理。

**使用示例**:

```cpp
auto redis = RedisService::GetInstance();
co_await redis->Set(refresh_key, token_hash, ttl_seconds, log_context);

const auto count =
    co_await redis->IncrWithExpire(rate_key, window_seconds, log_context);
```

```cpp
auto JwtAuthFilter::doFilter(const drogon::HttpRequestPtr& request)
    -> drogon::Task<drogon::HttpResponsePtr> {

    const auto& auth_header = request->getHeader("Authorization");

    if (auth_header.empty()) {
        co_return disk::Response::Error(disk::error::Code::TokenMissing);
    }

    if (!auth_header.starts_with("Bearer ")) {
        co_return disk::Response::Error(disk::error::Code::TokenMalformed);
    }

    const auto token = auth_header.substr(7);

    // 1. 验证 JWT 签名和有效期
    auto verify_result = m_token_service->VerifyAccessToken(token);
    if (!verify_result) {
        co_return disk::Response::Error(verify_result.error());
    }

    // 2. 提取 JTI（JWT ID）
    const auto jti = TokenService::ExtractJTI(token);

    // 3. 检查 Redis 黑名单
    auto blacklist_check = co_await m_token_service->IsBlacklisted(jti);
    if (!blacklist_check) {
        LOG_ERROR << "黑名单检查失败: " << blacklist_check.error().message;
        co_return disk::Response::Error(ErrorInfo(ErrorCode::InternalError));
    }

    if (blacklist_check.value()) {
        LOG_WARN << "Token 在黑名单中: " << jti;
        co_return disk::Response::Error(ErrorInfo(ErrorCode::TokenRevoked));
    }

    // 4. 验证通过，注入用户信息
    auto [user_id, username] = verify_result.value();

    request->attributes()->insert("user_id", user_id);
    request->attributes()->insert("username", username);

    LOG_DEBUG << "JWT 认证成功: user_id=" << user_id << ", username=" << username;

    co_return nullptr;  // 继续过滤器链
}
```

## 7. 数据迁移与备份

### 7.1 备份策略

| 备份类型 | 频率 | 保留时间 | 说明 |
|----------|------|----------|------|
| 全量逻辑备份 | 每日 | 30天 | `pg_dump --format=custom` 全库逻辑备份，用于可移植的隔离恢复与对象对账 |
| 物理基础备份 | 至少每日 | 30天 | `pg_basebackup` 或托管等价能力，保留并校验 `backup_manifest` |
| WAL 归档 | 连续 | 覆盖最老保留基础备份至批准恢复窗口 | 不允许按小时抽样复制；归档链必须连续到声明的 RPO |
| final Blob 快照 | 每日 | 30天 | 与数据库同一停写窗口的 local 快照或 S3 版本清单 |

数据库 dump 与 final Blob 快照必须组成带唯一 ID、校验和、schema 账本和对象版本信息的一致恢复集。创建恢复集时停止新写入并让 Worker 排空后停机，避免上传完成、回收站过期或 Blob GC 跨越两个快照。Redis 不保存上传、配额或文件的权威业务状态，也不进入该一致恢复集；但 refresh 当前哈希和 access/share 撤销键属于会话安全状态，必须由 Redis 持久化/复制保留。无法证明这些键完整时，恢复流程必须轮换 JWT Secret、重启全部 API 并强制所有既有会话重新认证。

### 7.2 备份命令示例

```bash
# 全量备份；custom format 已内置压缩能力
pg_dump -U disk_user --format=custom --no-owner --no-privileges \
    --file disk_backup_$(date -u +%Y%m%dT%H%M%SZ).dump disk

# 只恢复到预先创建的空隔离数据库
pg_restore -U disk_user --dbname disk_restore --exit-on-error \
    --no-owner --no-privileges disk_backup_20260113T020000Z.dump
```

声明支持 PostgreSQL 时间点恢复时，逻辑 dump 不能替代物理基础备份和连续 WAL。每个基础备份必须先通过 `pg_verifybackup`，再把 system identifier、timeline、备份起止 LSN、manifest 摘要和所需 WAL 范围写入恢复集；任何缺失或校验失败都阻断恢复。演练只能把未修改的基础备份复制到新的隔离数据目录，使用 `recovery.signal`、受控 `restore_command` 和唯一的 `recovery_target_time`/`recovery_target_lsn`/`recovery_target_xid` 恢复，不能覆盖源库或同时配置多个目标。

数据库到达目标后必须证明目标前已提交事务存在、目标后事务不存在，再提升到新 timeline；随后仍需配对目标时刻可恢复的 final Blob 快照，执行 schema、配额、引用计数、对象完整性和全量分页对账。数据库 PITR 成功本身不授权切流。

恢复完成不等于可上线。恢复环境必须指向与 `storage_path` 一致的对象根，启动真实 Worker，以唯一扫描 ID 完整执行 `contents`、`users`、`final` 三个对账范围并等待所有续页成功。切流前必须保证：`ref_count = files 引用 + file trash 引用`；`storage_used = files.size + trash.item_size`；`storage_reserved = status IN (0,4) 的 reserved_bytes`；每个有引用 final Blob 存在且大小一致；对象清单没有孤儿；没有未解决 finding 或 dead-letter 对账任务。修复后必须用新扫描 ID 重跑，禁止直接修改 finding 终态。

### 7.3 数据清理

进行中上传过期、staging 删除和零引用 Blob GC 必须由 Worker 通过状态条件、配额事务和持久任务执行。运维人员不得直接删除 `status IN (0, 4)` 的上传任务或 `ref_count=0` 的内容行；否则会绕过配额释放、对象删除确认和审计。以下 SQL 只清理已经收敛的终态元数据与独立日志：

```sql
-- 清理已完成/已取消/已过期/失败的旧任务。
-- 执行前必须确认关联 staging cleanup 已 Succeeded。
WITH to_delete AS (
    SELECT id FROM upload_tasks
    WHERE status IN (1, 2, 3, 5)
    AND finalized_at < NOW() - INTERVAL '7 days'
    AND NOT EXISTS (
        SELECT 1 FROM storage_jobs
        WHERE aggregate_id = upload_tasks.id
          AND job_type IN ('staging_cleanup', 'multipart_abort')
          AND status IN (0, 1, 2, 4)
    )
    LIMIT 1000
)
DELETE FROM upload_tasks
WHERE id IN (SELECT id FROM to_delete);

-- 清理过期操作日志（保留90天）
WITH to_delete AS (
    SELECT id FROM operation_logs
    WHERE created_at < NOW() - INTERVAL '90 days'
    LIMIT 10000
)
DELETE FROM operation_logs
WHERE id IN (SELECT id FROM to_delete);
```
