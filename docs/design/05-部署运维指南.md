# 网盘系统 - 部署运维指南

## 1. 环境要求

### 1.0 安全配置

**按下表的适用环境设置环境变量：**

| 变量名 | 说明 | 要求 | 适用环境 |
|--------|------|------|----------|
| `JWT_SECRET` | JWT签名密钥 | 最少32字符，建议64字符随机字符串 | **所有环境必须** |
| `DATABASE_PASSWORD` | PostgreSQL数据库密码 | 强密码，避免使用默认值 | 仅安全模式 |
| `REDIS_PASSWORD` | Redis认证密码 | 强密码，与redis.conf中requirepass一致 | 仅安全模式 |
| `DISK_SECURE_MODE` | 安全模式开关 | 设置为`true`或`1`启用严格验证 | 生产环境必须 |

**启动验证行为：**
- `JWT_SECRET` 在所有环境中都会强制验证（最少32字符），缺失或过短时应用拒绝启动
- 当 `DISK_SECURE_MODE=true` 时，应用启动时还会额外验证 `DATABASE_PASSWORD` 和 `REDIS_PASSWORD`
- 如果任何必需变量缺失，应用将拒绝启动并输出错误信息

**设置环境变量示例：**

```bash
# 生产环境 - /etc/disk/env
JWT_SECRET="your-very-long-and-secure-jwt-secret-key-at-least-32-characters"
DATABASE_PASSWORD="your_strong_db_password"
REDIS_PASSWORD="your_strong_redis_password"
DISK_SECURE_MODE=true
```

**生成安全密钥：**

```bash
# 生成JWT密钥（推荐64字符）
openssl rand -base64 48

# 生成数据库密码
openssl rand -base64 24
```

> **重要**: 永远不要在 `config.json` 中存储生产环境密码。所有敏感配置必须通过环境变量注入。

### 3.4 数据库增量迁移

> **重要**: 前向迁移只允许 expand-compatible 变更，可新增对象、回填数据和验证约束，但不在前向 manifest 中执行 `DROP COLUMN`/`DROP TABLE`/`DROP DATABASE`。应用回滚永久保留已提交的 expand schema 和迁移账本；`*_rollback.sql` 只能用于新能力启用前、单独批准的 schema 撤销，不是紧急应用回滚步骤。

#### 3.4.1 迁移基线与账本

新建空库直接执行 `sql/init.sql`，不重放存量迁移。存量库先按 3.4.7 节达到
V002 兼容基线，再由 `sql/migrations/manifest.tsv` 以固定顺序声明分布式改造迁移：

| 版本 | 前向文件 | 主要效果 |
|------|----------|----------|
| `V003_distributed_upload` | `V003_distributed_upload_forward.sql` | 上传任务暂存定位、状态版本、完成租约、诊断字段、分片对象元数据与持久 `storage_jobs` |
| `V004_storage_reconciliation` | `V004_storage_reconciliation_forward.sql` | 可分页、可查询的 `storage_reconciliation_findings` 对账发现表 |

`scripts/migrate-db.sh` 管理 `schema_migrations(version, checksum, applied_at)`。每个 manifest 条目都计算
SHA-256，在单个 PostgreSQL 事务内取 advisory lock、执行前向 SQL 并记账。已记账版本的
checksum 与当前文件不同时必须停止，禁止改写已应用的迁移文件或手工删除账本行。API 和
Worker 启动只校验 schema 版本，不执行 DDL。

#### 3.4.2 发布流程

```mermaid
flowchart TD
    A[冻结发布并记录候选版本] --> B[完成备份和空隔离库恢复演练]
    B --> C[核对 manifest、checksum<br/>与升级兼容门禁]
    C --> D[单实例 migration Job<br/>执行 scripts/migrate-db.sh]
    D --> E{schema、账本和数据对账通过?}
    E -->|否| F[停止发布<br/>保留已提交 expand]
    F --> G[前向修复后重试<br/>灾难时单独评审恢复]
    E -->|是| H[先发布兼容 Worker]
    H --> I[滚动发布 API<br/>回收旧连接计划]
    I --> J{健康、功能和对账通过?}
    J -->|否| K[回退应用、配置或流量<br/>schema_action=preserve_expand]
    J -->|是| L[灰度开启 S3 新任务]
    L --> M[持续监控并执行四域对账]
```

#### 3.4.3 执行前预检

1. 固定应用、`manifest.tsv` 和 SQL 的同一候选提交，检查目标库为 V002 兼容基线。
2. 按 9.1 节生成数据库备份，先恢复到空隔离库，再在该副本完成同版本迁移和全量业务对账。
3. 候选制品必须通过 `FullSchemaUpgradeIntegration` 和 `ExpandMixedVersionIntegration`；记录备份 ID、恢复演练、候选提交和审批单。
4. 检查长事务、DDL 锁等待、旧实例与 local 非终态任务；不在未评估的长事务或锁等待上直接执行。
5. 比较账本与 manifest；账本可在首次执行 V003 前不存在，但既有行不得出现未知版本、重复版本或 checksum 漂移。

```sql
SELECT to_regclass('public.schema_migrations') AS migration_ledger;

SELECT pid, usename, xact_start, state, wait_event_type, wait_event,
       left(query, 120) AS query
FROM pg_stat_activity
WHERE datname = current_database()
  AND xact_start IS NOT NULL
ORDER BY xact_start;
```

#### 3.4.4 迁移 Job 与对账

只启动一个不接入业务流量的 migration Job，使用受保护的环境变量注入 PostgreSQL 连接信息：

```bash
export PGHOST=db.internal.example
export PGPORT=5432
export PGDATABASE=disk
export PGUSER=disk_user
export PGPASSWORD='<secret-from-approved-store>'

scripts/migrate-db.sh

sha256sum \
  sql/migrations/V003_distributed_upload_forward.sql \
  sql/migrations/V004_storage_reconciliation_forward.sql
```

执行器使用 `psql -X --set ON_ERROR_STOP=1`，并对每个待应用版本使用单事务和 advisory lock。某一版本失败只会自动回滚该版本；先前已提交的 manifest 前缀仍保留，修正根因后重新执行会根据账本幂等续跑。不要并行手工执行单个 SQL 文件。

迁移后保存脚本输出并执行以下结构/数据对账；两个版本的 checksum 必须与候选提交中对应文件的 SHA-256 相等，后四个计数查询必须都返回 0：

```sql
SELECT version, checksum, applied_at
FROM schema_migrations
WHERE version IN ('V003_distributed_upload', 'V004_storage_reconciliation')
ORDER BY version;

SELECT count(*) AS missing_required_relations
FROM (VALUES ('storage_jobs'), ('storage_reconciliation_findings')) AS expected(name)
WHERE to_regclass('public.' || expected.name) IS NULL;

WITH expected(table_name, constraint_name) AS (
    VALUES
        ('upload_tasks', 'ck_upload_tasks_status'),
        ('upload_tasks', 'ck_upload_tasks_staging_backend'),
        ('upload_tasks', 'ck_upload_tasks_nonnegative'),
        ('upload_tasks', 'ck_upload_tasks_staging_prefix'),
        ('upload_tasks', 'ck_upload_tasks_finalizing_lease'),
        ('upload_tasks', 'ck_upload_tasks_completed_file'),
        ('upload_tasks', 'fk_upload_tasks_completed_file_id'),
        ('upload_task_chunks', 'ck_upload_task_chunks_index'),
        ('upload_task_chunks', 'ck_upload_task_chunks_size'),
        ('upload_task_chunks', 'ck_upload_task_chunks_hash'),
        ('storage_jobs', 'uk_storage_jobs_dedupe_key'),
        ('storage_jobs', 'ck_storage_jobs_status'),
        ('storage_jobs', 'ck_storage_jobs_attempts'),
        ('storage_jobs', 'ck_storage_jobs_running_lease'),
        ('storage_reconciliation_findings', 'uk_storage_reconciliation_finding'),
        ('storage_reconciliation_findings', 'ck_storage_reconciliation_severity'),
        ('storage_reconciliation_findings', 'ck_storage_reconciliation_strategy'),
        ('storage_reconciliation_findings', 'ck_storage_reconciliation_occurrences')
)
SELECT count(*) AS missing_or_invalid_constraints
FROM expected
WHERE NOT EXISTS (
    SELECT 1
    FROM pg_constraint
    WHERE conrelid = to_regclass('public.' || expected.table_name)
      AND conname = expected.constraint_name
      AND convalidated
);

SELECT count(*) AS missing_required_indexes
FROM (
    VALUES
        ('idx_upload_tasks_finalizing_lease'),
        ('idx_upload_tasks_staging_backend'),
        ('idx_storage_jobs_ready'),
        ('idx_storage_jobs_expired_lease'),
        ('idx_storage_jobs_type_status'),
        ('idx_storage_reconciliation_unresolved')
) AS expected(name)
WHERE to_regclass('public.' || expected.name) IS NULL;

SELECT count(*) AS invalid_staging_rows
FROM upload_tasks
WHERE staging_backend NOT IN ('local', 's3')
   OR (staging_backend = 's3'
       AND (staging_prefix IS NULL OR staging_prefix = ''));
```

然后核对 local 非终态任务、`storage_jobs` 各状态、未解决 finding、用户配额、文件数、
`file_contents.ref_count` 和对象存储存在性。启动兼容 Worker/API 后按 3.4.8 节回收旧连接计划，再执行 readiness、profile、local 上传探针、下载/Range 探针和新 `scan_id` 的 `contents/users/staging/final` 四域全分页对账。

#### 3.4.5 应用回滚与灾难恢复

迁移或对账失败时立即停止后续发布，保留已提交的 expand schema、账本和证据。应用、配置或流量验证失败只回退运行组件，并记录 `schema_action=preserve_expand`。只能回退到已通过 expand 兼容矩阵的制品；没有兼容制品时保留当前处理面并前向修复。

只有新能力从未启用、迁移专用数据门禁归零、备份/恢复演练和独立 schema 变更单均已验收时，才允许按 3.4.8 节调用 `scripts/reverse-expand-migration.sh` 做预激活撤销。生产写入已发生或状态不确定时，必须保留 expand。

备份恢复只用于损坏或丢失等灾难场景：先恢复到空隔离数据库，按 9.2 节完成账本、schema、四域对账和下载探针，再通过独立变更单切换流量。禁止把备份直接覆盖仍在服务的数据库来模拟普通应用回滚。

#### 3.4.6 停止条件

任一条件成立都要停止发布，保留 expand 与现场证据，不得继续灰度：

1. 备份、空隔离恢复演练、V002 基线或两项候选制品升级门禁未完成。
2. manifest 缺失/顺序异常，已记账 checksum 漂移，出现未知账本版本，或迁移 Job 任一 SQL 失败。
3. DDL 锁等待超过批准窗口，数据回填/约束验证失败，或所需表、索引、约束与候选版本不符。
4. 配额、文件数、`ref_count`、上传预留、任务队列、finding 或 DB/对象存储双向对账不一致。活跃用户的 `storage_reserved` 和活动 `upload_task_chunks` 可合法非零，不能把“全部为零/空表”作为存量升级前提。
5. Worker/API readiness、旧连接回收、上传、下载/Range 或四域对账探针失败，且没有已验证的 expand-compatible 回退制品。
6. 有人试图在紧急应用回滚中运行 `*_rollback.sql`、删除账本行或执行 contract DDL。

#### 3.4.7 V002 分享审计操作者可空迁移

V002 使 `operation_logs.user_id` 可空，并把用户外键从 `ON DELETE CASCADE` 改为 `ON DELETE SET NULL`。新建数据库已经在 `sql/init.sql` 使用相同定义；存量 PostgreSQL 数据库必须先执行迁移，再发布包含分享访客审计的应用版本。

```bash
# 前向迁移；脚本在单个事务中重建外键，可重复执行
psql -v ON_ERROR_STOP=1 -U disk_user -h localhost -d disk \
  -f sql/migrations/V002_share_audit_forward.sql

# 对账：is_nullable 应为 YES，delete_rule 应为 SET NULL
psql -U disk_user -h localhost -d disk -c "
SELECT c.is_nullable, rc.delete_rule
FROM information_schema.columns c
JOIN information_schema.referential_constraints rc
  ON rc.constraint_name = 'fk_operation_logs_user_id'
WHERE c.table_schema = 'public'
  AND c.table_name = 'operation_logs'
  AND c.column_name = 'user_id';"
```

发布后验证至少包含：所有者 `share_create`/`share_cancel` 的 `user_id` 为真实操作者；访客 `share_access`/`share_pwd_fail`/`share_download` 的 `user_id IS NULL`；`details` 不含密码、密码哈希、原始 Share Token 或认证请求头；90 天分批清理语句同时覆盖两类日志。

V002 审计写入失败是 fail-open 且不自动重试。运维应对 `Failed to record share audit event` 错误日志告警，修复数据库后通过业务事件和日志时间窗口对账，不得把访客事件补记到分享所有者名下。

回滚脚本会在存在 `user_id IS NULL` 的日志时主动失败，避免静默删除或伪造操作者。它只允许在访客审计尚未启用的预激活窗口撤销迁移；应用已经写入或紧急回滚时必须保留 expand。完成备份、独立审批和只读证据后，按 3.4.8 节设置四项授权变量再执行：

```bash
scripts/reverse-expand-migration.sh V002_share_audit
```

回滚后 `user_id` 恢复 `NOT NULL`、外键恢复 `ON DELETE CASCADE`，旧应用可继续运行；包含访客审计的新应用不得在回滚后的 schema 上发布。

#### 3.4.8 V003 分布式上传 expand 迁移

ADR-002 的数据库升级依次使用 `sql/migrations/V003_distributed_upload_forward.sql` 和
`V004_storage_reconciliation_forward.sql`，并由独立迁移任务调用 `scripts/migrate-db.sh` 执行。
V003 建立上传租约和持久任务队列，V004 建立可查询的对账发现表。执行器使用
`schema_migrations` 保存脚本 SHA-256，并在同一 PostgreSQL 事务内获取 advisory lock、执行 DDL 和
记录版本。API 和 Worker 启动流程只校验 schema 版本，不执行 DDL，避免多副本并发迁移。

V003 采用 expand/data/contract 三阶段：

1. **Expand**：为 `upload_tasks` 增加暂存后端、状态版本、完成租约、诊断和完成结果字段；为 `upload_task_chunks` 增加大小、MD5、对象 key 和 ETag；新增 `storage_jobs`、约束和认领索引。新增列必须允许旧应用继续读写现有任务。
2. **Data**：把存量进行中任务标记为 `staging_backend=local` 并生成稳定 `staging_prefix`；上线前统计进行中任务和本地暂存目录，迁移期由旧实例完成或取消这些任务。新任务逐步切换到 `s3`。
3. **Contract**：只在所有旧实例退出、没有 local 暂存任务且对账通过后，删除临时兼容默认值或废弃路径。本轮不在 expand 脚本中执行破坏性 contract DDL。

```bash
export DISK_S3_ENDPOINT='https://s3.example.internal'

scripts/migrate-final-blobs.py copy \

# 3. 先验证 cutover；确认 DB 仍与清单一致后执行一次事务切换。
scripts/migrate-final-blobs.py cutover \

scripts/migrate-final-blobs.py cutover \

  --manifest /var/lib/disk-migration/final-blobs.jsonl
scripts/migrate-final-blobs.py rollback \
  --manifest /var/lib/disk-migration/final-blobs.jsonl --execute
```

manifest 是 JSONL：首行为版本、生成时间、规范化 local 根目录、bucket、object prefix 和对象总数，后续
按 content ID 排序记录原 locator、根目录相对源文件、大小、MD5、SHA-256 与目标 key。生成阶段拒绝
根目录逃逸、缺失/非普通文件、重复 SHA-256、非法哈希和超过 `storage_path VARCHAR(512)` 的目标 key。
manifest 在可重复读只读事务中生成，不初始化 S3、不发起对象请求、不创建 checkpoint，且不改动
`file_contents` 或 local 源 Blob。它以 `0600` 权限写入同目录临时文件，数据落盘后才以不覆盖语义
原子发布；已有同名清单、并发发布冲突或中途验证失败都必须保留已有证据且不留最终半成品。
评审后记录 manifest 的 SHA-256，并在 copy/cutover 全程使用同一文件。
copy 每次都重新读取源并计算 MD5/SHA-256；目标存在时完整 GET 并校验，不覆盖冲突对象。上传成功只有在
完整 GET 得到相同大小和双哈希后才提交 SQLite checkpoint。进程在任意对象中途退出时，已提交对象可重验
复用，当前对象由 S3 单对象原子可见性或 multipart abort/lifecycle 收敛，下一次执行重新处理。
`--max-objects N` 可用于首批有界演练；`--rate-limit-mib-per-second R` 的正值对上传回调和随后完整
目标 GET 共享一个聚合字节预算，因此新对象的网络计费字节至少为大小的两倍；`0` 禁用限速，负值拒绝。
dry-run 仍执行源双哈希和目标 HEAD/已存目标 GET 校验，但不 PUT、不创建 checkpoint、不更改数据库。

cutover 会先以只读方式打开与 manifest/目标绑定的 checkpoint，要求每个对象都有完整验证记录，再次完整 GET 所有目标并
校验大小、MD5 和 SHA-256，然后才以 `ACCESS EXCLUSIVE NOWAIT` 锁验证数据库完整
集合。任何新增、删除、哈希/大小/路径漂移或混合源/目标状态都会终止且不修改 DB。成功提交后，在恢复任何
进程前把所有 API/Worker 同时配置为相同 bucket、`storage_backend=s3` 和 manifest 中的 object prefix，
执行下载/Range 探针与全量对账后再开放流量。旧 local Blob、manifest 和 checkpoint 至少保留到备份恢复
演练及配额、`ref_count`、DB/对象对账全部通过；不得因 checkpoint 显示完成就删除源文件。
无 checkpoint、checkpoint 少任意一条或复制后目标损坏都必须保持全部原路径；cutover 不负责补传或修复对象。

#### 3.5.5 常见问题排查

**问题 1: 连接超时**

```bash
# 检查防火墙；自管 Redis 只允许应用私网子网访问

```

**问题 2: 认证失败**

```bash
# 测试密码
redis-cli -h 127.0.0.1 -p 6379 -a wrong_password ping
# 预期: (error) NOAUTH Authentication required.

# 检查配置
cat /etc/redis/redis.conf | grep requirepass
# 确认 Redis 服务密码与注入的 REDIS_PASSWORD 一致
```

**问题 3: 连接池耗尽**

```bash
# 查看 Redis 最大连接数
redis-cli -a your_redis_password CONFIG GET maxclients

# 增加最大连接数
redis-cli -a your_redis_password CONFIG SET maxclients 10000
```

**注意事项**:

1. **生产环境安全**:
   - ✅ 必须设置 Redis 密码
   - ✅ 使用环境变量 `${REDIS_PASSWORD}`
   - ❌ 不要在配置文件中硬编码密码
   - ❌ 不要将 Redis 暴露到公网

2. **网络安全**:
   - 使用内网 IP，不要使用公网 IP
   - 配置防火墙，只允许应用服务器访问
   - 使用 Redis 6.0+ 的 ACL（访问控制列表）

3. **监控告警**:
   - 监控 Redis 连接数、内存使用、命令延迟
   - 设置告警阈值：连接数 > 80%、内存使用 > 90%

4. **连接池配置**:
   - 保持每进程 4 条的已验证基线，不按单机高并发值直接放大
   - 扩容前按 `4 * (API 副本 + Worker 副本 + 替换副本)` 核算总连接
   - 监控连接池使用情况和 Redis `maxclients` 余量

| `worker_lease_duration_seconds` | integer | 120 | 30-3600 | 持久任务认领租约时长；执行期间按其三分之一续租 |
| `worker_drain_timeout_seconds` | integer | 30 | 1-300 | SIGTERM/SIGINT 后停止认领并等待在途任务的最长时间 |
| `s3.bucket` | string | disk | 非空 | S3/MinIO bucket |
| `s3.region` | string | us-east-1 | 非空 | S3 region |
| `s3.endpoint` | string | 空 | 空或纯 origin | 自定义 S3/MinIO endpoint；只允许与 `use_ssl` 一致的 `scheme://authority`，AWS S3 可留空 |
| `s3.use_ssl` | boolean | true | - | endpoint 是否使用 HTTPS |
| `s3.force_path_style` | boolean | false | - | MinIO 通常设置为 true |
| `s3.verify_ssl` | boolean | true | - | 是否校验证书 |
| `s3.object_prefix` | string | objects | 相对 key 前缀 | 最终 blob 对象 key 前缀 |
| `s3.staging_prefix` | string | staging | 相对 key 前缀 | 上传分片、组装结果和临时对象 key 前缀 |
| `s3.max_connections` | integer | 16 | 1-256 | 每进程 AWS SDK HTTP 连接池上限 |
| `s3.io_threads` | integer | 4 | 1-64 | 每进程执行阻塞 S3 SDK 调用的专用线程上限 |
| `s3.connect_timeout_ms` | integer | 3000 | 100-60000 | 单次 S3 连接超时，毫秒 |
| `s3.request_timeout_ms` | integer | 300000 | 1000-3600000 | 单次 S3 请求超时，毫秒；不含请求级重试次数 |
| `s3.max_retries` | integer | 3 | 0-10 | 首次请求之外的最大重试次数；0 表示禁用请求内重试 |
| `s3.retry_base_delay_ms` | integer | 100 | 1-60000 | 可重试错误的指数退避基数，毫秒 |

S3 前缀会移除首尾 `/`；每个 `/` 分隔段只允许 ASCII 字母、数字、`.`、`_`、`-`，
且不允许空段、`.`、`..` 或反斜杠。空配置分别回退为 `objects` 和 `staging`，非法前缀
会使进程启动失败，不会在运行时拼接未经验证的对象 key。两类前缀不得相同或互为父子
前缀，以保证 staging 生命周期规则和清理操作永远不能覆盖 final Blob。

自定义 `s3.endpoint` 只能是绝对 origin，例如 `https://s3.internal.example:9000`、
`http://127.0.0.1:9000` 或 `https://[2001:db8::10]:9000`。不得包含路径（包括尾随 `/`）、
userinfo、query、fragment、反斜杠、百分号、空白或控制字符；端口必须是 `1..65535`。
scheme 必须与 `s3.use_ssl` 一致，非法值在 SDK 初始化和监听端口开放前使启动失败，诊断不得
回显 endpoint。该值只来自启动配置，任何 API 请求都不能覆盖目标。私有 MinIO 是受支持场景，
因此生产环境还必须用 DNS allowlist、NetworkPolicy、防火墙或出口代理将访问限制到批准的 S3 服务。

`s3.io_threads` 不得大于 `s3.max_connections`；不满足时进程在启动阶段失败。连接池是网络资源
上限，I/O 线程是应用同时发起同步 SDK 调用的上限；两者均按进程计算，不是集群共享配额。

S3 请求仅对 HTTP 408、429、5xx 和连接/网络类错误执行有界重试。认证、签名、bucket、参数及
其他普通 4xx 错误立即失败；即使 SDK 将其标记为 retryable，永久错误分类仍优先。每次业务调用
最多执行 `1 + s3.max_retries` 次请求，达到预算后把最后一次错误返回调用方，由上传租约或持久
Worker 决定是否进行更高层重试，禁止在任一层无限重试。

`process_role` 在非安全模式下默认为 `all`，仅供本地单进程开发和测试。`DISK_SECURE_MODE=true`
时必须通过 `DISK_PROCESS_ROLE` 或 `custom_config.disk.process_role` 显式选择 `api`/`worker`，
且禁止 `all`；这使生产误用单进程兼容模式时在启动阶段失败。

`worker_claiming_enabled` 只改变 `worker`/`all` 角色是否启动持久任务认领和周期任务播种，不跳过
数据库、任务表或对象存储 readiness 检查。该值只在启动时读取，不是运行时暂停按钮；从观察模式切换
为执行模式必须以 `true` 重新部署或重启。优雅排空仍由进程信号和 `worker_drain_timeout_seconds`
控制，两者不得混用。

`instance_id` 在同一进程内跨 `LoadConfig()` 保持稳定。未配置时，每次进程启动生成新的 UUID；容器编排环境应通过 Downward API 或等价机制注入唯一的 `DISK_INSTANCE_ID`。任一显式 JSON 值或环境变量值超出表中约束时，应用必须启动失败，不能静默回退。

> **迁移范围**：旧版本中 `storage_backend=s3` 仅表示最终 Blob 使用对象存储，上传仍在本地暂存。ADR-002 实现后，`upload_staging_backend=s3` 才表示新任务使用 S3-native staging；每个任务把实际后端写入 PostgreSQL，因此滚动发布期间 local 与 s3 任务可并存。生产多实例在迁移完成后必须同时使用 `storage_backend=s3` 和 `upload_staging_backend=s3`；完成归零门禁后的制品会直接拒绝安全模式 API 使用 local 暂存。

同一集群的所有 API/Worker 必须使用相同的 `s3.staging_prefix`。运行时只接受精确等于
`{configured_staging_prefix}/{upload_id}` 的 S3 会话描述符；若要变更该前缀，必须先停止创建
新上传并排空或显式迁移所有 `staging_backend='s3'` 的非终态任务，不能在滚动发布中直接切换。

`upload_staging_backend=s3` 要求 `storage_backend=s3`，不支持把 S3 暂存提升到 local final。
迁移期间的兼容制品允许 `storage_backend=s3 + upload_staging_backend=local`。归零门禁制品只允许显式
`worker` 角色在安全模式下保留 local，以处理已经持久化的遗留描述符；`api` 角色会在监听前拒绝该组合，
因此不能再用它创建新的 local 任务。非安全模式 local 仅供开发、测试和隔离迁移环境。

新建 final Blob 的 S3 key 固定为
`{s3.object_prefix}/sha256/{sha256[0:2]}/{sha256}.bin`；local 开发后端使用对应的
`{storage_base_path}/sha256/{sha256[0:2]}/{sha256}.bin`。历史 MD5 布局不会随配置加载自动迁移，
API 和 Worker 始终按 `file_contents.storage_path` 读取或删除已有对象。变更 `s3.object_prefix` 前
必须排空写流量并迁移数据库中的路径，不能只修改配置后滚动发布。

S3 原生完成先在 staging 前缀生成 assembled 对象，再使用 server-side multipart copy 提升到
final 前缀。每个 multipart upload ID 在首个 part 前登记到 `storage_jobs`，失败路径会即时 Abort；
Abort 失败或进程退出后由 Worker 按租约接管，assembled 会保留供完成租约接管或对账。bucket 生命周期
规则只能覆盖 staging 前缀和未完成 multipart，禁止覆盖 final 前缀。应用 cleanup Worker 上线前，
生命周期过期时间必须大于上传最大有效期、最长租约接管窗口和允许的人工恢复窗口之和。

生产发布必须同时配置未完成 multipart 的服务端回收，覆盖 S3 返回 upload ID 到
PostgreSQL 任务登记之间的极短崩溃窗口。AWS S3 使用 bucket 级
`AbortIncompleteMultipartUpload`；仓库固定的 MinIO `RELEASE.2025-04-22T22-12-26Z`
不接受该 lifecycle action，因此样例服务端显式设置
`MINIO_API_STALE_UPLOADS_EXPIRY=168h` 和 `MINIO_API_STALE_UPLOADS_CLEANUP_INTERVAL=6h`。两种机制的保留时间都必须大于应用最大上传有效期；发布校验需要同时确认“未完成 multipart 回收已启用”和“final 前缀没有 Expiration”。仅依赖服务端过期会延迟资源回收且无法提供任务级审计，因此不能关闭 `multipart_abort` Worker。

仓库的 `deploy/minio/lifecycle.json` 是 MinIO 默认前缀的可执行基线：`staging/` 对象保留 7 天，`objects/` 不设置 Expiration；未完成 multipart 由上述 MinIO API 配置清理。`docker-compose.s3.yml` 在建桶后执行：

```bash
mc ilm rule import local/disk < /config/lifecycle.json
mc ilm rule export local/disk
```

生产 AWS S3 使用包含 staging Expiration 和 `AbortIncompleteMultipartUpload` 的
`deploy/s3/lifecycle.json` 执行
`aws s3api put-bucket-lifecycle-configuration --bucket <bucket> --lifecycle-configuration file://deploy/s3/lifecycle.json`，
随后用 `get-bucket-lifecycle-configuration` 复核。若 `s3.staging_prefix` 或 `s3.object_prefix` 不使用
默认值，发布前必须同步生成并校验对应规则；禁止直接复用前缀不匹配的样例。

S3 前缀是对象 key namespace，不是需要预先创建的目录。不得向 `objects/`
或 `staging/` 写入零字节目录 marker：final 对账会将未被数据库引用的 marker
识别为孤儿对象。建 bucket、导入 lifecycle 后，由应用首个对象写入自然具现前缀。

`deploy/minio/app-policy.json` 是本地 `disk` bucket 的最小权限基线。bucket 级只允许
`GetBucketLocation` 和带 `objects`/`staging` 前缀条件的 `ListBucket`；对象级只允许
`GetObject`、`PutObject`、`DeleteObject`、`AbortMultipartUpload` 和
`ListMultipartUploadParts`，资源精确限定到 `objects/*` 与 `staging/*`。应用凭据不能修改
bucket policy/lifecycle，不能管理用户，也不能读写其他前缀。非 `disk` bucket 或自定义前缀必须在发布产物中生成等价的精确 ARN，不得用 `arn:aws:s3:::*` 或 `s3:*` 回避模板化。
后端启动时用 `GetBucketLocation` 验证 bucket 可达，不调用需要无前缀
`ListBucket` 权限的 `HeadBucket`；因此 policy 可以继续拒绝两个业务前缀之外的清单请求。

MinIO 样例由 `minio-init` 使用 root 凭据执行一次性建 bucket、导入 lifecycle、
创建/更新 `DISK_S3_ACCESS_KEY` 服务账号并绑定 `disk-app` policy；API/Worker
只接收独立的 `DISK_S3_ACCESS_KEY`/`DISK_S3_SECRET_KEY`，不接收
`DISK_MINIO_ROOT_USER`/`DISK_MINIO_ROOT_PASSWORD`。root 凭据只存在受限的密钥系统和初始化任务中，初始化完成后不注入业务容器。

对象存储上线监控至少同时覆盖：API/Worker readiness 的 staging/final 有界读探针；
`disk_dependency_calls_total{dependency="s3"}` 的短暂/永久错误告警；
`disk_reconciliation_findings_unresolved` 的缺失、大小不符和孤儿对象告警；以及目标 S3/MinIO 原生的可用性、容量、节点/故障域、请求错误、复制/修复和 lifecycle 执行指标。仓库告警只覆盖应用视角，不得用它代替对象存储服务端的原生监控。

#### 4.1.2 分享操作限流配置

分享访问、浏览和下载使用三组相互独立的正整数配置。字段缺失、为零、为负数或不能作为正整数使用时，应用使用下表代码默认值：

| 字段 | 默认值 | Redis 身份 | 覆盖范围 |
|------|--------|------------|----------|
| `share_access_rate_limit_per_minute` | 30 | 规范化客户端 IP | `/api/share/access/{share_id}` |
| `share_access_rate_limit_window_seconds` | 60 | 同上 | access 固定窗口秒数 |
| `share_browse_rate_limit_per_minute` | 60 | 已验证 Share Token JTI | `/api/share/browse/{share_id}` |
| `share_browse_rate_limit_window_seconds` | 60 | 同上 | browse 固定窗口秒数 |
| `share_download_rate_limit_per_minute` | 10 | 已验证 Share Token JTI | 下载元数据、内容和保存到网盘共享 |
| `share_download_rate_limit_window_seconds` | 60 | 同上 | download 固定窗口秒数 |

字段名中的 `per_minute` 为现有配置命名约定；实际窗口由对应 `*_window_seconds` 决定。调整窗口时 limit 表示“每个配置窗口的请求数”，不得按名称再次换算。

**破坏性配置迁移**：`share_public_rate_limit_per_minute` 和 `share_public_rate_limit_window_seconds` 已从新合同删除。新版本不读取旧键，也不把旧值复制到三组新键；发布前必须显式配置六个新键。保留旧键只会造成运维误判，不会改变运行时默认值。

**Redis 键与窗口**：

```text
rate:share_access:{normalized_ip}:{window}
rate:share_browse:{jti}:{window}
rate:share_download:{jti}:{window}
```

`window` 是按配置秒数取整的 Unix 固定窗口起点。第一次 `INCR` 原子设置 TTL，后续递增不刷新；因此不需要单独清理正常过期键。升级前遗留的 `rate:share_public:*` 不再读取，可等待原 TTL 自然过期。禁止使用原始 Share Token、`X-Share-Token`、Authorization、密码或密码哈希构造键、日志或审计字段。

达到边界后返回 HTTP 429 / `10005 TooManyRequests` / `Too many requests`，并包含 `X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset` 和 `Retry-After`。Redis 计数失败采用 fail open：记录操作类型和不含凭据的诊断信息后继续底层请求。生产监控应对该错误日志告警，因为 fail open 期间接口可用但滥用防护暂时降级。

可使用不回显 value 的 `SCAN` 检查键族分布：

```bash
redis-cli --scan --pattern 'rate:share_access:*'
redis-cli --scan --pattern 'rate:share_browse:*'
redis-cli --scan --pattern 'rate:share_download:*'
```

不要把扫描结果连同请求头或 token 保存到工单、日志或测试 evidence。JTI 不是可重放 token，但仍只应在短 TTL 限流键和请求内属性中使用。

文件列表缓存不使用 `SCAN` 删除。每个用户保持永久的 `file_list_version:{user_id}` 计数器，数据库写入成功后用 `INCR` 切换列表命名空间；`file_list:{user_id}:{version}:...` 结果键保留 30 秒 TTL 后自动回收。不得手工删除版本键作为常规清缓存操作；版本键缺失时应用从 `0` 开始，Redis 读取异常时列表查询降级到 PostgreSQL 且不回填。

### 4.2 环境变量

进程先读取 `DISK_CONFIG_FILE` 指定的 JSON（未设置时为工作目录下的 `config.json`），再以环境变量覆盖运行时连接、监听和对象存储字段。覆盖值必须完整通过类型和范围校验；变量存在但为空、布尔值不是 `true/false/1/0`、端口或连接池越界时，进程直接启动失败。最终生效配置只传给 Drogon，不写回文件，也不得完整打印到日志。PostgreSQL 连接池大小必须使用 Drogon 支持的 `db_clients[0].connection_number`；`DATABASE_POOL_SIZE` 只覆盖该字段，旧拼写 `num_connection_number` 不属于兼容配置，不能用于容量规划或指标口径。

支持的覆盖变量如下：

| 范围 | 环境变量 | JSON 目标 |
|------|----------|-----------|
| 配置文件 | `DISK_CONFIG_FILE` | 运行时配置文件路径 |
| HTTP | `DISK_LISTEN_ADDRESS`、`DISK_LISTEN_PORT` | `listeners[0].address/port` |
| PostgreSQL | `DATABASE_HOST`、`DATABASE_PORT`、`DATABASE_NAME`、`DATABASE_USER`、`DATABASE_PASSWORD`、`DATABASE_POOL_SIZE` | `db_clients[0]` |
| Redis | `REDIS_HOST`、`REDIS_PORT`、`REDIS_DB`、`REDIS_PASSWORD`、`REDIS_POOL_SIZE` | `redis_clients[0]` |
| 进程 | `DISK_PROCESS_ROLE`、`DISK_INSTANCE_ID`、`DISK_WORKER_CLAIMING_ENABLED` | `custom_config.disk.process_role/instance_id/worker_claiming_enabled`；环境变量继续由 `ConfigMgr` 冻结 |
| 存储 | `DISK_STORAGE_BACKEND`、`DISK_UPLOAD_STAGING_BACKEND`、`DISK_UPLOAD_TASK_CREATION_ENABLED` | `custom_config.disk.storage_backend/upload_staging_backend/upload_task_creation_enabled` |
| S3 | `DISK_S3_BUCKET`、`DISK_S3_REGION`、`DISK_S3_ENDPOINT`、`DISK_S3_USE_SSL`、`DISK_S3_FORCE_PATH_STYLE`、`DISK_S3_VERIFY_SSL`、`DISK_S3_OBJECT_PREFIX`、`DISK_S3_STAGING_PREFIX`、`DISK_S3_MAX_CONNECTIONS`、`DISK_S3_IO_THREADS`、`DISK_S3_CONNECT_TIMEOUT_MS`、`DISK_S3_REQUEST_TIMEOUT_MS`、`DISK_S3_MAX_RETRIES`、`DISK_S3_RETRY_BASE_DELAY_MS` | `custom_config.disk.s3.*` |
| S3 凭据 | `DISK_S3_ACCESS_KEY`、`DISK_S3_SECRET_KEY`、`DISK_S3_SESSION_TOKEN` | 仅传给 AWS SDK 凭据提供链，不进入 JSON |

`DATABASE_PASSWORD` 和 `REDIS_PASSWORD` 会覆盖 Drogon 客户端的 `passwd` 字段。分布式配置模板中的两个字段必须为空，生产密码通过环境、容器 Secret 或密钥注入器提供。`DISK_S3_ACCESS_KEY` 与 `DISK_S3_SECRET_KEY` 必须同时存在；未设置时允许 AWS SDK 使用实例角色等默认凭据链。

通用 API 响应和自由文本测试证据必须通过共享保存入口递归脱敏 access/refresh/share token、
Authorization、密码、JWT/S3/数据库/Redis 密钥等字段，并对 Header、环境变量赋值和 JWT 形态的
纯文本执行同等处理。证据可以保留不可用于认证的 `upload_id`、`jti` 和分页 continuation token。
专用发布/迁移脚本只能直接原子发布经过字段白名单评审的非敏感摘要；raw 字节入口只允许仓库生成的
合成下载夹具，禁止写入真实响应、配置、Header 或环境快照。生成目录 `.sisyphus/evidence/` 不提交
版本库，发布前仍需执行凭据扫描。

创建 `/etc/disk/env` 文件：

```bash
# 运行时配置文件；后端不解析 -c/--config 命令行参数
DISK_CONFIG_FILE=/etc/disk/config.distributed.json

# JWT密钥（至少 32 字符随机字符串）
JWT_SECRET=your_very_long_and_secure_jwt_secret_key_here
```

> **重要**: systemd 会在降权前以 root 读取此文件；保持 `root:root 0600`，不要授予应用进程直接读取 Secret 文件的权限。

`/etc/disk/env` 是所有副本共享的集群级环境文件，不得在其中设置 `DISK_PROCESS_ROLE`、
`DISK_INSTANCE_ID`、`DISK_LISTEN_ADDRESS` 或 `DISK_LISTEN_PORT`。角色和监听地址由编排平台逐副本注入；
本指南的 systemd 方式将它们放在 `/etc/disk/instances/<instance>.env`。`DISK_INSTANCE_ID`
在 systemd/NSSM 示例中保持未设置，由进程每次启动生成新 UUID；外部编排平台若显式注入，
也必须使用每次进程启动唯一的值，不得复用稳定的主机名或副本槽位名。
后端 `main()` 不解析 `-c` 或 `--config`，任何服务管理器都必须使用 `DISK_CONFIG_FILE` 指向 JSON。

`DISK_SECURE_MODE=true` 除验证 JWT、数据库和 Redis 密码外，还要求显式 `api`/`worker` 角色；安全模式 `api` 必须使用 `upload_staging_backend=s3`，配置为 local 时在监听端口开放前失败。显式 `worker` 可暂时保留 local 以完成遗留清理，但它不提供新上传创建路径。当 final 或 staging 选择 S3 时，必须同时启用 `s3.use_ssl` 与 `s3.verify_ssl`。`upload_staging_backend=s3` 仍要求 `storage_backend=s3`，空 bucket、重叠前缀和非纯 origin endpoint 同样会使启动失败。endpoint 校验不能替代目标环境的 DNS 和网络出口策略。仓库的本地 Compose 明确运行在非安全模式并使用隔离开发网络上的 HTTP MinIO，不能照搬为生产配置。

`DISK_TEST_FAULT_INJECTION`、`DISK_TEST_PAUSE_AFTER_FINALIZE_CLAIM_UPLOAD_ID`、`DISK_TEST_PAUSE_AFTER_ASSEMBLY_UPLOAD_ID`、`DISK_TEST_PAUSE_AFTER_FINALIZE_COMMIT_UPLOAD_ID` 与 `DISK_TEST_PAUSE_AFTER_BLOB_DELETE_JOB_ID` 只属于受控集成测试，不是可部署的运行配置；生产环境不得设置。后端只在非安全模式、总开关精确为 `1` 且对应阶段变量精确匹配当前 upload ID 或十进制 `storage_jobs.id` 时，才会在 Finalizing 认领提交后、assembled 成功创建后、最终事务成功提交后或 Blob 删除成功但任务事务尚未写回时进入测试停顿；安全模式必须无条件忽略全部停顿点。

##### 双 API 无粘性随机路由门禁

运行时门禁必须从唯一负载均衡地址发起，禁止为了构造结果而把业务请求直接发送到 `18081/18082`。
同一持久 HTTP 客户端保持固定 cookie，对一个唯一非秒传上传依次执行 init、有界的同分片幂等重试、
complete 和 download；每个响应都必须携带应用生成的 `X-Disk-Instance-Id`。在 complete 前，实例序列
必须已经同时包含 `disk-api-a` 与 `disk-api-b`，否则即使 Nginx 文件中不存在 sticky/cookie/ip-hash
也判定失败。随后必须对账 `Completed + completed_file_id`、唯一文件/内容引用/final 对象、reserved
精确结算和逐字节下载。

Compose 路径验证真实 Nginx `least_conn` 入口；无 Docker 的本地进程入口使用测试专用的随机洗牌池，
每轮把两个 ready upstream 随机排列且各选择一次，非幂等请求仍不做代理级重放。两条路径复用
`test_distributed_flow.py` 的相同业务断言，并把实例序列、分片重试次数、文件 ID 和内容 SHA-256

直连 A/B 的交叉实例用例不能勾选本门禁。

#### 4.5.1 Worker 只读观察部署

expand schema 和过渡版本验证通过后，先用 `DISK_WORKER_CLAIMING_ENABLED=false` 部署 Worker。
观察实例仍连接 PostgreSQL 和对象存储，检查 `storage_jobs` schema 并查询真实队列快照；它不调用
`ClaimReadyJobs`，不续租或完成任务，也不注册上传过期、回收站过期和对账等周期播种器。此时
`/api/health/ready` 应为 200，响应中的 `worker_claiming_enabled=false`、
`worker_accepting=false` 明确区分“受控观察”和 drain；`/metrics` 中
`disk_worker_claiming_enabled 0`、`disk_worker_accepting_jobs 0` 必须与之相符。

Compose 样例可按以下顺序只启动依赖和观察 Worker；环境变量必须在 Compose 渲染时传入，不能只在
容器启动后修改：

```bash
cp deploy/distributed.env.example .env.distributed

  docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  up -d --build worker-a worker-b

docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  exec -T worker-a curl -fsS http://127.0.0.1:8080/api/health/ready
docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  exec -T worker-a sh -c \
  "curl -fsS http://127.0.0.1:8080/metrics | grep -E 'disk_(worker_claiming_enabled|worker_accepting_jobs|metrics_snapshot_success)'"
```

部署前后至少间隔三个 `worker_poll_interval_ms`，用下列查询记录 Ready 任务的 `id/status/attempts/locked_by/locked_until`
和聚合队列深度；观察实例 ID 不得出现在 `locked_by`，相同任务不得因观察实例改变状态、尝试次数或租约，
且不得出现由观察实例播种的新周期任务。若 readiness/快照指标失败、任何任务被观察实例认领，或周期任务
数量意外变化，立即停止本次发布并保留 `false`。

```sql
SELECT id, job_type, status, attempts, locked_by, locked_until
FROM storage_jobs
WHERE status IN (0, 1, 2)
ORDER BY id;

SELECT job_type, status, count(*)
FROM storage_jobs
GROUP BY job_type, status
ORDER BY job_type, status;
```

#### 4.5.2 为新任务启用 S3 staging

`DISK_UPLOAD_STAGING_BACKEND` 是启动期新任务 backend 选择器，不是停止上传的回滚开关，也不是对存量任务的动态迁移指令。
标准 `config.json` 继续默认 `local` 以保护过渡发布；分布式 Compose 将该值从环境显式
渲染，最终拓扑默认 `s3`。只有 API 在初始化新上传时使用该默认值；创建事务必须先将
`staging_backend` 和 `{s3.staging_prefix}/{upload_id}` 精确写入 `upload_tasks`，后续 API/Worker
始终读取行内描述符。

启用前必须确认：所有不理解 S3 任务的旧实例已退出；expand/transition 和 Worker 观察门已通过；
final S3、bucket 权限、lifecycle 和 staging/final 前缀已验收；当前发布仍能处理已固化的
local 任务。旧 local 任务可在本阶段继续排空，但在其归零前不得删除亲和路由或原卷。

在目标环境持久修改 `.env.distributed` 中的值，先检查 Compose 渲染结果，再重建当前版本
API；一次性 shell 覆盖只可用于预览，不能代替受控的部署配置。

```bash
# .env.distributed
DISK_UPLOAD_STAGING_BACKEND=s3

docker compose --env-file .env.distributed -f docker-compose.distributed.yml config \
  | grep 'DISK_UPLOAD_STAGING_BACKEND: s3'
docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  up -d --no-deps --force-recreate api-a api-b
```

重建后先创建一个非秒传探针上传，在接受首个分片前保存其 `upload_id`，并执行：

```sql
SELECT id, staging_backend, staging_prefix, status, created_at
FROM upload_tasks
WHERE id = '<probe-upload-id>';
```

结果必须为 `staging_backend='s3'`，且 `staging_prefix` 精确等于当前配置前缀加
`/<probe-upload-id>`。随后完成分片、完成上传和 staging cleanup，确认该任务的分片/
assembled 对象未出现在任一 API 本地暂存目录。开关前已存在的 local/S3 任务行必须逐行
对比 backend/prefix 不变。

或存量任务描述符发生变化，立即停止扩大并把新任务开关恢复为 `local` 后重建 API。
该回退只影响之后创建的任务；已创建 S3 任务仍必须由兼容当前版本完成或显式取消，
禁止回退到不理解新 schema/状态的旧应用。

##### 回滚时关闭新任务创建

当停止条件要求阻断新增 S3 staging 状态时，不得把 `DISK_UPLOAD_STAGING_BACKEND` 改成 `local` 作为
替代。应保持兼容版本及其 S3 配置，把所有仍承接 upload init 的 API 配置为：

```bash
DISK_UPLOAD_STAGING_BACKEND=s3
DISK_UPLOAD_TASK_CREATION_ENABLED=false

docker compose --env-file .env.distributed -f docker-compose.distributed.yml config \
  | grep -E 'DISK_UPLOAD_(STAGING_BACKEND: s3|TASK_CREATION_ENABLED: false)'
docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  up -d --no-deps --force-recreate api-a api-b
```

这是启动期开关，必须替换全部兼容 API，不能依赖热加载。替换后用一个从未出现过的 hash 发起合法非秒传
init，必须得到 `503 + 50012`；请求前后的以下查询必须证明任务数和预留配额均未变化：

```sql
SELECT COUNT(*) AS upload_task_count FROM upload_tasks;
SELECT id, storage_used, storage_reserved FROM users WHERE id = <probe-user-id>;
```

随后对一个已存在 S3 任务重复 init，必须返回原 `upload_id`；再经兼容 API 完成一个既有任务，并验证
backend/prefix、任务状态、配额和 cleanup。秒传不创建任务，开关关闭时仍可按既有逻辑创建文件引用并计入
逻辑配额。任一新任务被创建、拒绝请求改变 reserved、resume 生成新 ID、既有描述符改变或生命周期接口失败，
都停止回滚并保留当前兼容池。

旧二进制不包含该配置，未知环境变量不会使它拒绝 init；因此不得仅把
`DISK_UPLOAD_TASK_CREATION_ENABLED=false` 注入旧 Pod 就认为门禁生效。只要数据库中仍存在
`staging_backend='s3'`、`status=4 (Finalizing)` 或任何旧版本不理解的状态/字段，upload init、chunk、
complete、cancel 以及相应 Worker 认领都必须与旧版本隔离。禁止批量把 S3 描述符改成 local，禁止让旧版本
“试读”这些任务。兼容任务全部终态或按下一节的冻结流程处理并完成数据校验前，不得移除最后一个兼容 handler。

`503/50013`、`Retry-After: 30` 和 `Cache-Control: no-store`。门禁直连检查每个声明的兼容 API，
必须看到唯一 `instance_id`、`role=api`、`upload_task_creation_enabled=false` 和
`business_requests_inflight=0`；通过入口发出的探针必须命中网关冻结响应，不能是应用的

1. `--mode drain`：`InProgress=0` 且 `Finalizing=0`，可记录为已排空；入口仍保持冻结，这不自动准入整体旧版本。
2. `--mode freeze`：允许上述活动行保留原状，证据标记 `compatible_handlers_required=true` 和 `old_release_upload_route_allowed=false`。自然过期的 `Finalizing` 租约不立即改写；恢复后仍由兼容 complete CAS 接管。

`contract_migration_allowed=false`；通过上传门禁不能授权执行 migration rollback 或 contract DDL。

不得将 `Finalizing` 改回 `InProgress`、清空 owner/租约、把 S3 描述符改成 local，或以
`Failed` 伪造排空。门禁失败、证据缺失或活动描述符摘要在回滚窗口内变化，都必须停止引入旧版本。

##### 封死生产 local 创建路径

100% S3 新建流量稳定后，先停止发布变更，在同一只读事务中确认 local 非终态任务和未成功的

```sql
FROM upload_tasks
WHERE staging_backend = 'local' AND status IN (0, 4);

FROM storage_jobs
WHERE job_type = 'staging_cleanup'
  AND payload->>'backend' = 'local'

```

#### 4.5.4 容量起步配置与扩容边界

仓库分布式样例固定以下保守起步值。它们来自 2026-07-20 的 API 扩展、文件负载、S3
组装、故障施压和 Worker 积压基线；是部署初值，不是未经生产依赖验证的容量上限。

| 资源 | 每实例建议值 | 适用范围与边界 |
|------|-------------:|----------------|
| API 副本 | 2 | 高可用最小建议；先横向扩容，超过本机已测 4 API 矩阵前重新压测业务路径 |
| Worker 副本 | 2 | 高可用常态；积压恢复可临时扩到已测的 4 个，超过 4 个必须重新压测 |
| Drogon HTTP 线程 | 4 | `app.threads_num`，所有应用进程固定；不得使用按宿主机核数自动展开的 `0` |
| 认证 CPU 线程 | 4 | `auth_cpu_pool_threads`，只由 API 创建；不得按每个 API 重复使用全部宿主机逻辑 CPU |
| PostgreSQL 连接 | 8 | 每个 API/Worker 的 `connection_number` |
| Redis 连接 | 4 | 每个 API/Worker 的 `number_of_connections` |
| S3 HTTP / I/O 线程 | 16 / 4 | 每进程；`io_threads <= max_connections` |
| 上传组装并发 | 2 | 每 API 的 `assembly_max_concurrent`；真实 MinIO/云 S3 上调前重测吞吐、内存和临时对象增长 |
| Worker 并发 | 1 | `worker_concurrency=1`；`worker_claim_batch_size=20` 的当前有效认领量仍为 1 |
| local 文件 I/O 线程 | 4 | 仅 local 后端；S3 分布式配置不创建该线程池 |

令 `A`、`W` 分别为 API 和 Worker 副本数。默认 PostgreSQL 预算必须满足
`8 * (A + W) + 8 <= max_connections`，末尾 8 条作为一个当前应用进程的操作预留，可用于
滚动替换，或在没有替换进程占用时用于迁移、诊断和对账；这些操作不得重复占用同一预留。Compose 的

advisory lock，当前样例不宣称兼容事务池模式。

#### 4.5.5 Worker 回滚停领与租约恢复

Worker 必须逐台退出，不能同时把共享 `DISK_WORKER_CLAIMING_ENABLED` 改成 false 后重建整个池。
该开关是启动期观察模式，不是运行时 drain。处理 `worker-a` 前先确认 `worker-b` 使用兼容制品、理解
现存全部 job type/payload 与存储描述符，并且 readiness 为 200；再向 A 发送 SIGTERM：

```bash
docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  exec -T worker-b curl -fsS http://127.0.0.1:8080/api/health/ready

# 在另一运维会话持续探测 worker-a readiness/metrics 和下方数据库快照。
docker compose --env-file .env.distributed -f docker-compose.distributed.yml \
  stop --timeout 40 worker-a
```

分布式配置的 `worker_drain_timeout_seconds` 为 30 秒；Compose 的
`stop_grace_period=${DISK_STOP_GRACE_PERIOD:-40s}` 必须严格大于它，禁止把 `docker compose kill`、
宿主机 `SIGKILL` 或更短的编排宽限当作正常回滚。信号后 A 应先返回 readiness 503，并报告
`draining=true`、`worker_claiming_enabled=true`、`worker_accepting=false`；指标接受值变为 0，日志不再
出现新的 `Storage job execution started` 或周期 seed cycle。当前 handler 若在 30 秒内完成，正常写回
终态；若超时，A 记录 drain deadline 并退出，停止心跳。

信号前、A 退出后和接管后分别保存同一组只读查询；不得在其间执行 UPDATE：

```sql
SELECT id, job_type, status, attempts, locked_by, locked_until,
       locked_until > NOW() AS lease_live, available_at, updated_at, completed_at
FROM storage_jobs
WHERE status IN (0, 1, 2)
ORDER BY id;

SELECT job_type, status, count(*) AS jobs
FROM storage_jobs
GROUP BY job_type, status
ORDER BY job_type, status;
```

A 超时退出的任务必须继续保持 `Running + locked_by=disk-worker-a + 原 attempts`；B 在
`locked_until > NOW()` 时不得触碰该行。只有 PostgreSQL 时间达到截止后，B 才能通过正常认领把
attempts 增加 1，并在日志记录 `lease_takeover=1`。最终核对任务终态、对象/内容行、finding、去重键和
业务不变量；禁止清空 owner、缩短租约、改回 Pending/Retry 或手工增加 attempts。该任务完成或已有明确
可审计的自然接管状态、B 的 readiness/积压均正常后，才可处理下一台 Worker。

#### 4.5.6 complete 响应丢失恢复

complete 超时、连接重置或发布期间 API 退出，只能判定“响应未知”，不能判定上传失败。保留原
`upload_id`、认证用户、`X-Request-Id` 和命中实例；先通过兼容 API 重放同一业务请求：

```bash
curl --fail-with-body -sS \
  -H "Authorization: Bearer ${ACCESS_TOKEN}" \
  -H "X-Request-Id: ${ORIGINAL_REQUEST_ID}-replay" \
  -H 'Content-Type: application/json' \
  --data "{\"upload_id\":\"${UPLOAD_ID}\"}" \
  https://disk.example.com/api/file/upload/complete
```

返回 200 时记录 `data.file.id`，再用只读诊断确认 `Completed + completed_file_id` 一致、租约为空、
`finalize_attempts` 未增加且关联 staging cleanup 唯一。返回 `409/10004` 表示仍有有效 owner，应等待该
请求完成或租约自然到期后重试；只有 owner 已确认死亡且业务不能等待时，才按 8.3 节执行受审计的 lease
release dry-run/二次确认。其他错误先诊断其持久状态，不得换一个 upload ID 猜测重传。

禁止用 `aws s3 rm`、`mc rm`、控制台删除、生命周期临时规则或直接 SQL 清空 final/staging 对象、
`completed_file_id`、owner、租约或状态。final Blob 是内容寻址的共享候选，人工删除可能破坏已提交文件
或并发引用；staging 只由最终事务中入队的幂等 cleanup 任务处理。cleanup 未收敛时查询关联任务，按
dead-letter 重放流程恢复 Worker，不把对象删除当作 complete 补偿。目标环境证据至少保存首次连接失败、
重放响应、上传诊断、cleanup 终态，以及 final key 的版本 ID/版本数/Delete Marker 只读快照。

目标 MinIO/云 S3 和编排器演练；目标环境必须重复执行并保存自身的连接失败、重放、DB 只读
快照、cleanup 终态和 final 版本证据。

8 物理核参考机上，4 API x 2 HTTP 线程已消耗 7.830 CPU 核；因此默认 2 API x 4 HTTP
线程已经覆盖相同的 8 线程预算。增加线程数前先确认 CPU 配额和 API P99，而不是把
`threads_num` 恢复为自动。Worker 积压基线中 1/2/4 副本分别达到 186.342、259.515、
491.639 jobs/s；只能用 `预计排空秒数 = 当前积压 / 对应实测 jobs/s` 估算相同类型的本机
`staging_cleanup` 负载。真实 S3、不同任务混合或不同对象大小必须重新测量，不能线性外推。

组装基线使用 Moto 且单 API 串行完成，只证明 16 条 S3 连接、4 个 I/O 线程和有界流式
内存在当前代码路径可用；它不证明真实 MinIO/云 S3 的吞吐。生产上线前应在目标 endpoint
复跑 S3 环境门控和组装容量测试，并根据连接拒绝、请求延迟、临时对象增长与队列深度决定
是否保持或降低上述值。

Nginx upstream 不配置 cookie、`ip_hash` 或其他粘性策略；它传递 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto` 和 `X-Request-Id`，关闭请求缓冲以支持分片流式转发，并且不启用 `proxy_next_upstream non_idempotent`，因此不会自动重放已发送的 POST/PUT/PATCH 请求。

验收时必须证明：相邻分片可被不同 API 接收；完成请求可由未接收任何分片的 API 处理；一个 API 或 Worker 被强制退出后任务可通过租约接管恢复；负载均衡配置不含 sticky/cookie/ip-hash。具体命令和断言由 `docs/design/04-系统测试计划.md` 管理。

## 5. 服务管理

### 5.1 Systemd 服务配置

仓库的 `deploy/systemd/disk@.service` 是角色化安装模板。`%i` 只选择实例环境文件，不作为租约
owner。角色与监听地址来自实例文件，未设置的 `DISK_INSTANCE_ID` 由进程每次启动生成；
不得从 unit 名称派生稳定 owner。模板通过 `DISK_CONFIG_FILE` 选择配置，
`ExecStart` 不传入后端不会解析的 `-c` 参数。

```bash
sudo install -o root -g root -m 644 deploy/systemd/disk@.service \
  /etc/systemd/system/disk@.service

sudo install -o root -g disk -m 640 /dev/stdin /etc/disk/instances/api-a.env <<'EOF'
DISK_PROCESS_ROLE=api
DISK_LISTEN_ADDRESS=0.0.0.0
DISK_LISTEN_PORT=8080
EOF

sudo install -o root -g disk -m 640 /dev/stdin /etc/disk/instances/worker-a.env <<'EOF'
DISK_PROCESS_ROLE=worker
DISK_LISTEN_ADDRESS=127.0.0.1
DISK_LISTEN_PORT=8081
DISK_WORKER_CLAIMING_ENABLED=true
EOF
```

同机增加副本时必须使用新的实例文件和空闲监听端口。当前示例由进程在每次启动时生成
全局唯一的 `instance_id`，并在日志、readiness 和 `disk_process_info` 指标中暴露以供诊断。Worker 监听端口
只供内网探针与 Prometheus，不加入业务入口。模板的
`TimeoutStopSec=40s` 大于当前 30 秒 drain，`Restart=on-failure` 不会把人工停止当作故障重启；
`ProtectSystem=strict`、`ProtectHome=true`、`NoNewPrivileges=true` 与 `ReadWritePaths` 将写权限
限制在 `/var/lib/disk` 和 `/var/log/disk`。修改 unit、公共环境或实例环境后必须重启对应实例，
应用不支持 HUP 配置热加载。

### 5.2 服务操作

```bash
# 重新加载 systemd 配置
sudo systemctl daemon-reload

# 首次启用一个 API 和一个 Worker
sudo systemctl enable --now disk@api-a disk@worker-a

# 查看角色化服务状态与日志
sudo systemctl status disk@api-a disk@worker-a
sudo journalctl -u disk@api-a -u disk@worker-a -f

# 单实例滚动重启；先确认同角色其他副本 ready
sudo systemctl restart disk@worker-a
sudo systemctl restart disk@api-a

# 停止前先从入口/认领集合摘除并观察 readiness 失败
sudo systemctl stop disk@api-a
sudo systemctl stop disk@worker-a
```

不得同时重启全部 API 或全部 Worker。API 必须先从负载均衡池摘除并确认无新业务流量；Worker
收到 SIGTERM 后停止认领并排空，超时任务由其他 Worker 在 PostgreSQL 租约到期后接管。

### 5.3 Windows 服务配置

使用 NSSM（Non-Sucking Service Manager）：

```powershell
# 下载 NSSM
# https://nssm.cc/download

# API 服务；后端不接受 -c，配置路径必须通过环境变量注入
nssm install DiskApi "C:\disk\bin\disk.exe"
nssm set DiskApi AppDirectory "C:\disk"
nssm set DiskApi AppEnvironmentExtra "DISK_CONFIG_FILE=C:\ProgramData\Disk\config.distributed.json" "DISK_PROCESS_ROLE=api" "DISK_LISTEN_ADDRESS=0.0.0.0" "DISK_LISTEN_PORT=8080"
nssm set DiskApi Start SERVICE_AUTO_START

# Worker 使用独立服务、每次启动的新 owner 和仅内网可达的端口
nssm install DiskWorker "C:\disk\bin\disk.exe"
nssm set DiskWorker AppDirectory "C:\disk"
nssm set DiskWorker AppEnvironmentExtra "DISK_CONFIG_FILE=C:\ProgramData\Disk\config.distributed.json" "DISK_PROCESS_ROLE=worker" "DISK_LISTEN_ADDRESS=127.0.0.1" "DISK_LISTEN_PORT=8081" "DISK_WORKER_CLAIMING_ENABLED=true"
nssm set DiskWorker Start SERVICE_AUTO_START

nssm start DiskWorker
nssm start DiskApi
```

两个 Windows 服务都必须使用专用低权限账号，并通过服务管理器或 Secret 注入公共数据库、Redis、JWT
与 S3 环境变量。显式 `DISK_CONFIG_FILE` 消除了对 `%USERPROFILE%` 和服务工作目录的依赖。NSSM
示例同样不设置 `DISK_INSTANCE_ID`，由每次启动的进程生成新 owner；若使用外部包装器注入，包装器
必须在每次服务启动时生成新的合法值。

### 5.4 API 与 Worker 角色

生产环境分别运行 API 与 Worker。同一制品通过 `DISK_PROCESS_ROLE`
（优先）或 `custom_config.disk.process_role` 选择角色：

| 角色 | 启动 HTTP 路由 | 认领 `storage_jobs` | 运行集群级定时扫描 | 用途 |
|------|---------------|--------------------|----------------------|------|
| `api` | 是 | 否 | 否 | 无状态请求处理，可水平扩容 |
| `worker` | 仅探针/指标 | 是 | 是 | 持久存储任务、清理和对账 |
| `all` | 是 | 是 | 是 | 单机开发和兼容部署，不用于多副本生产 |

`worker` 进程仍启动 HTTP 监听以提供内部探针和指标，但 pre-routing 角色门禁只放行
`/api/health`、`/api/health/live`、`/api/health/ready` 和 `/metrics`；其监听地址必须只在集群内网可达，
且不得被业务 Service/Ingress 选中。

API 收到终止信号后先从 readiness 摘除并由入口门禁拒绝新业务请求；Worker 先停止认领新任务，再在 `worker_drain_timeout_seconds` 内等待在途任务。超时后进程退出并停止续租，未完成任务在租约到期后由其他 Worker 接管。每个副本的 `instance_id` 必须唯一并保持到进程退出，滚动重启产生新 ID。

Worker 启动后立即播种当前周期任务，之后每分钟重试。`expire_uploads` 和
`expire_trash` 的 `scan_id` 为 UTC 小时（`YYYYMMDDTHHZ`）；`storage_reconcile`
的四个 scope 共享 UTC 日 `scan_id`（`YYYYMMDD`）。多个 Worker 的播种请求可重复，
`storage_jobs.dedupe_key` 唯一约束保证每个窗口只有一组逻辑扫描；不使用任意单机时区。

## 6. HTTPS 配置

### 6.1 获取 SSL 证书

#### 使用 Let's Encrypt（推荐）

```bash
# 安装 certbot
sudo apt install -y certbot

# 获取证书（需要域名解析到服务器）
sudo certbot certonly --standalone -d your-domain.com

# 证书位置
# /etc/letsencrypt/live/your-domain.com/fullchain.pem
# /etc/letsencrypt/live/your-domain.com/privkey.pem

# 配置自动续期
sudo systemctl enable certbot.timer
```

#### 自签名证书（测试用）

```bash
# 生成私钥
openssl genrsa -out disk.key 2048

# 生成证书签名请求
openssl req -new -key disk.key -out disk.csr

# 生成自签名证书
openssl x509 -req -days 365 -in disk.csr -signkey disk.key -out disk.crt

# 移动到指定位置
sudo mv disk.crt /etc/ssl/certs/
sudo mv disk.key /etc/ssl/private/
sudo chmod 600 /etc/ssl/private/disk.key
```

### 6.2 TLS 终止边界

生产分布式入口采用单一 TLS 终止点：证书只安装在 Nginx，Nginx 对外监听 `443`，API 继续使用 `deploy/config.distributed.json` 的 HTTP `8080`。API 端口必须位于容器网络或服务器私网，并只允许负载均衡节点访问；不得把 `8080` 暴露到公网，也不得再给 Drogon 增加 `443` 监听器。

Let's Encrypt 的续期方式必须与实际 challenge 插件匹配。启用 `certbot.timer` 后还要在 Nginx 已运行的状态下执行 `sudo certbot renew --dry-run`；若仍使用会独占 `80` 端口的 standalone 插件，必须先迁移到 webroot、Nginx 或 DNS challenge，不能把定时器“已启用”当作续期已验证。证书、私钥路径只写入第 7 节的 Nginx 站点配置。

## 7. 反向代理配置

### 7.1 Nginx 配置

安装 Nginx：

```bash
sudo apt install -y nginx
```

仓库将负载均衡和代理行为拆成受评审片段：

- `deploy/nginx/includes/upstream.inc`：声明 `least_conn` upstream，并加载当前 API 池；
- `deploy/nginx/includes/proxy-server.inc`：统一请求头、流式转发、超时、重试和公网 `/metrics` 拒绝策略；
- `deploy/nginx/upstreams/production.example.inc`：两台私网 API 的生产 upstream 示例；
- `deploy/nginx/disk-tls.conf.example`：HTTP 到 HTTPS 的 `308` 重定向和 TLS 站点；
- `deploy/nginx/disk.conf`：本地 Compose 使用的明文入口，同样加载上述两份共享策略。

安装生产配置：

```bash
sudo install -d -o root -g root -m 755 /etc/nginx/disk
sudo install -o root -g root -m 644 deploy/nginx/includes/upstream.inc \
  /etc/nginx/disk/upstream.inc
sudo install -o root -g root -m 644 deploy/nginx/includes/proxy-server.inc \
  /etc/nginx/disk/proxy-server.inc
sudo install -o root -g root -m 644 deploy/nginx/upstreams/production.example.inc \
  /etc/nginx/conf.d/disk-api-upstreams.inc
sudo install -o root -g root -m 644 deploy/nginx/upload-mode/open.inc \
  /etc/nginx/conf.d/disk-upload-mode.inc
sudo install -o root -g root -m 644 deploy/nginx/disk-tls.conf.example \
  /etc/nginx/sites-available/disk
```

用 `sudoedit` 修改 `/etc/nginx/conf.d/disk-api-upstreams.inc` 中的两台 API 私网地址，并修改 `/etc/nginx/sites-available/disk` 中的 `server_name`、证书和私钥路径。API 池不得使用公网地址；成员片段保持受评审的 `max_fails=2`、`fail_timeout=5s`，共享 upstream 片段统一管理 `least_conn` 和 keepalive 连接池。

示例 TLS 站点的关键结构如下，完整内容以仓库文件为准，不要在运维文档中维护第二份代理参数：

```nginx
include /etc/nginx/disk/upstream.inc;

server {
    listen 80;
    server_name disk.example.com;
    return 308 https://$server_name$request_uri;
}

server {
    listen 443 ssl http2;
    server_name disk.example.com;
    ssl_certificate /etc/letsencrypt/live/disk.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/disk.example.com/privkey.pem;
    include /etc/nginx/disk/proxy-server.inc;
}
```

共享代理策略将 `client_max_body_size` 固定为 `20m`，对应当前 `5 MiB` 分片并保留余量；若修改 `chunk_size`，必须同步调整并重新执行上传门禁。请求和响应缓冲均关闭，下载直接流式转发，不再为下载路径维护一份缺少认证转发头的特殊 `location`。连接超时为 3 秒，上传/下载读写超时为 330 秒。

upstream 不配置 cookie、`ip_hash` 或其他粘性策略。`proxy_next_upstream` 未包含 `non_idempotent`，配合关闭请求缓冲，Nginx 不会在已开始发送请求体后把 POST/PUT/PATCH 自动重放到另一台 API；complete 响应未知时按 4.5.6 节用原 `upload_id` 恢复。

启用配置：

```bash
sudo ln -sfn /etc/nginx/sites-available/disk /etc/nginx/sites-enabled/disk
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t` 失败时禁止 reload；保持当前已加载配置作为恢复点。上线后从入口验证 HTTP `308`、HTTPS readiness、`X-Disk-Instance-Id` 随机路由和 `/metrics` 返回 404，并从每台 API 的直接私网 readiness 确认实例可用。仓库静态合同不替代目标环境中的真实 Nginx 语法检查、证书链检查和双 API 随机路由门禁。

## 8. 监控与日志

### 8.1 日志管理

#### 日志轮转配置

创建 `/etc/logrotate.d/disk`：

```
/var/log/disk/*.log {
    daily
    missingok
    rotate 30
    compress
    delaycompress
    notifempty
    copytruncate
    create 0640 disk disk
}
```

后端没有 HUP 日志重开或配置热加载合同，因此 logrotate 不得调用 `systemctl reload`。优先使用
Drogon 配置中的内建大小/数量轮转；若必须由系统 logrotate 接管，则使用上面的
`copytruncate`，并避免与应用内建轮转同时管理同一文件。

#### 日志级别配置

在 `config.json` 中配置日志级别：

```json
{
  "app": {
    "log": {
      "log_path": "/var/log/disk/",
      "log_level": "INFO",
      "log_max_size": 104857600,
      "log_max_num": 30
    }
  }
}
```

生产 API 和 Worker 的常态日志级别必须保持 `INFO` 或更高。上传分片采用确定性的结果分层，而不是随机抽样：

| 信号 | 常态保留比例 | 规则 |
|------|--------------|------|
| 成功分片的接收、参数和结果明细，以及 `[upload_chunk] outcome=success` 摘要 | `0%` | 固定为 `DEBUG`，生产 `INFO` 不落盘 |
| `[upload_chunk] outcome=failure` 摘要及对应告警上下文 | `100%` | 固定为 `INFO`/`WARN`/`ERROR`，禁止概率采样 |
| 分片请求数、字节数和延迟指标 | `100%` | 由 `/metrics` 无采样累计，容量与错误率告警不得依赖成功日志 |
| 操作审计记录 | `100%` | 不属于高频诊断日志，禁止用本节策略删除或抽样 |

不得把成功分片的 `Received`、参数校验或成功摘要提升到 `INFO`，也不得通过逐分片成功日志计算吞吐；使用 `disk_upload_chunks_total`、`disk_upload_chunk_bytes_total` 和 HTTP 延迟指标。需要排障时只能在从入口摘除的单个 API 实例上临时启用 `DEBUG`，预先限定最长 15 分钟和日志空间预算，结束后恢复 `INFO` 并确认轮转正常。调试日志仍不得包含请求正文、JWT、Share Token 或 S3 凭据。

### 8.2 系统监控

#### 基础监控脚本

创建 `/opt/disk/scripts/monitor.sh`：

```bash
#!/bin/bash

set -euo pipefail

API_UNIT="${API_UNIT:-disk@api-a}"
WORKER_UNIT="${WORKER_UNIT:-disk@worker-a}"
API_URL="${API_URL:-http://127.0.0.1:8080}"
WORKER_URL="${WORKER_URL:-http://127.0.0.1:8081}"

# 检查服务状态
check_service() {
    systemctl is-active --quiet "$API_UNIT"
    systemctl is-active --quiet "$WORKER_UNIT"
    echo "Services: API and Worker running"
}

# 检查角色化 readiness；响应必须分别报告 api/worker
check_readiness() {
    test "$(curl -fsS "$API_URL/api/health/ready" | jq -r '.data.role')" = "api"
    test "$(curl -fsS "$WORKER_URL/api/health/ready" | jq -r '.data.role')" = "worker"
    echo "Readiness: API and Worker ready"
}

# 本机只监控请求临时目录与日志；S3 容量另由 provider 指标监控
check_disk() {
    usage=$(df /var/lib/disk | tail -1 | awk '{print $5}' | tr -d '%')
    echo "Disk Usage: ${usage}%"
    if [ "$usage" -gt 90 ]; then
        echo "Warning: Disk usage above 90%"
    fi
}

# 检查数据库连接
check_postgresql() {
    if pg_isready -h "$DATABASE_HOST" -p "$DATABASE_PORT" -U "$DATABASE_USER" \
        -d "$DATABASE_NAME" &>/dev/null; then
        echo "PostgreSQL: Connected"
    else
        echo "PostgreSQL: Disconnected"
        exit 1
    fi
}

# 检查 Redis 连接
check_redis() {
    if REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli -h "$REDIS_HOST" -p "$REDIS_PORT" ping \
        | grep -qx PONG; then
        echo "Redis: Connected"
    else
        echo "Redis: Disconnected"
        exit 1
    fi
}

# 由 root 的 systemd timer 执行，以读取 0600 的公共 Secret 文件
source /etc/disk/env
check_service
check_readiness
check_disk
check_postgresql
check_redis
```

#### 健康检查 API

```bash
# liveness：仅证明进程事件循环可响应，不探测外部依赖
curl -fsS http://localhost:8080/api/health/live | jq .

# readiness：按角色验证当前副本是否可以承载新工作
curl -fsS http://localhost:8080/api/health/ready | jq .
```

`api` readiness 必须验证初始化状态、PostgreSQL、Redis PING，以及 staging/final 前缀各最多一项的有界只读 inventory；`worker` readiness 不依赖 Redis，但必须额外验证 `storage_jobs` 可读且任务运行时仍接受认领；`all` 检查两者并集。对象写权限由启动前配置校验和部署验收证明，禁止健康探针持续创建对象。依赖异常时 readiness 返回非 2xx，使负载均衡器停止分配新工作；liveness 不因短暂外部依赖异常失败，避免故障期间形成重启风暴。旧 `/api/health` 保持为 readiness 的精确兼容别名。响应包含 `role`、`instance_id` 和各依赖的有限状态，不回显地址、用户名、bucket、对象 key、凭据或底层异常文本。

部署验收必须分别短暂停止 PostgreSQL、Redis 和 S3/MinIO，且一次只注入一个故障。每次都要记录 API 容器与进程身份，确认故障期间 liveness 为 200、readiness 为 503，恢复后不重启应用即可重新 ready。恢复证明必须包含真实业务访问：PostgreSQL 和 Redis 恢复后读取认证用户资料，S3/MinIO 恢复后下载故障前已存在的最终对象并逐字节校验。测试清理前必须恢复所有依赖；探针和失败响应不得包含密码、令牌、endpoint 或对象 key。

### 8.3 指标、告警与死信操作

`/metrics` 只允许监控网络访问。Compose 的 Nginx 对公网入口精确返回 404，Prometheus 应直接抓取 API/Worker 的 8080 端口。抓取间隔建议 15 秒，超时 5 秒；指标不得经过面向用户的负载均衡器暴露。

项目直接实现 Prometheus text exposition，不需要也不得在同一路径额外启用 Drogon Prometheus
插件。请求量和错误率使用 `disk_http_requests_total`，请求延迟使用
`disk_http_request_duration_seconds`；上传吞吐使用 `rate(disk_upload_chunks_total[5m])` 和
`rate(disk_upload_chunk_bytes_total[5m])`。`disk_upload_tasks_active` 是数据库集群级快照，多个抓取
目标之间使用 `max(disk_upload_tasks_active)`；分片 counter 按实例求和。完成阶段 P99 示例：

```promql
histogram_quantile(
  0.99,
  sum by (stage, le) (rate(disk_upload_complete_stage_duration_seconds_bucket[10m]))
)
```

完成阶段标签固定为 `claim_lease`、`load_metadata`、`assemble`、`dedup_lookup`、`promote` 和
`commit`。命中内容去重时没有 `promote` 样本；阶段开始后失败仍计时，可结合
`disk_http_requests_total{operation="upload_complete",status_class=~"4xx|5xx"}` 判断影响。

依赖调用使用 `disk_dependency_calls_total{dependency,outcome}` 和
`disk_dependency_call_duration_seconds{dependency}`。`dependency` 固定为 `postgresql/redis/s3`，
错误结果固定归入 `timeout/connection/conflict/not_found/retryable/permanent/protocol/other`，成功归入
`success`；不得加入 SQL、key、bucket、endpoint 或异常正文标签。连接容量面板同时展示
`disk_dependency_pool_capacity`、`disk_dependency_pool_demand` 和
`disk_dependency_pool_utilization_ratio`。其中 demand 是应用观察到的在途调用加 PostgreSQL
事务租约，ratio 按配置容量封顶计算，只用于判断实例容量压力，不代表 Drogon/AWS SDK 未公开的
精确 busy 连接数。`disk_thread_queue_depth{queue}` 是尚未开始执行的任务数，必须与
`disk_thread_queue_workers{queue}` 一起观察；`queue` 只允许
`local_file/local_assembly/local_blob/s3`。

依赖 P99 示例：

```promql
histogram_quantile(
  0.99,
  sum by (dependency, le) (rate(disk_dependency_call_duration_seconds_bucket[10m]))
)
```

最低告警规则：

仓库可直接加载 `deploy/prometheus/disk-alerts.yml`；其中的 `disk-api`/`disk-worker`
job 名是监控系统的稳定合同，实例 ID 只作为 target 标签，不写入规则表达式。
readiness 探针周期必须不超过 30 秒，使每个 1 分钟告警观测窗口至少包含一次请求。API
错误率使用真实 5xx/全部业务请求比例，并以 5 分钟至少 20 次请求作为样本门槛；无流量或低于门槛时不告警。

| 告警 | 建议条件 | 处置入口 |
|---|---|---|
| 进程可用性 | API/Worker `up == 0` 持续 2 分钟 | 抓取目标、进程和编排平台事件 |
| readiness | 每个 1 分钟窗口均有 health 5xx，持续 2 分钟 | 健康响应组件、对应 `instance` 的依赖日志 |
| API 错误率 | 5 分钟业务请求不少于 20 且 5xx 真实比例 > 1%，持续 5 分钟 | 请求日志的 `request_id/instance_id` 与 `operation` |
| API 延迟 | 10 分钟 P99 > 1 秒，持续 10 分钟 | `operation` 低基数标签和依赖日志 |
| 任务积压 | 最老 Pending/Retry 年龄 > 300 秒，持续 5 分钟 | `GET /api/admin/storage-jobs` |
| 租约过期 | Running 任务的过期租约数 > 0，持续 1 分钟 | Worker 实例日志、任务详情与底层依赖延迟 |
| 死信 | dead-letter 数量 > 0 持续 1 分钟 | 任务详情、修复依赖、dry-run 后重放 |
| 反复接管 | 10 分钟租约接管增量 > 3 | Worker 实例日志、租约时长和依赖延迟 |
| S3 临时错误 | 5 分钟 `timeout/connection/retryable` 总数 >= 5，持续 2 分钟 | S3 端点健康、网络、限流与 Worker 重试 |
| S3 永久错误 | 5 分钟 `permanent/protocol/other` 总数 > 0，持续 1 分钟 | 凭据/权限、bucket 配置、请求协议与对象存储日志 |
| 对账差异 | 任一固定 `finding_type` 的未解决 finding 数量 > 0 | 对账 finding 与关联任务；未知类型从 `unknown` 标签排查版本兼容性 |
| 指标快照失败 | `disk_metrics_snapshot_success == 0` 持续 2 个抓取周期 | PostgreSQL 连通性和查询超时 |

S3 的 `not_found` 和 `conflict` 用于 HEAD、幂等删除和条件写竞争等正常控制流，不纳入上述两类 S3 错误告警。

告警发布前必须同时通过两层验收：`uv run test/integration/test_alert_fault_injection.py`
向真实 Disk 进程注入任务与受控 S3 故障，验证应用产出超阈值指标；在
`deploy/prometheus/` 目录执行 `promtool test rules disk-alerts.test.yml` 验证 PromQL、边界值和
`for` 持续时间。发布环境必须提供 `promtool`；CTest 在未安装时将该项明确标记为环境跳过，不得将跳过视为发布通过。

死信处理固定流程：

1. 使用列表接口按 `dead_letter` 和 `job_type` 定位任务，再用详情接口核对聚合 ID、payload、尝试次数和最后错误；禁止直接更新数据库。
2. 修复底层依赖或确认永久输入问题已经消除。
3. 先调用重放接口的默认 dry-run，确认 `eligible=true`。
4. 使用精确路径 ID、相同 `confirm_job_id`、`dry_run=false` 和非空原因执行一次重放。
5. 从任务列表确认状态进入 Pending/Running/Succeeded，并使用任务详情中的 `dedupe_key` 调用 `GET /api/admin/logs?action=admin.storage_job.replay&target_type=storage_job&target_name=<URL 编码后的 dedupe_key>`，再核对精确 `target_id`、操作者、原状态和原因；不得直接查询或修改数据库。

重放不改变 `dedupe_key`，也不跳过 Worker 的 payload 校验、Blob 引用复核或租约门禁。冲突、已被其他管理员重放或不再是 DeadLetter 均不得强制覆盖。本组接口不提供任意 SQL、任意 payload 或直接对象删除能力。

上传故障的只读诊断流程：

1. 从失败请求保留业务资源 ID（完成上传请求中的 `upload_id`）以及响应的 `X-Request-Id`、`X-Disk-Instance-Id`。网关传入的 `X-Request-Id` 必须为 1-128 个 `[A-Za-z0-9._:-]` 字符；应用会保留合法值，缺失或非法时生成新的 UUID 并在响应中返回。
2. 以 `request_id=<响应值>` 精确检索应用日志，确认同一条完成日志中的 `instance_id` 与响应一致、`operation=upload_complete` 且 `status` 为实际失败状态。不得用模糊文件名或对象 key 搜索代替请求关联。
3. 使用 `GET /api/admin/uploads/{upload_id}/diagnostics?chunk_page=1&chunk_page_size=20` 读取 PostgreSQL 任务状态、当前租约、分片描述符和对象 HEAD。
4. 对照 `state_version`、`lease.expired`、`finalize_attempts`、`last_error_code` 与分片 `object_head.status/matches_record`；分片超过一页时逐页查询，不一次 HEAD 全部大上传。
5. 从 `related_jobs.items` 进入现有任务详情；只有确认底层依赖已恢复后，才按上述 dry-run 流程重放 dead-letter。
6. 诊断端点不改写上传、租约、分片、对象或任务；需要解除租约/重建任务时使用独立的受审计命令，禁止直接更新数据库。

示例：

```bash
curl -fsS \
  -H "Authorization: Bearer ${ADMIN_ACCESS_TOKEN}" \
  "http://localhost:8080/api/admin/uploads/${UPLOAD_ID}/diagnostics?chunk_page=1&chunk_page_size=20" \
  | jq '{task: .data.task, chunks: .data.chunks, jobs: .data.related_jobs}'
```

受审计恢复流程：

1. owner 对应实例已经退出且不应等待原租约自然到期时，先对 `/api/admin/uploads/${UPLOAD_ID}/lease/release` 执行 dry-run，记录诊断返回的 owner/version；实际请求同时确认 upload ID、owner、版本和原因。成功后确认版本递增、数据库租约已过期，再由客户端重试 complete 接管。该命令不会回退状态或直接完成上传。
2. 终态上传仍残留 staging 时，先诊断关联任务。清理任务缺失或已 Succeeded 才调用 `/api/admin/uploads/${UPLOAD_ID}/cleanup/rebuild`；活跃任务等待 Worker，DeadLetter 修复依赖后使用任务 replay。接口只从上传行重建精确 payload，不接受人工前缀。
3. 事故后对账使用新的、可追踪的 scan ID，例如 `ops-20260720-staging-01`，分别对需要的 scope 调用 `/api/admin/storage-reconciliation/${SCAN_ID}/enqueue`。每次先 dry-run；同一 ID/scope 已存在时查原任务，不覆盖历史。
4. 对所有实际恢复操作，调用 `/api/admin/logs` 并同时传精确 `action`、`target_type` 和 `target_name`（upload ID 或 scan ID），核对操作者、原因和 CAS 前后信息。例如租约解除使用 `?action=admin.upload.lease_release&target_type=upload&target_name=${UPLOAD_ID}`。审计缺失即视为操作未提交，禁止直接查询数据库或用 SQL 补写状态。

常见恢复闭环不得依赖数据库写权限：先使用诊断 API 定位状态、对象和关联任务；确认底层依赖或缺失对象已经由其权威系统恢复后，执行恢复命令 dry-run；使用返回的精确 ID、owner 和版本二次确认；通过管理日志 API 核对审计；最后让原业务请求重试并再次诊断终态。数据库访问只属于受控测试夹具和数据库维护流程，不属于日常运维步骤。

### 8.4 Kubernetes 参考部署与滚动发布

参考生产部署使用一个 API Deployment、一个 Worker Deployment 和一个一次性 migration Job。Service 只选择 API Pod，且不配置会话亲和；Worker 不进入业务流量 Service。API 的 readiness/liveness 分别指向上述探针，Worker 使用同一端点但按角色判断依赖。

滚动发布顺序固定为：运行并验证 expand migration Job，发布 Worker，再发布 API，最后开启新暂存 backend。`maxUnavailable=0` 只保证 HTTP 容量，不替代 schema 兼容；新旧 API 并存期间，数据库字段和任务格式必须双向兼容。回滚时先在全部兼容 API 设置 `DISK_UPLOAD_TASK_CREATION_ENABLED=false` 并验证 503/50012、零任务/配额副作用和既有任务 resume/complete，再把旧版本与所有 S3/`Finalizing` 生命周期路由隔离；只要新 schema 已承载任务就保留 expand 结构，禁止自动运行破坏性 rollback。

PostgreSQL、Redis 和 S3/MinIO 必须使用具备高可用能力的外部服务或独立集群：PostgreSQL 提供单一可写主端点和自动故障转移，Redis 使用托管服务或 Sentinel 代理稳定写端点，S3 由服务端保证对象冗余。应用不自行选主，也不把数据库、Redis 或对象存储暴露到公网。

Redis Cluster 仍不在第一阶段支持范围内；虽然文件列表已不依赖前缀扫描，上线 Cluster 前仍必须验证 refresh token CAS/Lua、限流原子命令的 hash slot 与 Drogon 客户端 MOVED/ASK 处理。

### 8.5 性能监控

Prometheus 直接抓取项目自有的 `http://<api-or-worker>:8080/metrics`。Grafana 面板使用本节给出的
低基数指标与聚合规则；不得通过动态路径、上传 ID、文件名或对象 key 拆分时间序列。

## 9. 备份与恢复

### 9.1 一致恢复集

一次可用备份必须是一个不可拆分的恢复集，至少包含 PostgreSQL custom-format dump、final Blob 快照和恢复集 manifest。manifest 记录唯一 `recovery_set_id`、UTC 时间、数据库 dump 的 SHA-256、`schema_migrations` 快照、local 根目录或 S3 bucket/prefix，以及对象快照 ID/版本。Redis 不进入 PostgreSQL/final Blob 一致恢复集：缓存、限流和租约状态可按合同重建；但 refresh 当前哈希和 access/share 撤销键属于会话安全状态，必须由 Redis 自身的持久化/复制方案保留，或按 9.5 节执行全会话失效，不能以“缓存可清空”为由直接丢弃。

创建恢复集前先停止新写入，让 Worker 排空已认领任务后停止 API/Worker；在维护窗口结束前不得运行上传完成、回收站过期或 Blob GC。final Blob 虽然按内容寻址且不可变，但 GC 会删除对象，因此数据库与对象快照仍必须在同一停写窗口内完成。分别在凌晨 2 点备份数据库、凌晨 3 点复制文件不是一致恢复点，不得作为生产恢复集。

数据库备份使用 custom format，并让命令失败时立即终止：

```bash
set -euo pipefail
RECOVERY_SET_ID="$(date -u +%Y%m%dT%H%M%SZ)"
BACKUP_DIR="/data/backups/${RECOVERY_SET_ID}"
mkdir -p "${BACKUP_DIR}"

PGPASSWORD="${DATABASE_PASSWORD}" pg_dump \
    --host "${DATABASE_HOST}" --port "${DATABASE_PORT}" \
    --username "${DATABASE_USER}" --dbname "${DATABASE_NAME}" \
    --format custom --no-owner --no-privileges \
    --file "${BACKUP_DIR}/disk.dump"
sha256sum "${BACKUP_DIR}/disk.dump" > "${BACKUP_DIR}/disk.dump.sha256"
```

local 后端在同一停写窗口内对 `storage_base_path` 创建只读文件系统快照；没有快照能力时才使用保留权限、时间和稀疏属性的受控复制。S3/MinIO 使用版本化 bucket 的不可变快照或复制任务，并把对象版本/清单写入 manifest。备份目录不得位于 `storage_base_path` 内，否则 final inventory 会把备份文件识别为孤儿对象。恢复集上传异地存储前应加密，并定期校验 dump 哈希、对象清单和实际可读性。

### 9.2 隔离恢复

恢复必须落到空数据库和不承载业务流量的对象根/prefix。local `file_contents.storage_path` 是权威定位符；若其中保存绝对路径，恢复环境必须挂载到相同路径。S3 恢复必须保留完整对象 key。任何路径改写都属于独立、可恢复的 locator 迁移，不能在 restore 命令中临时替换字符串。

```bash
set -euo pipefail
sha256sum --check "/data/backups/${RECOVERY_SET_ID}/disk.dump.sha256"
PGPASSWORD="${PG_ADMIN_PASSWORD}" createdb \
    --host "${DATABASE_HOST}" --port "${DATABASE_PORT}" \
    --username postgres --owner "${DATABASE_USER}" disk_restore
PGPASSWORD="${DATABASE_PASSWORD}" pg_restore \
    --host "${DATABASE_HOST}" --port "${DATABASE_PORT}" \
    --username "${DATABASE_USER}" --dbname disk_restore \
    --exit-on-error --no-owner --no-privileges \
    "/data/backups/${RECOVERY_SET_ID}/disk.dump"

# local 示例：恢复到与持久 locator 一致、当前不对外服务的挂载点。
rsync -aHAX --numeric-ids \
    "/data/backups/${RECOVERY_SET_ID}/final/" "/data/disk/files/"
```

恢复后先核对 `schema_migrations` 与 manifest，再启动一个指向恢复数据库和恢复对象根的 Worker。API 保持在维护模式；如果通过管理 API 入队，只启动不接入负载均衡的维护 API。为本次恢复生成唯一 `scan_id`，通过 `POST /api/admin/storage-reconciliation/{scan_id}/enqueue` 分别入队 `contents`、`users`、`staging`、`final`，等待四个范围的所有分页任务（含 continuation）全部进入 `succeeded`。不得只观察首个任务。

### 9.3 恢复验收与切流门禁

恢复集只有同时满足下列条件才可切流：

1. 四个扫描范围没有 pending/running/retry/dead-letter 任务，且 `storage_reconciliation_findings` 没有未解决项。
2. 每个 `file_contents.ref_count` 等于 `files` 与 file 类型 `trash` 的结构化引用数；不存在意外零引用内容。
3. 每个用户的 `storage_used` 等于活动文件与回收站条目字节和，`storage_reserved` 等于 `status IN (0, 4)` 上传的 `reserved_bytes` 之和。
4. 每个有引用的 `file_contents.storage_path` 对象存在且大小匹配，final inventory 中不存在数据库未引用对象；活动上传分片引用与 staging inventory 双向一致，provider 可见的未完成 multipart 数量为零。
5. 对代表性文件执行完整下载与哈希校验，并确认 schema 账本以及用户、文件、内容、上传和分片行数与恢复集 manifest 一致。

任一条件失败都必须保持流量关闭，保留原恢复集和隔离现场，修复权威数据后使用新的 `scan_id` 重跑全部四个范围。finding 不得靠直接更新 `resolved_at` 绕过；只能在不变量恢复后由下一轮对账消解。验收结果需保存恢复集 ID、扫描 ID、任务终态、finding 快照、provider multipart inventory 和下载探针证据。生产恢复演练至少每季度执行一次，并验证从空库恢复、全量分页对账、失败阻断与重新验收。

### 9.5 Redis 会话安全状态持久化与灾难处置

`refresh_token:*`、`access_token_blacklist:*` 和 `share_token_blacklist:*` 是带绝对过期时间的会话安全状态。常规维护重启和声明为无数据损失的自动故障切换，必须保留已确认写入的键、值和原过期时间；重启后使用 `PTTL` 抽样时必须为正且小于重启前值。文件列表缓存、版本键和限流窗口不进入这一安全持久化门禁，但丢失限流窗口仍须触发边缘限流和告警策略。

Compose 的单节点 AOF 仅用于本地协议验证，不是生产高可用方案。自管 Redis 至少开启 AOF、受控持久卷和启动加载错误阻断；目标端点还必须记录持久化模式、复制确认语义、最近一次切换的旧/新主身份、切换前后安全键抽样 TTL、应用进程 PID、RTO 和实际 RPO。若提供方只能给出可能丢失已确认写入的非零 RPO，本系统不得在不失效会话的情况下继续服务。

无法证明安全键完整时执行全会话失效：保持 Nginx 认证/分享入口关闭，生成新的生产 JWT Secret，通过 Secret 管理系统更新并滚动重启全部 API，确认不存在仍使用旧 Secret 的 ready 实例；随后从隔离探针验证故障前的 access、refresh、share token 全部被拒绝，再开放入口。不得把旧 Redis 数据与空实例选择性合并，不得重置撤销键 TTL，也不得只清空应用本地缓存。JWT Secret 和任何探针 token 不写入恢复证据。

仓库门禁 `test_redis_session_persistence.py` 启动测试专属、`appendfsync always` 的 Redis/Valkey，写入真实 refresh 状态和 access 撤销后确认 AOF 无待处理 fsync，再 `SIGKILL` Redis。它在同一持久目录重启 Redis，要求两个安全键的 `PTTL` 继续递减；原 API 无需重启即可恢复 readiness，新启动的冷 API 必须从 Redis 拒绝旧 access token，两 API 对持久化 refresh token 并发轮换仍只能有一个赢家。该测试不证明跨节点复制或目标环境 RPO。

## 10. 故障排查

### 10.1 常见问题

#### 服务无法启动

1. **检查日志**
   ```bash
   sudo journalctl -u disk@api-a -u disk@worker-a -n 100
   ```

2. **检查配置文件**
   ```bash
   # 验证 JSON 与实例环境；服务不解析 -c 参数
   jq . /etc/disk/config.distributed.json
   sudo systemctl show disk@api-a -p EnvironmentFiles -p Environment
   ```

3. **检查端口占用**
   ```bash
   sudo netstat -tuln | grep 8080
   ```

4. **检查权限**
   ```bash
   ls -la /opt/disk/ /etc/disk/
   ls -la /var/lib/disk/
   ls -la /var/log/disk/
   ```

#### 数据库连接失败

1. **检查 PostgreSQL 服务**
   ```bash
   sudo systemctl status postgresql
   ```

2. **检查连接**
   ```bash
   psql -U disk_user -h localhost -d disk
   ```

3. **检查用户权限**
   ```sql
   \du disk_user
   ```

#### Redis 连接失败

1. **检查 Redis 服务**
   ```bash
   sudo systemctl status redis
   redis-cli ping
   ```

2. **检查密码配置**
   ```bash
   redis-cli -a your_password ping
   ```

#### 上传失败

1. **检查生产 S3 与共享状态**
   ```bash
   curl -fsS http://127.0.0.1:8080/api/health/ready | jq .data.components
   df -h /var/lib/disk
   ```

2. **仅在 local 开发/隔离迁移配置下检查本地目录**
   ```bash
   ls -la /data/disk/blobs/
   ls -la /data/disk/staging/
   ```

3. **检查上传限制与暂存后端**
   - 逻辑文件大小由 `custom_config.disk.max_file_size` 控制。
   - Drogon/Nginx 的请求体限制只需大于 `custom_config.disk.chunk_size`，不是最大文件大小。
   - 上传限流吞吐约为 `chunk_size * upload_rate_limit_per_minute / 60`；默认 5MiB、240 次/分钟约为 20MiB/s。
   - S3 staging 的分片、assembled 和 final 对象不落 API 本地目录；检查 staging/final readiness、S3 错误指标、上传诊断和相关 `storage_jobs`。
   - 只有 local 兼容路径会同时保留分片和组装文件，原卷至少预留约 2 倍文件大小；跨文件系统复制兜底时可能接近 3 倍。
   - Nginx 的 `client_max_body_size`、`proxy_send_timeout`、`proxy_read_timeout` 需要覆盖单个分片和完成组装耗时。

#### S3 最终 blob 删除失败

1. S3 删除在存储工作线程内最多尝试 3 次，不在 Drogon 事件循环中阻塞等待；每次失败日志都包含 `bucket`、`key`、`attempt`、错误码和错误消息。
2. 三次均失败时，调用方收到最后一次错误并保留可诊断日志；确认 endpoint、凭据、bucket 权限和网络状态后可安全重试清理。
3. 对不存在 key 的删除按成功处理，因此补偿删除、永久删除和维护任务可以重复执行而不会把已删除对象视为故障。

## 11. 安全加固

### 11.1 系统安全

```bash
# 确认 4.3 节创建的专用账户无交互式登录能力
getent passwd disk
sudo usermod --lock --shell /usr/sbin/nologin disk

# 制品和配置由 root 管理，运行账户只能写状态与日志目录
sudo chown -R root:root /opt/disk
sudo chmod -R go-w /opt/disk
sudo chown root:root /etc/disk/env
sudo chmod 600 /etc/disk/env
sudo chown root:disk /etc/disk/config.distributed.json /etc/disk/instances
sudo chmod 640 /etc/disk/config.distributed.json
sudo chmod 750 /etc/disk/instances
sudo find /etc/disk/instances -maxdepth 1 -type f -name '*.env' \
  -exec chown root:disk {} +
sudo find /etc/disk/instances -maxdepth 1 -type f -name '*.env' \
  -exec chmod 640 {} +
sudo chown -R disk:disk /var/lib/disk /var/log/disk
sudo chmod 750 /var/lib/disk /var/log/disk

# 配置防火墙
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
# 以下 CIDR 是示例，必须替换为实际负载均衡和监控子网
sudo ufw allow from 10.0.30.0/24 to any port 8080 proto tcp
sudo ufw allow from 10.0.40.0/24 to any port 8081 proto tcp
sudo ufw enable
```

### 11.2 数据库安全

```bash
# 自管 PostgreSQL 只绑定数据库私网地址，不监听公网接口
# 编辑 /etc/postgresql/16/main/postgresql.conf
listen_addresses = '10.0.20.10'

# 自管 Redis 只绑定数据库私网地址并保持 protected mode
# 编辑 /etc/redis/redis.conf
bind 10.0.20.11
protected-mode yes

# 数据库主机只允许应用私网子网访问
sudo ufw allow from 10.0.10.0/24 to any port 5432 proto tcp
sudo ufw allow from 10.0.10.0/24 to any port 6379 proto tcp
```

托管 PostgreSQL/Redis 应使用服务商的私网稳定入口和安全组实现同等边界；不得把实例端口暴露到公网。

## 12. 升级指南

### 12.1 升级前检查

1. **备份数据**
   ```bash
   /opt/disk/scripts/backup_db.sh
   /opt/disk/scripts/backup_files.sh
   ```

2. **检查变更日志**
   - 阅读新版本的 CHANGELOG
   - 检查数据库迁移脚本

3. **测试环境验证**
   - 在测试环境先验证升级流程

4. **分享限流配置迁移**（升级到独立操作限流版本时）
   - 在待部署配置中删除两个 `share_public_rate_limit_*` 键。
   - 同时加入六个 `share_access_*`、`share_browse_*`、`share_download_*` 键并校验为正整数。
   - 运行 `jq` 和预发布 `test_share_rate_limit.py`，确认三桶边界、429 响应和 Redis fail-open 证据。
   - 旧二进制与新配置、或新二进制与旧配置都不是受支持的长期组合；二进制和配置必须作为同一发布单元切换。

### 12.2 升级步骤

以下命令只适用于已经批准维护停机的小规模部署；分布式生产必须使用 4.5 节的 Worker/API 逐实例
发布和入口摘除流程，禁止同时停止全部 API 或全部 Worker。数据库变更统一由 3.4 节的 manifest 与
`scripts/migrate-db.sh` 执行，不直接运行临时 `migrations/v1.x.x.sql`。

```bash
# 1. 明确维护窗口后停止本机角色实例
sudo systemctl stop disk@api-a disk@worker-a

# 2. 备份当前二进制和对应配置
sudo install -o root -g root -m 755 \
  /opt/disk/bin/disk /opt/disk/bin/disk.bak
sudo cp -a /etc/disk/config.distributed.json \
  /etc/disk/config.distributed.json.bak

# 3. 更新代码
cd /path/to/disk/source
git fetch origin
git checkout v1.x.x  # 切换到新版本

# 4. 重新编译
cmake --build --preset linux-release-clang

# 5. 部署新版本
sudo install -o root -g root -m 755 \
  build/linux-release-clang/src/disk /opt/disk/bin/disk

# 6. 同步与该二进制匹配的配置
sudo install -o root -g disk -m 640 \
  deploy/config.distributed.json /etc/disk/config.distributed.json

# 7. 执行数据库迁移（如需要）；PG* 已由独立迁移任务的 Secret 注入
: "${PGHOST:?missing PGHOST}" "${PGPORT:?missing PGPORT}"
: "${PGDATABASE:?missing PGDATABASE}" "${PGUSER:?missing PGUSER}"
: "${PGPASSWORD:?missing PGPASSWORD}"
sudo --preserve-env=PGHOST,PGPORT,PGDATABASE,PGUSER,PGPASSWORD \
  -u disk /path/to/source/scripts/migrate-db.sh

# 8. 启动服务
sudo systemctl start disk@worker-a disk@api-a

# 9. 分别验证角色与依赖
curl -fsS http://127.0.0.1:8081/api/health/ready | jq -e '.data.role == "worker"'
curl -fsS http://127.0.0.1:8080/api/health/ready | jq -e '.data.role == "api"'
```

### 12.3 回滚步骤

```bash
# 1. 从入口/认领集合摘除后停止本机角色实例
sudo systemctl stop disk@api-a disk@worker-a

# 2. 只恢复明确备份的二进制，不递归删除安装目录
sudo install -o root -g root -m 755 \
  /opt/disk/bin/disk.bak /opt/disk/bin/disk

# 旧版本回滚时同时恢复与旧二进制匹配的配置；旧版本需要两个
# share_public_rate_limit_* 键，新版本需要六个操作专用键
sudo cp -a /etc/disk/config.distributed.json.bak \
  /etc/disk/config.distributed.json

# 3. 普通应用回滚保留 expand schema 与迁移账本，不恢复或覆盖在线数据库
#    只有 9.2/9.3 节的隔离灾难恢复验收完成后，才允许独立切换恢复集。

# 4. 启动服务
sudo systemctl start disk@worker-a disk@api-a
```
