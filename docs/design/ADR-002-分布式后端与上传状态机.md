# ADR-002：分布式后端与上传状态机

## 状态

**已接受**

---

## 背景

当前后端已经把核心元数据放在 PostgreSQL、把令牌与限流状态放在 Redis，并支持将最终 Blob 保存到 S3/MinIO。但这些能力尚不足以证明后端可在无粘性会话的负载均衡后运行多个实例：

1. `S3ObjectStorage` 仍使用 `LocalFileStorage` 保存上传分片和组装文件，同一上传的请求必须命中同一节点。
2. `AssemblyWorkerPool` 的同 `upload_id` 单飞和并发上限只在单进程内生效。
3. 完成上传在持久化认领任务之前执行组装与 Blob 提升，两个实例可以同时产生外部副作用。
4. 上传任务本地缓存的失效不传播到其他实例，终态任务可能被另一实例的陈旧缓存继续接受分片。
5. `ScheduledTasks` 由每个 API 进程注册，副本数会放大周期清理的扫描与执行次数。
6. 访问令牌与分享令牌的撤销负缓存允许其他实例在短窗口内继续接受已撤销令牌。

本次重构的目标不是按领域拆分微服务，而是先把现有模块化单体变成可横向扩容、可接管、可对账的分布式后端。API、Worker、PostgreSQL、Redis 和对象存储之间必须有明确的一致性边界。

---

## 决策

### 1. 保持模块化单体

继续构建一个 C++23/Drogon 后端制品，通过运行角色区分 API 与 Worker：

- `api`：监听公开 HTTP 端口，不运行集群级周期任务。
- `worker`：认领持久任务，不提供公开业务接口。
- `all`：仅用于本地开发和单进程测试。

第一阶段不拆分独立微服务，不引入分布式 SQL，也不改变控制器、DTO、服务和存储层的现有职责边界。只有监控数据证明某一领域需要独立发布、独立容量或独立故障域时，才重新评估服务拆分。

### 2. PostgreSQL 是持久状态的唯一事实来源

上传状态、任务所有权、配额、内容引用和待执行存储任务全部由 PostgreSQL 决定。Redis 不作为上传状态机或持久任务的唯一锁服务。

跨实例互斥使用带版本号和到期时间的条件更新：

```sql
UPDATE upload_tasks
SET status = 4,
    state_version = state_version + 1,
    lease_owner = $1,
    lease_expires_at = NOW() + $2::interval,
    finalize_attempts = finalize_attempts + 1
WHERE id = $3
  AND user_id = $4
  AND (
      status = 0
      OR (status = 4 AND lease_expires_at < NOW())
  )
RETURNING *;
```

实际 SQL 可以为覆盖检查和类型绑定做调整，但必须保持以下语义：

- 只有条件更新成功的实例拥有本轮完成权。
- 所有租约判断使用 PostgreSQL `NOW()`，不使用实例本地时钟决定所有权。
- 续租、提交和放弃操作同时校验 `lease_owner` 与 `state_version`。
- 外部对象存储 I/O 不放在长数据库事务中。

### 3. 上传状态机

保留既有状态数值并新增状态：

| 值 | 状态 | 是否终态 | 说明 |
|---:|---|---|---|
| 0 | `InProgress` | 否 | 接受分片，可取消、可过期、可认领完成 |
| 1 | `Completed` | 是 | 文件、内容引用和配额转换已提交 |
| 2 | `Cancelled` | 是 | 用户取消，reserved quota 已释放 |
| 3 | `Expired` | 是 | 超时回收，reserved quota 已释放 |
| 4 | `Finalizing` | 否 | 某实例持有有期限租约并执行完成流程 |
| 5 | `Failed` | 是 | 超过恢复上限或遇到不可恢复的数据损坏 |

允许的主要迁移如下：

```text
InProgress -> Finalizing -> Completed
     |             |
     |             +-> Finalizing（租约到期后由新 owner 接管）
     +-> Cancelled
     +-> Expired

Finalizing -> Failed（仅不可恢复错误或超过明确重试上限）
```

`Finalizing` 不接受取消和新分片。短暂外部错误保留在 `Finalizing`，由当前 owner 重试或在租约到期后接管；不得为重试先退回 `InProgress`，以免重新开放分片写入。

### 4. S3/MinIO 原生上传暂存

生产多实例部署的上传分片必须写入对象存储，不使用共享 POSIX 文件系统作为最终方案。对象布局为：

```text
staging/{upload_id}/chunks/{chunk_index}-{chunk_md5}.part
staging/{upload_id}/assembled/{state_version}.bin
objects/sha256/{sha256[0:2]}/{sha256}.bin
```

存储接口中的组装结果使用 `{backend, locator, size, md5, sha256}` 描述，不以
`std::filesystem::path` 代表所有后端。`locator` 是不含 endpoint 和凭据的稳定定位符：
local 后端保存规范化文件路径字符串，S3 后端保存对象 key。最终 Blob 提升只能根据
`backend` 解释该定位符，禁止调用方把对象 key 当作本地路径打开。

上传会话描述符使用 `{upload_id, backend, prefix}`，必须由
`upload_tasks.staging_backend/staging_prefix` 恢复，并传入每个分片写入、组装、
丢弃组装物和会话清理操作。存储层不接受脱离描述符的裸 `upload_id`：
local 实现只处理 `backend=local`，S3 组合实现在迁移窗口内对 local 任务调用
local 兼容实现，对 `backend=s3` 任务使用对象存储。配置只决定新任务，
已建任务的路由始终以持久化描述符为准。

S3 客户端边界只暴露存储中立的数据结构，提供 Put、带大小/ETag 的 Head、Range Get、
分页 List、最多 1000 key 的批量 Delete，以及 multipart create/upload-part/copy-part/
complete/abort 原语。part 编号和 ETag 由调用方显式保存并按序完成；失败或租约丢失时
必须可重复调用 abort。AWS SDK 类型和同步调用不得越过 `S3ObjectStorage` 的专用工作线程。

分片 Put 使用 `If-None-Match: *`，不得以“先 HEAD、再无条件覆盖”实现幂等。首次写入返回
对象 ETag；命中既有 key 时必须重新 HEAD，并以有界 Range 流读取计算 MD5，确认大小、内容
和 key 中的内容标识一致后才返回成功。条件冲突、超时或响应丢失不得导致覆盖同 key 的不同
内容；无法证明对象一致时返回错误并交由请求重试或对账处理。

S3 组装目标固定为 `staging/{upload_id}/assembled/{state_version}.bin`。实现按索引逐个 HEAD
并 Range 读取权威分片，流式计算分片 MD5、整文件 MD5/SHA-256，同时通过 multipart upload
写入 assembled 对象；除最后一个 part 外不得小于 5 MiB，内存缓冲保持有界，part 数不得超过
10000。S3 返回 upload ID 后、上传任何 part 前，存储层必须同步登记持久 `multipart_abort` 任务；
每个 part 和 complete 前续租，multipart 未完成的任意退出路径都必须尝试 Abort。Complete 或 Abort
成功后才将任务收敛为成功，Abort 失败立即释放任务供 Worker 重试，assembled 成功后再返回后端
无关描述符。
会话清理只能分页列举严格验证后的 `{staging_prefix}/{upload_id}/`，每批最多删除 1000 个 key；
对象不存在按成功处理，任何返回到该前缀之外的 key 都必须拒绝删除。

具体前缀允许配置，但必须满足：

- `upload_id`、索引和 hash 经过严格格式验证后才能构造 key。
- 分片 key 对已验证内容不可变；重复上传同一分片必须幂等。
- `upload_task_chunks` 保存对象 key、大小、MD5 和 ETag，并继续作为唯一上传进度来源。
- 对象已写但数据库未记录时，该对象属于可识别的 staging 孤儿，由对账任务清理。
- 数据库记录存在但对象缺失或元数据不一致时，完成请求失败并产生一致性告警。

不采用直接把客户端分片映射为最终 multipart parts 的方案。原因是 multipart ETag 不是稳定的整文件 MD5，乱序重试也会扩大 part ETag 与数据库元数据的竞态。第一阶段将分片保存为独立 staging 对象，完成阶段按索引流式读取、计算整文件 MD5/SHA-256，并写入唯一的 assembled staging 对象。

### 5. 完整性校验与最终 Blob 寻址

完成阶段继续由服务端验证：

- 分片覆盖连续且数量正确。
- 每个分片的对象大小、MD5 与数据库记录一致。
- 组装结果总大小与上传任务一致。
- 整文件 MD5 与初始化请求一致。
- 整文件 SHA-256 由服务端计算并写入 `file_contents`。

multipart ETag 不作为 MD5。新写入的最终 Blob 使用 SHA-256 内容寻址：S3 key 固定为
`{object_prefix}/sha256/{sha256[0:2]}/{sha256}.bin`，local 路径固定为
`{storage_base_path}/sha256/{sha256[0:2]}/{sha256}.bin`。SHA-256 必须是 64 位小写十六进制；
任何不满足该格式的提升请求都在访问存储前失败。

数据库 `file_contents.storage_path` 是读取位置的唯一权威。文件所有者下载和分享下载都必须把该字段
放入 Blob 描述符，存储实现按其原值读取、HEAD、Range 和删除，不得从 MD5、SHA-256 或当前配置
重新构造既有对象路径。现有 MD5 路径因此继续按已保存的 `storage_path` 读取，不在请求路径中自动
搬迁；存量对象迁移采用可断点、可校验、可重复执行的独立工具。

SHA-256 目标对象的创建和复用必须幂等。S3 assembled 对象提升时先严格校验 locator 位于当前
`staging_prefix/{upload_id}/assembled/{state_version}.bin` 形态且 HEAD 大小一致，再使用有界 part
数量的 server-side multipart copy 写入 final key，不能依赖有单对象大小上限的单次 copy。任一
copy part 或 complete 失败都必须尝试 Abort，并使用与 assembled 组装相同的持久任务协议；目标已经存在时必须验证大小一致。提升成功不删除
assembled 对象，只有最终数据库事务提交并持久化 cleanup 任务后才能清理 staging 会话。

### 6. 同步完成 API 与幂等结果

第一阶段保持 `POST /api/file/upload/complete` 的同步接口形态，避免要求现有桌面客户端引入异步轮询协议：

- 成功认领的请求执行完成流程并返回现有 `file` 响应。
- 任务已经 `Completed` 时，通过 `completed_file_id` 重建并返回同一响应。
- 其他 owner 持有有效 `Finalizing` 租约时，返回 `409 + 10004 ResourceConflict`，并可附带 `Retry-After`。
- `Cancelled`、`Expired`、`Failed` 返回稳定、已文档化的终态错误。
- 当前 owner 崩溃后，客户端重试可以在租约到期后接管。

未来如完成耗时的监控数据证明同步请求不可接受，再新增版本化的 `202 Accepted + status` 合同；不得静默改变当前接口。

### 7. 完成上传使用可恢复 Saga

完成流程分为短事务和可重试外部步骤：

1. 从 PostgreSQL 校验用户、任务状态和完整分片覆盖。
2. 使用条件更新认领 `Finalizing` 租约。
3. 在事务外读取分片、流式组装、计算 hash 并创建 assembled staging 对象。
4. 幂等确保 SHA-256 final Blob 存在。
5. 在一个短事务中原子完成内容 upsert/ref_count、文件记录、目录计数、reserved-to-used 配额、`Completed + completed_file_id` 和 staging cleanup 任务入队。
6. Worker 异步删除 staging 对象；删除失败不回滚已完成文件。

第 5 步的内容引用必须由 `file_contents(hash_md5, hash_sha256)` 唯一约束和单条
`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 完成。冲突时只在内容大小一致的前提下增加
`ref_count`，并保留已有 `storage_path`；事务外预查询只用于优化，不能决定唯一性。文件记录使用
`files(user_id, folder_id, name)` 唯一约束裁决并发同名写入，无返回行映射为稳定领域冲突。

最终事务失败时，不立即删除可能被其他事务复用的 final Blob。系统记录可识别的孤儿候选，由 Blob 对账/GC 在确认数据库无引用后删除。

### 8. 取消、过期与分片竞态

取消和过期必须在同一个数据库事务中完成状态条件更新、reserved quota 释放、分片元数据处理和 cleanup 任务入队。只有成功从 `InProgress` 迁移到终态的事务可以释放配额。

完成、取消和过期共用 `staging-cleanup:{upload_id}` 去重键。任务 payload 保留该上传会话创建时持久化的 backend/prefix，Worker 不根据当前默认存储配置重建位置。业务事务提交后完全由 Worker 执行幂等会话清理，API 不再以一次最佳努力删除代替持久任务。

分片写入采用两次持久状态检查：对象写入前校验任务与几何信息，写入后使用只对 `InProgress` 生效的条件 SQL 记录分片。若取消或完成在对象写入期间获胜，迟到请求不得改变终态；产生的对象由 staging 对账清理。

进程内上传缓存只能缓存文件大小、分片大小、总分片数等不可变几何信息。它不能替代写入后的数据库状态条件。

### 9. PostgreSQL 持久任务队列

集群级任务使用 PostgreSQL 持久任务表，并通过 `FOR UPDATE SKIP LOCKED` 认领。任务至少覆盖：

- staging 清理；
- multipart abort；
- 零引用 Blob GC；
- 过期上传扫描；
- DB/对象一致性对账。

任务使用唯一去重键，状态为 `Pending/Running/Retry/Succeeded/DeadLetter`，并保存尝试次数、可执行时间、owner、租约截止和最后错误。临时错误使用有上限、带抖动的指数退避；永久错误或超过上限后进入 dead-letter。

认领是数据库原子操作：候选集同时包含到期的 `Pending/Retry` 和租约过期且仍有尝试余量的 `Running`，通过 `FOR UPDATE SKIP LOCKED` 分配给唯一 `instance_id`。所有续租和结果回写都校验当前 owner；过期 owner 恢复后不能覆盖接管者的结果。认领时增加 `attempts`，崩溃留下的最后一次过期租约由下一轮扫描直接收敛到 dead-letter。

Worker 对认领批次使用有界串行执行，即当前每类 handler 和整个 Worker 的并发上限均为 1，后续只能根据指标显式提高。执行前续租一次，执行期间每隔 `lease_duration / 3` 心跳续租；回写时 owner 不匹配则只记录租约丢失，不再尝试覆盖任务。`staging_cleanup` 严格校验 `aggregate_id/upload_id/backend/prefix`，然后调用幂等 `CleanupSession`；缺失对象按成功、输入契约错误直接 dead-letter、存储/DB 临时错误进入 retry。

`multipart_abort` 的聚合标识是 `SHA-256(object_key + "\n" + upload_id)`，去重键为
`multipart-abort:{digest}`，payload 仅含 `backend="s3"`、`key` 和 `upload_id`。创建 multipart 的
请求先以独立 owner 将任务写为 Running，再上传 part；请求按 part 边界续租，Complete 或即时 Abort
成功后 owner 条件收敛任务，Abort 失败则立即转为 Retry。进程退出留下的 Running 租约到期后由
Worker 接管幂等 Abort。S3 返回 upload ID 到任务写入之间的极短窗口由 bucket 的未完成 multipart
生命周期规则兜底；final 前缀不得配置对象过期规则。

零引用内容使用稳定的 `blob-gc:{content_id}` 去重键。引用归零事务写入任务；已成功的同键任务可
被重置为 Pending，以覆盖同一内容在“重新引用、再次归零”后的新一轮生命周期。引用增长事务先
锁定 `file_contents` 行：任一 Pending/Running/Retry/DeadLetter GC 都返回可重试冲突，只有无任务
或 Succeeded 状态允许递增。失败删除可能已经在对象存储端生效，因此不能靠取消 Retry/DeadLetter
恢复引用。Worker 认领任务后，持有该内容行的 `FOR UPDATE` 锁复核引用，执行幂等 Blob 删除，
并在同一 PostgreSQL 事务中删除零引用元数据、写入任务成功状态；这是对象存储调用跨数据库事务
边界规则的 GC 专用例外。若上传事务外预查计划
复用旧内容，最终引用原语还要校验预查 content_id；旧行已被 GC 删除时必须冲突重试并重新提升
候选对象，不能插入指向缺失 Blob 的元数据。

重试延迟为有上限的 `base * 2^(attempts-1)`，再加上由 `job_id + attempts` 稳定派生的 0-25% 抖动。稳定抖动使单次故障可复现，同时避免大量任务在同一秒重试。

Worker 通过按 `job_type` 建立的 handler registry 分派任务；未知类型和不满足 payload 合同的任务
作为永久错误进入 dead-letter，不得调用存储或修改业务状态。`expire_uploads` 复用上传生命周期服务的
条件过期事务，每个任务按 `expires_at/id` 稳定顺序查询至多 `limit` 条；payload 固定为
`scan_id/page/limit`，查询候选数达到 `limit` 时以新的 `page` 去重键入队下一页，不能用 CAS
实际成功数判断是否续页。每条过期事务仍原子完成状态迁移、reserved quota 释放、staging cleanup
入队和分片元数据删除。

`storage_reconcile` 的 payload 固定为 `scan_id/scope/after_id/continuation_token/limit`。scope 分为
`contents`、`users`、`staging` 和 `final`：数据库 scope 使用单调 `id` 游标，对象清单 scope 使用
后端 continuation token，每页均有硬上限并显式入队下一页。去重键中的 `cursor_digest` 固定为
`SHA-256(scope + "\n" + decimal(after_id) + "\n" + continuation_token)` 的 64 位小写十六进制；
声称还有下一页时，新游标必须与当前游标不同，否则当前任务进入 dead-letter，防止无进展循环。
巡检发现持久写入
`storage_reconciliation_findings`，重复发现增加 occurrence 并更新时间；健康复核可将对应发现标记
resolved。自动修复仅限能够再次证明安全的零引用内容，即入队既有 `blob_gc`；引用计数、配额、
缺失/大小不符对象以及孤儿 final 只告警或人工处理。孤儿 staging 由 cleanup 任务和生命周期规则
回收，对账本身不根据一次清单观察直接删除对象。

周期扫描通过唯一周期任务行保证一个周期只产生一次逻辑扫描：去重键包含 UTC 固定窗口
`scan_id`，多个 Worker 可同时尝试入队但只有一个成功。API 副本不得注册集群级清理定时器。

### 10. Redis 与撤销一致性

第一阶段使用支持故障切换的单一写入端点，例如托管 Redis 或 Sentinel 前的稳定代理。Redis Cluster 在验证以下行为前不属于受支持部署：

- `SCAN`/按前缀失效能覆盖所有分片；
- Lua/CAS 与多 key 操作满足 hash slot 约束；
- Drogon 客户端能够正确处理拓扑和 MOVED/ASK。

访问令牌和分享令牌不再缓存“未撤销”结果。进程内缓存只保存已撤销的正结果，并以令牌剩余 TTL 到期。因此实例 A 成功写入 Redis 的撤销状态后，实例 B 的下一次校验必须访问共享 Redis 并立即拒绝令牌。

安全相关 Redis 校验失败采用 fail closed；限流是否降级由各公开接口的安全合同单独定义，不能把 Redis 错误当作“未撤销”。

### 11. 参考部署

实现保持编排平台无关，参考生产部署使用 Kubernetes：

- 无粘性 L7 Service/Ingress 后运行至少两个 API Pod。
- Worker 使用独立 Deployment，至少两个副本。
- schema migration 使用单独 Job，在 API/Worker 滚动发布前执行。
- PostgreSQL 使用单写高可用端点；上传状态、权限和配额查询不读异步副本。
- Redis 使用受支持的高可用写入端点。
- S3/MinIO 必须跨 API/Worker 共享；单节点 MinIO 不作为生产高可用证据。
- liveness 只判断进程是否可继续运行；readiness 判断当前角色所需的 PostgreSQL、Redis、S3 和初始化状态。

Docker Compose 用于本地双 API/双 Worker/MinIO 验收环境。现有 systemd 单机方式继续支持开发和小规模单实例部署，但不宣称为分布式高可用部署。

## 不变量与故障处理

| 故障点 | 持久结果 | 恢复方式 |
|---|---|---|
| 分片对象写入成功、DB 记录失败 | staging 孤儿对象 | 客户端幂等重试或对账清理 |
| 认领后、组装前退出 | `Finalizing` + 到期租约 | 客户端重试或恢复任务接管 |
| assembled 创建后、final 提升前退出 | 可识别 staging 对象 | 新 owner 复用/重建，后续清理 |
| final 创建后、DB 事务失败 | 无引用 final 候选 | 对账确认无引用后 GC，禁止即时盲删 |
| DB 事务成功、HTTP 响应丢失 | `Completed + completed_file_id` | 重复 complete 返回原文件 |
| DB 事务成功、staging 清理失败 | 已完成文件 + pending cleanup | Worker 重试，不影响文件可见性 |
| Blob GC 与秒传/复制竞争 | 未成功 GC 任务或已删除内容行 | 仅一方越过内容行/任务门禁；引用方冲突后重新查询/提升 |
| 上传预查复用后 Blob 被 GC | 旧 content_id 已不存在 | 最终事务返回冲突，重试后重新提升对象 |
| Worker 删除成功、任务完成写回失败 | 对象已不存在 | 重试删除按成功处理并完成任务 |

任何路径都不得导致：

- 同一上传创建多个文件；
- reserved quota 被释放或转换两次；
- `file_contents.ref_count` 与文件引用数量永久失配；
- 一个失败事务删除另一个成功事务正在使用的 Blob；
- 进程退出后任务只能由原实例恢复。

## 进程内状态与定时器盘点

2026-07-19 对 `src/` 的 `runEvery`/`runAfter`、容器、锁、原子量和工作队列进行了基线盘点。后续新增同类状态必须更新本表。

| 位置 | 当前进程内状态/定时器 | 分类 | 分布式处理要求 |
|------|----------------------|------|------------------|
| `UploadService` | `m_upload_task_cache` 与 60 s 驱逐定时器 | 本地提示缓存 | 仅缓存任务几何等不可变数据；每次分片最终写仍以 PostgreSQL `InProgress` 条件为准。缓存可随进程丢失，不做跨实例失效协议 |
| `TokenService` | access/share 撤销 `ExpiryCache` 与 60 s 驱逐定时器 | 本地安全优化 | 删除“未撤销”负缓存，只正缓存已撤销；缓存未命中必须查询 Redis，Redis 错误 fail closed |
| `TokenService` | JWT CPU pool 的 active/total/peak 原子计数与指标定时器 | 本地观测 | 仅实例标签指标，可重置、可丢失；聚合由监控系统完成 |
| `AssemblyWorkerPool` | `m_active_upload_ids`、running 计数和本机最大并发 | 本地容量保护 | 不再作为 upload owner；先取得 PostgreSQL 租约，再占本机执行槽。跨实例互斥只认数据库 |
| `LocalFileStorage` / `LocalBlobStore` / `S3ObjectStorage` | `ConcurrentTaskQueue`、在途 awaiter 原子标志和 `runAfter` I/O 超时 | 本地执行资源 | 仅承载当前调用，不保存待办业务事实；需要跨退出恢复的工作先写入 `storage_jobs` |
| `ScheduledTasks` | 每小时 `RunExpiredCleanupOnce()` | 集群唯一业务任务 | 从 API 移除；Worker 通过持久周期任务/数据库唯一门控生成扫描，一个周期只产生一次逻辑任务 |
| `ApplicationContext`、`StorageMgr`、`BlobStoreMgr`、`ConfigMgr` | 单例服务指针和启动后只读配置 | 本地依赖装配 | 每个进程独立构造，不能存放任务所有权或业务状态；角色与 instance ID 在启动时冻结 |
| Drogon/存储回调 | `queueInLoop` 恢复协程 | 本地调度细节 | 只恢复当前请求；不能作为完成、清理或重试已持久化的证明 |

Redis 文件列表缓存本身是共享、可重建状态，不属于进程内状态；其删除失败只造成短暂陈旧，不得影响数据库写入正确性。除此之外，源码中用于 DTO 白名单和错误码映射的静态只读容器不属于可变业务状态。

## 备选方案

### 方案 A：负载均衡 sticky session + 本地暂存

**拒绝作为最终方案。** 实现成本低，但节点退出会中断进行中上传，扩缩容需要迁移本地状态，也无法解决跨实例完成和清理竞态。仅可作为切换期间处理旧 local 任务的短期措施。

### 方案 B：NFS/CephFS 共享暂存

**拒绝作为默认方案。** 它可以消除分片节点亲和，但仍需要跨实例状态机和租约，并引入共享文件系统性能、锁和运维故障域。对象存储已经是项目支持的生产依赖，统一暂存可减少存储模型数量。

### 方案 C：Redis 分布式锁

**拒绝作为上传所有权来源。** 上传终态和配额在 PostgreSQL；把所有权放入 Redis 会产生双系统事务和锁丢失语义。Redis 可以承担限流和可重建缓存，但持久状态迁移使用 PostgreSQL CAS/租约。

### 方案 D：立即拆分微服务

**拒绝。** 当前主要问题是共享状态、外部副作用和故障恢复，而不是代码发布边界。提前拆分会增加网络调用、分布式事务和部署复杂度，不会自动解决现有竞态。

### 方案 E：客户端直接 multipart 上传 final key

**暂缓。** 该方案可以减少 API 带宽，但会改变客户端合同，并且不能直接继承当前整文件 MD5/SHA-256 校验语义。完成本 ADR 的服务端代理路径后，再根据监控数据设计版本化 API。

## 影响

### 正面影响

- API 实例可在无粘性会话下横向扩容。
- 上传与清理在实例退出后可以接管。
- 终态、配额、内容引用和外部副作用具有可证明的幂等边界。
- 孤儿对象和失败任务可观测、可重试、可对账。
- 保持现有客户端 API，降低第一阶段迁移风险。

### 成本与风险

- 每个上传分片至少包含一次对象存储写入，完成阶段还需读取和组装，增加 S3 请求与网络成本。
- 新写 final Blob 使用 SHA-256 key，现有 MD5 key 需要长期按 `storage_path` 兼容或执行独立迁移。
- PostgreSQL 新增高频状态更新和任务认领，需要连接预算、索引和 vacuum 监控。
- 同步完成请求仍可能较长，必须配置代理超时、租约续期和有界内存。
- S3 兼容实现对条件写、multipart 和 server-side copy 的行为需要在 MinIO 与目标生产服务分别验证。

---

## 迁移顺序

1. 以 expand-only migration 增加上传状态、租约、分片元数据和任务表。
2. 发布能读取旧任务并写入新字段的兼容版本，默认仍使用 local staging。
3. 部署 S3 staging 和 Worker，先 dry-run/小流量验证。
4. 仅对新上传启用 S3 staging，并把 backend 固化到每个任务。
5. 旧 local 任务完成、取消或过期后，关闭生产 local staging 创建。
6. 启动第二个 API、关闭 sticky session并进行随机路由验收。
7. 关闭 API 内集群级定时任务，由 Worker 独占持久任务。
8. 经过至少一个完整过期/回收周期和全量对账后，执行 contract migration 并删除过渡代码。

紧急回滚不删除 expand schema。旧二进制不理解 `Finalizing` 或 S3 staging 任务时，必须先停止新上传并排空/冻结新状态任务，不能直接把流量切回旧版本。

---

## 验收条件

- 两个 API 实例在无粘性路由下完成初始化、交叉分片、完成、取消和下载。
- 100 个并发重复完成请求只产生一个文件、一次配额转换和一个内容引用增量。
- API/Worker 在关键故障点退出后，任务在约定 RTO 内被重试或接管。
- 两个 Worker 并发运行不产生重复业务副作用。
- DB/对象不一致、过期租约、任务积压和 dead-letter 均有指标、告警和运维路径。
- 完整单元、PostgreSQL 集成、MinIO、多实例、故障注入、迁移和压力测试通过。
