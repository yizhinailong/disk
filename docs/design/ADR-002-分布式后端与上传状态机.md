# ADR-002：分布式后端与上传状态机

## 状态

**已接受**

---

## 背景

本 ADR 制定时，后端已经把核心元数据放在 PostgreSQL、把令牌与限流状态放在 Redis，并支持将最终 Blob 保存到 S3/MinIO，但尚不足以证明后端可在无粘性会话的负载均衡后运行多个实例。当时的主要缺口如下：

1. `S3ObjectStorage` 仍使用 `LocalFileStorage` 保存上传分片和组装文件，同一上传的请求必须命中同一节点。
2. `AssemblyWorkerPool` 的同 `upload_id` 单飞和并发上限只在单进程内生效。
3. 完成上传在持久化认领任务之前执行组装与 Blob 提升，两个实例可以同时产生外部副作用。
4. 上传任务本地缓存的失效不传播到其他实例，终态任务可能被另一实例的陈旧缓存继续接受分片。
5. `ScheduledTasks` 由每个 API 进程注册，副本数会放大周期清理的扫描与执行次数。
6. 访问令牌与分享令牌的撤销负缓存允许其他实例在短窗口内继续接受已撤销令牌。

本次重构的目标不是按领域拆分微服务，而是先把现有模块化单体变成可横向扩容、可接管、可对账的分布式后端。API、Worker、PostgreSQL、Redis 和对象存储之间必须有明确的一致性边界。

---

## 决策

### 1. 保持模块化单体

继续构建一个 C++23/Drogon 后端制品，通过运行角色区分 API 与 Worker：

- `api`：监听公开 HTTP 端口，不运行集群级周期任务。
- `worker`：认领持久任务，不提供公开业务接口。
- `all`：仅用于本地开发和单进程测试。

第一阶段不拆分独立微服务，不引入分布式 SQL，也不改变控制器、DTO、服务和存储层的现有职责边界。只有监控数据证明某一领域需要独立发布、独立容量或独立故障域时，才重新评估服务拆分。

### 2. PostgreSQL 是持久状态的唯一事实来源

上传状态、任务所有权、配额、内容引用和待执行存储任务全部由 PostgreSQL 决定。Redis 不作为上传状态机或持久任务的唯一锁服务。

跨实例互斥使用带版本号和到期时间的条件更新：

```sql
UPDATE upload_tasks
SET status = 4,
    state_version = state_version + 1,
    lease_owner = $1,
    lease_expires_at = NOW() + $2::interval,
    finalize_attempts = finalize_attempts + 1
WHERE id = $3
  AND user_id = $4
  AND (
      status = 0
      OR (status = 4 AND lease_expires_at < NOW())
  )
RETURNING *;
```

实际 SQL 可以为覆盖检查和类型绑定做调整，但必须保持以下语义：

- 只有条件更新成功的实例拥有本轮完成权。
- 所有租约判断使用 PostgreSQL `NOW()`，不使用实例本地时钟决定所有权。
- 续租、提交和放弃操作同时校验 `lease_owner` 与 `state_version`。
- 外部对象存储 I/O 不放在长数据库事务中。

所有 API、Worker 和 migration Job 只连接一个稳定的 PostgreSQL 主库写端点；第一阶段不做业务分片，也不让上传状态、权限、配额或任务认领读取异步副本。端点背后的控制面必须先隔离旧主，确认候选副本已经重放本次切换要求保留的 WAL，再提升候选并切换稳定端点；旧主身份或复制位置不明确时禁止恢复写流量。

切换窗口内已经建立的连接必须受 SQL 命令超时约束，数据库业务请求返回受控错误，liveness 保持成功而 readiness 将 database 标为失败。应用不得自动重放提交结果未知的写请求；客户端只通过既有幂等业务操作恢复。端点切换并关闭旧连接后，原 API/Worker 进程的 Drogon 连接池必须重建连接，并以切换前数据读取和切换后跨实例写读证明恢复。仓库同主机物理副本提升门禁只验证应用协议，不替代目标控制面、TLS、独立故障域、备份/PITR 和经批准的 RTO/RPO 演练。

连接预算需要代理收敛时，第一阶段只准入 PgBouncer 1.25.2 及以上的事务池模式，并保持代理后端仍指向上述单一稳定主库写端点。`pool_mode=transaction`、非零 `max_prepared_statements` 和关闭 `server_reset_query_always` 是不可拆分的合同：前者让一个后端连接在完整事务内保持独占，第二项让 PgBouncer 跟踪并重写 Drogon/libpq 的协议级命名 prepared statement，最后一项避免在每次事务归还时注入会话重置。应用池是 PgBouncer 的客户端连接预算，PgBouncer 后端池才计入 PostgreSQL `max_connections`，两层必须分别限额。

事务池只支持事务边界内的状态。业务与运维 SQL 可以使用 `pg_advisory_xact_lock`、`SET LOCAL` 和同一事务内的 `CREATE TEMP TABLE ... ON COMMIT DROP`；禁止会话级 `pg_advisory_lock`/`pg_try_advisory_lock`、SQL 级 `PREPARE`/`EXECUTE`/`DEALLOCATE`、`LISTEN`/`UNLISTEN`、`WITH HOLD` cursor、跨事务临时表及依赖 `SET`/`RESET` 保留的会话状态。迁移 Job 必须在一个客户端事务中完成 advisory lock、DDL 和账本写入；final Blob 切换临时表也必须在创建事务提交时删除。任何新增 SQL 引入这些会话特性，或将 `max_prepared_statements` 设为 0，都必须撤回事务池声明并重新执行兼容性门禁。

### 3. 上传状态机

保留既有状态数值并新增状态：

| 值 | 状态 | 是否终态 | 说明 |
|---:|---|---|---|
| 0 | `InProgress` | 否 | 接受分片，可取消、可过期、可认领完成 |
| 1 | `Completed` | 是 | 文件、内容引用和配额转换已提交 |
| 2 | `Cancelled` | 是 | 用户取消，reserved quota 已释放 |
| 3 | `Expired` | 是 | 超时回收，reserved quota 已释放 |
| 4 | `Finalizing` | 否 | 某实例持有有期限租约并执行完成流程 |
| 5 | `Failed` | 是 | 兼容保留终态；当前自动完成流没有生产入口 |

允许的主要迁移如下：

```text
InProgress -> Finalizing -> Completed
     |             |
     |             +-> Finalizing（租约到期后由新 owner 接管）
     +-> Cancelled
     +-> Expired

Finalizing -> Failed（保留迁移，当前没有生产调用者）
```

`Finalizing` 不接受取消和新分片。短暂外部错误保留在 `Finalizing`，由当前 owner 重试或在租约到期后接管；不得为重试先退回 `InProgress`，以免重新开放分片写入。

`Failed` 的数值、读取和终态拒绝语义为 schema/API 兼容保留；当前生产代码只记录 `last_error_code/last_error_at` 并保持 `Finalizing` 可恢复，不暴露或调用 `Finalizing -> Failed` 的持久化原语。后续若批准自动失败终结，必须先定义恢复上限和错误分类，并在一个事务中完成 owner/version CAS、reserved quota 释放、分片处理和 cleanup 入队；对应真实 PostgreSQL 集成测试通过前不得接入调用。Phase 2 状态机验收只覆盖当前可达迁移，不把该保留边计作已执行行为。

`UploadTaskRepository` 的公开原语必须与生产调用路径对应：无调用的通用查找、旧完成/删除包装、未接入的失败迁移、重复分片覆盖查询和脱离事务的分片删除包装应在调用点审计后删除。这类 C++ 接口清理不等于迁移兼容退役；`Failed` 持久值、`temp_path` 回退、local staging 和可空分片描述字段仍受独立退役准入合同保护。

### 4. S3/MinIO 原生上传暂存

生产多实例部署的上传分片必须写入对象存储，不使用共享 POSIX 文件系统作为最终方案。对象布局为：

```text
staging/{upload_id}/chunks/{chunk_index}-{chunk_md5}.part
staging/{upload_id}/assembled/{state_version}.bin
objects/sha256/{sha256[0:2]}/{sha256}.bin
```

存储接口中的组装结果使用 `{backend, locator, size, md5, sha256}` 描述，不以
`std::filesystem::path` 代表所有后端。`locator` 是不含 endpoint 和凭据的稳定定位符：
local 后端保存规范化文件路径字符串，S3 后端保存对象 key。最终 Blob 提升只能根据
`backend` 解释该定位符，禁止调用方把对象 key 当作本地路径打开。

上传会话描述符使用 `{upload_id, backend, prefix}`，必须由
`upload_tasks.staging_backend/staging_prefix` 恢复，并传入每个分片写入、组装、
丢弃组装物和会话清理操作。存储层不接受脱离描述符的裸 `upload_id`：
local 实现只处理 `backend=local`，S3 组合实现在迁移窗口内对 local 任务调用
local 兼容实现，对 `backend=s3` 任务使用对象存储。配置只决定新任务，
已建任务的路由始终以持久化描述符为准。

存储组合边界只持有实际能力：`StorageFactory` 返回明确命名的
`upload_staging_storage` 与 `blob_store`，`StorageMgr` 直接管理
`UploadStagingStorage`，上传服务只注入 `UploadStagingStorage` 和 `IBlobStore`。
不再保留无方法、只用于透传指针的聚合存储标记接口。该 C++ 边界清理不改变
`LocalFileStorage` 与 `S3ObjectStorage` 内按持久化描述符处理遗留 local 任务的兼容语义，
也不代表 `temp_path`、local staging 或可空迁移字段已获准退役。

暂存清理公开面只接受已验证的上传会话和组装描述符：单个组装工件使用
`DiscardAssembly(session, assembly)`，整个会话使用 `CleanupSession(session)`。
`LocalFileStorage` 不暴露接受任意文件系统路径的 `DeletePath`；测试和业务流程也必须走
上述后端无关能力，避免绕过 backend、upload ID、locator 一致性校验。删除该旧入口不影响
local staging 兼容处理，也不授权删除持久任务或迁移字段。

最终 Blob 存在性检查同样只暴露 `BlobExists(blob_descriptor)`。local 与 S3 实现必须从
描述符读取持久化 `storage_path` 并执行各自的路径/key 校验；`IBlobStore` 不再同时保留
接受裸 `std::filesystem::path` 的 `Exists` 转发接口。持久 Blob GC 在内容行删除后仍按
任务 payload 调用幂等 `DeleteBlob(storage_path)`，该恢复合同不属于存在性接口清理范围。

组合管理器的公开面必须与调用路径对应。`StorageMgr`、`BlobStoreMgr` 和
`ProcessRuntimeMgr` 只保留启动装配和运行时消费者实际调用的 set/get 操作；无调用的
静态 `IsInitialized` 探针不作为 readiness 依据并应删除。健康检查与指标继续读取
`ProcessRuntimeState::IsInitialized` 的实例级真实状态，该状态不属于本次公开面清理。

S3 客户端边界只暴露存储中立的数据结构，提供 Put、带大小/ETag 的 Head、Range Get、
分页 List、最多 1000 key 的批量 Delete，以及 multipart create/upload-part/copy-part/
complete/abort 原语。part 编号和 ETag 由调用方显式保存并按序完成；失败或租约丢失时
必须可重复调用 abort。AWS SDK 类型和同步调用不得越过 `S3ObjectStorage` 的专用工作线程。

每个进程必须显式绑定 AWS SDK HTTP 连接池和阻塞 S3 工作队列，不依赖 SDK 或硬编码
默认值。`s3.max_connections` 限制该进程的 HTTP 连接池，`s3.io_threads` 限制同时执行
同步 SDK 调用的专用线程数；必须满足 `1 <= io_threads <= max_connections`。默认为 16 个
连接和 4 个 I/O 线程，扩容前按所有 API/Worker 副本求和并为迁移、对账工具预留容量。

2026-07-20 容量与故障基线确定了分布式生产起步配置：每个应用进程使用 4 个 HTTP
线程、8 条 PostgreSQL 连接、4 条 Redis 连接、16 条 S3 连接和 4 个 S3 I/O 线程；每个
API 另使用 4 个认证 CPU 线程和最多 2 个本机组装槽位，Worker 并发固定为 1。高可用
起步拓扑为 2 API + 2 Worker；4 Worker 只作为已测量的积压恢复档位，不是线性扩展承诺。
认证 CPU 池不得再按宿主机逻辑 CPU 数为每个 API 重复放大。以上值是仓库样例的保守
起点而非容量上限，跨过已测副本/并发矩阵或切换真实 MinIO/云 S3 后必须重新压测。

AWS SDK 重试策略由应用显式覆盖，不能依赖 SDK 版本的默认次数。认证、签名、bucket、参数和
其他普通 4xx 错误判定为永久错误；HTTP 408、429、5xx，以及 SDK 标记的连接/网络错误判定为
可重试错误。永久错误即使被 SDK 标记为 retryable 也不得重试。`s3.max_retries` 表示首次请求
之外允许的重试次数，达到预算后返回最后一次错误；退避使用 `s3.retry_base_delay_ms` 作为
指数退避基数。该请求内预算与持久 Worker 的任务级重试相互独立，两层都必须有界。

分片 Put 使用 `If-None-Match: *`，不得以“先 HEAD、再无条件覆盖”实现幂等。首次写入返回
对象 ETag；命中既有 key 时必须重新 HEAD，并以有界 Range 流读取计算 MD5，确认大小、内容
和 key 中的内容标识一致后才返回成功。条件冲突、超时或响应丢失不得导致覆盖同 key 的不同
内容；无法证明对象一致时返回错误并交由请求重试或对账处理。

S3 组装目标固定为 `staging/{upload_id}/assembled/{state_version}.bin`。实现按索引逐个 HEAD
并 Range 读取权威分片，流式计算分片 MD5、整文件 MD5/SHA-256，同时通过 multipart upload
写入 assembled 对象；除最后一个 part 外不得小于 5 MiB，内存缓冲保持有界，part 数不得超过
10000。S3 返回 upload ID 后、上传任何 part 前，存储层必须同步登记持久 `multipart_abort` 任务；
每个 part 和 complete 前续租，multipart 未完成的任意退出路径都必须尝试 Abort。Complete 或 Abort
成功后才将任务收敛为成功，Abort 失败立即释放任务供 Worker 重试，assembled 成功后再返回后端
无关描述符。
会话清理只能分页列举严格验证后的 `{staging_prefix}/{upload_id}/`，每批最多删除 1000 个 key；
对象不存在按成功处理，任何返回到该前缀之外的 key 都必须拒绝删除。

具体前缀允许配置，但必须满足：

- `upload_id`、索引和 hash 经过严格格式验证后才能构造 key。
- 分片 key 对已验证内容不可变；重复上传同一分片必须幂等。
- `upload_task_chunks` 保存对象 key、大小、MD5 和 ETag，并继续作为唯一上传进度来源。
- 对象已写但数据库未记录时，该对象属于可识别的 staging 孤儿，由对账任务清理。
- 数据库记录存在但对象缺失或元数据不一致时，完成请求返回 `ChunkVerifyFailed`，以
  `upload_id` upsert `upload_staging_mismatch` 持久发现，并通过确定性的
  `upload-integrity-<digest>` scan ID 立即排入一页 staging 对账。finding 和任务均不得保存
  凭据、签名 URL 或对象正文；重复失败只增加 occurrence 或复用/重置同一逻辑任务。

不采用直接把客户端分片映射为最终 multipart parts 的方案。原因是 multipart ETag 不是稳定的整文件 MD5，乱序重试也会扩大 part ETag 与数据库元数据的竞态。第一阶段将分片保存为独立 staging 对象，完成阶段按索引流式读取、计算整文件 MD5/SHA-256，并写入唯一的 assembled staging 对象。

### 5. 完整性校验与最终 Blob 寻址

完成阶段继续由服务端验证：

- 分片覆盖连续且数量正确。
- 每个分片的对象大小、MD5 与数据库记录一致。
- 组装结果总大小与上传任务一致。
- 整文件 MD5 与初始化请求一致。
- 整文件 SHA-256 由服务端计算并写入 `file_contents`。

multipart ETag 不作为 MD5。新写入的最终 Blob 使用 SHA-256 内容寻址：S3 key 固定为
`{object_prefix}/sha256/{sha256[0:2]}/{sha256}.bin`，local 路径固定为
`{storage_base_path}/sha256/{sha256[0:2]}/{sha256}.bin`。SHA-256 必须是 64 位小写十六进制；
任何不满足该格式的提升请求都在访问存储前失败。

数据库 `file_contents.storage_path` 是读取位置的唯一权威。文件所有者下载和分享下载都必须把该字段
放入 Blob 描述符，存储实现按其原值读取、HEAD、Range 和删除，不得从 MD5、SHA-256 或当前配置
重新构造既有对象路径。现有 MD5 路径因此继续按已保存的 `storage_path` 读取，不在请求路径中自动
搬迁；存量对象迁移采用可断点、可校验、可重复执行的独立工具。

当前 schema 没有 per-content backend，运行时 final backend 由进程配置统一选择，因此 local final
到 S3 的存量迁移只能在停写维护窗口切换，不能在同一集群内逐行修改 `storage_path` 后继续提供服务。
本 ADR 明确选择最长 120 分钟且不允许延期的停写维护窗口，不引入 per-content backend，也不做
在线逐行切换、双写或无截止日期双读。窗口必须指定迁移、数据库和回滚负责人，并使用
`deploy/final-blob-maintenance-window.json` 与 `scripts/check-final-blob-cutover-plan.py` 的受评审策略门禁。
目标环境必须另行记录不超过该上限的 UTC 起止时间和实际值班人；仓库文件是策略而不是生产变更单。

维护窗口超时时不得原地延长。若数据库尚未切换，停止复制并保留 manifest、checkpoint、
已验证目标和 local 源，在新审批窗口续传；若数据库已切换但流量尚未恢复，或下载/Range 探针、
全量对账任一失败，则保持入口关闭并依据同一 manifest 恢复全部原路径。只有全部后置门禁通过才能开放流量。
`scripts/migrate-final-blobs.py` 的迁移合同为：

1. API、Worker 和 Blob GC 全部停止后，以 PostgreSQL repeatable-read 只读快照生成 JSONL manifest；
   每行固定 content ID、原 `storage_path`、相对 local 根目录的源文件、大小、MD5、SHA-256 和目标 key。
2. copy 阶段在上传前逐字节校验源文件大小、MD5 和 SHA-256；目标已存在时必须完整下载并得到同一组三元组，
   不得覆盖冲突对象。新上传对象也必须通过完整 GET 校验，multipart ETag 或用户 metadata 均不能代替内容哈希。
3. SQLite checkpoint 与 manifest SHA-256、bucket 和 object prefix 绑定，只在目标完整校验后提交单对象记录。
   中断后允许重跑；已记录对象仍再次校验目标内容，但不重复上传。工具提供无写入 dry-run、有界对象批次和传输限速；
   正值限速对 S3 上传回调与目标完整 GET 校验使用同一个聚合字节预算，`0` 才表示禁用。
4. cutover 再次验证全部 checkpoint 和目标对象，在 `ACCESS EXCLUSIVE NOWAIT` 表锁内确认数据库内容集合
   与 manifest 全部处于原路径或已全部处于目标路径；只有前一种状态执行单事务全量更新，混合或漂移状态拒绝。
   checkpoint 缺失或少任意对象、目标在复制后缺失/损坏时，都在修改任何 `storage_path` 前失败；
   cutover 只做完整 GET 重验和原子切库，不在此阶段上传或修复对象。
5. 数据库提交后才把所有进程统一切换为 S3 配置并恢复流量。旧 local Blob 在备份恢复和全量对账完成前保留；
   数据库已切换但应用尚未恢复时，可依据同一 manifest 在事务内恢复原路径，不能删除源文件后回滚。
6. 旧 local Blob 回收与 cutover 分离。受评审策略只能在回滚窗口关闭、切换后一致恢复集及隔离恢复演练通过、
   下载/Range 探针通过、`contents/users/staging/final` 全分页对账成功且未完成任务、finding、配额与
   `ref_count` 差异全部为零后准入“排期”；原源 inventory 仍须与 manifest 一致，manifest/checkpoint 已归档。
   排期不得早于全部条件通过后 30 天。当前工具不生成删除命令；实际隔离/删除属于独立破坏性变更，必须在目标环境重验。

下载在构造 200/206 响应前必须以 `file_contents.size` 对最终 Blob 执行一次 HEAD/大小预检。
对象缺失、实际长度不符或预检后无法打开读取流时，所有者与分享路由统一返回 HTTP 500 +
`50011 FileReadError`，并以 `content_id` 为稳定资源 ID 写入 `missing_final_blob`、
`final_blob_size_mismatch` 或 `final_blob_read_interrupted` 对账记录。对账详情只保存预期/实际字节数、
Range 起点和已传输字节数等有界字段，不保存凭据、签名 URL 或底层原始错误。

流式响应一旦开始发送便不能改写为 JSON 错误信封。Range GET 或其他上游读取在声明的
`Content-Length` 满足前结束时，响应器必须立即关闭读取流，使客户端观察到不完整 HTTP 传输，
并异步持久化 `final_blob_read_interrupted`；客户端可按既有 Range 合同重试。周期内容巡检只有在
同一 Blob 再次存在且大小与数据库一致后，才可把该中断 finding 标记为已恢复。

SHA-256 目标对象的创建和复用必须幂等。S3 assembled 对象提升时先严格校验 locator 位于当前
`staging_prefix/{upload_id}/assembled/{state_version}.bin` 形态且 HEAD 大小一致，再使用有界 part
数量的 server-side multipart copy 写入 final key，不能依赖有单对象大小上限的单次 copy。任一
copy part 或 complete 失败都必须尝试 Abort，并使用与 assembled 组装相同的持久任务协议；目标已经存在时必须验证大小一致。提升成功不删除
assembled 对象，只有最终数据库事务提交并持久化 cleanup 任务后才能清理 staging 会话。

### 6. 同步完成 API 与幂等结果

第一阶段保持 `POST /api/file/upload/complete` 的同步接口形态，避免要求现有桌面客户端引入异步轮询协议：

- 成功认领的请求执行完成流程并返回现有 `file` 响应。
- 任务已经 `Completed` 时，通过 `completed_file_id` 重建并返回同一响应。
- 其他 owner 持有有效 `Finalizing` 租约时，返回 `409 + 10004 ResourceConflict`，并可附带 `Retry-After`。
- `Cancelled`、`Expired`、`Failed` 返回稳定、已文档化的终态错误。
- 当前 owner 崩溃后，客户端重试可以在租约到期后接管。

未来如完成耗时的监控数据证明同步请求不可接受，再新增版本化的 `202 Accepted + status` 合同；不得静默改变当前接口。

### 7. 完成上传使用可恢复 Saga

完成流程分为短事务和可重试外部步骤：

1. 从 PostgreSQL 校验用户、任务状态和完整分片覆盖。
2. 使用条件更新认领 `Finalizing` 租约。
3. 在事务外读取分片、流式组装、计算 hash 并创建 assembled staging 对象。
4. 幂等确保 SHA-256 final Blob 存在。
5. 在一个短事务中原子完成内容 upsert/ref_count、文件记录、目录计数、reserved-to-used 配额、`Completed + completed_file_id` 和 staging cleanup 任务入队。
6. Worker 异步删除 staging 对象；删除失败不回滚已完成文件。

第 5 步的内容引用必须由 `file_contents(hash_md5, hash_sha256)` 唯一约束和单条
`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 完成。冲突时只在内容大小一致的前提下增加
`ref_count`，并保留已有 `storage_path`；事务外预查询只用于优化，不能决定唯一性。文件记录使用
`files(user_id, folder_id, name)` 唯一约束裁决并发同名写入，无返回行映射为稳定领域冲突。

最终事务失败时，不立即删除可能被其他事务复用的 final Blob。系统记录可识别的孤儿候选，由 Blob 对账/GC 在确认数据库无引用后删除。

### 8. 取消、过期与分片竞态

取消和过期必须在同一个数据库事务中完成状态条件更新、`state_version` 递增、reserved quota 释放、分片元数据处理和 cleanup 任务入队。条件更新必须返回提交后的版本；只有成功从 `InProgress` 迁移到终态的事务可以使用该版本记录成功并释放配额，CAS 未命中不得伪造版本或重复副作用。

完成、取消和过期共用 `staging-cleanup:{upload_id}` 去重键。任务 payload 保留该上传会话创建时持久化的 backend/prefix，Worker 不根据当前默认存储配置重建位置。业务事务提交后完全由 Worker 执行幂等会话清理，API 不再以一次最佳努力删除代替持久任务。

分片写入采用两次持久状态检查：对象写入前校验任务与几何信息，写入后使用只对 `InProgress` 生效的条件 SQL 记录分片。若取消或完成在对象写入期间获胜，迟到请求不得改变终态；产生的对象由 staging 对账清理。

该窗口必须由真实 API 进程故障注入验证：测试进程同时设置 `DISK_TEST_FAULT_INJECTION=1`、精确的 `DISK_TEST_PAUSE_AFTER_CHUNK_WRITE_UPLOAD_ID` 和 `DISK_TEST_CHUNK_WRITE_RELEASE_FILE`，只允许目标 upload 在 `WriteChunk` 成功返回之后、调用 `RecordChunkIfInProgress` 之前等待 release 文件。夹具必须先确认对象已存在且目标分片数据库行尚未改变，再分别让正常 complete、cancel 和 expire 事务提交；释放后迟到分片必须以冲突结束，不能重建分片元数据、改变终态或重复结算配额。停顿点默认关闭，安全模式下无条件忽略，且不得根据分片索引、对象 key 或请求正文进行宽泛匹配。

进程内上传缓存只能缓存文件大小、分片大小、总分片数等不可变几何信息。它不能替代写入后的数据库状态条件。

### 9. PostgreSQL 持久任务队列

集群级任务使用 PostgreSQL 持久任务表，并通过 `FOR UPDATE SKIP LOCKED` 认领。任务至少覆盖：

- staging 清理；
- multipart abort；
- 零引用 Blob GC；
- 过期上传扫描；
- 过期回收站扫描；
- DB/对象一致性对账。

任务使用唯一去重键，状态为 `Pending/Running/Retry/Succeeded/DeadLetter`，并保存尝试次数、可执行时间、owner、租约截止和最后错误。临时错误使用有上限、带抖动的指数退避；永久错误或超过上限后进入 dead-letter。

DeadLetter 不由业务流自动清除。管理员可通过有界分页接口查询列表和单项 payload；重放默认 dry-run，实际执行要求路径 ID 与请求体确认 ID 一致并填写原因。`DeadLetter -> Pending` 的重置与 `admin.storage_job.replay` 操作日志必须在同一 PostgreSQL 事务提交，并发重放仅允许一个赢家。接口不接受任意 payload、SQL 或强制状态覆盖。

认领是数据库原子操作：候选集同时包含到期的 `Pending/Retry` 和租约过期且仍有尝试余量的 `Running`，通过 `FOR UPDATE SKIP LOCKED` 分配给唯一 `instance_id`。所有续租和结果回写都校验当前 owner；过期 owner 恢复后不能覆盖接管者的结果。认领时增加 `attempts`，崩溃留下的最后一次过期租约由下一轮扫描直接收敛到 dead-letter。

Worker 按可立即执行的并发容量认领任务：有效认领量为 `min(worker_claim_batch_size, worker_concurrency)`。当前每类 handler 和整个 Worker 的并发上限均为 1，因此每轮最多认领 1 条，后续只能在实现同批并行续租与执行后根据指标显式提高；禁止串行 Worker 预先持有尚未开始任务的租约。一次调度被触发后，只要上一轮仍领取到任务且进程继续接受工作，就立即领取下一轮，直到队列暂时为空或本轮失败；`worker_poll_interval_ms` 仅用于空闲唤醒，不能成为积压任务之间的固定延迟。执行前续租一次，执行期间每隔 `lease_duration / 3` 心跳续租；回写时 owner 不匹配则只记录租约丢失，不再尝试覆盖任务。失败结果必须在新事务上下文中按 PostgreSQL `smallint` 状态类型收敛为 Retry 或 DeadLetter，不能因参数类型推断失败而遗留 Running 租约。`staging_cleanup` 严格校验 `aggregate_id/upload_id/backend/prefix`，然后调用幂等 `CleanupSession`；缺失对象按成功、输入契约错误直接 dead-letter、存储/DB 临时错误进入 retry。

Worker 回滚按实例执行 SIGTERM drain，而不是把共享 `worker_claiming_enabled` 当作运行时暂停按钮。信号边界先停止新的 poll 和周期播种，使 readiness 失败并报告 `draining=true`、`worker_accepting=false`；已经进入 handler 的任务可在 `worker_drain_timeout_seconds` 内继续执行和续租。超时后进程退出，不能主动清空或缩短 `locked_by/locked_until`，另一兼容 Worker 只能在 PostgreSQL `NOW() >= locked_until` 后通过正常认领 CTE 接管。编排器的终止宽限期必须大于应用 drain 超时；滚动回滚始终保留至少一个理解全部已持久化 job type/payload 和存储描述符的 ready Worker，并逐台等待完成/自然接管证据后再处理下一台。

`multipart_abort` 的聚合标识是 `SHA-256(object_key + "\n" + upload_id)`，去重键为
`multipart-abort:{digest}`，payload 仅含 `backend="s3"`、`key` 和 `upload_id`。创建 multipart 的
请求先以独立 owner 将任务写为 Running，再上传 part；请求按 part 边界续租，Complete 或即时 Abort
成功后 owner 条件收敛任务，Abort 失败则立即转为 Retry。进程退出留下的 Running 租约到期后由
Worker 接管幂等 Abort。S3 返回 upload ID 到任务写入之间的极短窗口由 bucket 的未完成 multipart
生命周期规则兜底；final 前缀不得配置对象过期规则。

零引用内容使用稳定的 `blob-gc:{content_id}` 去重键。引用归零事务写入任务；已成功的同键任务可
被重置为 Pending，以覆盖同一内容在“重新引用、再次归零”后的新一轮生命周期。引用增长事务先
锁定 `file_contents` 行：任一 Pending/Running/Retry/DeadLetter GC 都返回可重试冲突，只有无任务
或 Succeeded 状态允许递增。失败删除可能已经在对象存储端生效，因此不能靠取消 Retry/DeadLetter
恢复引用。Worker 认领任务后，持有该内容行的 `FOR UPDATE` 锁复核引用，执行幂等 Blob 删除，
并在同一 PostgreSQL 事务中删除零引用元数据、写入任务成功状态；这是对象存储调用跨数据库事务
边界规则的 GC 专用例外。若上传事务外预查计划
复用旧内容，最终引用原语还要校验预查 content_id；旧行已被 GC 删除时必须冲突重试并重新提升
候选对象，不能插入指向缺失 Blob 的元数据。

重试延迟为有上限的 `base * 2^(attempts-1)`，再加上由 `job_id + attempts` 稳定派生的 0-25% 抖动。稳定抖动使单次故障可复现，同时避免大量任务在同一秒重试。

Worker 通过按 `job_type` 建立的 handler registry 分派任务；未知类型和不满足 payload 合同的任务
作为永久错误进入 dead-letter，不得调用存储或修改业务状态。`expire_uploads` 复用上传生命周期服务的
条件过期事务，每个任务按 `expires_at/id` 稳定顺序查询至多 `limit` 条；payload 固定为
`scan_id/page/limit`，查询候选数达到 `limit` 时以新的 `page` 去重键入队下一页，不能用 CAS
实际成功数判断是否续页。每条过期事务仍原子完成状态迁移及版本递增、reserved quota 释放、staging cleanup
入队和分片元数据删除；逐上传成功日志使用该事务返回的版本，扫描任务级日志不把 job generation 冒充上传版本。

`expire_trash` 的 payload 固定为 `scan_id/after_id/limit`，去重键为
`periodic:expire-trash:{scan_id}:{after_id}`。每页按 `trash.id ASC` 查询 `id > after_id`
的有界候选；任一分块失败时当前任务进入重试，不入队下一页。整页成功且
候选数达到 `limit` 时，才以本页最大 ID 生成下一个持久任务。已成功删除的记录
在重试时自然消失，因此重复执行不会重复释放配额或内容引用。

`storage_reconcile` 的 payload 固定为 `scan_id/scope/after_id/continuation_token/limit`。scope 分为
`contents`、`users`、`staging` 和 `final`：数据库 scope 使用单调 `id` 游标，对象清单 scope 使用
后端 continuation token，每页均有硬上限并显式入队下一页。去重键中的 `cursor_digest` 固定为
`SHA-256(scope + "\n" + decimal(after_id) + "\n" + continuation_token)` 的 64 位小写十六进制；
声称还有下一页时，新游标必须与当前游标不同，否则当前任务进入 dead-letter，防止无进展循环。
巡检发现持久写入
`storage_reconciliation_findings`，重复发现增加 occurrence 并更新时间；健康复核可将对应发现标记
resolved。自动修复仅限能够再次证明安全的零引用内容，即入队既有 `blob_gc`；引用计数、配额、
缺失/大小不符对象以及孤儿 final 只告警或人工处理。孤儿 staging 由 cleanup 任务和生命周期规则
回收，对账本身不根据一次清单观察直接删除对象。

周期扫描通过唯一周期任务行保证一个周期只产生一次逻辑扫描：去重键包含 UTC 固定窗口
`scan_id`，多个 Worker 可同时尝试入队但只有一个成功。过期上传和过期回收站使用
UTC 小时窗口，四个对账 scope 使用 UTC 日窗口。Worker 每分钟尝试播种当前窗口的
首页，启动后立即尝试一次；数据库唯一去重键是集群唯一性的最终裁决。
API 副本不得注册集群级清理定时器。

过期上传、过期回收站和存储对账的每个分页 handler 都必须记录成对的开始/结束事件。
两个事件均包含固定的 `instance_id/job_type/scan_id/scope/current_cursor`；结束事件额外包含
`outcome/duration_ms/candidates/succeeded/failed/skipped/next_cursor/continuation_enqueued`。任何返回、异常或
继续游标不前进都必须产生失败结束事件。数据库游标记录有界整数；对象存储 continuation
token 只记录与任务去重键相同的 SHA-256 游标摘要，不记录原始 token、对象 key 或错误正文。

### 9.1 PostgreSQL 读路由边界

第一阶段的读副本准入白名单为空。当前认证与用户状态、文件/目录/搜索/回收站/分享、上传任务与分片、
配额、租约、持久任务、管理员诊断与恢复、健康检查和指标查询，均直接或间接参与权限裁决、写后读、
任务接管或运维判断；现有 REST 合同也没有声明最大陈旧时间或返回数据版本。因此这些查询全部通过同一
主库写端点执行，不能仅凭 SQL 语句是 `SELECT` 就路由到异步副本。

运行时配置只允许一个 `db_clients` 对象且名称必须为 `default`，所有生产代码只取得 Drogon 默认
`DbClient`。缺失、重命名或追加第二个数据库客户端时，进程必须在连接和服务初始化前失败，且诊断信息
不得回显客户端名称、主机或凭据。这一门禁防止部署配置绕过查询分类；它不替代数据库端对稳定写端点的
网络和权限控制。

未来只有独立、版本化且明确允许最终一致性的非权限报表接口可以重新进入评估。启用前必须为每条查询
记录最大允许复制延迟、响应中的数据版本或观测时间、主库回退/拒绝策略、延迟与错误指标以及故障测试；
不得复用现有业务服务的 `DbClient`，也不得把授权、上传状态、配额、租约、Worker、readiness 或恢复
判断加入白名单。

### 10. Redis 与撤销一致性

第一阶段使用支持故障切换的单一写入端点，例如托管 Redis 或 Sentinel 前的稳定代理。Redis Cluster 在验证以下行为前不属于受支持部署：

- Lua/CAS 与多 key 操作满足 hash slot 约束；
- Drogon 客户端能够正确处理拓扑和 MOVED/ASK。

文件列表缓存使用每用户单调版本号，不按目录执行 `SCAN`/前缀删除。版本键为永久键 `file_list_version:{user_id}`，缺失时视为 `0`；列表键为 `file_list:{user_id}:{version}:{parent_id}:{type}:{sort_by}:{sort_order}:{page}:{page_size}`，TTL 为 30 秒。任一会改变该用户文件、文件夹或目录计数的数据库写入，均必须先收到 PostgreSQL commit callback 的成功结果，再对版本键执行一次原子 `INCR`；仅析构或 `reset()` 事务句柄不等于提交已可见。`TransactionRunner::Commit` 在检查 owner 前最多让出当前事件循环三个 tick，使已经完成的 Drogon SQL awaiter 释放临时事务引用；让步后仍存在的 owner 视为调用方泄漏并拒绝提交。这使旧版本下的并发回填不可达，同时覆盖源/目标目录、根目录、子树和祖先 `item_count` 的派生列表。

文件列表是可重建缓存：读取版本或列表键失败时直接查 PostgreSQL 且跳过回填；数据库写入成功但版本递增失败时记录可观测告警，不回滚业务事务，最旧结果由 30 秒 TTL 收敛。Redis 恢复后的下一次成功写入会再次切换命名空间。

访问令牌和分享令牌不再缓存“未撤销”结果。进程内缓存只保存已撤销的正结果，并以令牌剩余 TTL 到期。因此实例 A 成功写入 Redis 的撤销状态后，实例 B 的下一次校验必须访问共享 Redis 并立即拒绝令牌。

安全相关 Redis 校验失败采用 fail closed；限流是否降级由各公开接口的安全合同单独定义，不能把 Redis 错误当作“未撤销”。

Redis 中的状态必须按恢复语义分级，不能统一称为“可随意清空的缓存”。文件列表缓存、缓存版本和限流窗口可以按既有降级合同重建或自然过期；`refresh_token:*` 当前哈希、`access_token_blacklist:*` 与 `share_token_blacklist:*` 则是带 TTL 的会话安全状态。受支持的常规重启或故障切换必须保留已经确认写入的安全键及其原始绝对过期时间，恢复后 TTL 只能继续递减，不能重新获得完整寿命。

生产 Redis 端点必须给出已确认写入的持久化/复制保证和可验证 RPO。若一次故障切换或灾难恢复无法证明所有未过期安全写均被保留，则不能把空 Redis 当成正常缓存冷启动：先保持认证入口关闭，轮换 JWT 签名密钥并让全部 API 使用新密钥重启，再验证旧 access、refresh 和 share token 均被拒绝后开放流量。仓库的单节点 AOF 测试只证明同一持久卷上的进程崩溃恢复，不替代目标高可用端点的复制与切换演练。

受支持的写主切换必须先隔离旧主，并确认待提升副本已经收到安全键，再把稳定写端点指向新主；应用不直接发现或选择 Redis 节点。切换窗口内，已经建立的连接可能阻塞到配置的命令超时，安全校验和 refresh 必须以 `70002` fail closed，liveness 保持成功而 readiness 失败。端点恢复后，Drogon Redis 客户端必须在原 API 进程内重建连接；持久 refresh 状态继续通过 Lua CAS 只产生一个赢家，撤销键继续拒绝，所有 TTL 按原绝对到期时间递减。

业务实现不以 `SCAN` 决定授权、上传状态或缓存失效。运维工具若在切换时持有旧主游标，必须丢弃该游标并从新主的游标 `0` 重新开始完整、幂等扫描；不同 Redis 节点之间不承诺游标可移植。第一阶段继续只支持单一稳定写端点，不因本地复制提升测试而宣称支持 Redis Cluster 的 MOVED/ASK 或跨 slot 多键语义。

### 11. 参考部署

实现保持编排平台无关，参考生产部署使用 Kubernetes：

- 无粘性 L7 Service/Ingress 后运行至少两个 API Pod。
- Worker 使用独立 Deployment，至少两个副本。
- schema migration 使用单独 Job，在 API/Worker 滚动发布前执行。
- PostgreSQL 使用单写高可用端点；上传状态、权限和配额查询不读异步副本。
- Redis 使用受支持的高可用写入端点。
- S3/MinIO 必须跨 API/Worker 共享；单节点 MinIO 不作为生产高可用证据。
- liveness 只判断事件循环是否可响应且不访问外部依赖；readiness 检查初始化与 drain 状态，并按角色检查 PostgreSQL、API 所需 Redis、Worker 任务表以及 staging/final 存储。旧 `/api/health` 是 readiness 的兼容别名，探针响应不得回显底层异常或连接参数。
- PostgreSQL、Redis 或 S3/MinIO 的短暂中断不得依赖重启 API/Worker 才能恢复。中断期间 liveness 保持成功、readiness 标记精确依赖失败；依赖恢复后，既有连接池/客户端必须重新就绪，并分别以数据库读取、令牌校验和最终 Blob 下载证明原进程可以继续承载业务。

仓库参考清单位于 `deploy/kubernetes/`，以 Kubernetes 1.30 为最低版本，并把平台前置资源、一次性 migration Job 和长驻工作负载分开。基础清单只保留无敏感的稳定端点占位符；仓库不提供 Secret，目标环境必须预先创建 `disk-runtime-secrets` 并由密钥管理系统注入 PostgreSQL、Redis、JWT 和 S3 凭据。参考镜像占位标签不可直接发布，候选环境必须替换为已评审的不可变 digest。

API 和 Worker 均以 2 副本起步，并由 `autoscaling/v2` HPA 在 2–4 副本内调整；4 是已测矩阵的硬上限，超出时先重新压测。API 以 CPU 和每副本在途业务请求扩容，Worker 以 CPU 和集群最老可执行任务年龄扩容；后两个信号由 Prometheus 记录规则聚合后通过 External Metrics API 暴露。每个角色要求不同主机的硬反亲和，并用 `topology.kubernetes.io/zone` 与 `minDomains=2` 阻止两个最小副本落在同一故障域。在 4 副本上限与 `maxSurge=1` 下，目标集群必须有至少 5 个符合节点选择条件的节点；这是发布前调度容量门禁，不可通过删除硬反亲和规避。PodDisruptionBudget 只限制自愿中断，不代替这些调度约束或底层依赖的高可用。

发布顺序由 `deploy/kubernetes/release-plan.json` 固定为：渲染/服务端 dry-run 与容量门禁、单实例 expand migration、Worker 滚动、API 滚动、发布后探针与业务对账。Worker 与 API 都使用 `maxUnavailable=0/maxSurge=1`，一次只发布一个角色，与容量门禁的一个替换进程预留保持一致。migration Job 复用同一候选镜像，镜像必须内含 `psql`、受控脚本和 manifest 声明的 SQL；业务 Pod 不执行 DDL。回滚仅回滚应用镜像，已执行的 expand schema 默认保留，不从编排器自动调用破坏性 rollback SQL。

Docker Compose 用于本地双 API/双 Worker/MinIO 验收环境。四个应用副本必须使用同一镜像，角色、实例 ID、数据库/Redis 连接与 S3 非秘密参数通过严格校验的环境覆盖层注入；密码和对象存储凭据只来自环境或 Secret，不写入分布式 JSON。安全模式拒绝 `all` 角色，以及 S3 明文传输或关闭证书校验的组合。现有 systemd 单机方式继续支持开发和小规模单实例部署，但不宣称为分布式高可用部署。

#### 11.1 对象存储服务形态与自建 MinIO 准入

第一阶段生产默认选择由供应商承担磁盘、节点和基础设施故障域冗余的托管 S3。该选择减少团队同时维护数据库、Redis 和对象存储控制面的风险，但不豁免 bucket 版本控制、服务端加密、TLS、最小权限、生命周期、容量、备份和恢复演练。自建 MinIO 不是禁止项，而是目标环境提交完整证据后才能重新批准的条件项；仓库的单节点 Compose 只用于协议和故障注入，不属于候选拓扑。

评估以仓库固定的 MinIO `RELEASE.2025-04-22T22-12-26Z` 为版本边界。该版本官方 sizing 表给出的生产下限是 4 个 server、每节点 2 块 drive、8 shard stripe、默认 4 parity，可容忍 2 个节点故障后读取、1 个节点故障后写入。这个下限不能满足 Disk 的“丢失一个完整基础设施故障域仍可读写”目标，因此不准入。自建候选基线采用 6 个专用 server、每节点 2 块近似同容量本地盘、12 shard stripe、默认 4 parity，平均分布到 3 个独立故障域；官方表对应的读写节点容忍数均为 2，目标环境还必须实际关闭同一故障域的 2 个节点验证读写、修复和容量余量。节点使用同构操作系统、网络和盘数，数据盘使用 XFS，不使用 NFS 或共享网络文件系统承载 MinIO 数据目录。

纠删码只处理盘或节点损坏，不是备份。自建方案必须把版本化 bucket 复制或快照到主集群故障域之外的独立站点/供应商，默认不复制 delete marker 或永久删除，并保留对象版本 manifest、加密异地副本、周期哈希/可读性检查和隔离恢复演练。上线申请必须填入并批准目标 RPO/RTO、容量与修复窗口、TLS/KMS 和网络边界，完成整域故障与备份恢复演练；同机、同机架或同集群内的第二份数据不算独立备份。

版本化评估合同位于 `deploy/minio/self-hosted-assessment.json`，由 `test_s3_lifecycle_config.py` 校验上游生产下限、Disk 候选拓扑、备份边界和未完成证据。当前合同明确选择 `managed_s3` 且将自建状态保持为 `not_approved`；只有包含目标环境证据的独立评审才能同时修改选择、RPO/RTO 和批准状态。该评估完成不代表生产 bucket 或对象存储故障切换已经验收。

### 12. 上传与请求指标合同

`/metrics` 使用项目内统一的低基数 registry，不再引入第二套框架插件。请求生命周期在 pre-routing
记录开始时间，在 pre-sending 按固定 `operation/status_class` 枚举累计请求数和延迟；错误率由
`4xx/5xx` 请求 counter 的区间增量计算，不暴露随抓取窗口变化的进程内比例 gauge。

上传指标遵循以下稳定语义：

- `disk_upload_tasks_active` 是 PostgreSQL 快照中 `InProgress + Finalizing` 的集群级总数；每个实例都会暴露同一事实来源的快照，跨副本查询必须取 `max`，不能求和。
- `disk_upload_chunks_total` 与 `disk_upload_chunk_bytes_total` 只在 staging 写入成功且分片元数据仍被 PostgreSQL `InProgress` 条件接受后累计。相同内容的幂等重放仍代表本实例实际处理的一次分片请求，因此计入吞吐。
- `disk_upload_complete_stage_duration_seconds` 只允许 `claim_lease/load_metadata/assemble/dedup_lookup/promote/commit` 六个 `stage` 值。阶段一旦开始，无论成功或失败都记录一次；命中去重时不执行也不伪造 `promote` 样本。

外部依赖指标在实际调用边界记录，而不是从请求总耗时反推：PostgreSQL 使用透明 `DbClient`
代理覆盖原始 SQL、`CoroMapper` 和事务内 SQL，并保持参数二进制格式、回调和事务析构提交语义；
Redis 命令统一经过 `RedisService`；S3 在 `IS3Client` 的 AWS 实现中记录每次最终 SDK 调用结果。
`disk_dependency_calls_total{dependency,outcome}` 的 `dependency` 仅允许
`postgresql/redis/s3`，`outcome` 仅允许 `success/timeout/connection/conflict/not_found/retryable/permanent/protocol/other`；
`disk_dependency_call_duration_seconds{dependency}` 与 `disk_dependency_calls_inflight{dependency}`
分别暴露调用延迟和当前在途数，不把 SQL、Redis key、对象 key 或异常正文作为标签。

S3 的日志关联与低基数指标共用同一个最终 SDK 结果分类，但不把高基数上下文加入指标标签。`LogContext` 由 API 或已认领 Worker 作为值显式穿过存储抽象和 S3 工作队列，`IS3Client` 只保留调用方已确定的顶层业务 `operation`；内部 `sdk_operation` 和结果均由编译期枚举转换，不从 key、endpoint、异常消息或线程状态推断。正常/幂等结果只记 `DEBUG`，其他最终失败记 `WARN`；两者均排除 bucket、对象 key、远端 multipart ID、continuation token、凭据、正文和 SDK 异常正文。

Drogon 和 AWS SDK 当前不公开各连接池的实时 busy/idle 连接数，因此
`disk_dependency_pool_capacity` 表示有效配置容量，`disk_dependency_pool_demand` 表示应用侧当前
在途调用与已持有 PostgreSQL 事务租约之和，`disk_dependency_pool_utilization_ratio` 为
`min(demand, capacity) / capacity`。该比率是每实例容量压力信号，不得解释成底层连接池的精确
busy 比例；容量为零时比率固定为零。`disk_thread_queue_depth{queue}` 直接读取 Trantor 队列中
尚未开始的任务数，`disk_thread_queue_workers{queue}` 给出 `local_file/local_assembly/local_blob/s3`
四类固定队列的执行线程数，二者均为进程级 gauge。

分片 counter 与完成阶段 histogram 是进程内累计量，跨 API 副本使用 `sum(rate(...))` 或对 histogram
bucket 先按 `le/stage` 求和后计算分位数。任何指标均不得加入 `request_id/upload_id/job_id`、用户、文件名、
对象 key、租约 owner 或异常正文标签；实例维度由 Prometheus target 标签提供。

### 13. 告警合同

Prometheus 规则使用稳定的 `disk-api`/`disk-worker` job 标签。所有规则必须配置
`for`，不用单次抓取或单个低流量请求直接切换告警状态。最低覆盖为：

- 进程持续 2 分钟无法抓取，或 readiness 在每个 1 分钟窗口内都有 5xx 且持续 2 分钟时，视为可用性故障。readiness 探针周期必须不超过 30 秒。
- API 5xx 比例只统计 `disk-api` 的业务请求，排除 health/metrics；5 分钟真实比例超过 1%、样本不少于 20 次且持续 5 分钟才告警，不得使用分母下限稀释低流量的真实错误率。
- API P99 在 10 分钟窗口内超过 1 秒并持续 10 分钟；任务最老可运行年龄超过 300 秒、租约 10 分钟内接管超过 3 次、dead-letter 非空或对账差异未解决时分别告警。
- S3 `timeout/connection/retryable` 5 分钟内累计至少 5 次且持续 2 分钟为临时错误告警；`permanent/protocol/other` 5 分钟内任一出现且持续 1 分钟为永久错误告警。用于幂等 HEAD/删除/条件写的 `not_found/conflict` 不视为 S3 故障。

告警表达式只按稳定低基数标签聚合；请求 ID、文件、对象 key 和租约 owner 仅通过日志与运维查询定位。

### 14. 只读上传诊断合同

管理员按精确 `upload_id` 诊断时，PostgreSQL 仍是任务状态、租约、分片描述符和关联任务的权威来源。
诊断服务先分页读取描述符，再通过 `UploadStagingStorage` 对每页至多 100 个精确对象做 HEAD；存储实现必须复用会话前缀、索引、MD5 和对象 key 验证，不得把可能被损坏的 DB key 当作任意存储读能力。

单个对象缺失或 HEAD 失败是诊断结果，不是整个请求的失败；响应只返回稳定状态、大小、ETag 和业务错误码。该路径不读对象正文，不获取签名 URL，不更新上传/租约/任务，也不记录对象 key 或 owner 到指标与通用请求日志。

### 15. 受审计恢复命令合同

恢复命令遵守“精确目标、默认 dry-run、CAS、同事务审计”四条规则。实际解除尚未自然到期的上传完成租约必须确认 upload ID、当前 owner 和 `state_version`；数据库只把租约截止写为 `NOW()` 并递增版本，保留 `Finalizing` 与 owner，不重新开放分片写入。旧 owner 被截止时间和新版本共同栅栏，恢复仍由正常 complete 接管完成；已过期或已解除的租约不重复变更。

重建 staging cleanup 只允许终态上传，且任务 payload 只能由持久化 backend/prefix 构造。缺失任务可创建、Succeeded 可 rearm，活跃任务保持原状，DeadLetter 使用已有重放命令。人工对账只接受安全 scan ID 和四个固定 scope，创建有界首任务；已存在的相同 scan/scope 不重置，避免擦除执行历史。

三类实际变化分别写入 `admin.upload.lease_release`、`admin.upload.cleanup_rebuild` 和 `admin.storage.reconcile`；业务更新/入队与操作日志必须在同一 PostgreSQL 事务提交。接口不接受任意 SQL、对象 key、存储前缀、游标或任务 payload，也不直接执行对象删除。

## 不变量与故障处理

| 故障点 | 持久结果 | 恢复方式 |
|---|---|---|
| 分片对象写入成功、DB 记录失败 | staging 孤儿对象 | 客户端幂等重试或对账清理 |
| 认领后、组装前退出 | `Finalizing` + 到期租约 | 有效租约期内重试拒绝；数据库时间判定到期后由新 owner 接管 |
| assembled 创建后、final 提升前退出 | 可识别且完整的 staging assembled 对象 | 有效租约期内重试拒绝；到期后的新 owner 按新状态版本安全重建，最终由会话清理任务删除 |
| final 创建后、DB 事务失败 | 无引用 final 候选 | 对账确认无引用后 GC，禁止即时盲删 |
| DB 事务成功、HTTP 响应丢失 | `Completed + completed_file_id`，首次进程可能尚未失效文件列表缓存 | 重复 complete 返回原文件并再次推进共享文件列表缓存代际 |
| DB 事务成功、staging 清理失败 | 已完成文件 + pending cleanup | Worker 重试，不影响文件可见性 |
| Blob GC 与秒传/复制竞争 | 未成功 GC 任务或已删除内容行 | 仅一方越过内容行/任务门禁；引用方冲突后重新查询/提升 |
| 上传预查复用后 Blob 被 GC | 旧 content_id 已不存在 | 最终事务返回冲突，重试后重新提升对象 |
| Worker 删除成功、任务完成写回失败 | 对象已不存在 | 重试删除按成功处理并完成任务 |

“认领后、组装前退出”必须由真实 API 进程故障注入验证：测试进程同时设置 `DISK_TEST_FAULT_INJECTION=1` 和精确的 `DISK_TEST_PAUSE_AFTER_FINALIZE_CLAIM_UPLOAD_ID` 后，仅目标 upload 在认领事务已提交、任何组装之前停顿。夹具观察到 PostgreSQL 中的 `Finalizing + lease_owner` 后强制杀死进程，不得通过直接改写任务状态或租约到期时间伪造恢复。两个环境变量均为测试专用，默认关闭，安全模式下无条件忽略。

“assembled 创建后、final 提升前退出”使用相同总开关与精确的 `DISK_TEST_PAUSE_AFTER_ASSEMBLY_UPLOAD_ID`。停顿点必须位于 `AssembleChunks` 成功返回之后、完成租约续租和任何查重、final 提升、最终事务之前。夹具必须先验证 assembled 对象内容完整且 final Blob、文件、内容引用和配额转换均未出现，再强制杀死 owner；有效租约内另一实例仍返回冲突，按 PostgreSQL 时间自然到期后以新状态版本安全重建并完成，最终只保留一个文件、一个内容引用、一次配额转换和一个 staging cleanup 任务。

“最终事务提交后、HTTP 响应前退出”使用相同总开关与精确的 `DISK_TEST_PAUSE_AFTER_FINALIZE_COMMIT_UPLOAD_ID`。停顿点必须位于最终事务协程成功返回之后、生命周期结果返回及 Redis 文件列表缓存失效之前。夹具先缓存不含目标文件的列表，再观察 PostgreSQL 已持久化 `Completed + completed_file_id`、租约已清空、分片已删除，且文件、内容引用、配额转换和 cleanup 任务各出现一次；此时缓存代际必须尚未推进。强制杀死 owner 后，另一实例无需等待租约即可重放同一 complete，返回相同文件并推进共享缓存代际；再次读取列表必须看到目标文件，所有数据库、配额、Blob 和任务副作用仍保持唯一。

发布回滚还必须在 S3-native staging/final 上独立验证该窗口：测试 bucket 开启版本控制，在 final 事务提交后记录规范 SHA-256 key 的唯一版本再杀死 owner。兼容实例重放同一 `upload_id` 后，版本 ID 必须不变、版本总数仍为 1、Delete Marker 为 0；数据库状态版本、完成尝试、文件、内容引用、配额转换和 cleanup 去重键均不得改变。随后只允许 Worker 执行 staging cleanup，final 对象不得由测试或运维脚本删除。客户端连接失败表示结果未知，不是补偿删除依据。

“续租期间数据库网络分区、旧 owner 恢复”由真实 TCP 转发夹具只隔离一个 API 与 PostgreSQL。测试使用总开关、精确的 `DISK_TEST_PAUSE_BEFORE_FINALIZE_TRANSACTION_UPLOAD_ID` 和一次性 release 文件，使目标请求在 Blob 晋升后的事务外续租已提交、最终事务 `BEGIN` 已建立而首条续租尚未发出时停顿；夹具先断开该 API 的双向数据库转发，再释放请求并确认旧请求的事务内续租流量已被阻塞。不得改写 `lease_expires_at`：等待 PostgreSQL 时间自然过期后，由直连数据库的另一 API 接管并完成；恢复转发后，旧请求必须在最终事务首条续租 CAS 上得到 `409 + 10004`，旧 API 进程保持存活并恢复 readiness。夹具必须精确对账新 owner 的 `completed_file_id`、状态版本、文件、内容引用、配额转换、分片清理、final Blob 和 staging cleanup 任务均未被旧请求改变。测试停顿点默认关闭且安全模式下无条件忽略，release 文件仅用于解除精确 upload 的测试停顿。

“Blob 删除成功、任务完成写回前退出”必须由真实 Worker 进程故障注入验证。测试进程同时设置 `DISK_TEST_FAULT_INJECTION=1` 和精确匹配 `storage_jobs.id` 的 `DISK_TEST_PAUSE_AFTER_BLOB_DELETE_JOB_ID`，停顿点位于 `DeleteBlob` 成功之后、删除 `file_contents`、解析对账发现和写回 `Succeeded` 之前。夹具观察到对象已缺失而零引用内容行、未解析 finding 与 `Running + owner` 任务仍存在后 `SIGKILL` owner；另一 Worker 在有效租约内不得接管，且不得直接改写 `locked_until`，只能等待 PostgreSQL 时间自然到期。接管后的第二次幂等删除必须把内容行删除、finding 解析和任务成功状态在同一事务提交，最终 `attempts=2` 且不遗留 owner 或租约。

任何路径都不得导致：

- 同一上传创建多个文件；
- reserved quota 被释放或转换两次；
- `file_contents.ref_count` 与文件引用数量永久失配；
- 一个失败事务删除另一个成功事务正在使用的 Blob；
- 进程退出后任务只能由原实例恢复。

## 进程内状态与定时器盘点

2026-07-19 对 `src/` 的 `runEvery`/`runAfter`、容器、锁、原子量和工作队列进行了基线盘点。后续新增同类状态必须更新本表。

| 位置 | 当前进程内状态/定时器 | 分类 | 分布式处理要求 |
|------|----------------------|------|------------------|
| `UploadService` | `m_upload_task_cache` 与 60 s 驱逐定时器 | 本地提示缓存 | 仅缓存任务几何等不可变数据；每次分片最终写仍以 PostgreSQL `InProgress` 条件为准。缓存可随进程丢失，不做跨实例失效协议 |
| `TokenService` | access/share 撤销 `ExpiryCache` 与 60 s 驱逐定时器 | 本地安全优化 | 删除“未撤销”负缓存，只正缓存已撤销；缓存未命中必须查询 Redis，Redis 错误 fail closed |
| `TokenService` | JWT CPU pool 的 active/total/peak 原子计数与指标定时器 | 本地观测 | 仅实例标签指标，可重置、可丢失；聚合由监控系统完成 |
| `AssemblyConcurrencyLimiter` | running 计数和本机最大并发 | 本地容量保护 | 接口不接收或保存 `upload_id`；调用方必须先取得 PostgreSQL 租约，再占本机执行槽。跨实例互斥和同任务排他只认数据库 |
| `LocalFileStorage` / `LocalBlobStore` / `S3ObjectStorage` | `ConcurrentTaskQueue`；Blob/S3 删除路径另有在途 awaiter 原子标志和 `runAfter` I/O 超时 | 本地执行资源 | 仅承载当前调用，不保存待办业务事实；需要跨退出恢复的工作先写入 `storage_jobs`；暂存实现不保留任意路径删除入口 |
| `ScheduledTasks` | 每小时 `RunExpiredCleanupOnce()` | 集群唯一业务任务 | 从 API 移除；Worker 通过持久周期任务/数据库唯一门控生成扫描，一个周期只产生一次逻辑任务 |
| `ApplicationContext`、`StorageMgr`、`BlobStoreMgr`、`ConfigMgr` | 单例服务指针和启动后只读配置 | 本地依赖装配 | 每个进程独立构造，不能存放任务所有权或业务状态；角色与 instance ID 在启动时冻结 |
| Drogon/存储回调 | `queueInLoop` 恢复协程 | 本地调度细节 | 只恢复当前请求；不能作为完成、清理或重试已持久化的证明 |

Redis 文件列表缓存本身是共享、可重建状态，不属于进程内状态；其每用户版本递增失败只造成 TTL 内的短暂陈旧，不得影响数据库写入正确性。除此之外，源码中用于 DTO 白名单和错误码映射的静态只读容器不属于可变业务状态。

## 备选方案

### 方案 A：负载均衡 sticky session + 本地暂存

**拒绝作为最终方案。** 实现成本低，但节点退出会中断进行中上传，扩缩容需要迁移本地状态，也无法解决跨实例完成和清理竞态。仅可作为切换期间处理旧 local 任务的短期措施。

### 方案 B：NFS/CephFS 共享暂存

**拒绝作为默认方案。** 它可以消除分片节点亲和，但仍需要跨实例状态机和租约，并引入共享文件系统性能、锁和运维故障域。对象存储已经是项目支持的生产依赖，统一暂存可减少存储模型数量。

### 方案 C：Redis 分布式锁

**拒绝作为上传所有权来源。** 上传终态和配额在 PostgreSQL；把所有权放入 Redis 会产生双系统事务和锁丢失语义。Redis 可以承担限流和可重建缓存，但持久状态迁移使用 PostgreSQL CAS/租约。

### 方案 D：立即拆分微服务

**拒绝。** 当前主要问题是共享状态、外部副作用和故障恢复，而不是代码发布边界。提前拆分会增加网络调用、分布式事务和部署复杂度，不会自动解决现有竞态。

### 方案 E：客户端直接 multipart 上传 final key

**暂缓。** 该方案可以减少 API 带宽，但会改变客户端合同，并且不能直接继承当前整文件 MD5/SHA-256 校验语义。完成本 ADR 的服务端代理路径后，再根据监控数据设计版本化 API。

## 影响

### 正面影响

- API 实例可在无粘性会话下横向扩容。
- 上传与清理在实例退出后可以接管。
- 终态、配额、内容引用和外部副作用具有可证明的幂等边界。
- 孤儿对象和失败任务可观测、可重试、可对账。
- 保持现有客户端 API，降低第一阶段迁移风险。

### 成本与风险

- 每个上传分片至少包含一次对象存储写入，完成阶段还需读取和组装，增加 S3 请求与网络成本。
- 新写 final Blob 使用 SHA-256 key，现有 MD5 key 需要长期按 `storage_path` 兼容或执行独立迁移。
- PostgreSQL 新增高频状态更新和任务认领，需要连接预算、索引和 vacuum 监控。
- 同步完成请求仍可能较长，必须配置代理超时、租约续期和有界内存。
- S3 兼容实现对条件写、multipart 和 server-side copy 的行为需要在 MinIO 与目标生产服务分别验证。

## 迁移顺序

1. 以 expand-only migration 增加上传状态、租约、分片元数据和任务表。
2. 发布能读取旧任务并写入新字段的兼容版本，默认仍使用 local staging。
3. 部署 S3 staging 和 Worker，先 dry-run/小流量验证。
4. 仅对新上传启用 S3 staging，并把 backend 固化到每个任务。
5. 旧 local 任务完成、取消或过期后，关闭生产 local staging 创建。
6. 启动第二个 API、关闭 sticky session并进行随机路由验收。
7. 关闭 API 内集群级定时任务，由 Worker 独占持久任务。
8. 经过至少一个完整过期/回收周期和全量对账后，执行 contract migration 并删除过渡代码。

第 4 步的新任务流量只能按 `10% -> 25% -> 50% -> 100%` 相邻扩大。仓库以
`deploy/staging-rollout-plan.json` 固定每一档的上一已通过档位、最小观测窗口与样本、全量
停止条件、责任角色、预演/执行/回退命令和只读校验查询。目标变更单必须把发布、回滚、数据库
校验和存储校验角色绑定到实际值班人；仓库角色名或占位符不是指派。任一停止条件、证据缺失、
只读查询失败或跨档请求都拒绝扩大；回退只改变之后的 upload init 权重，不改写既有任务或删除对象。

第 8 步的“完整周期”是 data-to-contract 准入门禁，不是从某次发布开始机械等待一个 TTL：

- 只有不兼容旧进程全部退出、生产 API 只创建 S3 staging 任务、local 非终态任务与未完成 local cleanup 均为零、逐原卷扫描无遗留后，才能记录数据库时间 `T_s3_only` 并开始观察。
- 在 `T_s3_only` 之后创建至少一个真实 S3 分片上传探针，不得更新其 `expires_at` 或直接改状态。必须等 PostgreSQL `NOW()` 越过任务固化的 `expires_at`，再等一个晚于该时点且成功的小时级 `expire_uploads` 扫描；随后确认 `Expired`、唯一 cleanup 成功、分片元数据删除、S3 session prefix 为空且 reserved 配额释放。
- 回收成功后还必须完成一个新的 S3 上传并验证下载/配额，再用新的 scan ID 跑完 `contents`、`users`、`staging`、`final` 四个范围的全量对账。活跃上传/租约、待处理或死信任务、空定位/分片兼容字段、未解决 finding 或配额差异任一非零，都重新开始调查而不是进入 contract。
- 仓库集成测试可以把 TTL 缩短，并在任务自然到期后才准入 Worker，以利用 Worker 的首次播种压缩测试时长；生产 Worker 持续运行时，仍必须等待真实配置 TTL 以及其后一个不同的小时扫描窗口。
- 通过门禁只产生可审阅的 contract-readiness 证据；V005 的具体 DDL、备份、恢复演练、应用兼容性和独立审批仍需另行完成。contract migration 永远不能充当紧急回滚。

expand 阶段的新旧二进制混跑只承诺以下兼容窗口：

- V003/V004 执行时，V002 旧进程可以保持在线；新增列的默认值必须使旧进程在迁移后继续创建、写入和完成 local 任务。V002 的任务创建 SQL 使用 `INSERT ... RETURNING *`，V003 增列会改变已缓存 prepared plan 的结果类型；迁移后、恢复该实例上传流量前必须受控回收其全部 PostgreSQL 连接（或滚动重启旧实例），不能把 schema 字段兼容误认为旧连接计划也兼容。
- 旧进程创建的任务和分片可以由兼容新版本接管；`staging_backend='local'`、可空 `staging_prefix`、可空分片对象元数据以及旧 `<upload_id>/<chunk_index>.chunk` 路径共同构成该接管合同。
- 只要仍有旧进程接收上传流量，负载均衡就必须按上传会话保持实例亲和，且所有新任务继续使用 local staging。新版本写入不可变 `chunks/<index>-<md5>.part` 后，不承诺旧版本能够反向完成该任务。V002 下载还会按 MD5 重建 final 路径，不能读取当前版本新建的 SHA-256 Blob；一旦当前版本开始完成新文件，所有者和分享 Blob 下载必须统一路由到当前版本。不得在此窗口启用 S3 staging、无粘性上传路由或把 `Finalizing`/S3 任务交给旧版本。
- 只有旧进程完全退出、旧 local 任务完成/取消/过期并通过对账后，才进入无粘性多实例验收。该过渡亲和不改变最终架构拒绝 sticky session 的决定。

可执行验收固定使用 V003 引入前的最后一个后端版本
`6ed0afefb9ae6614ac5cc735b237dead28d10ecb` 作为 V002 二进制基线，避免“旧版本”随分支历史漂移。验收在迁移后回收隔离数据库中的旧连接，并断言旧进程 PID 不变、连接池自动重连后继续处理请求。

local 暂存排空属于 data 阶段，不是把节点本地目录改造成共享存储：

- V002 的 `temp_path` 仅保存逻辑 upload ID；V003 的 local `staging_prefix` 也不保存主机或卷身份。数据库可以恢复任务状态和相对对象身份，但无法证明另一节点挂载了原暂存卷。发布前必须逐节点扫描目录并建立 `upload_id -> 原节点/卷` 清单；缺少归属或 DB/目录不一致的任务先冻结并告警。
- 原节点可以原地升级为兼容当前版本，只要 `temp_upload_path` 仍指向同一持久卷。该节点负责让旧 `InProgress` 任务完成、取消或过期；完成/取消请求和维护操作不得发往未挂载原卷的实例。测试中多个进程使用同一路径只是在模拟同一原卷，不代表生产全集群采用共享 POSIX 暂存。
- local 任务排空期间只允许一个挂载原卷的迁移 Worker 认领 `expire_uploads` 与 `staging_cleanup`。通用 Worker 池不得同时启动，因为当前任务 payload 不含节点 owner，未挂载原卷的 Worker 会把“本地路径不存在”视为幂等清理成功，留下原卷孤儿。
- 排空验收必须同时满足：local 非终态任务数为零、相关 cleanup job 成功、原卷会话目录/组装文件不存在、`storage_reserved` 已释放或转换、已完成文件可下载。此后才能删除节点路由清单、扩展 Worker 池并启用无粘性上传。

紧急回滚不删除 expand schema。为此新增独立的启动期布尔配置
`upload_task_creation_enabled`（环境覆盖为 `DISK_UPLOAD_TASK_CREATION_ENABLED`，默认 `true`）。
它不是 staging backend 选择器：关闭后，初始化流程仍先解析秒传和同用户同 hash 的断点续传；只有确实需要
创建新任务时才在配额预留和 `upload_tasks` INSERT 之前返回 `503 + 50012
UploadTaskCreationDisabled`。既有任务的 init resume、chunk、complete、cancel 和 Worker 清理继续依据行内
backend/prefix 执行，不允许把新请求回退为 local 任务，也不修改任何已持久化描述符。

该配置只被包含它的兼容版本执行，旧二进制会忽略未知环境变量，因此关闭开关不等于旧版本获得了新 schema
兼容能力。回滚必须先让所有仍承接 upload init 的兼容 API 以开关关闭状态完成替换，并用一个全新非秒传 hash
验证 `503/50012`、任务数和 `storage_reserved` 均不变化；然后保持 S3、`Finalizing` 及其他旧版本未知状态的
全部生命周期流量只进入兼容 API/Worker，直至它们达到终态或按运维流程冻结。任一旧版本不得接收这些任务，
也不得用批量 UPDATE 把 S3 描述符改成 local。只有该隔离边界已验证，才可继续评估旧应用回滚。

数据库处置固定为 `schema_action=preserve_expand`、`contract_migration_allowed=false`。历史
`*_rollback.sql` 不是紧急回滚工具，也不是生产 data-to-contract 脚本；它们只允许在对应新能力尚未
启用时，经 `scripts/reverse-expand-migration.sh` 执行迁移撤销。入口必须收到精确
`pre_activation_reversal` 上下文、显式批准、变更单和 64 位 readiness 证据 SHA-256；每个 SQL
在首条 DDL 前还会独立复核相同会话参数。缺失、伪造为 `emergency_application_rollback` 或数据门禁失败
都在事务内停止并保留 schema/迁移账本。生产激活后的 contract 必须新增独立 DDL、恢复演练、负责人、
证据和审批，不能复用历史 rollback SQL。

`Finalizing` 的回滚处置不增加临时状态也不逆转状态机，只有 drain 和 freeze 两种结果。
drain 是在新任务截止后让兼容处理面将 `InProgress/Finalizing` 收敛到终态，然后在上传入口
关闭期间证明两者都为零。freeze 是先由受信网关拦截所有 upload 生命周期路径，再等待每个
兼容 API 的在途业务请求为零，最后在只读重复读事务中对活动任务描述符生成 SHA-256。
freeze 不立即截断、清空或续期租约；有效租约的原 owner 已无在途请求时，它只会按 PostgreSQL
时间自然过期，之后仍只能由兼容 complete 通过既有 CAS 接管。

冻结证据始终将 `old_release_upload_route_allowed` 固定为 false；它只证明回滚前的上传处理面
已隔离，不证明旧版本可以读取新 SHA-256 Blob、S3 对象或其他新 schema。入口重开必须先恢复兼容
API 池；禁止把 `Finalizing` 改回 `InProgress`、清空租约或写成 `Failed` 来绕过门禁。

---

## 验收条件

- 两个 API 实例在无粘性路由下完成初始化、交叉分片、完成、取消和下载。
- 100 个并发重复完成请求只产生一个文件、一次配额转换和一个内容引用增量。
- API/Worker 在关键故障点退出后，任务在约定 RTO 内被重试或接管。
- 两个 Worker 并发运行不产生重复业务副作用。
- DB/对象不一致、过期租约、任务积压和 dead-letter 均有指标、告警和运维路径。
- 完整单元、PostgreSQL 集成、MinIO、多实例、故障注入、迁移和压力测试通过。
