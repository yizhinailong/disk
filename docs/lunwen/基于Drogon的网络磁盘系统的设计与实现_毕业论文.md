# 基于Drogon的网络磁盘系统的设计与实现

## 摘　要

学习、办公和项目开发会产生大量文档、图片、代码包和临时资料，文件分散后查找、备份和跨设备访问都不方便。公有云网盘虽然易用，但数据托管、容量、带宽和平台规则都受第三方限制。针对个人服务器和小型团队的数据自主管理需求，本文设计并实现了一套基于Drogon的私有化网络磁盘系统。

系统将后端服务和桌面客户端分开来进行实现，后端利用C++23和Drogon处理接口、文件传输、认证鉴权和后台管理，Qt 6或QML客户端通过RESTful API与后端进行交互，用户信息、文件元数据、目录结构、上传任务、分享记录、回收站数据、操作日志都会被写入MySQL数据库，令牌、登录失败计数、分享访问状态和限流计数会被存入Redis，真实文件按照内容哈希值保存到本地目录中。账号认证、文件管理、分片上传、断点续传、秒传、Range下载、外链分享、回收站和后台管理等流程都已实现。

运行和测试结果显示，主要业务流程已经走通。普通用户能够整理文件、处理传输任务并创建分享，管理员能够查看用户、分享、日志和系统状态。注册登录、文件传输、目录管理、分享访问和权限控制等测试结果与设计要求基本一致。

关键词：网络磁盘；文件管理；Drogon；C++23；RESTful API

---

## ABSTRACT

Digital materials from study, work, and projects are often scattered across devices, making management and access inconvenient. Public cloud drives are easy to use, but data hosting, capacity, bandwidth, and service rules depend on third-party platforms. This thesis designs and implements a private network disk system based on Drogon for personal servers and small teams.

The system separates the backend service from the desktop client. The backend uses C++23 and Drogon for APIs, file transfer, authentication, and management, while the Qt 6/QML client accesses it through RESTful APIs. MySQL stores users, file metadata, directories, upload tasks, shares, trash records, and logs; Redis stores tokens, login failure counters, share states, and rate-limiting counters. File entities are stored locally by content hash. The system implements authentication, file management, chunked and resumable upload, instant deduplication, Range download, sharing, trash handling, and backend management.

Operation and test results show that the system has completed its main workflows. Regular users can manage files, transfers, and shares, while administrators can view users, shares, logs, and system status. Registration, file transfer, directory management, share access, and permission control meet the design requirements.

KEYWORDS: Network Disk; File Management; Drogon; C++23; RESTful API

## 前　言

学习、办公和日常生活中会不断产生课程文档、项目代码、图片、视频等资料，这些资料分散保存后查找和备份都不方便，网络磁盘比本地硬盘更有利于跨设备访问和共享，不过公有云网盘在数据托管、容量、带宽和平台规则上仍然受到第三方的限制，个人用户和小型团队仍然需要拥有私有化的网盘服务。

网盘的日常操作主要包括上传、下载、整理目录、搜索和分享，大文件传输在遇到网络波动时，重新开始会消耗时间，因此断点续传是基本要求，如果分享链接没有有效期、访问密码和权限控制，也会增加后续管理成本。

管理员日常维护也需要统一入口。账号数量、存储占用、数据库连接、Redis状态和磁盘空间如果分散查看，排查问题会比较费时。因此，本文在实现普通用户文件管理的同时，也加入后台管理、操作日志和系统状态查询。

后端采用C++23和Drogon，主要考虑上传、下载对磁盘和网络I/O依赖较重。Drogon底层通过epoll（macOS/FreeBSD下为kqueue）处理网络事件，并支持协程化请求，用于这类等待时间较长的接口较合适。系统用MySQL保存元数据，Redis保存令牌和限流等短时状态，文件实体放在本地内容寻址目录中。

本文按照需求分析、系统设计、数据库设计、功能实现和测试验证的顺序展开。课题面向中小型私有化文件服务场景，验证Drogon、MySQL和Redis组合完成网络磁盘业务流程的可行性。

## 第1章 绪论

### 1.1研究背景

近几年，个人数字内容增长较快，在线存储的使用频率也明显提高，云存储确实方便了资料整理和团队协作，但是公有云盘仍然绕不开几个限制：文件托管在第三方服务器上，隐私数据和商业资料的保护存在不确定性，平台规则会影响容量、速度和服务策略，拥有合规要求的团队把数据存放在自有基础设施里会更加稳妥。

所以，自建私有化网盘拥有清晰的使用场景，文件实体和元数据保存在自有服务器上，用户可以自行配置数据位置、访问策略、存储空间和带宽，但是，将上传下载、目录管理、分享、权限控制和后台维护都进行完整处理，并保持部署负担处于可控状态，这并不简单，本文使用C++和Drogon Web模式来实现该系统，主要为了验证该路线在文件服务场景上的可行性。

### 1.2研究意义

本课题面向私有化网络磁盘场景，设计并实现一个文件服务系统。系统把文件管理、目录组织、大文件上传、文件分享和管理员后台整合到同一套后端服务中，并使用C++与Drogon承担文件传输和接口处理任务，是一个可部署、可运行、可测试的工程样例。

系统主要面向个人开发者、高校师生和中小团队，并且可以提供相应服务，文件上传、目录整理、检索和分享功能都集中在同一个客户端界面上，配额和已用空间信息直接显示，用户不用在不同工具之间进行切换，管理员端拥有账号管理、存储统计和系统状态入口，该页面降低了日常维护中对数据库客户端、Redis命令行和磁盘工具的依赖。

本文在工程实践中将C++系统编程、异步网络I/O、Web框架、关系型数据库、缓存状态和RESTful接口集成在一个项目中进行验证，实现过程不仅要完成接口调用，还要处理认证、文件传输、目录结构、权限边界和桌面客户端交互之间的配合，特别是上传取消、文件删除、分享失效等场景下的数据状态一致性。

### 1.3国内外研究现状

云存储和网络磁盘已经有了很多研究、工程实践，但是，如果把范围限定在基于C++Web框架的私有化网络磁盘系统上，可以直接参考的完整案例并不多。

国外云存储起步较早，分布式文件系统、对象存储和数据去重已有较多成熟方案。GFS、Amazon S3和OpenStack Swift主要面向数据中心级水平扩展，直接用于单机私有化部署会显得较重。Nextcloud和ownCloud功能较完整，但对服务器配置和运行性能有一定要求；SeaweedFS、MinIO等项目更偏向对象存储基础设施。

国内公有云网盘发展较快，百度网盘、阿里云盘等产品让文件秒传、内容去重和传输加速逐渐成为用户熟悉的能力。教学和毕业设计项目中的自建网盘，多采用Spring Boot、Django或Flask配合数据库和本地文件系统实现，基本功能一般可以满足演示需求，但高并发传输和资源占用控制仍有改进空间。用C++ Web框架贯通网盘主要业务的公开案例并不多。

已有研究和系统实践可以为云存储架构和私有网盘开发提供参考，但在中小规模、私有化部署和C++后端这几个条件同时存在时，仍需要结合具体工程进行验证。本文不以替代成熟云存储系统为目标，而是尝试给出一种面向单机或小团队环境的网络磁盘实现路径。

### 1.4本文的组织结构

本文主要针对私有化网络磁盘系统进行研究，重点解决文件存储访问、大文件传输、目录树管理、分享控制、后台运维等问题，课题目标并不是要复刻大型云盘，而是要完成一个普通用户和管理员都可以使用的网盘平台，并且要验证其部署、演示和维护是否可以做到。

用户侧接口具有账号认证、个人资料、文件和目录管理、分片上传、断点续传、秒传、Range下载、外链分享和回收站处理的功能，管理员侧主要进行维护工作，包括用户管理、存储统计、分享管理、系统概览和状态查询。

文件上传和下载请求包括较多磁盘与网络等待，后端使用Drogon异步非阻塞I/O和C++协程模型进行处理，上传任务和分片状态被写入数据库，客户端断线后只需要补传缺失的分片，文件内容哈希和引用计数用来进行秒传和去重，防止相同内容重复落盘，本文将令牌、限流和登录失败次数等短时状态交由Redis进行保存，从而减轻高频状态变化给MySQL带来的压力。

系统安全设计主要围绕几个边界处理，普通用户只能访问自己名下的文件和目录，管理员接口除了校验登录状态外，也会检查用户角色，公开分享访问不会直接复用用户的JWT，而是依靠分享短码、可选密码、短期分享令牌和有效期来共同限制访问范围，用户密码通过Argon2id算法进行哈希存储，登录失败计数和短时锁定机制用来降低暴力破解造成的风险。

后端按照认证、用户、文件、目录、分享、回收站、运维统计和操作日志这些模块进行拆分，控制器对请求进行解析并对响应进行转换，主要业务判断放在服务层。存储层把上传暂存与最终Blob分开：分片和组装文件保留在本地临时目录，最终内容既可使用本地文件系统，也可选择S3/MinIO兼容对象存储；文件版本历史、WebDAV接口和缩略图预览仍可在现有模块上继续扩展。

## 第2章 相关技术分析

### 2.1 Drogon框架与C++23协程

Drogon是面向HTTP服务的C++ Web框架，底层基于epoll（macOS/FreeBSD下为kqueue）处理非阻塞I/O。文件上传和下载以磁盘读写、网络等待为主，阻塞模型容易长时间占用线程。本系统采用C++23，并结合HttpController、HttpCoroFilter和drogon::Task组织控制器、过滤器和服务层逻辑；业务返回值采用Result<T>表达成功或失败状态。

### 2.2 MySQL数据库

MySQL属于一种常用的关系型数据库，该数据库具有比较稳定的特点，并且积累了比较多的数据，适合用来保存中小规模业务系统当中的长期数据，本文将账号、内容哈希、文件元数据、目录树、上传任务、分片记录、回收站、分享和操作日志等长期数据写入MySQL，文件列表、目录树遍历、秒传查重、配额统计、分享访问这些操作的查询频率比较高，所以表结构中对应地设置了联合索引、全文索引和唯一约束。

### 2.3 Redis缓存与状态管理

Redis属于内存型键值数据库，比较适合用来存放生命周期短且访问频率高的状态，该系统将Refresh Token、Access Token黑名单、登录失败计数、分享访问令牌、密码尝试次数和接口限流计数都存入Redis，经过这样的处理，那些容易过期或者变化频繁的数据就不需要写入MySQL，鉴权、限流和安全控制逻辑也更容易进行区分。

### 2.4 JWT身份鉴权机制

JWT（JSON Web Token）用于在各方之间传递身份认证信息。本系统登录成功后签发Access Token与Refresh Token，普通业务请求通过Authorization请求头携带访问令牌，令牌刷新和登出依赖Redis中的刷新令牌与黑名单状态；公开分享访问使用独立分享令牌，并通过X-Share-Token请求头传递。

### 2.5 CMake构建工具与安全基础库

CMake是跨平台构建工具，也是Drogon项目中常用的构建方式。本系统使用CMakeLists.txt、CMakePresets.json和vcpkg manifest管理依赖、构建预设和第三方库，使Linux与Windows下的编译、测试和部署步骤保持一致。

### 2.6 Qt框架与QML

Qt是常用的跨平台C++应用程序开发框架。本系统桌面客户端基于Qt 6实现，使用Qt Network访问后端RESTful API，处理分片上传、断点下载和JSON解析。界面层采用QML和Qt Quick Controls 2编写文件列表、目录导航、传输进度、分享管理和后台页面；C++侧保存网络请求与业务状态，两者通过属性绑定和信号槽连接。

## 第3章 需求分析

### 3.1系统需求概述

在建设私有化网络磁盘系统之前，需要从技术条件、经济成本和使用流程三个方面分析系统建设的可行性。结合课题目标和已选技术栈来看，本系统具备落地实现的基础条件。

技术方面，C++23、Drogon、MySQL和Redis可以覆盖本课题主要需求。Drogon提供HTTP路由、过滤器、控制器、协程任务、异步数据库访问和配置管理；MySQL保存用户、文件、目录、分享和日志等结构化数据；Redis保存令牌、限流和登录失败计数等短期状态。JWT鉴权、Argon2id密码哈希以及CMake/vcpkg构建体系也都有成熟库可用。

经济可行性方面，本系统所用软件和运行环境都有开源免费版本。普通个人计算机或低配云服务器即可完成编译、部署和演示，课题成本主要集中在开发、调试和测试时间上。

在使用流程上，系统主要面向普通用户、管理员和受限访客这三类对象，后端接口包括账号认证、文件上传下载、目录管理、分享、回收站、日志和运维统计功能，桌面客户端通过RESTful API进行接入。

### 3.2系统功能需求分析

私有化网络磁盘系统的需求主要来自普通用户和管理员两个方面。普通用户关注文件是否能够稳定上传、是否便于整理、是否可以在需要时进行分享；管理员则更加关注账号、存储资源和系统运行状态是否可控。围绕这两类角色，系统需求可以分为功能需求和非功能需求两个部分。

#### 3.2.1账号与用户模块需求分析

账号和用户模块主要负责进行身份识别，并且对登录状态进行维护，普通用户可以进行注册、登录、刷新令牌和登出操作，也可以查询或者修改资料、密码和存储空间，在注册阶段，系统会对用户名和邮箱进行检查，以确认它们是否已经被占用，在登录阶段，系统会对密码、账号状态和失败次数进行校验，认证完成后，后端将发送令牌，后续业务接口能够利用该令牌完成鉴权并进行续期。

管理员侧账号功能主要服务平台维护。用户列表查询、关键字与状态筛选、详情查看、存储使用量查询、可用空间调整、账号禁用或启用、角色变更和软删除都放在这一部分。由于这些操作会直接改变账号状态和权限边界，所有管理员接口都先经过普通JWT鉴权，再进行管理员角色鉴权。

#### 3.2.2文件与目录模块需求分析

文件模块包括上传、访问、整理和删除这些主要部分，文件和目录应当进行混合分页展示，并且提供按照名称进行搜索、对详情进行查询、进行重命名、对文件进行批量移动、对文件进行批量复制、执行软删除等操作，除了普通完整下载，本文也加入了HTTP Range断点下载功能，客户端在网络环境不稳定的条件下可以接着已有进度继续传输数据。

上传功能在文件模块中发生的状态变化最多，上传过程包括初始化、分片传输、完成合并和取消四个阶段，进度通过上传任务和分片记录进行保存，用来对断点续传进行支持，如果服务器内部已经存在相同内容的文件，后端使用内容哈希生成逻辑文件记录，就可以实现秒传，不需要重复接收和保存物理文件，目录模块也提供多级目录创建、目录树查询和面包屑路径查询功能，并依靠约束来防止同一用户在同一父目录下建立同名目录。

#### 3.2.3分享、回收站与管理模块需求分析

分享模块让用户可以为文件或目录生成外链，并且能够设置有效期、访问密码、查看或者下载权限，未登录访客在打开分享功能时，后端会先对分享短码、状态、有效期、访问密码进行校验，校验通过之后再签发短期分享访问令牌，访客在浏览分享内容或下载文件的过程中，系统通过独立的分享令牌来进行鉴权操作，以此防止公开访问流程同登录用户的JWT发生混用。

回收站模块主要负责对误删除的文件进行恢复，用户在删除文件或目录时，系统不会立刻清除物理内容，而是先把项目放入回收站，同时保存原路径、原所属目录、项目类型、内容引用和恢复所需数据，用户可以查看回收站列表，并且支持批量恢复、彻底删除或清空回收站，管理员和运维模块拥有对全局存储进行统计、对分享记录进行查看、对违规分享进行强制取消、对系统概览、数据库状态、Redis状态和磁盘空间状态进行查询等功能。

#### 3.2.4系统用例分析

该系统主要包括普通用户和管理员这两种账号角色，并且也考虑未登录访客对分享的公开场景进行访问，普通用户在用户端完成注册和登录操作，进行文件上传和下载，对目录进行管理和分享文件，访客可以通过分享短码、访问密码和分享令牌来浏览或下载授权内容，管理员通过后台进行用户管理，查看存储统计，并且进行系统参数配置。

普通用户在使用过程中主要围绕账号认证、个人资料维护、存储空间查看、文件上传下载、目录管理、搜索、重命名、移动复制、回收站处理、分享创建与访问、将分享内容保存到个人网盘这些功能来进行，管理员主要维护入口，包括用户列表和详情查看、账号状态调整、角色调整、空间设置、软删除用户、全局存储统计、分享管理、操作日志、系统概览和系统状态查看。

### 3.3系统非功能需求分析

#### 3.3.1系统性能需求分析

系统需适应单机私有化部署环境，并借助Drogon异步I/O处理文件传输。文件列表、目录导航和配额查询应尽快返回；上传和下载采用流式处理控制内存占用。上传任务和分片状态需要持久化，才能在中断后继续补传。

#### 3.3.2系统安全性与可维护性需求分析

系统需要对不同用户的文件资源严格隔离，普通用户只能访问自己名下的文件和目录，不能通过接口越权访问或下载他人文件；管理员接口需要单独鉴权，普通用户令牌无法访问管理员功能。文件分享链接需要使用随机短码、可选访问密码、有效期和短期分享访问令牌共同控制公开访问范围。用户密码必须经过安全哈希后存储，不得以明文形式保存在数据库中。

在可维护性方面，后端按照认证、用户、文件、目录、分享、回收站、管理员、日志和系统状态等模块进行划分，控制器对请求和响应进行处理，业务判断安排在服务层，数据库字段和约束需要保持清晰，以便于后续进行调整。

#### 3.3.3数据字典

该系统的主要业务数据实体包括用户信息、文件正文数据、文件元数据、目录结构信息、上传任务记录、上传分片数据、回收站条目、分享记录、分享文件关联关系和操作日志这十种类型。

用户信息（users）记录账号凭据、个人资料、登录安全状态和存储配额，是登录鉴权、文件归属判断和存储限额控制的依据。主要字段包括用户ID、用户名、邮箱、密码哈希、昵称、头像、存储配额、已用存储、预占用存储、账号状态、角色、失败登录次数、锁定时间、最后登录信息以及创建、更新时间。

文件内容记录物理文件索引，支持秒传去重和内容寻址，字段有内容ID、MD5、SHA256、大小、存储路径、MIME类型、引用计数和创建时间，多个用户文件能够指向同一个内容对象，这样可以防止数据出现重复存储。

文件元数据记录了用户视角下的文件描述，并且不会保存二进制内容，字段包括文件ID、用户ID、内容ID、文件类ID、文件名、大小、MIME类型、路径、收藏标记、下载次数和时间信息，系统会对文件列表、详情和权限进行判断，这些操作会读取该表。

目录信息（folders）维护用户目录树，支撑目录导航和路径组织。字段包括目录ID、用户ID、父目录ID、名称、路径、深度、子项数量和时间信息。父目录ID用于表示目录之间的父子关系。

上传任务（upload_tasks）用于分片上传和断点续传，记录任务状态、目标文件夹、文件名、大小、MD5、分片数量、预占用字节、临时路径和过期时间。上传分片（upload_task_chunks）以任务ID和分片索引作为联合主键，标记已上传分片。

回收站记录记录被软删除文件或目录的恢复信息，字段有记录ID、用户ID、项目类型、原项目ID、名称、大小、内容ID、原文件夹、原路径、数据备份、删除时间和过期时间，系统在对误删项目进行恢复时会读取这些数据，在进行彻底删除时会扣减引用计数，并且按照需要释放物理存储。

分享记录（shares）保存分享ID、短码、分享者、密码哈希、权限、访问和下载次数、状态及过期时间。分享文件关联（share_files）记录分享包含的文件或目录，使一个分享可关联多个项目。

操作日志operation_logs记录上传、下载、删除和分享等主要操作，字段包括用户、操作类型、目标对象、IP地址、客户端信息和创建时间，便于管理员对问题进行排查。

这些数据对象覆盖了系统主要业务信息。

## 第4章 系统设计

### 4.1系统架构设计

系统采用后端服务与桌面客户端分离的结构进行设计。后端通过RESTful HTTP接口提供认证、文件、目录、分享、回收站、日志和管理等能力，桌面端使用Qt/QML编写普通用户、访客和管理员界面，并通过统一网络层调用后端接口。该结构可以降低界面层和服务层之间的耦合程度，也便于后端接口脱离客户端进行单独测试。

后端内部划分为客户端接入层、过滤器层、控制器层、服务层、数据存储层，客户端发送HTTP请求，过滤器对JWT鉴权、管理员鉴权、分享令牌鉴权和接口限流进行处理，控制器会对请求进行解析，并且组织响应，服务层主要负责进行认证、用户、文件、目录、分享、回收站、管理员、日志、健康检查、系统信息等业务处理，数据存储层主要包括PostgreSQL、Redis、本地上传暂存和可配置的本地或S3/MinIO最终Blob存储，它们分别用来存放结构化业务数据、短生命周期状态、上传中间产物和内容对象。

#### 4.3.1用户认证模块设计

用户认证模块对注册、登录、令牌刷新、登出和接口鉴权进行处理，注册过程中，后端会对用户名和邮箱的唯一性进行校验，并利用Argon2id生成密码哈希，同时也会把默认配额写入到数据库中，在用户登录时，服务层会检查账号的状态、锁定时间、密码哈希，认证通过后系统签发令牌并且把令牌写入Redis。

JWT过滤器位于认证模块和业务控制器之间，业务请求在携带访问令牌之后，过滤器会对签名、过期时间和黑名单状态进行验证，然后把用户ID、用户名和角色写入到请求上下文中，管理员接口也要通过管理员鉴权过滤器进行处理，Refresh Token被存储在Redis数据库中，系统在进行刷新时会进行轮换操作，用户在登出时会删除刷新令牌，系统也把当前访问令牌加入黑名单中。

#### 4.3.2文件与目录模块设计

（1）文件管理模块

文件管理模块覆盖普通用户最常用的列表、搜索、上传、下载、重命名、移动、复制和删除等操作。后端由FileController暴露/api/file/* 系列接口，控制器处理请求解析和响应转换，具体业务判断交给FileService完成。

文件列表接口按照用户ID、目录ID、类型筛选、排序字段和分页参数对files与folders表进行查询，然后把当前目录下的文件和文件夹整理成统一列表并返回，搜索功能主要依靠文件名和目录名索引，可以按照关键词、类型和目录范围来进行检索，文件详情接口除了返回元数据，也返回面包屑路径，客户端根据该路径建立导航视图。

文件变更操作主要关注名称、路径和内容引用边界，重命名操作会检查名称长度、非法字符、保留名称和目录冲突，移动目录操作不可以将目标设为自身或子目录，复制文件会对file_contents内容对象进行复用，并且增加引用计数，普通删除只是把记录写入trash表，并且从正常列表里移除，系统在执行彻底删除操作时会减少引用计数并清理物理文件。

（2）目录管理模块

目录管理模块对用户的多级目录进行维护，folders表包括目录名称、父目录ID、完整路径、深度和子项数量，根目录使用parent_id=0表示，在创建目录时，后端先确认父目录归属，再利用唯一约束来防止同级目录出现重名。

目录树接口按照父子关系把目录层级返回，面包屑接口把根目录到指定目录的路径返回，服务层在建立目录树时限制深度以防止异常循环，并且在生成面包屑时检查重复节点，目录删除操作会统一进入回收站流程。

（3）文件上传模块

文件上传使用统一的分片流程，分片大小默认是5MB，包括初始化、分片传输、完成合并和取消这四个阶段，初始化请求会携带文件名、大小、目标目录和MD5信息，后端首先对配额进行检查，然后根据MD5值查询file_contents表，如果系统中已经存在相同内容的对象，服务端会直接建立files记录并把引用计数增加，上传操作在初始化阶段完成，也就是秒传。

文件分享模块会将用户自己拥有的文件或者目录生成成一个外链，供其他人进行访问，后端在创建分享时会在shares表中记录分享短码、分享者ID、可选访问密码哈希、权限类型、有效期和状态，并且在share_files表中保存被分享文件或目录的关联关系，分享权限包括查看和下载两种，分享状态有有效、取消和过期三种情况。

访客通过短码和可选密码对访问接口进行调用，在公开访问分享时，后端对状态、有效期和密码进行校验，校验成功后会签发短期分享令牌，当用户进行浏览或下载操作时，访客需要把令牌添加到X-Share-Token请求头里，并且由分享鉴权过滤器进行校验，浏览和下载次数会被记录，密码尝试次数则利用Redis进行限制。

（1）回收站模块

回收站模块可以把误删除所造成的数据丢失风险给降低下来，普通删除不会马上进行物理删除，而是把项目类型、原项目ID、原路径、项目名称、内容ID和完整数据备份写入trash表，用户可以分页查看回收站里的项目，也可以对回收站进行批量恢复、彻底删除或者清空，系统在进行恢复操作时，若原目录不存在，系统将返回到根目录。服务层在名称冲突发生时会生成新的名称，以此来避免覆盖现有的文件，定时清理任务会删除过期的回收站记录和过期的上传任务，这使临时数据不会长时间堆积。

#### 4.3.4管理员与运维模块设计

（1）用户管理模块

管理员用户管理模块通过/api/admin/users系列接口维护账号。管理员可以查看和筛选用户、查看详情和存储使用情况，也可以修改状态、调整角色、设置空间或软删除用户。所有管理员接口都先经过JWT鉴权，再经过管理员角色鉴权。

（2）存储统计与分享管理模块

存储统计模块汇总users、files、file_contents、folders等表，计算全平台用户数、文件数、内容对象数、存储占用以及各用户使用情况。由于系统采用内容寻址和引用计数机制，用户视角下的逻辑文件大小与物理内容占用并不总是一致，统计时需要分开处理。

管理员通过使用分享管理模块来进行相关操作，该模块可以查看全平台分享列表和单个分享详情，并且可以强制取消违规分享，主要用来处理公开链接滥用、误分享和过期分享等情况。

（3）系统状态与日志模块

系统状态模块主要负责部署检查和日常维护工作，它展示了服务的运行时间、版本信息、数据库连接状态、Redis连接情况、磁盘空间使用状况等各项指标，操作日志按照分页方式进行保存，包括了上传、下载、删除、分享等各类操作，方便管理员对异常请求进行排查。

## 第5章 系统实现

本文结合实际项目代码，对系统的具体实现过程进行说明，后端使用分层架构模式，将功能划分为控制器、过滤器、服务层、数据模型和存储抽象这五个模块，控制器主要负责路由请求的分发和响应结果的格式转换，服务层则承担着业务规则校验、数据库事务管理和Redis状态维护的主要职能，桌面端搭建了AuthShell、OwnerShell、VisitorShell、AdminShell四类外壳组件，分别适配登录流程、普通用户操作、访客内容分享、管理员后台管理四类不同的应用场景。

### 5.1用户与认证模块功能实现

（1）注册与登录实现

账号注册和登录接口由AuthController提供，具体判断由AuthService进行完成，在注册过程中，DTO会对用户名、邮箱和密码格式进行检查，服务层确认该数据未被占用后，使用Argon2id算法生成密码哈希，并将默认资料、配额、状态和角色等信息写入数据库。

登录接口可以支持用户名或者邮箱，服务层在读取账号状态、锁定时间和密码哈希之后逐项进行判断，当账号处于禁用、锁定或密码错误的状态时，系统会返回相应的结果，认证成功后系统会重置失败计数，同时签发Access Token和Refresh Token，并且把用户信息返回给客户端，客户端在保存会话之后，按照角色切换到普通用户或者管理员界面。

（2）令牌生命周期与鉴权过滤

令牌逻辑集中在TokenService中。Access Token采用JWT格式，携带用户ID、用户名、角色和过期时间；普通业务接口通过JwtAuthFilter校验Authorization请求头。Refresh Token保存在Redis中，用于续期；用户登出时，系统删除刷新令牌并把访问令牌加入黑名单。

不同访问边界使用不同过滤器。管理员接口在JWT校验后还要经过AdminAuthFilter，只有管理员角色可以访问/api/admin/* 路由；公开分享的浏览和下载接口使用ShareAuthFilter校验X-Share-Token，避免访客流程与登录用户JWT混在一起。桌面端网络层由RequestFactory按请求类型附加用户令牌、分享令牌或两者组合，请求来源也更容易区分。

（3）个人资料、密码与存储空间实现

用户中心由UserController和UserService实现，包括资料查询、资料更新、密码修改和空间查看。资料更新接口只修改请求中传入的字段；密码修改接口要求提交当前密码，校验通过后重新生成Argon2id哈希并更新users.password_hash。

存储空间接口读取users表中的storage_quota、storage_used和storage_reserved字段，并结合文件数、目录数返回已用空间、预占用空间、剩余配额和资源数量。桌面端SettingsPage和ProfileManager负责加载这些数据；用户修改资料或密码后，页面根据接口结果给出提示。

### 5.2文件传输模块功能实现

（1）分片上传初始化与秒传判断

文件上传由FileController提供初始化、上传分片、完成上传和取消上传接口，主要路径包括/api/file/upload/init、/api/file/upload/chunk和/api/file/upload/complete等。控制器绑定路由、HTTP方法和过滤器，上传接口接入JWT鉴权和限流过滤器，并用co_await等待服务层逻辑。

客户端选择文件后，TransferManager提交文件名、文件大小、目标目录和文件MD5。初始化阶段先检查用户配额，如果当前已用空间加上预占用空间已经超过配额上限，服务端直接返回空间不足，客户端不再继续上传分片。

初始化阶段也会依据文件哈希对file_contents表进行查询，当系统检测到相同内容对象时，服务层会直接生成files元数据并把引用计数增加，接着返回秒传结果，如果内容不存在，那么系统会创建upload_tasks记录，并且写入任务ID、目标目录、文件信息、分片信息、临时路径、预占用字节数、过期时间，同时系统会返回已经上传的分片列表。

（2）分片写入、断点续传与后台合并

分片上传接口按照任务ID和分片索引接收二进制内容。Drogon把请求体封装在HttpRequest对象中，控制器可以直接读取request->body()取得application/octet-stream数据，不需要再进行JSON封装。服务层随后检查任务归属和任务状态，确认无误后把分片写入临时目录，并在upload_task_chunks表中记录对应索引。

大文件被拆分成固定分片后，单次请求只处理部分数据，服务端内存峰值更容易得到控制，客户端在进行恢复上传时会再次调用初始化接口，获取到已上传的分片索引之后，仅对缺失分片进行补传，断点续传依靠上传任务表和分片记录表来共同进行支撑。

客户端在完成全部分片上传操作后会调用完成接口，后端先通过PostgreSQL条件更新和有期限租约取得唯一完成权，再使用不保存upload_id的AssemblyConcurrencyLimiter限制本机合并数量，并按照索引读取暂存分片，在生成完整文件后计算MD5和SHA256，并同初始化哈希进行比对。校验通过后，BlobStore把组装结果提升为内容寻址的S3/MinIO对象，服务层接着在同一数据库事务中写入file_contents和files表、把预占用空间转为已用空间；数据库提交失败时保留可供幂等重试或对账的候选Blob。当取消上传或任务过期时，系统由持久清理任务删除暂存分片，并且恢复任务状态和预占用空间。

（3）文件下载与Range断点下载

文件下载流程分为下载信息查询和文件流返回两个步骤。第一步向客户端返回文件名、大小和MIME类型等信息；第二步检查文件归属，确认当前用户具有访问权限后，由BlobStore按描述符打开本地文件或S3对象范围流，再交给DownloadResponder构造HTTP响应。

大文件下载时，不能把完整文件一次性加载到内存中。下载接口使用Drogon的HttpResponse::newStreamResponse实现流式返回，回调函数按固定块大小读取文件，再写入响应缓冲区。这样处理后，内存占用能够保持在相对稳定的范围内，服务端在发送文件的同时也可以继续处理其他连接。

请求头包含Range字段时，后端解析字节范围，只返回对应内容，并设置206 Partial Content、Content-Range、Accept-Ranges和Content-Length等响应头。范围超过文件大小时返回416。普通下载、断点续传和非法Range响应共用流式构造逻辑；桌面端由TransferManager和DownloadTaskModel管理下载进度、状态和失败原因。

（4）传输中心实现

TransferCenterPage实现了传输中心，它和文件列表页面是分开的，上传任务保存文件名、目标目录、已上传字节数、总字节数、状态和错误信息，下载任务会记录本地路径、进度、暂停状态、完成状态，处理完毕后，虽然上传或者下载所花费的时间比较长，用户仍然可以继续对文件进行浏览、对目录进行切换或者对其他操作进行处理，不需要一直停留在文件列表页面上等待任务完成。

（1）文件列表与资源管理器实现

DriveManager保存当前目录ID、列表模型、排序方式、选择状态和加载状态，根目录使用ID0来表示，用户在切换目录的过程中，页面不需要进行重建操作，系统只更新目录ID和列表数据，若请求出现失败或列表处于空状态，界面将显示出对应的提示信息，并且让用户可以进行重新加载，后端查询过程一直包括用户ID权限边界，普通用户虽然可以构造其他目录ID，但也不能越权读取他人文件。

目录树依据folders.parent_id进行组织，在建立过程中，服务层会对最大深度进行限制，并且对异常循环进行检测，面包屑路径会从当前目录逐级回溯至根目录来生成，桌面端左侧显示出目录树，顶部显示当前位置，用户点击节点后，文件列表会同步进行刷新。

重命名操作分别对files或folders中的名称和路径进行更新，服务层在写入之前会对名称的长度、非法字符、保留名称、同级重名进行检查，移动接口可以支持批量文件和目录的移动，移动目录时要对目标目录进行额外判断，不可以将目录移到自身或其子目录下，否则会破坏目录树结构，复制文件时系统仅新增逻辑文件记录并增加file_contents.ref_count，物理内容不会进行重复复制。

搜索接口依据关键词、项目类型和目录范围来返回分页结果，桌面端对关键词和排序方式进行保存，用户在输入后，DriveManager会向后端请求数据并且刷新列表，当用户进行批量移动、复制、删除和分享操作时，客户端会提交多个项目ID，后端会依次对各个项目进行处理，然后返回结果，界面随后显示成功状态或失败原因。

### 5.4回收站模块功能实现

回收站功能依靠TrashController和TrashService这两个模块共同来进行实现，用户在进行常规删除操作时，系统并不会立刻释放对应的存储空间，而是先把待删除对象的类型、原始ID、名称、所属父目录、完整存储路径、占用空间、内容关联标识、必需的JSON备份数据写入trash数据表，然后把该对象从正常的文件、目录索引列表中移除。桌面端通过使用DriveTrashView组件来对trash表中的全部记录进行加载，用户能够勾选多个对象以进行恢复或永久删除操作，也能够选择一键清空当前账号下的全部回收站内容。

图5-8 回收站管理功能截图

![图5-8 回收站管理功能截图](assets/回收站管理功能截图.png)

图5-8为回收站界面。列表中保留已删除项目的名称、路径、大小和删除时间，操作区提供恢复、彻底删除和清空入口。

系统在执行恢复操作时，服务层首先会对回收站记录进行确认，看其是否属于当前用户，如果原父目录仍然存在，项目会被优先恢复到原位置，如果原目录已经不存在，系统会把项目恢复到根目录，若目标目录内有同名项目，服务层会自动生成name(n).ext或name(n)形式的新名称，从而避免覆盖已有数据，该版本在恢复文件夹时使用了比较保守的方法，只对文件夹记录进行恢复，没有对子树进行递归恢复。

删除物理内容会影响到文件，对于文件项目，服务层会先对file_contents.ref_count进行扣减，在该值归零后，由iFileStorage对本地内容寻址文件进行删除，并对已用空间进行更新，在清空回收站时，系统会批量执行相同的过程，后台清理服务会定期对过期记录进行处理。

### 6.3系统性能测试

性能测试选取文件列表、目录导航、上传初始化和文件下载等接口，主要观察单机部署下的响应时间、吞吐量和错误率。后端使用Drogon异步I/O和协程服务层，本地文件按内容寻址保存。测试过程中没有出现明显超时或服务异常。

### 6.4系统安全性测试

安全性测试主要检查JWT鉴权、管理员角色校验、用户资源归属校验、分享访问令牌和密码错误限制等机制，未登录访问受保护接口、普通用户访问管理员接口、用户下载他人文件、访客使用错误或过期分享令牌等情况均分别进行测试，结果表明，这些请求可以被系统拦截或者返回对应的错误，登录之后的访问令牌也会因为黑名单状态而失效。

### 6.5测试总结

系统在完成功能测试之后，其主要业务基本可以保持稳定运行，普通用户、访客和管理员这三类角色的主要流程都通过了验证，这些流程包括认证鉴权、文件传输、目录管理、分享访问、回收站处理、管理员用户管理、分享管理、操作日志、存储统计和系统状态查询。

安全性测试包括用户访问他人文件、普通用户访问管理员接口、令牌过期、登录后继续请求、登录失败锁定、分享密码错误和分享令牌失效等场景，测试结果说明，系统会对这些请求进行拦截，或者按照预期返回错误。

当前测试仍然主要依靠毕业设计演示环境，并且大多是在本地单机环境下进行，还没有进行大规模的并发压力测试，操作日志和健康检查已经具备，但是监控告警、容量趋势分析和容灾恢复仍然比较基础，桌面端已经覆盖了主要页面，拖拽上传、缩略图预览和在线预览还没有完成，如果要进行实际部署，那么以后需要先进行性能压测、运维监控的补充。

## 总结与展望

本文完成了一套面向私有化部署的网络磁盘系统。论文说明了需求分析、总体架构、数据库结构、模块设计、功能实现和测试过程。系统后端采用C++23和Drogon，桌面端采用Qt 6和QML，数据层由MySQL、Redis和本地内容寻址文件系统组成。

在功能落地方面，该系统已经完成了用户注册登录、令牌生命周期管理、JWT权限校验、目录树展示、文件分片上传、断点续传、秒传、Range分段下载、文件分类整理、回收站、外链分享、操作日志留存、系统状态查询这些主要功能，桌面客户端实现了身份认证界面、网盘资源管理面板、传输任务中心、访客分享访问页、个人参数设置页和管理员管控后台这几个主要功能模块。文件上传和存储过程依靠upload_tasks、upload_task_chunks、file_contents这三张主要表，来分别进行分片上传状态的跟踪、秒传校验、文件资源去重的管理处理。

测试结果表明，系统基本达到毕业设计阶段的预期目标。注册登录、文件传输、目录管理、分享访问控制、回收站恢复、权限边界和管理员操作等流程都能够按照设计运行，RESTful接口的数据交互也较为清晰。通过本次系统实现可以看出，C++23、Drogon、MySQL、Redis和Qt/QML能够组合形成一套可运行的中小规模私有化网络磁盘系统。

该系统目前仍然存在一些不足，文件版本历史、WebDAV、在线预览、缩略图还没有完成，高并发压力测试和安全测试没有达到充分程度，在大规模文件传输时的吞吐量、延迟和稳定性也缺少更多数据，系统已经具备操作日志和状态接口，但是系统在监控告警、容量趋势分析、自动备份和容灾恢复方面比较基础，后续工作可以优先对客户端体验和压测数据进行补齐。
