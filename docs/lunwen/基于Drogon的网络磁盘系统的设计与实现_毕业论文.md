# 基于Drogon的网络磁盘系统的设计与实现

## 摘　要

个人电脑、手机和团队协作工具每天都会产生新文件，文档、图片、代码包和临时资料很容易散落在不同位置。公有云网盘使用方便，但文件放在第三方平台上，容量、带宽和服务规则都不完全由用户掌握。本课题关注的不是大型云盘如何扩容，而是另一个更具体的问题：在个人服务器或小团队环境里，能否做出一套结构不重、功能够用、部署成本可控的私有网盘系统。

后端选用C++23和Drogon框架，重点利用其异步I/O和协程接口处理文件传输、认证鉴权与管理接口；桌面端使用Qt 6和QML编写，并以RESTful API连接后端。数据分工按生命周期划开：MySQL保存用户、文件元数据、目录、上传任务、分享、回收站和操作日志等长期数据；Redis保存刷新令牌、黑名单、登录失败计数、分享访问状态和限流计数；文件内容则按哈希写入服务器本地目录。系统面向普通用户、访客和管理员三类场景，包含注册登录、令牌刷新、空间查看、文件列表与搜索、重命名、移动、复制、软删除、分片上传、断点续传、秒传、Range下载、外链分享、回收站处理，以及后台用户、分享、日志和系统状态管理。

目前，私有网盘的主线流程已经跑通。普通用户可在桌面端整理文件、执行传输任务并创建分享，管理员可以查看用户、分享、日志和系统状态。测试中，注册登录、文件传输、目录管理、分享访问和权限控制等流程与设计预期基本一致；上传下载和异步接口处理场景下，Drogon的协程与非阻塞I/O机制没有出现明显阻塞问题。本文最终完成的是一套可运行的C++文件服务后端和配套桌面客户端，而不是对商业云盘的完整复刻。

关键词：网络磁盘；文件管理；Drogon；C++23；RESTful API

## ABSTRACT

Digital files generated by personal computers, mobile devices, and collaboration tools are often scattered across different locations. Public cloud drives are convenient, but users do not fully control where their files are stored, how much bandwidth is available, or how service policies may change. This thesis focuses on a more limited but practical question: whether a private network disk can be built for personal servers or small teams with a lightweight structure, usable functions, and acceptable deployment cost.

The backend is developed with C++23 and the Drogon framework, mainly using asynchronous I/O and coroutine-based interfaces for file transfer, authentication, and management APIs. The desktop client is implemented with Qt 6 and QML and communicates with the backend through RESTful APIs. Data storage is divided by state lifetime. MySQL stores long-term data such as users, file metadata, directory structures, upload tasks, share records, trash records, and operation logs. Redis stores short-lived states such as refresh tokens, token blacklists, login failure counters, share access states, and rate-limiting counters. File contents are written to the server's local filesystem by content hash. The system covers regular users, visitors, and administrators, including registration and login, token refresh, storage querying, file listing and searching, renaming, moving, copying, soft deletion, chunked upload, resumable upload, instant deduplication, Range download, external sharing, trash handling, and backend management of users, shares, logs, and system status.

The main workflow of the private network disk has been implemented. Regular users can manage files, run transfer tasks, and create shares on the desktop client, while administrators can check users, shares, logs, and system status. Tests show that registration, login, file transfer, directory management, share access, and permission control generally match the design. In upload, download, and asynchronous API scenarios, Drogon's coroutine and non-blocking I/O mechanisms do not show obvious blocking problems. The result is a runnable C++ file-service backend with a desktop client, rather than a full replacement for commercial cloud drives.

KEYWORDS: Network Disk; File Management; Drogon; C++23; RESTful API

## 前　言

学习、工作和日常生活中的数字资料越来越多。课程文档、个人笔记、项目代码、图片和视频都需要固定存放，也需要能在不同设备之间取用。网络磁盘正好把文件保存和网络访问放在一起，所以成了常见工具。问题在于，公有云盘的便利性并不免费：隐私风险、带宽限速、免费空间有限，以及对平台规则的依赖，都会在某些场景里变成限制。对希望自己掌握数据和运行环境的用户来说，私有化网盘仍然有存在空间。

真正使用网盘时，需求其实很朴素：上传、下载、分享，再加上目录整理和搜索。大文件稍微麻烦一些，网络中断后如果只能从头上传，用户很快就会放弃，因此断点续传不能只当作附加项。分享也是如此，很多文件只是临时给别人看一眼或下载一次，没有有效期和权限控制，后续清理会很麻烦。

管理员侧的问题更容易被忽略。账号数量、存储占用、数据库连接、Redis状态和磁盘空间，如果散在不同工具里，平时还能凑合，一旦出错就会拖慢排查。因此，本系统没有只围绕普通用户的文件操作展开，而是把后台管理、日志和系统状态查询放在同一套服务里。

后端选择C++23和Drogon，主要因为文件服务对I/O和资源占用比较敏感。Drogon底层用epoll（macOS/FreeBSD下为kqueue）处理网络事件，也支持协程化请求，适合上传、下载这类等待时间较长的接口。相比脚本语言或阻塞式Web框架，C++后端更容易控制内存和请求处理细节，放到个人服务器或小型私有环境中也更有余量。数据部分没有做得过重：MySQL保存关系型元数据，Redis保存令牌和限流等短时状态，文件内容落在本地内容寻址目录中。

本文围绕这套取舍完成需求分析、总体结构、数据库设计、详细设计、功能实现和测试验证。课题不追求大型云存储那种复杂架构，而是在中小型文件服务场景下，验证Drogon、MySQL和Redis这套组合能否支撑一个完整的网盘业务流程。

## 第1章 绪论

### 1.1研究背景

近几年，个人数字内容和移动互联网应用增长很快，在线存储服务的使用频率也随之提高。云存储让文件不再固定在某一台设备上，用户只要有网络就能访问和管理资料，这确实方便了个人资料管理和团队协作。但公有云网盘并非处处合适：文件放在第三方服务器上，隐私和商业资料保护存在不确定性；免费套餐通常限制容量和速度，高级功能还需要持续付费；服务商调整策略、停止服务或发生安全事件时，用户很难掌握主动权。对部分有合规要求的机构或团队来说，数据必须留在自主可控的基础设施内，公有云盘自然就不够用了。

私有化自建网盘因此仍有现实空间。文件实体和元数据放在自己的服务器上，数据位置、访问策略、存储空间和网络带宽都能按自身条件调整。不过，真正做一个功能完整、运行稳定、部署负担又不太重的网盘并不轻松。传统脚本语言或解释型Web框架在高并发文件传输场景下，可能遇到吞吐不足或CPU占用偏高的问题。本文选择C++语言配合Drogon Web框架实现私有化网络磁盘系统，正是想在毕业设计范围内验证这条技术路线。

### 1.2研究意义

本课题面向私有化网络磁盘的实际使用场景，完成一个功能相对完整的网盘服务系统。用户文件管理、目录组织、大文件上传、文件分享和管理员后台都放进同一套后端服务中，C++与Drogon负责承担文件传输和接口处理压力。这样得到的不是一个概念模型，而是一个可以部署、可以测试的工程样例。

从使用角度看，这套系统更适合个人开发者、高校师生和中小团队。文件上传、目录整理、检索和分享集中在同一界面，用户不必在多个传输工具之间切换；存储配额和已用空间也会在用户侧展示，便于判断资源占用。管理员侧则负责账号管理、存储统计和系统状态查看，避免把运维信息拆散到数据库客户端、Redis命令行和系统磁盘工具里。

对笔者而言，这个课题的价值主要在工程串联。C++系统编程、异步网络I/O、Web框架、关系型数据库、缓存状态和RESTful接口单独看都不陌生，难点在于把认证、文件传输、目录结构、权限边界和客户端交互接在一起。尤其是出错之后，数据库记录、Redis状态和本地文件要能对得上。完成该系统后，笔者对Drogon请求处理、MySQL表设计以及前后端接口契约有了更具体的认识。

### 1.3国内外研究现状

云存储和网络磁盘并不是新问题，相关研究和工程实践已经很多。只是把范围缩到“C++ Web框架下的私有化网盘”时，可直接照搬的资料就少了不少。

国外在云存储领域起步较早，分布式文件系统、对象存储和数据去重都有成熟案例。Google文件系统（GFS）、Amazon S3和OpenStack Swift在架构层面影响很大，但它们服务的是数据中心级别的水平扩展，放到单机私有化部署中反而显得过重。开源网盘方面，Nextcloud和ownCloud功能丰富，不过PHP运行模型对服务器配置和性能有一定影响；SeaweedFS、MinIO等Go语言项目更偏对象存储基础设施，并不直接提供网盘式桌面交互。

国内公有云网盘发展较快，百度网盘、阿里云盘等产品也带动了文件秒传、内容去重、传输加速和版权保护等方向的讨论。教学和毕业设计中的自建网盘，常见做法是Java Spring Boot、Python Django或Flask配合关系型数据库和本地文件系统，功能通常够用，但高并发文件传输和资源占用仍有优化空间。用C++ Web框架，尤其是Drogon，来完成完整网盘业务的公开案例并不多，这也是本文选题的一个现实原因。

已有研究能给出云存储架构和私有网盘开发的参考，但中小规模、私有化、C++后端这几个条件同时成立时，仍需要结合具体工程做验证。本文不试图替代成熟云存储系统，而是给出一个面向单机或小团队环境的实现路径。

### 1.4本文的组织结构

本文讨论的是私有化网络磁盘系统的设计与实现，重点放在文件存储访问、大文件传输、目录树管理、分享链接控制和后台运维管理。课题目标很明确：做出一个普通用户和管理员都能使用的网盘平台，并用实现和测试证明它在毕业设计场景下可以部署、演示和维护。

用户侧接口覆盖账号注册、登录、令牌刷新与登出，个人资料与存储空间统计，文件和目录的分页列表、搜索、详情、重命名、移动、复制、软删除，目录树与面包屑路径查询，分片上传、断点续传、秒传去重、后台合并、Range下载，外链分享、分享密码校验、分享内容浏览与下载，以及回收站恢复和清空。管理员侧更偏运维，包括用户查询、状态切换、角色变更、软删除、用户文件与存储查看、全局存储统计、分享列表与强制取消、系统概览和系统状态查询。

文件上传、下载这类I/O等待较多的请求交给Drogon的异步非阻塞I/O和C++协程模型处理。上传任务和分片状态写入数据库，客户端断线后只补传缺失分片；文件内容哈希和引用计数用于秒传与去重，避免同一内容反复落盘。Redis承担令牌、限流和登录失败次数等短时状态，减少这些高频状态对MySQL的压力。

安全设计没有引入复杂模型，而是盯住几个容易出问题的边界：普通用户只能访问自己名下的文件和目录，管理员接口需要额外角色鉴权，分享访问不复用用户JWT，而是使用分享短码、可选密码、短期分享令牌和有效期限制公开访问范围。密码使用Argon2id哈希存储，登录失败计数和短时锁定用于降低暴力破解风险。

后端按认证、用户、文件、目录、分享、回收站、运维统计和操作日志等模块拆分。控制器负责请求解析和响应转换，业务判断放在服务层；存储层用IFileStorage隔离本地文件系统。后续如果接入对象存储、文件版本历史、WebDAV接口或缩略图预览，至少不必把现有控制器全部推倒重写。

## 第2章 相关技术分析

### 2.1 Drogon框架与C++23协程

Drogon是一个面向HTTP服务的C++ Web框架，底层网络库基于epoll（在macOS/FreeBSD下为kqueue）处理非阻塞I/O。文件上传和下载请求常常不是CPU计算耗时，而是等待磁盘和网络，这类场景如果采用阻塞模型，线程很容易被大量占住。本系统采用C++23标准，并结合Drogon的HttpController、HttpCoroFilter和drogon::Task协程接口组织控制器、过滤器和服务层逻辑。业务返回值使用std::expected风格的Result<T>表达成功或失败，避免在普通业务分支中大量依赖异常控制流。

### 2.2 MySQL数据库

MySQL是常用的关系型数据库，稳定性和资料都比较成熟，适合保存中小规模业务系统中的长期数据。本系统把用户账号、文件内容哈希、文件元数据、目录树、上传任务、上传分片、回收站记录、分享记录、分享文件关联和操作日志放在MySQL中。文件列表、目录树遍历、秒传查重、配额统计和分享访问等查询频率较高，因此表结构中设置了联合索引、全文索引和唯一约束。

### 2.3 Redis缓存与状态管理

Redis是内存型键值数据库，适合保存生命周期较短、访问频率较高的状态。本系统把Refresh Token、Access Token黑名单、登录失败计数、分享访问令牌、密码尝试次数和接口限流计数放在Redis中。这样做可以把易过期、变化快的状态从MySQL中拆出来，鉴权、限流和安全控制逻辑也更轻。

### 2.4 JWT身份鉴权机制

JWT（JSON Web Token）是一种基于JSON格式的开放标准（RFC 7519），用于在各方之间以紧凑、自包含的方式安全地传递身份认证信息。本系统在用户登录成功后签发Access Token与Refresh Token，普通业务请求通过Authorization: Bearer <token>携带访问令牌，令牌刷新和登出依赖Redis中保存的刷新令牌与黑名单状态实现轮换和失效控制；公开分享访问则使用独立的分享令牌并通过X-Share-Token请求头传递，避免将用户JWT暴露给未登录访客。

### 2.5 CMake构建工具与安全基础库

CMake是一种跨平台的构建系统生成工具，被Drogon生态所推荐使用。本系统通过CMakeLists.txt、CMakePresets.json和vcpkg manifest管理后端项目的编译依赖、构建预设和第三方库，简化了Linux与Windows环境下的编译、测试和部署流程。密码哈希方面，系统使用libsodium提供的Argon2id算法保存用户密码，避免明文密码或弱哈希方案带来的安全风险。

### 2.6 Qt框架与QML

Qt是跨平台C++应用程序开发框架，常用于桌面端和嵌入式界面开发。本系统桌面客户端基于Qt 6实现，网络请求部分使用Qt Network访问后端RESTful API，承担文件分片上传、断点下载和JSON数据解析等工作。界面层采用QML（Qt Modeling Language）配合Qt Quick Controls 2编写文件列表、目录导航、传输进度、分享管理和后台管理页面。在实现分工上，QML主要负责界面声明和状态绑定，C++侧保存网络请求与业务状态，两者通过属性绑定和信号槽机制连接，避免界面代码与通信逻辑过度耦合。

## 第3章 需求分析

### 3.1系统需求概述

在建设私有化网络磁盘系统之前，需要先判断它在技术、成本和使用流程上是否成立。结合课题目标和已选技术栈，系统可以落地，但三个层面的难度并不一样。

技术上，C++23、Drogon、MySQL和Redis可以覆盖本课题的大部分需求。Drogon已经提供HTTP路由、过滤器、控制器、协程任务、异步数据库访问和配置文件管理等能力，后端基础设施不必从零写起。MySQL负责用户、文件、目录、分享和日志等结构化数据；Redis承担令牌、限流、登录失败计数这类生命周期较短的状态。C++23中的协程、std::expected和std::filesystem分别对应异步流程、错误返回和文件路径处理。JWT鉴权、Argon2id密码哈希以及CMake/vcpkg构建体系也都有成熟库可用。

经济层面相对简单。系统依赖的软件工具和运行环境均可使用开源免费版本，包括Drogon、MySQL社区版、Redis、CMake、GCC/Clang以及常见Linux系统工具。硬件要求不高，普通个人计算机或低配云服务器即可完成编译、部署和演示。对毕业设计而言，真正消耗较多的是开发和调试时间，而不是软硬件采购。

使用流程上，系统面向普通用户和管理员两类账号，同时给未登录访客保留受限的分享访问入口。后端接口围绕账号认证、个人资料、文件上传下载、目录管理、分享、回收站、日志和运维统计展开，路径和响应格式尽量保持一致。桌面客户端以RESTful API接入后端，管理员功能由受保护的管理接口承担。权限校验、错误响应和业务状态放在后端统一处理，后续二次开发只需遵守接口契约。

### 3.2系统功能需求分析

私有化网络磁盘系统的需求来自两个方向。普通用户关心的是文件能不能稳定上传、方便整理、需要时能否分享；管理员关心的则是账号、存储资源和系统状态是否可控。围绕这两类角色，系统需求可以拆成功能需求和非功能需求两部分。

#### 3.2.1账号与用户模块需求分析

账号与用户模块先解决“谁在使用系统”这个问题。普通用户需要注册、登录、令牌刷新、登出、个人资料查询与更新、密码修改和存储空间查看等基础能力。注册时要检查用户名和邮箱是否重复；登录时不仅要校验密码，还要判断账号状态和失败次数。认证成功后，系统签发Access Token与Refresh Token，后续业务接口依赖它们完成鉴权和登录态续期。用户中心还展示已用空间、预占用空间、剩余配额、文件数和目录数，让用户能看清自己的存储资源。

管理员侧的账号功能更偏维护。系统需要支持用户列表查询、关键字与状态筛选、用户详情查看、存储使用量查询、可用空间调整、账号禁用或启用、角色变更和软删除。这里最容易出问题的是越权访问，因此所有管理员操作都必须先通过普通JWT鉴权，再经过管理员角色鉴权。

#### 3.2.2文件与目录模块需求分析

文件模块需要覆盖文件从上传、访问、组织到删除的完整生命周期。系统应支持文件和目录的混合分页列表展示、按名称搜索、文件详情查询、文件重命名、批量移动、批量复制和软删除；对于文件下载，需要支持普通完整下载和HTTP Range断点下载，以便客户端在网络不稳定场景下恢复下载进度。

上传功能是文件模块的核心需求。系统需要支持初始化上传、上传分片、完成合并和取消上传四个阶段，并通过上传任务与分片状态记录实现断点续传；当服务器已经存在相同内容文件时，应能够基于内容哈希完成秒传，避免重复上传和重复存储。目录模块需要支持多级目录创建、目录树查询和面包屑路径查询，并保证同一用户同一父目录下的目录名称不重复。

#### 3.2.3分享、回收站与管理模块需求分析

分享模块需要支持用户为文件或目录生成外链分享，并能够设置有效期、访问密码和查看或下载权限。未登录访客访问分享时，系统应先校验分享短码、分享状态、有效期和访问密码，校验成功后再签发短期分享访问令牌；访客浏览分享内容或下载分享文件时，需要通过独立的分享令牌完成鉴权，避免公开访问流程与登录用户JWT混用。

回收站模块需要支持误删除恢复场景。用户删除文件或目录时，系统应先将项目移动到回收站，保留原路径、原所属目录、项目类型、内容引用和恢复所需数据；用户可以查看回收站列表，执行批量恢复、彻底删除或清空回收站。管理员与运维模块则需要提供全局存储统计、分享记录查看、违规分享强制取消、系统概览、数据库状态、Redis状态和磁盘空间状态查询等能力。

#### 3.2.4系统用例分析

本系统主要涉及普通用户和管理员两个账号角色，并包含未登录访客访问分享的公开场景。普通用户通过用户端完成注册登录、文件上传与下载、目录管理、文件分享等操作；访客通过分享短码、访问密码和分享令牌浏览或下载授权内容；管理员通过后台完成用户管理、存储统计查看和系统参数配置等操作。

普通用户的核心用例主要包括：账号注册、账号登录、刷新令牌、登出、查看和更新个人资料、修改密码、查看存储空间、初始化上传、上传分片、完成上传、取消上传、下载文件、查看文件列表、搜索文件或目录、创建目录、查看目录树、查看面包屑路径、重命名文件或目录、移动或复制文件和目录、删除到回收站、查看回收站、恢复回收站项目、彻底删除回收站项目、生成分享链接、查看我的分享、更新或取消分享、通过分享密码访问分享、浏览分享内容、下载分享文件以及保存分享内容到个人网盘；管理员的核心用例则包括：管理员登录、查看全部用户列表、查看用户详情、禁用或启用用户账号、修改用户角色、调整用户可用空间、软删除用户、查看全平台存储统计、查看分享列表、查看分享详情、强制取消分享、查看操作日志、查看系统概览以及查看系统状态。

### 3.3系统非功能需求分析

#### 3.3.1系统性能需求分析

系统需要能够在单机私有化部署环境下稳定运行，利用Drogon框架的异步I/O能力提升文件传输吞吐量。对于文件列表、目录导航、存储配额查询等元数据请求，后端应在较短时间内完成响应；对于文件上传和下载操作，系统应利用流式处理机制避免将大文件全量加载入内存，减少内存峰值占用。上传任务和分片状态需要具备持久化能力，以便在客户端网络中断后继续上传缺失分片。

#### 3.3.2系统安全性与可维护性需求分析

系统需要对不同用户的文件资源严格隔离，普通用户只能访问自己名下的文件和目录，不能通过接口越权访问或下载他人文件；管理员接口需要单独鉴权，普通用户令牌无法访问管理员功能。文件分享链接需要使用随机短码、可选访问密码、有效期和短期分享访问令牌共同控制公开访问范围。用户密码必须经过安全哈希后存储，不得以明文形式保存在数据库中。

在可维护性方面，后端代码需要按认证、用户、文件、目录、分享、回收站、管理员、日志和系统状态等功能模块清晰划分。控制器只负责解析请求和转换响应，核心业务集中在服务层实现；数据库表结构应做到字段含义清晰、约束合理，方便后期维护和Schema演进。

#### 3.3.3数据字典

本系统涉及的核心数据对象主要包括用户信息、文件内容、文件元数据、目录信息、上传任务、上传分片、回收站记录、分享记录、分享文件关联和操作日志等，以下分别对主要数据对象的字段组成和含义进行说明。

用户信息（users）是整个系统的基础数据对象，主要用于保存用户的账号凭据、个人资料、登录安全状态和存储配额信息，是登录鉴权、文件归属判断和存储限额控制的核心依据。其主要字段包括用户主键ID、用户名、邮箱、哈希后的密码、昵称、头像、存储配额、已用存储、上传预占用存储、账号状态、角色类型、登录失败次数、锁定截止时间、最后登录时间、最后登录IP、创建时间和更新时间。

文件内容（file_contents）用于保存物理文件内容的索引信息，是秒传去重和内容寻址存储的基础。其主要字段包括内容主键ID、MD5哈希、SHA256哈希、文件大小、实际存储路径、MIME类型、引用计数和创建时间。多个用户文件记录可以引用同一个内容对象，从而避免相同内容被重复存储。

文件元数据（files）是文件管理功能的核心数据对象，用于保存每一个用户可见文件的描述性信息，而不直接存储文件二进制内容。其主要字段包括文件主键ID、所属用户ID、关联的内容ID、所属文件夹ID、文件名、扩展名、文件大小、MIME类型、完整路径、收藏标记、下载次数、最后访问时间、创建时间和更新时间。

目录信息（folders）用于维护用户的目录树结构，是目录导航和文件路径组织的基础数据表。其主要字段包括目录主键ID、所属用户ID、父目录ID（根目录以0表示）、目录名称、完整路径、目录深度、子项数量、创建时间和更新时间。通过父目录ID字段形成的递归引用关系，可以构建出任意层级深度的目录树结构。

上传任务（upload_tasks）用于支持大文件分片上传和断点续传机制，保存每个进行中、已完成、已取消或已过期上传任务的总体状态。其主要字段包括上传任务ID、用户ID、目标文件夹ID、文件名、文件大小、文件MD5、分片大小、总分片数、预占用字节数、临时存储路径、任务状态、过期时间、完成时间、失败原因、创建时间和更新时间。上传分片（upload_task_chunks）则以任务ID和分片索引作为联合主键，记录每个分片是否已经上传成功。

回收站记录（trash）用于保存软删除文件或目录的恢复信息。其主要字段包括回收站记录ID、用户ID、项目类型、原项目ID、项目名称、项目大小、关联内容ID、原所属文件夹ID、原完整路径、项目完整数据备份、删除时间和过期时间。通过回收站表，系统可以在彻底删除之前恢复误删项目，也可以在过期清理时减少内容引用计数并释放物理存储。

分享记录（shares）用于保存用户发起的分享操作的基础信息，是外链分享功能的数据基础。其主要字段包括分享ID、分享短码、分享者用户ID、访问密码哈希、权限类型、访问次数、下载次数、分享状态、过期时间、创建时间和更新时间。分享文件关联（share_files）用于描述某个分享包含的文件或目录，主要字段包括关联记录ID、分享ID、项目类型、项目ID和创建时间。该设计使一个分享可以关联一个或多个文件或目录，并支持后续扩展分享目录浏览能力。

操作日志（operation_logs）保存上传、下载、删除、分享等关键动作的记录。表中字段包括日志ID、用户ID、操作类型、目标类型、目标ID、目标名称、操作详情、IP地址、客户端信息和创建时间。当出现异常下载、误删文件或分享访问问题时，管理员可以先从这些记录中确认操作对象和发生时间。

上述对象基本覆盖了系统运行时需要保存的业务数据，后续数据库设计和服务层逻辑也围绕这些对象展开。

## 第4章 系统设计

### 4.1系统架构设计

系统采用后端服务与桌面客户端分离的结构。后端以RESTful HTTP接口暴露认证、文件、目录、分享、回收站、日志和管理能力；桌面端用Qt/QML编写普通用户、访客和管理员界面，再由统一网络层调用这些接口。这样划分后，界面改动不会频繁牵动服务层，后端接口也能脱离客户端单独测试。

后端内部可以看成五层：客户端接入、过滤器、控制器、服务层和数据存储。客户端发起HTTP请求；过滤器处理JWT鉴权、管理员鉴权、分享令牌鉴权和接口限流；控制器解析请求并组织响应；服务层拆分认证、用户、文件、目录、分享、回收站、管理员、日志、健康检查和系统信息等业务。数据存储由MySQL、Redis和本地文件系统组成，三者分别保存结构化业务数据、短生命周期状态和物理文件对象。

### 4.2系统模块设计

模块划分以角色为主线。普通用户端包含账号管理、用户中心、文件管理、目录管理、分享管理、回收站管理和存储空间查看。账号管理处理注册、登录、刷新令牌和登出；文件管理处理分片上传、秒传、下载、重命名、移动、复制、删除和搜索；目录管理负责创建目录、目录树和面包屑路径；分享管理处理分享链接、访问密码、有效期、权限、我的分享、取消分享、访客浏览和保存分享内容；回收站管理负责列表、恢复和彻底删除。管理员端则集中在用户管理、存储统计、分享管理、操作日志和系统状态。图4-1和图4-2给出了两个端的功能结构。

### 4.3系统功能设计

#### 4.3.1用户认证模块设计

用户认证模块是系统入口，负责注册、登录、令牌刷新、登出和接口鉴权。注册时，后端先校验用户名和邮箱是否唯一，再用libsodium的Argon2id算法生成密码哈希，并向users表写入默认存储配额。登录时，服务层检查账号状态、锁定时间和密码哈希；认证通过后签发Access Token与Refresh Token，并把刷新令牌写入Redis。密码连续错误会累计失败次数，达到阈值后短时锁定账号。

JWT过滤器连接认证模块和业务控制器。需要登录的接口在Authorization: Bearer <access_token>中携带访问令牌，过滤器验证签名、过期时间和黑名单状态，再把用户ID、用户名和角色写入请求上下文。管理员接口在JWT校验之后还要经过管理员鉴权过滤器。Refresh Token保存在Redis中并在刷新时轮换；用户登出时，系统删除刷新令牌，并把当前访问令牌加入黑名单，使它在自然过期前也不能继续调用接口。

#### 4.3.2文件与目录模块设计

（1）文件管理模块

文件管理模块承接普通用户最频繁的操作，包括列表、搜索、上传、下载、重命名、移动、复制和删除。后端由FileController暴露/api/file/* 系列接口，控制器只做请求解析和响应转换，真正的业务判断放在FileService中。

文件列表按用户ID、目录ID、类型筛选、排序字段和分页参数查询files与folders表，再把当前目录下的文件和文件夹合并为统一列表项返回。搜索依赖文件名和目录名索引，可按关键词、类型和目录范围检索。文件详情接口返回元数据和面包屑路径，客户端据此构建导航视图。

文件变更要处理更多边界。重命名会检查名称长度、非法字符、保留名称和同目录冲突；移动目录时不能把目录放进自身或子目录下；复制文件不重复写物理内容，而是复用file_contents中的内容对象并增加引用计数。删除则进入回收站流程，普通删除只把恢复信息写入trash表并从正常列表移除，彻底删除时才减少引用计数，必要时清理物理文件。

（2）目录管理模块

目录管理模块负责维护用户的多级目录树结构。系统通过folders表保存目录名称、父目录ID、完整路径、深度和子项数量，其中根目录以parent_id = 0表示。创建目录时，后端校验目标父目录是否属于当前用户，并通过(user_id, parent_id, name)唯一约束保证同级目录名称不重复。

目录树接口通过递归查询返回当前用户的目录层级结构，面包屑接口返回从根目录到指定目录的路径链路。为了避免异常数据导致无限递归，服务层会限制目录树深度并在面包屑构建过程中检测循环引用。目录删除不直接丢弃数据，而是进入回收站流程，保留恢复所需的原始路径和项目数据。

（3）文件上传模块

文件上传是本系统里最容易出错的部分。当前实现采用统一的分片上传流程，默认分片大小为5MB，流程分为初始化上传、上传分片、完成合并和取消上传。初始化请求携带文件名、文件大小、目标目录和文件MD5，后端先检查配额，再按MD5查询file_contents表。若相同内容已经存在，服务端不再接收物理分片，只创建新的files记录并增加内容引用计数，上传在初始化阶段就结束，这就是秒传。

若文件内容不存在，系统创建upload_tasks记录并预占用用户存储空间。客户端随后按分片索引上传数据，后端把分片写入临时目录，并在upload_task_chunks表中记录已上传分片。断点续传依赖初始化接口返回的已上传分片列表，客户端恢复上传时只补缺失部分。所有分片到齐后，AssemblyWorkerPool控制合并并发，临时分片按顺序合并为完整文件，随后计算并校验内容哈希，写入file_contents和files表，释放预占用空间并将任务标记为完成。

#### 4.3.3分享模块设计

文件分享模块允许用户将自己的文件或目录通过外链方式分享给他人。创建分享时，后端在shares表中写入分享短码、分享者ID、可选访问密码哈希、权限类型、有效期和状态，并在share_files表中写入被分享的文件或目录关联。分享权限支持查看和下载两类，分享状态支持有效、取消和过期。

公开访问分享时，访客首先通过分享短码和可选密码调用访问接口。后端校验分享是否存在、是否过期、是否取消以及密码是否正确；校验通过后签发短期分享访问令牌。后续浏览分享目录或下载分享文件时，访客需要在X-Share-Token请求头中携带该令牌，由分享鉴权过滤器完成校验。系统会分别记录浏览次数和下载次数，并使用Redis对分享密码尝试进行限流，避免暴力猜测分享密码。

（1）回收站模块

回收站模块用于降低误删除风险。普通删除不会立即物理删除文件，而是把项目类型、原项目ID、原路径、项目名称、内容ID和完整数据备份写入trash表。用户可以分页查看回收站项目，也可以批量恢复、彻底删除或清空回收站。恢复时，如果原目录不存在，就回退到根目录；如果名称冲突，服务层生成新名称，避免覆盖现有文件。定时清理任务负责删除过期回收站记录和过期上传任务，防止临时数据长期堆积。

#### 4.3.4管理员与运维模块设计

（1）用户管理模块

管理员用户管理模块通过/api/admin/users系列接口维护平台账号。管理员可以查看用户列表、按条件筛选用户、查看详情和存储使用情况，也可以修改用户状态、调整角色、设置可用空间或软删除用户。用户状态在数据库中以数值保存，包括禁用、正常和锁定；角色也用数值区分普通用户和管理员。所有管理员接口都先经过JWT鉴权，再经过管理员角色鉴权。

（2）存储统计与分享管理模块

存储统计模块聚合users、files、file_contents、folders等表，计算全平台用户数、文件数、内容对象数、存储占用和各用户使用情况。由于系统采用内容寻址和引用计数，用户视角的逻辑文件大小与物理内容占用并不总是一致，统计时必须分开处理。

分享管理模块供管理员查看全平台分享列表、查看单个分享详情并强制取消违规分享。它主要用于处理公开链接滥用、误分享和过期分享治理等场景。

（3）系统状态与日志模块

系统状态模块面向部署和维护，展示服务运行时间、版本信息、数据库连接、Redis连接和磁盘空间等指标；操作日志则按分页形式保留上传、下载、删除、分享等动作，方便排查异常请求或用户反馈。

## 第5章 系统实现

本章结合项目代码说明系统落地过程。后端按控制器、过滤器、服务层、数据模型和存储抽象组织：控制器绑定路由、解析参数并转换响应，服务层处理业务规则、数据库事务和Redis状态。桌面端使用AuthShell、OwnerShell、VisitorShell和AdminShell区分登录、普通用户、访客分享和管理员场景，各页面再由对应Manager访问后端接口。

### 5.1用户与认证模块功能实现

（1）注册与登录实现

账号注册和登录接口由AuthController暴露，具体判断放在AuthService中。注册时，后端接收用户名、邮箱和密码，先由DTO检查格式，再查询users表确认用户名和邮箱没有被占用。校验通过后，服务层使用libsodium的Argon2id算法生成密码哈希，并写入默认昵称、头像、存储配额、账号状态和角色等字段。桌面端对应RegisterPage页面，注册成功后提示用户回到登录页。

登录接口支持用户名或邮箱两种入口。服务层读取账号状态、锁定截止时间和密码哈希后逐项判断：账号禁用或仍在锁定期内，直接拒绝；密码错误则累计失败次数，达到阈值后设置短时锁定；认证成功时重置失败计数，签发Access Token与Refresh Token，并返回用户ID、用户名、昵称和角色。客户端LoginPage发起请求，SessionStore保存会话信息，ShellController再根据角色切换到普通用户界面或管理员界面。

登录页对应的后端入口是AuthController。用户输入账号和密码后，LoginRequest DTO先检查JSON格式，随后AuthService按用户名或邮箱查询users表，继续判断账号状态、锁定时间和密码哈希。认证通过后，后端签发Access Token和Refresh Token，客户端保存会话信息并进入对应角色的主界面。

（2）令牌生命周期与鉴权过滤

令牌逻辑集中在TokenService中。Access Token采用JWT格式，携带用户ID、用户名、角色和过期时间等声明；普通业务接口由JwtAuthFilter校验Authorization: Bearer <token>请求头。Refresh Token保存在Redis中，用于续期访问令牌。刷新成功后，旧Refresh Token被替换，新的Access Token和Refresh Token返回客户端。用户登出时，系统删除Redis中的刷新令牌，并把当前访问令牌加入黑名单，使其在自然过期前也不能继续访问受保护接口。

不同访问边界使用不同过滤器。管理员接口在JWT校验后还要经过AdminAuthFilter，只有管理员角色可以访问/api/admin/* 路由；公开分享的浏览和下载接口使用ShareAuthFilter校验X-Share-Token，避免访客流程与登录用户JWT混在一起。桌面端网络层由RequestFactory按请求类型附加用户令牌、分享令牌或两者组合，请求来源也更容易区分。

（3）个人资料、密码与存储空间实现

用户中心由UserController和UserService实现，主要包括个人资料查询、资料更新、密码修改和存储空间查看。资料更新接口支持修改昵称和头像URL，服务层只更新请求中实际传入的字段，并同步更新时间。密码修改接口要求用户提交当前密码，校验通过后重新生成Argon2id哈希并更新users.password_hash，避免明文密码出现在客户端或数据库中。

存储空间接口读取users表中的storage_quota、storage_used和storage_reserved字段，并结合文件数、目录数等统计信息，返回已用空间、预占用空间、剩余配额和资源数量。桌面端SettingsPage和ProfileManager负责加载这些数据，用户修改资料或密码后，页面会根据接口返回结果给出成功或失败提示。

### 5.2文件传输模块功能实现

（1）分片上传初始化与秒传判断

文件上传由FileController提供初始化、上传分片、完成上传和取消上传接口，主要路径包括/api/file/upload/init、/api/file/upload/chunk和/api/file/upload/complete等。控制器继承Drogon的HttpController，通过METHOD_LIST_BEGIN和ADD_METHOD_TO绑定路由、HTTP方法和过滤器，上传接口接入JWT鉴权和上传限流过滤器。各处理函数返回drogon::Task<drogon::HttpResponsePtr>，控制器用co_await等待服务层逻辑，数据库或文件状态处理期间不会长时间占住请求线程。

客户端选择文件后，TransferManager提交文件名、文件大小、目标目录和文件MD5。这里先查配额很关键：如果当前已用空间加上预占用空间会超过上限，初始化阶段直接返回空间不足，客户端也就不必继续上传分片。

初始化阶段还会按文件哈希查询file_contents表。若系统里已经有相同内容对象，服务层不要求客户端上传物理文件，而是创建新的files元数据记录、增加内容对象引用计数，并返回秒传结果。若内容不存在，则创建upload_tasks记录，写入任务ID、目标目录、文件名、文件大小、分片大小、总分片数、临时路径、预占用字节数和过期时间，同时查询upload_task_chunks表返回已上传分片列表，为断点续传留下恢复点。

（2）分片写入、断点续传与后台合并

分片上传接口按任务ID和分片索引接收二进制内容。Drogon已经把请求体放在HttpRequest对象里，控制器直接读取request->body()即可取得application/octet-stream数据，不需要再套一层JSON。服务层随后检查任务归属和任务状态，确认无误后把分片落到临时目录，并在upload_task_chunks表中记下对应索引。

把大文件切成5MB左右的块，看起来只是上传策略变化，实际解决的是服务端内存压力问题。单个请求只处理一小段数据，网络中断后也不会推翻前面已经完成的部分。客户端恢复上传时再次调用初始化接口，拿到已上传分片索引后只补缺失块，断点续传的逻辑就落在这张分片记录表上。

最后一步是合并。客户端确认分片全部上传后调用完成接口，后端用AssemblyWorkerPool限制同一任务的合并并发，避免重复触发。合并程序按索引顺序读取临时文件，生成完整文件后计算MD5和SHA256，再同初始化阶段提交的哈希比对。校验无误后，IFileStorage的本地实现把文件移入内容寻址存储目录，服务层写入file_contents和files表，释放预占用空间并更新用户已用空间。取消上传或任务过期时，临时分片会被删除，任务状态和预占用空间同步回滚；CleanupService负责兜底清理长期遗留的数据。

（3）文件下载与Range断点下载

下载流程拆成两步：先查下载信息，再返回文件流。前一步给客户端文件名、大小和MIME类型；后一步先检查文件归属，确认当前用户有权访问后，再由IFileStorage找到内容寻址文件，交给DownloadResponder生成HTTP响应。

真正容易踩坑的是大文件下载。如果一次把完整文件读进内存，几个并发请求就可能把服务端拖慢。因此下载接口使用Drogon的HttpResponse::newStreamResponse，回调函数按固定块大小读取文件并写入响应缓冲区。这样内存占用相对稳定，服务端在发送文件时也还能处理其他连接。

请求头带Range字段时，后端解析起止字节，只返回对应区间，并补齐206 Partial Content、Content-Range、Accept-Ranges和Content-Length等响应头。若范围超过文件大小，则返回416 Requested Range Not Satisfiable，同时告知当前文件长度。普通下载、断点续传下载和非法Range响应共用同一套流式构造逻辑。桌面端由TransferManager和DownloadTaskModel管理下载任务，记录进度、状态和失败原因，也支持取消、重试以及暂停后继续下载。

（4）传输中心实现

传输中心放在TransferCenterPage中，和文件列表页分开。上传任务保存文件名、目标目录、已上传字节数、总字节数、状态和错误信息；下载任务保存本地路径、进度、暂停状态和完成状态。这样做的好处很直接：上传或下载时间较长时，用户不必盯着当前目录等待，可以继续浏览文件、切换目录或处理其他操作。

### 5.3文件与目录管理模块功能实现

（1）文件列表与资源管理器实现

普通用户的大部分操作都从DriveBrowserPage进入。OwnerShell加载后，页面会分出“我的网盘”“分享”和“回收站”等视图；其中“我的网盘”由DriveMyFilesView承载文件列表，工具栏和右键菜单放置刷新、上传、下载、新建文件夹、重命名、移动、复制、分享和删除等入口。后端列表接口不简单返回某一张表的数据，而是由FileService同时查询files和folders，再按用户ID、目录ID、分页参数和排序字段整理成统一列表项，字段包括ID、名称、类型、大小、更新时间、MIME类型和下载次数。

DriveManager保存当前目录ID、列表模型、排序方式、选择状态和加载状态。根目录使用ID 0表示；用户切换目录时，页面不重建，只更新目录ID和列表数据。请求失败或列表为空时，界面显示对应提示并允许重新加载。后端查询始终带着用户ID边界，普通用户即使构造其他目录ID，也不能越权读取别人的文件。

（3）重命名、移动、复制和搜索实现

重命名操作分别更新files或folders中的名称和路径。服务层在写入前检查名称长度、非法字符、保留名称和同级重名。移动接口支持批量文件和目录；移动目录时必须额外判断目标目录，不能把一个目录移动到自身或它的子目录下，否则目录树会被破坏。复制文件时只新增逻辑文件记录并增加file_contents.ref_count，不重复复制物理内容。

搜索接口按关键词、项目类型和目录范围返回分页结果。桌面端工具栏保存关键词和排序方式，用户输入后由DriveManager请求后端并刷新列表。批量移动、复制、删除和分享时，客户端一次提交多个项目ID，后端逐项处理并返回结果；界面再分别显示成功状态或失败原因。这个处理比简单返回“全部成功/失败”更适合批量操作，因为真实使用时经常只有其中一两个项目出问题。

### 5.4回收站模块功能实现

回收站由TrashController和TrashService负责。普通删除并不立刻释放存储空间，而是把项目类型、原项目ID、项目名称、原目录、原路径、大小、内容引用和必要的JSON备份写入trash表，再从正常文件或目录列表中移除。桌面端DriveTrashView读取这些记录，用户可以多选后恢复、彻底删除，也可以清空当前账号的回收站。

图5-8 回收站管理功能截图

![图5-8 回收站管理功能截图](assets/回收站管理功能截图.png)

图5-8是回收站界面。列表中保留已删除项目的名称、路径、大小和删除时间，操作区提供恢复、彻底删除和清空入口。

恢复时，服务层先确认回收站记录属于当前用户。能回到原父目录的，优先恢复到原位置；原目录已经不存在时，则恢复到根目录；若目标目录里有同名项目，服务层自动生成name (n).ext或name (n)这样的新名称，避免覆盖已有数据。当前版本对文件夹恢复采取较保守的规则：只恢复文件夹记录本身，不递归恢复其子树。

### 5.6管理后台与运维模块功能实现

（1）管理员用户管理实现

管理员接口集中在AdminController和AdminService中。所有/api/admin/* 路由都要先过JWT鉴权，再由AdminAuthFilter确认角色。管理员登录后进入AdminShell和AdminPage，用户、分享和系统状态被放在不同标签页中。用户管理接口支持分页、关键词、账号状态和角色筛选，返回用户ID、用户名、邮箱、昵称、存储使用量、账号状态和角色等信息。

管理员可以禁用或启用普通用户、调整角色、设置可用空间，也可以软删除用户。这里不能只看接口是否能改字段，还要处理几个边界：管理员不能禁用或降级自己，系统里最后一个管理员也不能被降级或禁用。状态变更、角色变更等操作完成后，服务层会写入操作日志，便于之后追踪。桌面端UserTab和AdminManager负责加载列表、提交操作并显示结果。

操作日志由OperationLogController和OperationLogService写入。登录、登出、上传、下载、删除、恢复、重命名、移动、复制、创建分享、取消分享以及管理员操作等路径都会记录到operation_logs表。日志字段包括用户ID、操作类型、目标类型、目标ID、目标名称、JSON详情、IP地址、客户端信息和创建时间。桌面端管理界面分页展示这些记录，便于管理员回溯问题。

### 6.3系统性能测试

性能测试围绕文件列表查询、目录导航、上传初始化和文件下载等高频接口展开，观察单机部署下的响应时间、吞吐量和错误率。后端使用Drogon异步I/O和协程服务层，本地文件采用内容寻址存储；上传分片状态、令牌状态和限流计数分别落在MySQL与Redis中，压力没有集中在单一组件上。从测试结果看，在毕业设计演示和中小规模私有化部署的范围内，接口响应保持稳定，未出现明显超时或服务异常。

### 6.4系统安全性测试

安全性测试重点放在几条容易出错的边界上：JWT鉴权、管理员角色校验、用户资源归属校验、分享访问令牌和密码错误限制。未登录访问受保护接口、普通用户访问管理员接口、用户下载他人文件、访客使用错误或过期分享令牌等请求都被单独测试。结果显示，这些请求会被拦截或返回对应错误；登出后的访问令牌也会因为黑名单状态失效。就当前设计范围而言，账号认证、文件访问隔离和公开分享控制可以满足第3章提出的安全性需求。

### 6.5测试总结

功能测试后，系统的主线业务基本能够稳定运行。普通用户、访客和管理员三类角色的核心流程都已通过验证，包括用户认证与鉴权、令牌刷新与登出、分片上传、断点续传、秒传去重、文件下载、目录管理、分享生成与访问控制、分享内容保存、回收站恢复与彻底删除，以及管理员用户管理、分享管理、操作日志、存储统计和系统状态查询。

安全性测试中，几类容易出问题的场景被单独验证：用户访问他人文件、普通用户访问管理员接口、令牌过期、登出后继续请求、登录失败锁定、分享密码错误和分享令牌失效。测试结果表明，这些请求能够被拦截或按预期处理。存储配额限制也能在上传初始化阶段生效，避免客户端继续上传无效分片。

也要承认，当前测试仍然偏毕业设计演示环境。系统主要在本地单机条件下验证，尚未做充分的大规模并发压测，Drogon在真实高并发文件传输中的吞吐量和延迟还缺少数据支撑。操作日志和健康检查已经具备，但监控告警、容量趋势分析和容灾恢复仍然比较基础。桌面端覆盖了登录、文件浏览、传输中心、分享访问、回收站和管理后台等主要页面，不过拖拽上传、缩略图预览和文件在线预览还没有完成。如果面向实际部署，后续应优先补充性能压测和运维监控，再继续完善客户端体验。

## 总结与展望

本课题完成了一套面向私有化部署的网络磁盘系统。论文从需求分析写起，随后展开总体架构、数据库结构、模块设计、功能实现和测试过程。系统后端采用C++23和Drogon Web框架，桌面端采用Qt 6和QML，数据层由MySQL、Redis和本地内容寻址文件系统组成。最终系统区分普通用户、访客和管理员三类角色，覆盖文件存储、传输、分享和后台运维的主要流程。

功能层面，系统已经完成注册登录、Access Token与Refresh Token管理、JWT鉴权、管理员角色鉴权、个人资料与存储空间统计、多级目录树、面包屑路径、分片上传、断点续传、秒传去重、后台合并、Range下载、文件重命名、移动、复制、搜索、回收站软删除与恢复、外链分享、分享密码访问、分享浏览与下载、分享内容保存、操作日志、健康检查和系统状态查询等功能。桌面端对应实现了认证界面、网盘资源管理器、传输中心、访客分享访问页、个人设置页和管理员后台。上传与存储部分用upload_tasks和upload_task_chunks保存分片状态，再借助file_contents中的内容哈希和引用计数完成秒传与去重，这是本系统实现中比较关键的一条链路。

测试结果基本符合毕业设计阶段的预期。注册登录、文件传输、目录管理、分享访问控制、回收站恢复、权限边界和管理员操作等流程都能按设计运行，RESTful接口的数据交互也较清楚。对笔者而言，这次实现至少说明一点：C++23、Drogon、MySQL、Redis和Qt/QML可以组合出一套可运行的中小规模私有化网盘系统，而不必完全依赖重量级Web框架。

不足也比较明显。文件版本历史、WebDAV协议、在线预览和缩略图生成尚未完成；高并发压力测试和安全渗透测试还不充分，大规模文件传输下的吞吐量、延迟和稳定性缺少更多实验数据。系统已有操作日志、健康检查和状态接口，但监控告警、容量趋势分析、自动备份和容灾恢复仍然偏基础。若继续推进，笔者会先补两类工作：一是客户端体验，例如拖拽上传、缩略图和更细的传输错误提示；二是压测与运维数据，再根据结果考虑对象存储接入和更完整的监控能力。
