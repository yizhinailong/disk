# 基于Drogon的网络磁盘系统的设计与实现

## 摘　要

在学习、办公和项目开发过程中，用户会不断产生课程文档、图片、代码包和临时资料，这些文件如果长期分散在不同设备中，查找、备份和跨设备访问都会变得不方便。公有云网盘虽然降低了使用门槛，但文件需要交由第三方平台托管，容量、带宽、访问策略和账号规则也受到平台限制。针对个人服务器和小型团队中较常见的数据自主管理需求，本文设计并实现了一套基于Drogon的私有化网络磁盘系统。

系统开发时将后端服务和桌面客户端分开处理。后端采用C++23与Drogon框架，主要承担接口响应、文件传输、认证鉴权和后台管理等业务；桌面端采用Qt 6和QML编写界面，并通过RESTful API访问后端服务。系统运行数据按保存时间和使用频率进行区分：MySQL保存用户、文件元数据、目录、上传任务、分享、回收站和操作日志等长期数据，Redis保存刷新令牌、访问令牌黑名单、登录失败计数、分享访问状态和限流计数等短期状态，真实文件则按内容哈希写入服务器本地目录。围绕普通用户、访客和管理员三类场景，系统完成了注册登录、令牌刷新、空间查看、文件列表与搜索、重命名、移动、复制、软删除、分片上传、断点续传、秒传、Range下载、外链分享、回收站处理，以及后台用户、分享、日志和系统状态管理等功能。

从系统运行和测试结果来看，本文实现的私有化网络磁盘系统已经完成主要业务流程。普通用户可以在桌面端完成文件整理、传输任务处理和分享创建，管理员可以完成用户、分享、日志和系统状态查看。测试结果显示，注册登录、文件传输、目录管理、分享访问和权限控制等流程与设计要求基本一致，在上传下载和异步接口处理场景下，Drogon协程与非阻塞I/O机制能够支撑系统正常运行。

关键词：网络磁盘；文件管理；Drogon；C++23；RESTful API

## ABSTRACT

With the continuous growth of digital materials generated in study, work, and project collaboration, documents, images, code packages, and temporary files are increasingly stored in scattered locations, which makes unified management and cross-device access more difficult. Public cloud drives are convenient to use, but file data is hosted by third-party platforms, and storage capacity, bandwidth, access policies, and service rules are all limited by platform conditions. In order to improve data controllability in personal server and small-team environments, this thesis designs and implements a private network disk system based on Drogon.

The system adopts a separated architecture between the backend service and the desktop client. The backend is developed with C++23 and the Drogon framework to implement interface processing, file transfer, authentication, authorization, and backend management logic. The desktop client is built with Qt 6 and QML and communicates with the backend through RESTful APIs. Runtime data is divided according to its lifecycle. MySQL stores persistent data such as users, file metadata, directory structures, upload tasks, share records, trash records, and operation logs. Redis stores short-lived states such as refresh tokens, token blacklists, login failure counters, share access states, and rate-limiting counters. File entities are stored in the local server directory according to content hashes. Around the three usage scenarios of regular users, visitors, and administrators, the system implements registration and login, token refresh, storage querying, file listing and searching, renaming, moving, copying, soft deletion, chunked upload, resumable upload, instant deduplication, Range download, external sharing, trash handling, and backend management of users, shares, logs, and system status.

According to system operation and test results, the private network disk system implemented in this thesis has completed the main business workflows. Regular users can manage files, handle transfer tasks, and create shares on the desktop client, while administrators can view users, shares, logs, and system status. The test results show that registration, login, file transfer, directory management, share access, and permission control are basically consistent with the design requirements. In upload, download, and asynchronous interface scenarios, Drogon's coroutine and non-blocking I/O mechanisms can support normal system operation.

KEYWORDS: Network Disk; File Management; Drogon; C++23; RESTful API

## 前　言

学习、办公和日常生活中产生的数字资料越来越多，课程文档、个人笔记、项目代码、图片和视频等文件，都需要有一个相对集中的位置进行保存和访问。网络磁盘把文件存储与网络访问结合起来，使用起来比单纯依赖本地硬盘更方便，也适合团队之间共享资料。不过，公有云网盘并不能覆盖所有场景，数据托管、容量限制、带宽限制和平台规则变动都会影响实际使用。对于希望自己掌握数据和部署环境的个人用户或小型团队来说，私有化网络磁盘仍然有其必要性。

在实际使用中，网络磁盘最常被用到的还是上传、下载、目录整理、搜索和分享这些操作。大文件传输比较容易受到网络波动影响，如果中断后只能从头开始上传，用户很快就会感觉麻烦，所以文件传输模块必须考虑断点续传。分享功能看起来只是生成一个链接，但如果没有有效期、访问密码和权限控制，临时链接后续很容易变成安全和管理上的负担。

除了普通用户的文件操作，管理员日常维护时也需要有相应入口。账号数量、存储占用、数据库连接、Redis状态和磁盘空间等信息，如果每次都要分别到数据库客户端、Redis命令行和服务器终端中查看，排查问题会比较费时。因此，本文在实现普通用户文件管理的同时，也把后台管理、操作日志和系统状态查询放入同一套服务体系中。

后端选用C++23和Drogon框架，主要考虑文件服务对磁盘和网络I/O的依赖较重。Drogon底层通过epoll（macOS/FreeBSD下为kqueue）处理网络事件，并支持协程化请求处理，用在上传、下载这类等待时间较长的接口中比较合适。相比阻塞式Web框架，C++后端对内存和请求细节更容易控制。系统数据层使用MySQL保存关系型元数据，Redis保存令牌、限流等短时状态，文件实体放在本地内容寻址目录中。

本文按照需求分析、系统设计、数据库设计、功能实现和测试验证的顺序展开研究。课题不以大型分布式云存储系统为目标，而是面向中小型私有化文件服务场景，验证Drogon、MySQL和Redis组合完成网络磁盘业务流程的可行性。

## 第1章 绪论

### 1.1研究背景

近几年，个人数字内容增长较快，在线存储服务也更常见。云存储让文件不再固定在某一台设备中，用户联网后即可访问资料，确实方便了个人整理和团队协作。但公有云网盘并不适合所有场景：文件放在第三方服务器上，隐私数据和商业资料的保护存在不确定性；免费套餐常限制容量和速度，高级功能还需要持续付费；服务商调整策略或停止服务时，用户也很难掌握主动权。对有合规要求的机构和团队来说，数据必须留在自主可控的基础设施内，公有云盘的使用就会受到限制。

私有化自建网盘由此具有一定现实需求。文件实体和元数据保存在自有服务器上，数据位置、访问策略、存储空间和网络带宽都可以按照自身条件进行配置。不过，要设计一个功能完整、运行稳定且部署负担较低的网络磁盘系统并不简单。传统脚本语言或解释型Web框架在高并发文件传输场景下，可能会面临吞吐不足或资源占用较高的问题。本文选择C++语言和Drogon Web框架实现私有化网络磁盘系统，主要是为了在毕业设计范围内验证该技术路线在文件服务场景中的适用性。

### 1.2研究意义

本课题面向私有化网络磁盘的实际应用场景，设计并实现一个功能相对完整的文件服务系统。系统把用户文件管理、目录组织、大文件上传、文件分享和管理员后台等功能整合到同一套后端服务中，并使用C++与Drogon承担文件传输和接口处理任务。该系统不是停留在概念层面的设计方案，而是一个可以部署、可以运行、可以测试的工程实践样例。

从使用对象来看，该系统主要面向个人开发者、高校师生和中小团队，用来完成文件的集中保存和管理。文件上传、目录整理、文件检索和分享操作都放在同一客户端界面中，用户不必在多个工具之间来回切换；存储配额和已用空间也在用户侧展示，便于判断后续是否还能继续上传文件。管理员端则提供账号管理、存储统计和系统状态查看等入口，可以减少日常维护时对数据库客户端、Redis命令行和系统磁盘工具的依赖。

从工程实践角度看，本课题把C++系统编程、异步网络I/O、Web框架、关系型数据库、缓存状态和RESTful接口放到同一个项目中使用。实现时并不是把各个模块单独做完即可，还要处理认证、文件传输、目录结构、权限边界和桌面客户端交互之间的配合关系。特别是在上传取消、文件删除、分享失效等异常场景下，数据库记录、Redis状态和本地文件需要尽量保持一致。通过完成该系统，笔者对Drogon请求处理流程、MySQL表结构设计和前后端接口约定有了更具体的认识。

### 1.3国内外研究现状

云存储和网络磁盘并不是新的研究方向，相关理论和工程实践已经比较丰富。但是，当研究范围缩小到“基于C++ Web框架的私有化网络磁盘系统”时，可以直接借鉴的完整案例相对较少。

国外在云存储领域起步较早，分布式文件系统、对象存储和数据去重等方向已经形成了较多成熟方案。Google文件系统（GFS）、Amazon S3和OpenStack Swift等系统在架构层面具有较大影响，但这些系统主要面向数据中心级别的水平扩展场景，如果直接用于单机私有化部署，会显得结构较重。开源网盘系统中，Nextcloud和ownCloud功能较完整，但PHP运行模型对服务器配置和运行性能有一定要求；SeaweedFS、MinIO等Go语言项目更偏向对象存储基础设施，并不直接提供面向普通用户的桌面网盘交互。

国内公有云网盘发展速度较快，百度网盘、阿里云盘等产品推动了文件秒传、内容去重、传输加速和版权保护等相关方向的发展。在教学和毕业设计项目中，自建网盘系统常采用Java Spring Boot、Python Django或Flask配合关系型数据库和本地文件系统的方式实现，基本功能通常可以满足使用需要，但在高并发文件传输和资源占用控制方面仍有继续优化的空间。采用C++ Web框架，尤其是Drogon框架，完成完整网络磁盘业务流程的公开案例并不多，这也是本文选题的重要原因之一。

已有研究和系统实践可以为云存储架构和私有网盘开发提供参考，但在中小规模、私有化部署和C++后端这几个条件同时存在时，仍需要结合具体工程进行验证。本文不以替代成熟云存储系统为目标，而是尝试给出一种面向单机或小团队环境的网络磁盘实现路径。

### 1.4本文的组织结构

本文围绕私有化网络磁盘系统的设计与实现展开研究，重点内容包括文件存储访问、大文件传输、目录树管理、分享链接控制和后台运维管理。课题目标是完成一个普通用户和管理员均可使用的网络磁盘平台，并通过系统实现和测试结果验证其在毕业设计场景下具备部署、演示和维护的可行性。

用户侧接口主要包括账号注册、登录、令牌刷新与登出，个人资料与存储空间统计，文件和目录的分页列表、搜索、详情、重命名、移动、复制、软删除，目录树与面包屑路径查询，分片上传、断点续传、秒传去重、后台合并、Range下载，外链分享、分享密码校验、分享内容浏览与下载，以及回收站恢复和清空等功能。管理员侧功能更偏向系统维护，主要包括用户查询、状态切换、角色变更、软删除、用户文件与存储查看、全局存储统计、分享列表与强制取消、系统概览和系统状态查询。

对于文件上传和下载等I/O等待较多的请求，系统采用Drogon异步非阻塞I/O和C++协程模型进行处理。上传任务和分片状态写入数据库，客户端断线后只需要补传缺失分片；文件内容哈希和引用计数用于实现秒传与去重，避免相同内容重复落盘。Redis承担令牌、限流和登录失败次数等短时状态，从而减少高频状态变化对MySQL的压力。

系统安全设计主要围绕几个边界处理。普通用户只能访问自己名下的文件和目录；管理员接口除了校验登录状态，还要检查用户角色；公开分享访问不直接复用用户JWT，而是通过分享短码、可选密码、短期分享令牌和有效期共同限制访问范围。用户密码使用Argon2id算法进行哈希存储，登录失败计数和短时锁定机制则用于降低暴力破解带来的风险。

后端按照认证、用户、文件、目录、分享、回收站、运维统计和操作日志等模块进行拆分。控制器主要负责请求解析和响应转换，核心业务判断集中在服务层完成；存储层通过IFileStorage隔离本地文件系统。后续如果继续接入对象存储、文件版本历史、WebDAV接口或缩略图预览，也可以在现有模块基础上继续扩展。

## 第2章 相关技术分析

### 2.1 Drogon框架与C++23协程

Drogon是一个面向HTTP服务的C++ Web框架，底层网络库基于epoll（在macOS/FreeBSD下为kqueue）处理非阻塞I/O。文件上传和下载请求通常以磁盘读写和网络等待为主，如果采用阻塞模型，线程资源容易被长时间占用。本系统采用C++23标准，并结合Drogon提供的HttpController、HttpCoroFilter和drogon::Task协程接口组织控制器、过滤器和服务层逻辑。业务返回值采用std::expected风格的Result<T>表达成功或失败状态，减少普通业务分支对异常控制流的依赖。

### 2.2 MySQL数据库

MySQL是常用的关系型数据库，稳定性和资料都比较成熟，适合保存中小规模业务系统中的长期数据。本系统把用户账号、文件内容哈希、文件元数据、目录树、上传任务、上传分片、回收站记录、分享记录、分享文件关联和操作日志放在MySQL中。文件列表、目录树遍历、秒传查重、配额统计和分享访问等查询频率较高，因此表结构中设置了联合索引、全文索引和唯一约束。

### 2.3 Redis缓存与状态管理

Redis是内存型键值数据库，适合保存生命周期较短、访问频率较高的系统状态。本系统将Refresh Token、Access Token黑名单、登录失败计数、分享访问令牌、密码尝试次数和接口限流计数保存到Redis中。该设计可以把易过期、变化频繁的状态从MySQL中分离出来，使鉴权、限流和安全控制逻辑更加清晰。

### 2.4 JWT身份鉴权机制

JWT（JSON Web Token）是一种基于JSON格式的开放标准（RFC 7519），用于在各方之间以紧凑、自包含的方式安全地传递身份认证信息。本系统在用户登录成功后签发Access Token与Refresh Token，普通业务请求通过Authorization: Bearer <token>携带访问令牌，令牌刷新和登出依赖Redis中保存的刷新令牌与黑名单状态实现轮换和失效控制；公开分享访问则使用独立的分享令牌并通过X-Share-Token请求头传递，避免将用户JWT暴露给未登录访客。

### 2.5 CMake构建工具与安全基础库

CMake是跨平台构建工具，也是Drogon项目中比较常用的构建方式。本系统在后端工程中使用CMakeLists.txt、CMakePresets.json和vcpkg manifest管理编译依赖、构建预设和第三方库，使Linux与Windows环境下的编译、测试和部署步骤保持一致。密码处理方面，系统使用libsodium提供的Argon2id算法保存用户密码，避免把明文密码或弱哈希结果直接写入数据库。

### 2.6 Qt框架与QML

Qt是常用的跨平台C++应用程序开发框架，适合桌面端界面开发。本系统桌面客户端基于Qt 6实现，网络请求部分使用Qt Network访问后端RESTful API，处理分片上传、断点下载和JSON解析。界面层采用QML（Qt Modeling Language）和Qt Quick Controls 2编写文件列表、目录导航、传输进度、分享管理和后台管理页面。实现时，QML负责界面声明和状态绑定，C++侧保存网络请求与业务状态，两者通过属性绑定和信号槽机制连接，避免界面代码和通信逻辑混在一起。

## 第3章 需求分析

### 3.1系统需求概述

在建设私有化网络磁盘系统之前，需要从技术条件、经济成本和使用流程三个方面分析系统建设的可行性。结合课题目标和已选技术栈来看，本系统具备落地实现的基础条件。

技术方面，C++23、Drogon、MySQL和Redis可以覆盖本课题的大部分功能需求。Drogon已经提供HTTP路由、过滤器、控制器、协程任务、异步数据库访问和配置文件管理等能力，能够为后端服务开发提供基础支撑。MySQL负责保存用户、文件、目录、分享和日志等结构化数据，Redis负责保存令牌、限流、登录失败计数等生命周期较短的状态。C++23中的协程、std::expected和std::filesystem分别对应异步流程组织、错误返回表达和文件路径处理。JWT鉴权、Argon2id密码哈希以及CMake/vcpkg构建体系也都有成熟库可供使用。

经济可行性方面，本系统使用的软件和运行环境均有开源免费版本，包括Drogon、MySQL社区版、Redis、CMake、GCC/Clang以及常见Linux工具。系统对硬件要求不高，普通个人计算机或低配云服务器即可完成编译、部署和演示。对毕业设计项目来说，成本主要是开发、调试和测试时间，不需要额外投入较高的软硬件采购费用。

使用流程方面，系统面向普通用户和管理员两类账号，同时为未登录访客保留受限的分享访问入口。后端接口围绕账号认证、个人资料、文件上传下载、目录管理、分享、回收站、日志和运维统计展开，接口路径和响应格式保持相对统一。桌面客户端通过RESTful API接入后端，管理员功能由受保护的管理接口承担。权限校验、错误响应和业务状态由后端统一处理，后续二次开发只需要遵守既有接口契约。

### 3.2系统功能需求分析

私有化网络磁盘系统的需求主要来自普通用户和管理员两个方面。普通用户关注文件是否能够稳定上传、是否便于整理、是否可以在需要时进行分享；管理员则更加关注账号、存储资源和系统运行状态是否可控。围绕这两类角色，系统需求可以分为功能需求和非功能需求两个部分。

#### 3.2.1账号与用户模块需求分析

账号与用户模块主要负责身份识别和登录状态维护。普通用户可以注册、登录、刷新令牌、登出，也可以查询或修改个人资料、修改密码、查看存储空间。注册时，系统检查用户名和邮箱是否已被占用；登录时，除校验密码外，还要判断账号状态和失败次数。认证通过后，后端签发Access Token与Refresh Token，后续业务接口依赖令牌完成鉴权和续期。用户中心展示已用空间、预占用空间、剩余配额、文件数和目录数，方便用户了解存储使用情况。

管理员侧账号功能更偏向平台维护。系统需要支持用户列表查询、关键字与状态筛选、用户详情查看、存储使用量查询、可用空间调整、账号禁用或启用、角色变更和软删除。由于管理员操作会直接影响平台账号状态和权限边界，因此所有管理员操作都必须先经过普通JWT鉴权，再经过管理员角色鉴权。

#### 3.2.2文件与目录模块需求分析

文件模块覆盖上传、访问、整理和删除等主要环节。系统需要支持文件与目录混合分页展示、按名称搜索、详情查询、重命名、批量移动、批量复制和软删除等操作。下载方面，除普通完整下载外，还需要支持HTTP Range断点下载，使客户端在网络不稳定时可以继续已有进度。

上传功能是文件模块中状态变化最多的部分。系统需要把上传过程拆分为初始化上传、上传分片、完成合并和取消上传四个阶段，并通过上传任务和分片记录保存进度，从而支持断点续传。当服务器中已经存在相同内容文件时，系统应根据内容哈希完成秒传，不再重复接收和保存物理文件。目录模块则需要支持多级目录创建、目录树查询和面包屑路径查询，同时保证同一用户在同一父目录下不能创建同名目录。

#### 3.2.3分享、回收站与管理模块需求分析

分享模块需要支持用户为文件或目录生成外链分享，并能够设置有效期、访问密码和查看或下载权限。未登录访客访问分享时，系统应先校验分享短码、分享状态、有效期和访问密码，校验成功后再签发短期分享访问令牌；访客浏览分享内容或下载分享文件时，需要通过独立的分享令牌完成鉴权，避免公开访问流程与登录用户JWT混用。

回收站模块主要面向误删除后的恢复需求。用户删除文件或目录时，系统不应立即清除物理内容，而是先把项目放入回收站，并保存原路径、原所属目录、项目类型、内容引用和恢复所需数据。用户可以查看回收站列表，也可以执行批量恢复、彻底删除或清空回收站。管理员与运维模块则需要提供全局存储统计、分享记录查看、违规分享强制取消、系统概览、数据库状态、Redis状态和磁盘空间状态查询等功能。

#### 3.2.4系统用例分析

本系统主要涉及普通用户和管理员两个账号角色，并包含未登录访客访问分享的公开场景。普通用户通过用户端完成注册登录、文件上传与下载、目录管理、文件分享等操作；访客通过分享短码、访问密码和分享令牌浏览或下载授权内容；管理员通过后台完成用户管理、存储统计查看和系统参数配置等操作。

普通用户的核心用例主要包括：账号注册、账号登录、刷新令牌、登出、查看和更新个人资料、修改密码、查看存储空间、初始化上传、上传分片、完成上传、取消上传、下载文件、查看文件列表、搜索文件或目录、创建目录、查看目录树、查看面包屑路径、重命名文件或目录、移动或复制文件和目录、删除到回收站、查看回收站、恢复回收站项目、彻底删除回收站项目、生成分享链接、查看我的分享、更新或取消分享、通过分享密码访问分享、浏览分享内容、下载分享文件以及保存分享内容到个人网盘；管理员的核心用例则包括：管理员登录、查看全部用户列表、查看用户详情、禁用或启用用户账号、修改用户角色、调整用户可用空间、软删除用户、查看全平台存储统计、查看分享列表、查看分享详情、强制取消分享、查看操作日志、查看系统概览以及查看系统状态。

### 3.3系统非功能需求分析

#### 3.3.1系统性能需求分析

系统需要在单机私有化部署环境下保持稳定运行，并尽量利用Drogon框架的异步I/O能力提高文件传输效率。文件列表、目录导航、存储配额查询等元数据请求数据量相对较小，后端应在较短时间内返回结果；上传和下载面对的文件可能较大，不能简单地把完整文件一次性读入内存，而应采用流式处理方式控制内存峰值。上传任务和分片状态也需要持久化保存，这样客户端网络中断后才能继续补传缺失分片。

#### 3.3.2系统安全性与可维护性需求分析

系统需要对不同用户的文件资源严格隔离，普通用户只能访问自己名下的文件和目录，不能通过接口越权访问或下载他人文件；管理员接口需要单独鉴权，普通用户令牌无法访问管理员功能。文件分享链接需要使用随机短码、可选访问密码、有效期和短期分享访问令牌共同控制公开访问范围。用户密码必须经过安全哈希后存储，不得以明文形式保存在数据库中。

可维护性方面，后端代码按认证、用户、文件、目录、分享、回收站、管理员、日志和系统状态等模块划分。控制器处理请求解析和响应转换，业务判断放在服务层；数据库表结构需要字段含义清楚、约束设置合理，便于后续维护和Schema调整。

#### 3.3.3数据字典

本系统涉及的核心数据对象主要包括用户信息、文件内容、文件元数据、目录信息、上传任务、上传分片、回收站记录、分享记录、分享文件关联和操作日志等，以下分别对主要数据对象的字段组成和含义进行说明。

用户信息（users）是整个系统的基础数据对象，主要用于保存用户的账号凭据、个人资料、登录安全状态和存储配额信息，是登录鉴权、文件归属判断和存储限额控制的核心依据。其主要字段包括用户主键ID、用户名、邮箱、哈希后的密码、昵称、头像、存储配额、已用存储、上传预占用存储、账号状态、角色类型、登录失败次数、锁定截止时间、最后登录时间、最后登录IP、创建时间和更新时间。

文件内容（file_contents）保存物理文件的索引信息，秒传去重和内容寻址存储都依赖该表。主要字段包括内容ID、MD5哈希、SHA256哈希、文件大小、实际存储路径、MIME类型、引用计数和创建时间。多个用户文件记录可以指向同一个内容对象，相同文件内容不需要重复落盘。

文件元数据（files）保存用户视角下可见文件的描述信息，不直接保存文件二进制内容。其主要字段包括文件主键ID、所属用户ID、关联内容ID、所属文件夹ID、文件名、扩展名、文件大小、MIME类型、完整路径、收藏标记、下载次数、最后访问时间、创建时间和更新时间。文件列表、文件详情和权限判断等功能都会读取该表。

目录信息（folders）维护用户目录树，是目录导航和文件路径组织的基础表。主要字段包括目录ID、所属用户ID、父目录ID（根目录以0表示）、目录名称、完整路径、目录深度、子项数量、创建时间和更新时间。系统通过父目录ID形成父子关系，并据此构建多级目录。

上传任务（upload_tasks）用于大文件分片上传和断点续传，记录任务是进行中、已完成、已取消还是已过期。主要字段包括上传任务ID、用户ID、目标文件夹ID、文件名、文件大小、文件MD5、分片大小、总分片数、预占用字节数、临时存储路径、任务状态、过期时间、完成时间、失败原因、创建时间和更新时间。上传分片（upload_task_chunks）以任务ID和分片索引作为联合主键，用来标记已上传分片。

回收站记录（trash）保存被软删除文件或目录的恢复信息。其主要字段包括回收站记录ID、用户ID、项目类型、原项目ID、项目名称、项目大小、关联内容ID、原所属文件夹ID、原完整路径、项目完整数据备份、删除时间和过期时间。借助该表，系统可以在彻底删除前恢复误删项目；记录过期或用户执行彻底删除时，再减少内容引用计数并释放对应物理存储。

分享记录（shares）保存外链分享的基础信息，包括分享ID、分享短码、分享者用户ID、访问密码哈希、权限类型、访问次数、下载次数、状态、过期时间、创建时间和更新时间。分享文件关联（share_files）记录分享中包含的文件或目录，字段包括关联记录ID、分享ID、项目类型、项目ID和创建时间。拆成两张表后，一个分享可以关联多个项目，后续扩展目录浏览也更方便。

操作日志（operation_logs）记录上传、下载、删除、分享等关键动作。字段包括日志ID、用户ID、操作类型、目标类型、目标ID、目标名称、操作详情、IP地址、客户端信息和创建时间。出现异常下载、误删文件或分享访问问题时，管理员可以根据日志确认操作对象、发起用户和时间。

这些数据对象覆盖了系统运行时的主要业务信息，后续数据库设计和服务层逻辑也围绕它们展开。

## 第4章 系统设计

### 4.1系统架构设计

系统采用后端服务与桌面客户端分离的结构进行设计。后端通过RESTful HTTP接口提供认证、文件、目录、分享、回收站、日志和管理等能力，桌面端使用Qt/QML编写普通用户、访客和管理员界面，并通过统一网络层调用后端接口。该结构可以降低界面层和服务层之间的耦合程度，也便于后端接口脱离客户端进行单独测试。

后端内部可以划分为客户端接入层、过滤器层、控制器层、服务层和数据存储层。客户端负责发起HTTP请求；过滤器负责处理JWT鉴权、管理员鉴权、分享令牌鉴权和接口限流；控制器负责解析请求并组织响应；服务层负责认证、用户、文件、目录、分享、回收站、管理员、日志、健康检查和系统信息等业务处理；数据存储层由MySQL、Redis和本地文件系统组成，分别保存结构化业务数据、短生命周期状态和物理文件对象。

### 4.2系统模块设计

系统模块划分以用户角色和业务流程为主线。普通用户端包含账号管理、用户中心、文件管理、目录管理、分享管理、回收站管理和存储空间查看等模块。账号管理用于处理注册、登录、刷新令牌和登出；文件管理用于处理分片上传、秒传、下载、重命名、移动、复制、删除和搜索；目录管理负责创建目录、目录树和面包屑路径；分享管理负责分享链接、访问密码、有效期、权限、我的分享、取消分享、访客浏览和保存分享内容；回收站管理负责列表查询、恢复和彻底删除。管理员端主要包括用户管理、存储统计、分享管理、操作日志和系统状态。图4-1和图4-2给出了用户端和管理员端的功能结构。

### 4.3系统功能设计

#### 4.3.1用户认证模块设计

用户认证模块是系统的入口模块，主要负责注册、登录、令牌刷新、登出和接口鉴权等功能。注册时，后端先校验用户名和邮箱是否唯一，再使用libsodium提供的Argon2id算法生成密码哈希，并向users表写入默认存储配额。登录时，服务层检查账号状态、锁定时间和密码哈希；认证通过后签发Access Token与Refresh Token，并把刷新令牌写入Redis。密码连续错误会累计失败次数，达到阈值后账号进入短时锁定状态。

JWT过滤器用于连接认证模块和业务控制器。需要登录的接口在Authorization: Bearer <access_token>中携带访问令牌，过滤器验证签名、过期时间和黑名单状态，再把用户ID、用户名和角色写入请求上下文。管理员接口在JWT校验之后还需要经过管理员鉴权过滤器。Refresh Token保存在Redis中并在刷新时进行轮换；用户登出时，系统删除刷新令牌，并把当前访问令牌加入黑名单，使其在自然过期前不能继续调用受保护接口。

#### 4.3.2文件与目录模块设计

（1）文件管理模块

文件管理模块承担普通用户最常使用的文件操作功能，包括列表、搜索、上传、下载、重命名、移动、复制和删除。后端由FileController暴露/api/file/* 系列接口，控制器负责请求解析和响应转换，具体业务判断由FileService完成。

文件列表接口会根据用户ID、目录ID、类型筛选、排序字段和分页参数查询files与folders表，然后把当前目录下的文件和文件夹整理成统一列表项返回。搜索功能主要依赖文件名和目录名索引，支持按关键词、类型和目录范围检索。文件详情接口除返回元数据外，还会返回面包屑路径，客户端据此构建导航视图。

文件变更类操作需要处理名称、路径和内容引用等边界。重命名操作需要检查名称长度、非法字符、保留名称和同目录冲突；移动目录时不能把目录移动到自身或其子目录下；复制文件时不重复写入物理内容，而是复用file_contents中的内容对象并增加引用计数。删除操作进入回收站流程，普通删除只把恢复信息写入trash表并从正常列表移除，彻底删除时才减少引用计数，必要时清理物理文件。

（2）目录管理模块

目录管理模块维护用户的多级目录结构。系统在folders表中保存目录名称、父目录ID、完整路径、深度和子项数量，根目录统一用parent_id = 0表示。创建目录时，后端先确认父目录属于当前用户，再通过(user_id, parent_id, name)唯一约束避免同级重名。

目录树接口按父子关系返回当前用户的目录层级，面包屑接口返回从根目录到指定目录的路径链路。为避免异常数据造成循环引用，服务层构建目录树时会限制最大深度，生成面包屑时也会检查重复节点。目录删除不直接丢弃数据，而是先进入回收站流程，保留恢复所需的原始路径和项目数据。

（3）文件上传模块

文件上传是本系统中状态变化较多的功能。当前系统采用统一的分片上传流程，默认分片大小为5MB，流程包括初始化上传、上传分片、完成合并和取消上传四个阶段。初始化请求携带文件名、文件大小、目标目录和文件MD5，后端先检查用户配额，再按照MD5查询file_contents表。若系统中已经存在相同内容对象，服务端不再接收物理分片，而是创建新的files记录并增加内容引用计数，上传流程在初始化阶段即可完成，该过程即为秒传。

如果服务器中还没有对应文件内容，系统会创建upload_tasks记录，并先预占用用户存储空间。客户端随后按照分片索引上传数据，后端把分片写入临时目录，同时在upload_task_chunks表中记录已完成的分片。断点续传时，初始化接口返回已上传分片列表，客户端只补传缺失部分即可。全部分片上传完成后，AssemblyWorkerPool控制合并并发，后端按顺序合并临时分片，计算并校验内容哈希，再写入file_contents和files表，最后释放预占用空间并把任务状态改为完成。

#### 4.3.3分享模块设计

文件分享模块用于把用户自己的文件或目录生成外链，供其他人访问。创建分享时，后端在shares表中写入分享短码、分享者ID、可选访问密码哈希、权限类型、有效期和状态，并在share_files表中保存被分享文件或目录的关联关系。分享权限分为查看和下载两类，分享状态则包括有效、取消和过期。

公开访问分享时，访客首先通过分享短码和可选密码调用访问接口。后端校验分享是否存在、是否过期、是否取消以及密码是否正确；校验通过后签发短期分享访问令牌。后续浏览分享目录或下载分享文件时，访客需要在X-Share-Token请求头中携带该令牌，由分享鉴权过滤器完成校验。系统会分别记录浏览次数和下载次数，并使用Redis对分享密码尝试进行限流，避免暴力猜测分享密码。

（1）回收站模块

回收站模块用于降低用户误删除带来的数据丢失风险。普通删除不会立即物理删除文件，而是把项目类型、原项目ID、原路径、项目名称、内容ID和完整数据备份写入trash表。用户可以分页查看回收站项目，也可以批量恢复、彻底删除或清空回收站。恢复时，如果原目录不存在，则恢复到根目录；如果名称冲突，服务层生成新的名称，避免覆盖现有文件。定时清理任务负责删除过期回收站记录和过期上传任务，防止临时数据长期堆积。

#### 4.3.4管理员与运维模块设计

（1）用户管理模块

管理员用户管理模块通过/api/admin/users系列接口维护平台账号。管理员可以查看用户列表、按条件筛选用户、查看详情和存储使用情况，也可以修改用户状态、调整角色、设置可用空间或软删除用户。用户状态在数据库中以数值保存，包括禁用、正常和锁定；角色也用数值区分普通用户和管理员。所有管理员接口都先经过JWT鉴权，再经过管理员角色鉴权。

（2）存储统计与分享管理模块

存储统计模块聚合users、files、file_contents、folders等表，计算全平台用户数、文件数、内容对象数、存储占用和各用户使用情况。由于系统采用内容寻址和引用计数机制，用户视角下的逻辑文件大小与物理内容占用并不总是一致，因此统计时需要分别处理。

分享管理模块用于支持管理员查看全平台分享列表、查看单个分享详情并强制取消违规分享，主要面向公开链接滥用、误分享和过期分享治理等场景。

（3）系统状态与日志模块

系统状态模块用于部署检查和日常维护，页面展示服务运行时间、版本信息、数据库连接、Redis连接和磁盘空间等指标。操作日志分页保存上传、下载、删除、分享等动作，管理员排查异常请求或处理用户反馈时，可以先从这些记录确认情况。

以上十张数据表完成了系统主要业务数据的物理结构设计，包括字段类型、约束规则和索引设置。索引围绕文件列表查询、目录导航、内容哈希查重、上传断点续传、回收站恢复、分享访问和操作审计等场景设置，为各业务模块提供数据基础。

## 第5章 系统实现

本章结合项目代码说明系统的具体实现过程。后端按照控制器、过滤器、服务层、数据模型和存储抽象进行组织，其中控制器负责绑定路由、解析参数并转换响应，服务层负责处理业务规则、数据库事务和Redis状态。桌面端使用AuthShell、OwnerShell、VisitorShell和AdminShell区分登录、普通用户、访客分享和管理员场景，各页面再通过对应Manager访问后端接口。

### 5.1用户与认证模块功能实现

（1）注册与登录实现

账号注册和登录接口由AuthController提供，具体业务判断由AuthService完成。注册时，后端接收用户名、邮箱和密码，先由DTO检查参数格式，再查询users表确认用户名和邮箱没有被占用。校验通过后，服务层使用libsodium的Argon2id算法生成密码哈希，并写入默认昵称、头像、存储配额、账号状态和角色等字段。桌面端对应RegisterPage页面，注册成功后提示用户返回登录页。

登录接口支持用户名或邮箱两种方式。服务层读取账号状态、锁定截止时间和密码哈希后依次判断，账号禁用或仍处于锁定期时直接拒绝，密码错误时累计失败次数，达到阈值后设置短时锁定；认证成功时重置失败计数，签发Access Token与Refresh Token，并返回用户ID、用户名、昵称和角色。客户端LoginPage发起请求后，SessionStore保存会话信息，ShellController再根据用户角色切换到普通用户界面或管理员界面。

（2）令牌生命周期与鉴权过滤

令牌相关逻辑集中在TokenService中。Access Token采用JWT格式，携带用户ID、用户名、角色和过期时间等声明；普通业务接口通过JwtAuthFilter校验Authorization请求头。Refresh Token保存在Redis中，用于续期访问令牌。刷新成功后，旧Refresh Token被替换，新的令牌返回客户端。用户登出时，系统删除Redis中的刷新令牌，并把当前访问令牌加入黑名单，使其在自然过期前不能继续访问受保护接口。

不同访问边界使用不同过滤器。管理员接口在JWT校验后还要经过AdminAuthFilter，只有管理员角色可以访问/api/admin/* 路由；公开分享的浏览和下载接口使用ShareAuthFilter校验X-Share-Token，避免访客流程与登录用户JWT混在一起。桌面端网络层由RequestFactory按请求类型附加用户令牌、分享令牌或两者组合，请求来源也更容易区分。

（3）个人资料、密码与存储空间实现

用户中心由UserController和UserService实现，主要包括个人资料查询、资料更新、密码修改和存储空间查看。资料更新接口支持修改昵称和头像URL，服务层只更新请求中实际传入的字段，并同步更新时间。密码修改接口要求用户提交当前密码，校验通过后重新生成Argon2id哈希并更新users.password_hash，避免明文密码出现在客户端或数据库中。

存储空间接口读取users表中的storage_quota、storage_used和storage_reserved字段，并结合文件数、目录数返回已用空间、预占用空间、剩余配额和资源数量。桌面端SettingsPage和ProfileManager负责加载这些数据；用户修改资料或密码后，页面根据接口结果给出提示。

### 5.2文件传输模块功能实现

（1）分片上传初始化与秒传判断

文件上传由FileController提供初始化、上传分片、完成上传和取消上传接口，主要路径包括/api/file/upload/init、/api/file/upload/chunk和/api/file/upload/complete等。控制器继承Drogon的HttpController，通过METHOD_LIST_BEGIN和ADD_METHOD_TO绑定路由、HTTP方法和过滤器，上传接口接入JWT鉴权和上传限流过滤器。各处理函数返回drogon::Task<drogon::HttpResponsePtr>，控制器用co_await等待服务层逻辑，数据库或文件状态处理期间不会长时间占住请求线程。

客户端选择文件后，TransferManager会提交文件名、文件大小、目标目录和文件MD5。初始化阶段先检查用户配额，如果当前已用空间加上预占用空间已经超过配额上限，服务端直接返回空间不足，客户端也就不再继续上传分片。

初始化阶段还会按照文件哈希查询file_contents表。若系统中已经存在相同内容对象，服务层不要求客户端上传物理文件，而是创建新的files元数据记录、增加内容对象引用计数，并返回秒传结果。若内容不存在，则创建upload_tasks记录，写入任务ID、目标目录、文件名、文件大小、分片大小、总分片数、临时路径、预占用字节数和过期时间，同时查询upload_task_chunks表返回已上传分片列表，为断点续传提供状态依据。

（2）分片写入、断点续传与后台合并

分片上传接口按照任务ID和分片索引接收二进制内容。Drogon把请求体封装在HttpRequest对象中，控制器可以直接读取request->body()取得application/octet-stream数据，不需要再进行JSON封装。服务层随后检查任务归属和任务状态，确认无误后把分片写入临时目录，并在upload_task_chunks表中记录对应索引。

大文件拆成固定分片后，单次请求只处理一部分数据，服务端内存峰值更容易控制。客户端恢复上传时再次调用初始化接口，拿到已上传分片索引后，只补传缺失分片。断点续传由上传任务表和分片记录表共同支撑。

客户端确认全部分片上传完成后调用完成接口，后端使用AssemblyWorkerPool限制同一任务的合并并发，避免重复触发合并流程。合并程序按照索引顺序读取临时文件，生成完整文件后计算MD5和SHA256，再与初始化阶段提交的哈希进行比对。校验通过后，IFileStorage的本地实现把文件移动到内容寻址存储目录，服务层写入file_contents和files表，释放预占用空间并更新用户已用空间。取消上传或任务过期时，临时分片会被删除，任务状态和预占用空间同步回滚；CleanupService负责清理长期遗留的数据。

（3）文件下载与Range断点下载

文件下载流程分为下载信息查询和文件流返回两个步骤。前一步向客户端返回文件名、大小和MIME类型等信息；后一步先检查文件归属，确认当前用户具有访问权限后，再由IFileStorage定位内容寻址文件，并交给DownloadResponder生成HTTP响应。

大文件下载时，不能把完整文件一次性加载到内存中。下载接口使用Drogon的HttpResponse::newStreamResponse实现流式返回，回调函数按固定块大小读取文件，再写入响应缓冲区。这样处理后，内存占用能够保持在相对稳定的范围内，服务端在发送文件的同时也可以继续处理其他连接。

请求头包含Range字段时，后端解析起止字节位置，只返回对应区间内容，并设置206 Partial Content、Content-Range、Accept-Ranges和Content-Length等响应头。若请求范围超过文件大小，则返回416 Requested Range Not Satisfiable，同时告知当前文件长度。普通下载、断点续传下载和非法Range响应共用同一套流式响应构造逻辑。桌面端由TransferManager和DownloadTaskModel管理下载任务，记录进度、状态和失败原因，并支持取消、重试以及暂停后继续下载。

（4）传输中心实现

传输中心由TransferCenterPage实现，并与文件列表页面分开。上传任务记录文件名、目标目录、已上传字节数、总字节数、状态和错误信息；下载任务记录本地路径、进度、暂停状态和完成状态。这样处理以后，用户在上传或下载时间较长时，仍然可以继续浏览文件、切换目录或处理其他操作，不必一直停留在文件列表页面等待任务结束。

### 5.3文件与目录管理模块功能实现

（1）文件列表与资源管理器实现

普通用户的大部分文件操作都从DriveBrowserPage进入。OwnerShell加载后，页面划分为“我的网盘”“分享”和“回收站”等视图；其中“我的网盘”由DriveMyFilesView承载文件列表，工具栏和右键菜单提供刷新、上传、下载、新建文件夹、重命名、移动、复制、分享和删除等入口。后端列表接口由FileService同时查询files和folders，再按照用户ID、目录ID、分页参数和排序字段整理成统一列表项，字段包括ID、名称、类型、大小、更新时间、MIME类型和下载次数。

DriveManager负责保存当前目录ID、列表模型、排序方式、选择状态和加载状态。根目录使用ID 0表示；用户切换目录时，页面不需要重建，只更新目录ID和列表数据。请求失败或列表为空时，界面显示对应提示并允许重新加载。后端查询始终带有用户ID权限边界，普通用户即使构造其他目录ID，也无法越权读取他人文件。

重命名操作分别更新files或folders中的名称和路径。服务层在写入前检查名称长度、非法字符、保留名称和同级重名。移动接口支持批量文件和目录；移动目录时需要额外判断目标目录，不能把目录移动到自身或其子目录下，否则会破坏目录树结构。复制文件时只新增逻辑文件记录并增加file_contents.ref_count，不重复复制物理内容。

搜索接口按照关键词、项目类型和目录范围返回分页结果。桌面端工具栏保存关键词和排序方式，用户输入后由DriveManager请求后端并刷新列表。批量移动、复制、删除和分享时，客户端一次提交多个项目ID，后端逐项处理并返回结果，界面再分别显示成功状态或失败原因。该处理方式可以更准确地反馈批量操作中每个项目的执行结果。

### 5.4回收站模块功能实现

回收站由TrashController和TrashService负责。普通删除并不立即释放存储空间，而是把项目类型、原项目ID、项目名称、原目录、原路径、大小、内容引用和必要的JSON备份写入trash表，再从正常文件或目录列表中移除。桌面端DriveTrashView读取这些记录，用户可以多选后进行恢复、彻底删除，也可以清空当前账号的回收站。

![图5-8 回收站管理功能截图](assets/回收站管理功能截图.png)

图5-8为回收站界面。列表中保留已删除项目的名称、路径、大小和删除时间，操作区提供恢复、彻底删除和清空入口。

恢复时，服务层先确认回收站记录属于当前用户。能够回到原父目录的项目优先恢复到原位置；原目录已经不存在时，则恢复到根目录；若目标目录中存在同名项目，服务层自动生成name (n).ext或name (n)形式的新名称，避免覆盖已有数据。当前版本对文件夹恢复采取较保守的规则，只恢复文件夹记录本身，不递归恢复其子树。

保存分享内容使用/api/share/save/{share_id}接口。该接口同时经过JwtAuthFilter和ShareAuthFilter，调用者既要登录自己的账号，也要已经通过该分享的访问校验。保存时，服务层按照share_files中的关联关系为当前用户创建文件或目录记录；文件内容继续复用file_contents对象，只增加引用计数，不再写入新的物理文件。通过该方式，访客可以把授权文件保存到个人网盘，同时仍然受到自身配额和权限边界限制。

### 5.6管理后台与运维模块功能实现

（1）管理员用户管理实现

管理员接口集中在AdminController和AdminService中。所有/api/admin/* 路由都需要先经过JWT鉴权，再由AdminAuthFilter确认管理员角色。管理员登录后进入AdminShell和AdminPage，用户、分享和系统状态被放在不同标签页中。用户管理接口支持分页、关键词、账号状态和角色筛选，返回用户ID、用户名、邮箱、昵称、存储使用量、账号状态和角色等信息。

管理员可以禁用或启用普通用户、调整角色、设置可用空间，也可以软删除用户。服务层在处理这些操作时需要同时考虑权限边界，例如管理员不能禁用或降级自己，系统中最后一个管理员也不能被降级或禁用。状态变更、角色变更等操作完成后，服务层会写入操作日志，便于后续追踪。桌面端UserTab和AdminManager负责加载列表、提交操作并显示结果。

功能测试完成后，系统主线业务基本能够稳定运行。普通用户、访客和管理员三类角色的核心流程均已通过验证，包括用户认证与鉴权、令牌刷新与登出、分片上传、断点续传、秒传去重、文件下载、目录管理、分享生成与访问控制、分享内容保存、回收站恢复与彻底删除，以及管理员用户管理、分享管理、操作日志、存储统计和系统状态查询。

当前测试仍以毕业设计演示环境为主。系统主要在本地单机条件下验证，尚未进行充分的大规模并发压测，Drogon在真实高并发文件传输中的吞吐量和延迟还缺少数据支撑。操作日志和健康检查已经具备，但监控告警、容量趋势分析和容灾恢复仍较基础。桌面端覆盖了登录、文件浏览、传输中心、分享访问、回收站和管理后台等主要页面，但拖拽上传、缩略图预览和文件在线预览尚未完成。若面向实际部署，后续应优先补充性能压测和运维监控，再完善客户端体验。

## 总结与展望

本文完成了一套面向私有化部署的网络磁盘系统。论文从需求分析入手，依次说明总体架构、数据库结构、模块设计、功能实现和测试过程。系统后端采用C++23和Drogon Web框架，桌面端采用Qt 6和QML，数据层由MySQL、Redis和本地内容寻址文件系统组成。系统区分普通用户、访客和管理员三类角色，覆盖文件存储、文件传输、文件分享和后台运维等主要流程。

在功能实现方面，系统已经完成注册登录、Access Token与Refresh Token管理、JWT鉴权、管理员角色鉴权、个人资料与存储空间统计、多级目录树、面包屑路径、分片上传、断点续传、秒传去重、后台合并、Range下载、文件重命名、移动、复制、搜索、回收站软删除与恢复、外链分享、分享密码访问、分享浏览与下载、分享内容保存、操作日志、健康检查和系统状态查询等功能。桌面端对应实现了认证界面、网盘资源管理器、传输中心、访客分享访问页、个人设置页和管理员后台。上传与存储部分使用upload_tasks和upload_task_chunks保存分片状态，并借助file_contents中的内容哈希和引用计数完成秒传与去重，该部分是系统文件传输流程中的关键环节。

测试结果表明，系统基本达到毕业设计阶段的预期目标。注册登录、文件传输、目录管理、分享访问控制、回收站恢复、权限边界和管理员操作等流程都能够按照设计运行，RESTful接口的数据交互也较为清晰。通过本次系统实现可以看出，C++23、Drogon、MySQL、Redis和Qt/QML能够组合形成一套可运行的中小规模私有化网络磁盘系统。

当前系统仍存在一些不足。文件版本历史、WebDAV协议、在线预览和缩略图生成尚未完成；高并发压力测试和安全渗透测试还不充分，大规模文件传输下的吞吐量、延迟和稳定性缺少更多实验数据。系统已有操作日志、健康检查和状态接口，但监控告警、容量趋势分析、自动备份和容灾恢复仍然较为基础。后续工作可以优先从客户端体验和压测数据两方面展开，再根据测试结果考虑对象存储接入以及更完整的运维能力建设。
