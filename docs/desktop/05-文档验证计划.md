# 桌面客户端 — 文档验证计划

## 1. 文档说明

### 1.1 文档目的

本文档为新文档系列（`docs/desktop/00-06`）定义验证范围、验证维度、验证命令、证据要求和失败口径。采用后端测试计划式结构（参考 `docs/design/04-系统测试计划.md`），确保文档质量可被自动化校验工具验证。

**关键约束**：文档任务只做文档校验，不触发 Qt 编译，不运行 Qt Quick Test。验证聚焦结构、术语、交叉引用、实现锚点与 docs-only diff。

### 1.2 权威来源

| 来源 | 路径 | 用途 |
|------|------|------|
| 文档治理基线 | `docs/desktop/00-桌面客户端系统概述与文档治理.md` | 权威层级、状态标签、ID 前缀 |
| 信息架构与功能视图 | `docs/desktop/01-信息架构与功能视图.md` | VIEW-/PAGE- taxonomy、五类对象定义 |
| 页面布局与交互规范 | `docs/desktop/02-页面布局与交互规范.md` | 交互矩阵、布局规范 |
| 状态模型与导航模型 | `docs/desktop/03-状态模型与导航模型.md` | 导航规则、状态迁移、FLOW- 编号 |
| 组件页面与实现映射 | `docs/desktop/04-组件页面与实现映射.md` | 实现锚点、测试证据、规划条目清单 |
| 后端测试计划（参考） | `docs/design/04-系统测试计划.md` | 测试计划文档的组织方式 |
| 后端单元测试用例（参考） | `docs/design/06-单元测试用例.md` | 用例/统计类文档的表格形式 |

### 1.3 冻结不变量

1. 文档验证不要求运行 Qt 构建，不要求编译 `desktop-client` 或 `desktop-unit-tests`。
2. 每个验证维度必须有可执行的 Bash/Python 文本校验命令。
3. 验证结果必须产生证据文件，存放于 `.sisyphus/evidence/desktop-docs/`。
4. 验证只检查文档内部一致性、术语规范、结构完整性和引用完整性，不验证运行时行为。

### 3.7 V7：docs-only diff 验证

检查最终变更是否仅限于 `docs/` 和 `.sisyphus/` 路径。由于文档重建工作可能包含尚未 commit 的新建文件（untracked），验证必须同时覆盖已跟踪变更和未跟踪文件。

```bash
# CASE-DIFF-001: 所有变更（tracked + untracked）不包含 docs/ 和 .sisyphus/ 以外的文件
python3 - <<'PY'
import subprocess

def get_all_changed_files():
    """Collect tracked-changed and untracked files into one set.
    Uses -z (NUL-separated) to avoid git quoting non-ASCII filenames."""
    files = set()
    # Tracked: staged + unstaged changes vs HEAD
    r = subprocess.run(
        ['git', 'diff', '-z', '--name-only', 'HEAD'],
        capture_output=True
    )
    if r.returncode != 0:
        raise SystemExit('git diff failed: ' + r.stderr.decode())
    files.update(f.decode() for f in r.stdout.split(b'\0') if f)
    # Untracked (not yet added to index)
    r2 = subprocess.run(
        ['git', 'ls-files', '-z', '--others', '--exclude-standard'],
        capture_output=True
    )
    if r2.returncode != 0:
        raise SystemExit('git ls-files failed: ' + r2.stderr.decode())
    files.update(f.decode() for f in r2.stdout.split(b'\0') if f)
    return sorted(files)

changed = get_all_changed_files()
outside = [f for f in changed if not f.startswith('docs/') and not f.startswith('.sisyphus/')]
raise SystemExit(0 if not outside else ('non-doc changes: ' + ', '.join(outside)))
PY
```

```bash
# CASE-DIFF-002: 没有修改 QML/C++/测试/构建文件（.sisyphus/ 路径下的任何文件类型均豁免）
python3 - <<'PY'
import subprocess

def get_all_changed_files():
    """Collect tracked-changed and untracked files via -z (NUL-separated)."""
    files = set()
    r = subprocess.run(
        ['git', 'diff', '-z', '--name-only', 'HEAD'],
        capture_output=True
    )
    if r.returncode != 0:
        raise SystemExit('git diff failed: ' + r.stderr.decode())
    files.update(f.decode() for f in r.stdout.split(b'\0') if f)
    r2 = subprocess.run(
        ['git', 'ls-files', '-z', '--others', '--exclude-standard'],
        capture_output=True
    )
    if r2.returncode != 0:
        raise SystemExit('git ls-files failed: ' + r2.stderr.decode())
    files.update(f.decode() for f in r2.stdout.split(b'\0') if f)
    return sorted(files)

forbidden_exts = ['.qml', '.cpp', '.hpp', '.h', '.c', '.cmake', '.sql', '.sh', '.ps1']
# .json 在 .sisyphus/ 下是允许的（orchestration state、evidence 等），
# 但在其他路径下仍被禁止（防止误改 config.json、vcpkg.json 等）
forbidden_prefixes = ['CMake', 'vcpkg', 'src/', 'test/', 'sql/', 'scripts/']
changed = get_all_changed_files()
bad = []
for f in changed:
    # .sisyphus/ 下的一切文件类型均豁免
    if f.startswith('.sisyphus/'):
        continue
    if any(f.endswith(e) for e in forbidden_exts):
        bad.append(f)
    elif f.endswith('.json'):
        bad.append(f)
    elif any(f.startswith(p) for p in forbidden_prefixes):
        bad.append(f)
raise SystemExit(0 if not bad else ('forbidden file changes: ' + ', '.join(bad)))
PY
```

## 4. 失败口径与证据要求

### 4.1 严重程度定义

| 严重程度 | 含义 | 处理方式 |
|----------|------|----------|
| **P0 阻断** | 文档体系核心约束被违反（如双权威、`[已实现]` 无证据、实现锚点文件不存在） | 必须立即修正，不允许带 P0 发布 |
| **P1 严重** | 重要验证维度失败（如必需元节缺失、术语不一致、交叉引用悬空） | 必须在当前任务中修正 |
| **P2 一般** | 轻微不一致或风格偏差（如行号范围偏移、术语表缺少数项） | 记录到证据文件，可在后续波次修正 |
| **P3 建议** | 改进建议（如措辞优化、表格格式统一） | 记录但不阻塞 |

### 4.2 各维度严重程度映射

| 维度 | P0 触发条件 | P1 触发条件 | P2 触发条件 |
|------|------------|------------|------------|
| V1 结构 | 文件不存在或为空 | 必需元节缺失 | 编号不连续 |
| V2 术语 | taxonomy 倒挂（组件被标为页面） | 核心术语缺失 | 术语表缺项 |
| V3 交叉引用 | 引用路径指向不存在的文件 | 旧文档被当作规范来源 | 引用格式不统一 |
| V4 traceability | ID 前缀未在 DOC-00 注册 | 引用的 ID 无定义来源 | ID 编号不连续 |
| V5 实现锚点 | 声称已实现但文件不存在 | 行号范围明显超出文件长度 | 行号微偏移 |
| V6 状态标签 | 未实现功能被标为 `[已实现]` | `[已实现]` 无测试或代码锚点 | 措辞模糊 |
| V7 docs-only diff | 修改了 `src/` 或 `clients/` 下的源代码 | 修改了构建配置文件 | 修改了无关文档 |
| V8 legacy 迁移 | 旧文件仍在新系列中被当作规范引用 | 旧文件未归档 | 归档目录缺少非关键文件 |

### 4.3 证据输出约定

#### 4.3.1 证据文件命名

```
.sisyphus/evidence/desktop-docs/task-{N}-{slug}.{ext}
```

- `{N}`：任务编号（1-8）
- `{slug}`：简短描述（kebab-case），如 `doc-governance`、`validation-plan`
- `{ext}`：`txt`（命令输出）、`json`（结构化结果）或 `log`（运行日志）

#### 4.3.2 证据文件内容要求

每份证据文件必须包含：

1. 执行的命令原文
2. 执行时间戳（`date --iso-8601=seconds`）
3. 命令退出码
4. 命令的标准输出和标准错误

#### 4.3.3 证据收集命令模板

```bash
# 运行验证命令并收集证据
EVIDENCE_DIR=".sisyphus/evidence/desktop-docs"
mkdir -p "$EVIDENCE_DIR"

run_check() {
    local slug="$1"
    shift
    local outfile="$EVIDENCE_DIR/$slug.txt"
    {
        echo "=== Evidence: $slug ==="
        echo "Timestamp: $(date --iso-8601=seconds)"
        echo "Command: $*"
        echo "---"
        "$@"
        echo "---"
        echo "Exit code: $?"
    } > "$outfile" 2>&1
}

# 使用示例
run_check "task-7-struct-validation" python3 - <<'PY'
# ... 验证命令内容 ...
PY
```

### 4.4 执行顺序

验证命令按以下顺序执行，前序维度失败时后续维度仍应继续执行以收集完整失败画像：

1. V1 结构验证（基础依赖，文件必须存在）
2. V2 术语验证（依赖文件可读）
3. V3 交叉引用验证（依赖文件内容）
4. V4 ID traceability 验证（依赖全系列文件内容）
5. V5 实现锚点验证（依赖 DOC-04 和代码库）
6. V6 状态标签验证（依赖 DOC-04 和 DOC-00 规则）
7. V7 docs-only diff 验证（依赖 git 状态）
8. V8 legacy 迁移完成验证（依赖 DOC-06 完成状态）

### 4.5 验证结果报告格式

```markdown

**执行者**: {agent-name}
```
