# 03-架构设计

## 1. 架构概述

Disk Web 客户端是 Disk 网盘系统的 Vue 3 浏览器端实现，与 Qt 桌面客户端共享同一套后端 REST API。整体采用**分层架构 + 特性驱动目录（Feature-Based）**的组织方式，将业务领域垂直切分为独立的模块，每个模块自治管理自身的页面、组件、状态和 API。

技术栈：Vue 3 + Vite + TypeScript + Element Plus + Pinia + Axios + Vue Router 4。

架构设计参考了桌面端的组织经验：

- 桌面端的 `Application` 依赖注入中心，在 Web 端映射为 **Pinia Store 模块 + Vue 插件初始化**
- 桌面端的 6 个 Manager（Drive、Transfer、Share、Trash、Profile、Admin），在 Web 端映射为 **6 个 Pinia Store**
- 桌面端的 `RequestFactory` 双认证域隔离，在 Web 端映射为 **Axios 多实例 + 请求拦截器**
- 桌面端的 4 个 Shell（Auth、Owner、Visitor、Admin），在 Web 端映射为 **路由守卫 + 布局组件**

## 2. 目录结构设计

### 目录组织原则

- `views/` 按业务领域分组，每个领域一个子目录，与 `stores/`、`api/` 的模块名一一对应
- `components/` 分为 `base/`（纯通用）和 `drive/share/transfer/admin/`（业务专用），业务组件不允许被其他领域直接引用
- `composables/` 提供可复用的逻辑层，复杂 Store 操作通过组合式函数暴露给组件
- `types/` 集中管理接口契约类型，与后端 DTO 保持一致

## 3. 路由设计

使用 Vue Router 4，采用**布局嵌套 + 路由守卫**模式。路由表按认证域划分，与桌面端的 4 个 Shell 概念对齐。

### 路由表

| 路径 | 组件 | 布局 | 权限 | 说明 |
|------|------|------|------|------|
| `/login` | `LoginView` | `AuthLayout` | 公开 | 用户登录 |
| `/register` | `RegisterView` | `AuthLayout` | 公开 | 用户注册 |
| `/share/access/:shareId` | `ShareAccessView` | `VisitorLayout` | 公开 | 分享密码校验 |
| `/share/browse/:shareId` | `ShareBrowseView` | `VisitorLayout` | 需 Share Token | 浏览分享内容 |
| `/drive` | `DriveView` | `OwnerLayout` | 需 JWT | 我的文件（默认视图模式 myfiles） |
| `/drive/shared` | `DriveView` | `OwnerLayout` | 需 JWT | 他人分享给我的文件 |
| `/drive/trash` | `DriveView` | `OwnerLayout` | 需 JWT | 回收站视图 |
| `/drive/search` | `SearchResultView` | `OwnerLayout` | 需 JWT | 搜索结果页 |
| `/transfer` | `TransferCenterView` | `OwnerLayout` | 需 JWT | 上传/下载任务中心 |
| `/settings/profile` | `ProfileView` | `OwnerLayout` | 需 JWT | 个人资料 |
| `/settings/security` | `SecurityView` | `OwnerLayout` | 需 JWT | 密码修改 |
| `/settings/storage` | `StorageView` | `OwnerLayout` | 需 JWT | 容量统计 |
| `/admin/dashboard` | `AdminDashboardView` | `AdminLayout` | 需 Admin JWT | 管理概览 |
| `/admin/users` | `AdminUsersView` | `AdminLayout` | 需 Admin JWT | 用户管理 |
| `/admin/shares` | `AdminSharesView` | `AdminLayout` | 需 Admin JWT | 分享管理 |
| `/admin/logs` | `AdminLogsView` | `AdminLayout` | 需 Admin JWT | 操作日志 |
| `/` | 重定向到 `/drive` | - | - | 根路径自动跳转 |
| `/:pathMatch(.*)*` | `NotFoundView` | `AuthLayout` | 公开 | 404 页面 |

### 路由守卫策略

```
全局前置守卫 (beforeEach)
    │
    ├─ 路径以 /admin 开头?
    │   └─ 检查 JWT 存在且 role === 1
    │       └─ 否 → 跳转 /login
    │
    ├─ 路径以 /share 开头?
    │   ├─ /share/access → 公开，允许访问
    │   └─ /share/browse → 检查 localStorage 中是否有 share_token_{shareId}
    │       └─ 否 → 跳转 /share/access/:shareId
    │
    ├─ 路径在公开白名单中? (/login, /register, /share/access/*)
    │   └─ 是 → 直接放行
    │
    └─ 其余路径需要 JWT
        ├─ 检查 access_token 存在?
        │   └─ 否 → 跳转 /login
        ├─ 检查 token 是否即将过期?
        │   └─ 是 → 静默刷新后再放行
        └─ 是 → 放行
```

### 布局组件职责

- `AuthLayout`: 居中卡片式布局，无侧边栏，用于登录注册
- `OwnerLayout`: 左侧导航栏（文件/传输/设置）+ 顶部工具栏 + 主内容区，DriveView 内嵌视图模式切换（myfiles/shared/trash）
- `VisitorLayout`: 简化头部（分享标题 + 返回按钮）+ 主内容区，无左侧导航
- `AdminLayout`: 独立管理导航菜单 + 主内容区，与普通用户界面隔离

### Store 职责说明

| Store | 职责 | 对应桌面端 Manager | 核心 State |
|-------|------|-------------------|-----------|
| `auth` | 管理登录态、双令牌存储、认证域切换 | `AuthService` + `SessionStore` | `accessToken`, `refreshToken`, `user`, `authDomain: 'owner' \| 'visitor'` |
| `drive` | 文件列表、目录导航、视图模式、选中状态 | `DriveManager` | `items`, `currentFolderId`, `viewMode: 'myfiles' \| 'shared' \| 'trash'`, `selectedIds`, `breadcrumb` |
| `transfer` | 上传/下载任务队列、状态机、进度追踪 | `TransferManager` | `uploadTasks`, `downloadTasks`, `activeUploadCount`, `reservedBytes` |
| `share` | 我的分享列表、分享创建、分享浏览 | `ShareManager` | `myShares`, `browseItems`, `currentShareId`, `shareDetail` |
| `trash` | 回收站列表、恢复、彻底删除 | `TrashManager` | `items`, `pagination`, `selectedIds` |
| `profile` | 用户资料、存储统计、密码修改 | `ProfileManager` | `profile`, `storageStats` |
| `admin` | 用户管理、分享管理、系统监控 | `AdminManager` | `users`, `shares`, `operationLogs`, `overviewStats`, `systemStatus` |

### Store 设计原则

- 每个 Store 只管理一个业务领域的状态，不跨域引用其他 Store 的 state
- 异步操作（API 调用）使用 `async/await` action，错误统一通过 `apiError` 事件或返回值传递
- 持久化状态（token、用户偏好）通过 `pinia-plugin-persistedstate` 写入 `localStorage`
- 上传任务状态因数据量大且需要实时更新，单独使用 `transfer` Store 管理，不混入 `drive`

### 组件设计原则

- **页面组件**（`views/`）只负责布局编排和数据分发，不实现具体交互逻辑
- **业务组件**（`components/drive/`, `components/share/` 等）只服务于单一领域，通过 `props` 接收数据，通过 `emit` 上报用户操作
- **基础组件**（`components/base/`）完全无业务逻辑，只接收纯数据 `props` 和通用事件
- 复杂交互逻辑（如文件多选、拖拽上传）封装在 `composables/` 中，供页面组件使用

## 6. API 客户端架构

API 层参考桌面端 `RequestFactory` 的双认证域隔离模式，通过 Axios 实例和请求拦截器实现不同认证域的请求分发。

```
│  │ - 刷新失败→登出│ │   校验分享密码 │ │             │          │
│  └──────┬──────┘ └──────┬──────┘ └──────┬──────┘          │

│                         ▼                                   │

│  │              统一响应处理与错误适配                     │   │

│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 拦截器职责

**请求拦截器（Owner Client）**

1. 从 `localStorage` 读取 `access_token`
2. 附加 `Authorization: Bearer <token>` 请求头
3. 若 token 将在 60 秒内过期，先执行静默刷新

**请求拦截器（Visitor Client）**

1. 从 `localStorage` 读取 `share_token_<shareId>`
2. 附加 `X-Share-Token: <token>` 请求头

**响应拦截器（统一）**

1. 解析后端统一响应格式 `{ code, message, data }`
2. `code === 0` 时返回 `data`
3. `code !== 0` 时抛出标准化错误对象 `{ code, message, status }`
4. HTTP 401 触发认证错误事件，由 `auth` Store 处理重定向

### API 模块组织

每个业务领域一个 API 模块文件，导出该领域的所有接口函数：

```typescript
// api/drive.ts 示例
```


### Token 存储策略

| Token | 存储位置 | 键名 | 有效期 |
|-------|---------|------|--------|
| Access Token | `localStorage` | `disk_access_token` | 与后端一致（默认 15 分钟） |
| Refresh Token | `localStorage` | `disk_refresh_token` | 与后端一致（默认 7 天） |
| Share Token | `localStorage` | `disk_share_token_{shareId}` | 与分享有效期一致 |

### 认证域隔离规则

与桌面端 `RequestFactory` 保持一致，两种认证域严格隔离：

- **Owner 域请求**：只带 `Authorization: Bearer <access_token>`，不带 `X-Share-Token`
- **Visitor 域请求**：只带 `X-Share-Token: <share_token>`，不带 `Authorization`
- **Public 请求**：不带任何认证头
- 不存在同时携带两种令牌的请求场景

## 8. 上传架构设计

上传是网盘客户端最复杂的交互场景。Web 端继承桌面端的上传状态机，并针对浏览器环境做适配（使用 `FileReader` + `crypto.subtle` 或 `spark-md5` 计算哈希，使用 `XMLHttpRequest` 或 `fetch` 实现分片上传进度追踪）。

### 上传状态机

```
                         ┌─────────────┐
                         │   Queued    │  ← 用户选择文件，加入队列
                         └──────┬──────┘
                                │ 开始处理
                                ▼
                         ┌─────────────┐
                         │   Hashing   │  ← 计算文件 MD5（Web Worker）
                         └──────┬──────┘
                                │ 哈希完成
                                ▼
                         ┌─────────────┐
                         │ Initializing│  ← POST /api/file/upload/init
                         └──────┬──────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
       ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
       │InstantUploaded│  │  Resuming   │  │  Uploading  │
       │   (秒传)     │  │ (断点续传)   │  │ (全新上传)   │
       └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
              │                 │                 │
              │                 │ 上传缺失分片      │ 逐片上传
              │                 ▼                 ▼
              │            ┌─────────────┐  ┌─────────────┐
              │            │  Uploading   │  │  Uploading   │
              │            │  (续传中)    │  │  (新上传中)   │
              │            └──────┬──────┘  └──────┬──────┘
              │                   │                │
              └───────────────────┼────────────────┘
                                  │ 所有分片上传完成
                                  ▼
                           ┌─────────────┐
                           │  Completing │  ← POST /api/file/upload/complete
                           └──────┬──────┘
                                  │
                    ┌─────────────┼─────────────┐
                    │             │             │
                    ▼             ▼             ▼
             ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
             │  Completed  │ │   Failed    │ │  Cancelled  │
             │  (成功)     │ │  (失败)     │ │  (用户取消)  │
             └─────────────┘ └──────┬──────┘ └─────────────┘
                                    │
                                    │ 可重试
                                    ▼
                             ┌─────────────┐
                             │   Queued    │  ← 重新进入队列（Retry）
                             └─────────────┘

Initializing / Uploading / Completing 任意阶段:
    │
    ├─ 网络错误 → 自动重试（最多 3 次）→ 仍失败 → Failed
    ├─ 用户点击取消 → CancelPending → DELETE /api/file/upload/{id} → Cancelled
    └─ 后端返回任务过期 → Expired → 可重新初始化
```

### 上传状态定义

| 状态 | 说明 | 用户可操作 |
|------|------|---------|
| `queued` | 等待处理 | 取消 |
| `hashing` | 计算文件 MD5 | 取消 |
| `initializing` | 请求上传初始化 | 取消 |
| `instant_uploaded` | 秒传成功 | 无 |
| `resuming` | 断点续传，获取已上传分片 | 取消 |
| `uploading` | 正在上传分片 | 暂停/取消 |
| `completing` | 请求完成合并 | 取消 |
| `completed` | 上传成功 | 清除记录 |
| `failed` | 上传失败 | 重试/清除 |
| `cancelled` | 已取消 | 清除记录 |
| `expired` | 任务过期 | 重新上传 |

### 上传并发与调度

- 全局最大并发上传数：`3`（可配置）
- 单个文件分片大小：`5 MB`（与后端 `chunk_size` 对齐）
- 分片上传使用 `XMLHttpRequest` 而非 `fetch`，以便获取 `onprogress` 事件
- 上传任务队列在 `transfer` Store 中维护，组件通过订阅 `uploadTasks` 获取实时状态

### 下载架构（简要）

下载相对简单，主要支持两种模式：

1. **完整下载**：直接创建 `<a>` 标签触发浏览器下载，或通过 `fetch` + `Blob` 保存
2. **Range 断点下载**：通过 `Range: bytes=start-end` 请求分片，前端合并（适用于大文件或需要进度展示的场景）

下载状态机：`idle → fetching_metadata → ready → transferring → completed/failed/cancelled`

### 环境配置

| 环境变量 | 说明 | 示例 |

### 部署方式

Web 客户端为纯静态 SPA，部署方式灵活：

1. **独立部署**：`dist/` 目录部署到 Nginx / CDN / S3，配置 fallback 到 `index.html`
2. **与后端同域部署**：将 `dist/` 复制到 Drogon 的静态文件目录，由后端统一 serve
3. **Docker 部署**：基于 `nginx:alpine` 镜像，多阶段构建

### Nginx 配置要点

```nginx
server {
    listen 80;
    root /var/www/disk-web;
    index index.html;

    # API 代理到后端
    location /api/ {
        proxy_pass http://backend:8080;
    }

    # SPA fallback
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```
